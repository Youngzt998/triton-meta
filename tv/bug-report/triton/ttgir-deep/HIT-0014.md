## Why this is NOT an expected numerics change
*(evidence, not a verdict -- the call is the reviewer's)*

Groups of the culprit passes: ['layout', 'layout', 'layout'].
No culprit pass is in the numerics-changing group (accelerate-matmul, f32-dot-tc, optimize-thread-locality, optimize-accumulator-init, tmem-load-reduce).  The remaining passes only move data, change layouts, schedule, or lower to hardware.
A layout-family pass is in the culprit set and the kernel contains tt.dot / tt.reduce, so the layout can legitimately change the summation tree.

### Integer-input control

With inputs that are integers in `[-8, 8]`, every fp32 accumulator in family
`loop_reduce` stays below `2^24 = 16777216` (bound here: `65536`,
exactness `yes`), so every accumulator add is exact and the
summation ORDER cannot change the result. acc += v*v with |v| <= 8 gives |acc| <= 64*C, and tl.sum / tl.max over integers are exact

Result of re-running this comparison on integer-valued inputs:
**`equal`**.

The control holds but the integer-valued inputs do NOT reproduce the difference, so this one is only visible on inputs where reassociation is also possible.

### Allocator perturbation (heap shift)

The comparison was repeated 3 times with the GPU allocator perturbed, so the
buffers land at different addresses with identical values. The difference
survived **3/3** of those runs. A difference caused
by an out-of-bounds or uninitialised read usually moves or disappears; a value
difference does not.
