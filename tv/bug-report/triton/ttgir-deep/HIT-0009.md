## Addendum written by the agent that launched the campaign (2026-08-17)

### Which side is right?

The non-warp-specialized build is **bit-identical to an exact fp32 model**, and
the warp-specialized build is not.  This is not floating-point reassociation.

With the `intvalued` distribution the inputs are integers in `[-8, 8]`, so the
`tl.dot` accumulator is an integer with `max|acc| = 1828`, far below `2^24`.
Every fp32 add in the K loop is therefore exact and the result does not depend
on the summation order at all.  Reproducing the whole kernel in torch fp32
(`artifacts/HIT-0009/cross_check_vs_torch.py`, output in
`cross_check_output.txt`) gives:

```
acc integral? True   max|acc| 1828.0
ref   vs torch fp32 model: bitequal=True    ndiff=0       maxabs=0.0
cand  vs torch fp32 model: bitequal=False   ndiff=43898   maxabs=24.0
ref vs cand ndiff: 43898
```

So on this input the warp-specialized build produces 43,898 wrong values out of
262,144, while the same pipeline without `hopper-warpspec` is exactly right.

### Where it fires

`artifacts/HIT-0009/sweep_mm_epilogue.py` sweeps the whole `mm_epilogue`
family: dtype in {fp16, bf16} x block in {128x128x64, 64x64x64} x num_stages in
{2, 3} x `warp_specialize` in {True, False} x input distribution in
{randn, intvalued, zeros, wide} = **64 (config, distribution) pairs**.
Output in `sweep_output.txt`.  **10 of the 64 differ**, and the pattern is
sharp:

| condition | differs? |
|---|---|
| `warp_specialize=False` (32 pairs) | never |
| `warp_specialize=True`, block 64x64x64 (16 pairs) | never |
| `warp_specialize=True`, block 128x128x64, `zeros` input (2 pairs) | never (all inputs are 0) |
| `warp_specialize=True`, block 128x128x64, other inputs (14 pairs) | **10 differ** |

Worst case seen: bf16, 128x128x64, `wide` distribution — 72 elements differ
with `max_abs_diff = 2.1e6`.

Two things this does **not** say, because they were not tested here: it does
not say the bug needs a 128-wide tile in general (only that 64x64x64 was clean
in these 16 pairs), and it does not say the plain `mm_tma` family is immune
(the campaign has run thousands of warp-specialized `mm_tma` experiments with
no mismatch, which is evidence but not proof).

### What is different about this kernel

`mm_epilogue` is the same TMA + `warp_specialize=True` matmul as the clean
`mm_tma` family, plus a post-loop epilogue: a pointer `tl.load` of a bias
vector, `acc + bias[:, None]`, `acc * tl.sigmoid(acc)`, a `tl.max(acc, 1)` row
reduction, `acc - rmax[:, None]`, then the TMA store.  So the suspicion is the
interaction between the Hopper warp-specialization code partition and an
epilogue that both loads from global memory with plain pointers and does a
cross-lane reduction, not the matmul loop itself.
