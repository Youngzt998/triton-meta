# HIT-0009: Hopper warp specialization applies the row offset twice in the epilogue of a data-partitioned matmul

Verdict: **CONFIRMED COMPILER BUG** (wrong results, silently)
Line:    ttgir-deep
Arch:    Hopper / sm_90 only (the failing IR is `ttg.warp_specialize` + wgmma + TMA)
Culprit pass: `nvgpu-warp-specialization` (`--nvgpu-warp-specialization`), Hopper
              warp-specialization, data-partition step
Reviewed: 2026-08-17; re-checked 2026-08-17 against the amended review criteria

**Re-check against the amended criteria (2026-08-17).** The criteria gained an
exception to the one-sided NaN/Inf keep rule: reject if the difference goes away
once fast math is removed. It does not touch this report, which is kept under a
different bullet — the difference **survives the exact-integer control** — and
no NaN or Inf is involved. Checked anyway: re-running the published repro with
`TRITON_DEFAULT_FP_FUSION=0` (Triton's fast-math-off equivalent: LLVM fp
contraction off plus ptxas `--fmad=false`) gives the same mismatch, 43898 of
262144 elements, `max_abs_diff 24.0`, unchanged to the bit. The bug is a wrong
load address, not an arithmetic rounding choice, so no floating-point flag can
explain it. **Keep stands.**

## What goes wrong, in one sentence

When Hopper warp specialization splits a `128 x 128` tile into two `64 x 128`
halves, the second half's epilogue adds the `+64` row offset **twice**, so the
bias vector it loads comes from 64 rows further down the tensor than it should.

---

## 1. Root cause in the source

Public Triton `3.8.0+git3277063a` (commit `3277063a6`), file
`third_party/nvidia/hopper/lib/Transforms/WarpSpecialization/WSDataPartition.cpp`.

`doDataPartition` (line 1304) builds **one** `IRMapping` per partition and
reuses it for every op of that partition:

```cpp
for (int i = 0; i < partitionScheme.numPartitions; i++) {
  IRMapping mappings, reverseMappings;               // line 1327
  for (int j = 0; j < numOps; j++)
    sliceOp(partitionScheme.ops[j], i, mappings, reverseMappings, ...);
```

Inside `sliceOp` there are two independent places that introduce the
"this partition starts 64 rows later" offset.

**Place 1 — `MakeRangeOp`, lines 968-983.** The range is renumbered:

```cpp
int sliceSize = (newRangeEnd - newRangeStart) / numOfPartitions;   // 128/2 = 64
newRangeStart += offset * sliceSize;                               // 0 + 1*64 = 64
newRangeEnd    = newRangeStart + sliceSize;                        // 128
```

So `tl.arange(0, 128)` becomes `tt.make_range {start = 64, end = 128}` in
partition 1. The `+64` is now baked into the range itself.

**Place 2 — `DescriptorLoadOp` / `DescriptorStoreOp`, lines 991-1013.** The
descriptor coordinate is shifted with a fresh `arith.addi`:

```cpp
auto newCoordVal = coordVal;
if (offset) {
  builder.setInsertionPointAfter(coordVal.getDefiningOp());
  Value offsetVal = builder.createWithAsyncTaskIds<arith::ConstantIntOp>(
      op->getLoc(), offset * shape[dim] / numOfPartitions, 32);   // 1*128/2 = 64
  newCoordVal = builder.createWithAsyncTaskIds<arith::AddIOp>(
      op->getLoc(), coordVal, offsetVal);
  mappings.map(coordVal, newCoordVal);            // <-- the bug, line 1009
  reverseMappings.map(newCoordVal, coordVal);
}
```

`mappings.map(coordVal, newCoordVal)` is a **global** substitution for the rest
of that partition, not a local one for this descriptor op. `coordVal` here is
the plain `i32` scalar `off_am`. Every op cloned afterwards goes through
`cloneAndSetResultType` (line 780), which calls `builder.clone(*op, mappings)`,
so **any later use of `off_am` silently becomes `off_am + 64`**.

In this kernel `off_am` has two uses:

* the M coordinate of `c_desc.store((off_am, off_bn), ...)` — place 2 correctly
  shifts it to `off_am + 64` for partition 1;
* `rows = off_am + tl.arange(0, BM)`, used to index the bias vector — its
  `tt.make_range` was already shifted by place 1, and now its `tt.splat %off_am`
  also picks up the poisoned mapping.

The two mechanisms compose, and the result is `off_am + 64 + (64..127)`.

### The generated IR, side by side

`artifacts/HIT-0009/cand.ttgir`, partition 0 (rows `off_am + 0..63`) — correct:

```mlir
%rows    = tt.make_range {end = 64 : i32, start = 0 : i32}
%rows_21 = tt.splat %off_am
%rows_22 = arith.addi %rows_21, %rows        // off_am + 0..63     OK
```

Partition 1 (should be rows `off_am + 64..127`) — wrong:

```mlir
%36      = arith.addi %off_am, %c64_i32_6    // the descriptor-store shift
%rows    = tt.make_range {end = 128 : i32, start = 64 : i32}   // 64..127
%rows_21 = tt.splat %36                                        // off_am + 64
%rows_22 = arith.addi %rows_21, %rows        // off_am + 128 .. off_am + 191
```

`%rows_22` then feeds both the bias address and the bias mask:

```mlir
%bias_23 = arith.cmpi slt, %rows_22, %M
%bias_25 = tt.addptr %bias_24, %rows_22
%bias_26 = tt.load  %bias_25, %bias_23, %cst
```

while the TMA store still writes the right place, `%c_desc_19[%36, %off_bn]`.
So the addresses written are correct and the *values* written are wrong.

### Consequence, measured

`M = 512`, `BM = 128`, so `pid_m` runs 0..3 and `off_am` is 0/128/256/384.
Partition 1 reads `d_ptr[off_am+128 .. off_am+191]`:

| `pid_m` | rows it computes | bias rows it should read | bias rows it reads |
|---|---|---|---|
| 0 | 64-127  | 64-127  | 128-191 |
| 1 | 192-255 | 192-255 | 256-319 |
| 2 | 320-383 | 320-383 | 384-447 |
| 3 | 448-511 | 448-511 | 512-575 -> all masked off, bias becomes 0.0 |

Measured on the output tensor: **every** differing element sits in a row with
`row mod 128 >= 64`, i.e. only in partition 1's half; 232 of 512 rows and
43,898 of the 131,072 elements in those rows differ. Partition 0's half is
bit-perfect.

### Which side is right

With integer inputs the whole kernel is exactly computable, so there is a
ground truth. `artifacts/HIT-0009/cross_check_vs_torch.py` builds it in torch
fp32:

```
acc integral? True   max|acc| 1828.0
ref   (no warp specialization) vs torch fp32 model: bitequal=True    ndiff=0
cand  (warp specialized)       vs torch fp32 model: bitequal=False   ndiff=43898  maxabs=24.0
```

The warp-specialized build is the wrong one.

## 3. Where it reproduces

**Hopper (sm_90) only, and only with `warp_specialize=True`.**

* The pass is `third_party/nvidia/hopper/.../WSDataPartition.cpp`, reached
  through `--nvgpu-warp-specialization`, which the sm_90 pipeline runs. The
  Blackwell path (`lib/Dialect/TritonGPU/Transforms/WarpSpecialization/`) is a
  different implementation and is not covered by this evidence.
* The candidate IR is full of Hopper-only constructs: `ttg.warp_specialize`,
  `ttng.warp_group_dot` (wgmma), `ttng.async_tma_copy_global_to_local`,
  `ttng.init_barrier` / `wait_barrier` (mbarrier). It cannot be built for a
  non-Hopper NVIDIA target, and there is no AMD equivalent.
* The faulty rewrite itself is plain MLIR bookkeeping with nothing
  architecture-specific in it, so if another backend ever reuses
  `WSDataPartition.cpp` it will inherit the bug.

The family sweep in `artifacts/HIT-0009/sweep_mm_epilogue.py` (64 config x
distribution pairs, output in `sweep_output.txt`) narrows it further:

| condition | differs? |
|---|---|
| `warp_specialize=False`, 32 pairs | never |
| `warp_specialize=True`, block 64x64x64, 16 pairs | never |
| `warp_specialize=True`, block 128x128x64, all-zero input, 2 pairs | never |
| `warp_specialize=True`, block 128x128x64, other inputs, 14 pairs | **10 differ** |

That fits the analysis: the data partition only splits when the tile is large
enough to split (128 rows into 2 x 64), and an all-zero bias vector makes the
wrong read harmless. The worst case seen is bf16, 128x128x64, `wide` inputs:
72 elements differ with `max_abs_diff = 2.1e6`.

**Scope limit, stated plainly:** these 64 pairs are one family on one GPU. They
show the bug happens; they do not show that a 64-row tile is safe in general or
that other kernels are immune. What is general is the code path: any kernel
where a scalar feeds both a descriptor coordinate and some other partitioned
index expression will hit the same double-count.

## 4. Plain-language explanation

Warp specialization splits the work of one tile between two groups of warps.
The tile has 128 rows; group 0 takes rows 0-63 and group 1 takes rows 64-127.
The compiler has to tell group 1 "you start 64 rows later".

It says that twice. Once it rewrites the row counter `0..127` into `64..127`.
Then, while fixing up the address the group writes to, it also records
"wherever you see the tile's starting row, use starting row + 64 instead" — and
that note applies to the rest of the group's code, including the row counter it
had already fixed. So group 1 thinks it is working on rows 128-191 when it is
really working on rows 64-127. The output goes to the right place; the bias
values it adds come from the wrong rows.

## 5. Can an SMT solver model this?

**Yes, in principle, and it is a good fit.** This is a deterministic,
single-program-instance, value-semantics difference.

What a checker would need:

* **Symbolic addressing.** The bug is an address error, not an arithmetic one.
  The check "for every lane, the address this load reads in the specialized
  program equals the address the original program reads" is a pure integer
  (bit-vector) query over `pid`, `off_am` and the lane index. No floating point
  is involved at all — the exact-integer control already shows the difference
  survives with integer data.
* **Warp-specialize regions as parallel composition.** The `ttg.warp_specialize`
  op has a default region plus N partition regions. The checker must treat the
  op as the composition of its regions and compare the *union* of their memory
  effects against the single loop plus epilogue of the reference. That is a
  structural obligation, not a concurrency one.
* **No memory-ordering model is required for this bug.** The two partitions
  write disjoint row ranges and read a read-only bias vector, so the result
  does not depend on interleaving. A checker could soundly assume race freedom
  here (it would need a separate argument that the ranges really are disjoint,
  which is itself an integer query).
* **No bit-exact FP is required.** Treating fp values as uninterpreted terms is
  enough: the two programs apply the *same* function to *different* loaded
  values, so an uninterpreted-function model already separates them.

The one real cost is that the property has to be checked per lane, and the tile
here is 128 x 128. Because the address is an affine function of the lane index,
a checker that keeps the index symbolic (rather than unrolling 16384 lanes)
should discharge it cheaply; a checker that unrolls will be slow but not
hopeless.

So: **capturable, and cheaply, provided the model covers `warp_specialize`
regions and keeps tile indices symbolic.**

## 6. Confidence

**High.** What the conclusion rests on:

1. The wrong IR is visible in the checked-in artifact — `tt.splat %36` where
   partition 0 has `tt.splat %off_am`, with `%36 = off_am + 64` and the
   `make_range` already shifted to `64..127`. No inference needed.
2. The two source lines that each add the offset are quoted above, and
   `doDataPartition` provably shares one `IRMapping` across all ops of a
   partition, so the `mappings.map(coordVal, newCoordVal)` at line 1009 does
   leak.
3. The predicted blast radius matches the measurement exactly: every differing
   element lies in a row with `row mod 128 >= 64`, and none outside.
4. There is a ground truth: with integer inputs the whole kernel is exact, and
   the non-specialized build matches a torch fp32 model bit for bit while the
   specialized build does not.

What is *not* established, and what would settle it:

* I did not build a patched compiler. The fix that the analysis implies —
  scope the descriptor-coordinate remap to the descriptor op instead of putting
  it in the shared `IRMapping`, or make `MakeRangeOp` not shift when the
  enclosing expression's base is already shifted — has not been compiled or
  tested. Building it and re-running the sweep would close the last gap.
* The exact reason only 43,898 of the 131,072 affected elements differ (rather
  than nearly all of them) is not pinned down. It is consistent with `pid_m=3`
  reading an all-masked bias of 0.0 and with bf16 rounding collapsing many
  small differences, but I did not verify that split.
* Whether the same double-count fires on the Blackwell warp-specialization
  path is untested.

## Determinism re-verified at 200 reps (2026-08-17)

The earlier determinism evidence in this report was a 20-rep check. Against a
build that disagrees with itself on 4% of reps — the rate measured on the
warp-specialized `mm_tma` references that were retracted — a 20-rep check only
detects a disagreement about 54% of the time, so that evidence was weak. It has
been redone properly.

`HIT-0009/verify_determinism.py` launches each build 200 times on the same
input and compares every rep against the first, under **both** allocation
patterns (`alive` keeps every rep's tensors so the buffers drift; `free`
releases each rep so the allocator hands the same blocks back), across five
inputs. That is 20 runs of 200 reps = **4000 launches**.

```
                                        reps differing from the first
  input                 side        alive     free
  intvalued/1262280619  reference   0/200     0/200      <- this report's input
  intvalued/1262280619  candidate   0/200     0/200
  randn/1262280619      reference   0/200     0/200
  randn/1262280619      candidate   0/200     0/200
  intvalued/4242        reference   0/200     0/200
  intvalued/4242        candidate   0/200     0/200
  tiny/99               reference   0/200     0/200
  tiny/99               candidate   0/200     0/200
  wide/7                reference   0/200     0/200
  wide/7                candidate   0/200     0/200

  TOTAL self-inconsistent reps: 0 of 4000
  distinct outputs per run: 1 (every run produced exactly one bit pattern)
```

A 200-rep run detects a 4%-per-rep flaky build with probability
`1 - 0.96^199 ≈ 99.98%`; on this report's own input the two sides were checked
with 800 launches between them. Both builds are stable, so the difference
between them is a property of the pass set, not run-to-run noise.

Raw numbers: `HIT-0009/determinism_200reps.json`.

This is the one warp-specialized report that survived. Seven others
(HIT-0015, 0016, 0018, 0019, 0020, 0021, 0022) were retracted precisely because
their reference builds fail this check — see `RETRACTED.md`.
