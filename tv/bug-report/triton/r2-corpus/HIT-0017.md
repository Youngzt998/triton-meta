## Review

Group B explains it: it is not reassociation (it survives whole-number inputs),

### 1. Root cause in the source

`lib/Dialect/TritonGPU/Transforms/ReduceDataDuplication.cpp`, the single
`mod.walk([&](triton::gpu::ConvertLayoutOp cvtOp)` body (lines 33-62 of that
file). For every `convert_layout` whose destination is a `ttg.dot_op` encoding
and for which `cvtNeedsSharedMemory(cvtOp)` is true, it builds

```cpp
auto tmpType = triton::gpu::MemDescType::get(
    dstType.getShape(), dstType.getElementType(),
    triton::gpu::SwizzledSharedEncodingAttr::get(
        mod.getContext(), dstDotOp, srcType.getShape(), order,
        triton::gpu::getCGALayout(srcEncoding), srcType.getElementType()),
    sharedMemorySpace);
auto tmp = triton::gpu::LocalAllocOp::create(builder, cvtOp.getLoc(), tmpType,
                                             cvtOp.getSrc());
auto newConvert = triton::gpu::LocalLoadOp::create(builder, cvtOp.getLoc(),
                                                   dstType, tmp);
```

Two things are wrong once `num_ctas > 1`.

* **The CGA layout is copied from the *source*.** `getCGALayout(srcEncoding)`
  takes how the value happened to be *loaded* and stamps it on the shared buffer.
  On this kernel the B operand is loaded as
  `tensor<16x16xf16, #blocked{... CGALayout = [[1,0],[2,0]]}>`, i.e. the 16 K-rows
  are split four ways across the four CTAs of the cluster, and the pass produces
  `!ttg.memdesc<16x16xf16, #ttg.swizzled_shared<{..., CGALayout = [[1,0],[2,0]]}>>`.
  The consumer is `#ttg.dot_op<{opIdx = 1, parent = #mma}>` where `#mma` splits
  only **M** across CTAs, so every CTA needs *all* 16 K-rows. The pass never
  compares the source and destination CTA split; there is no
  `getCTASplitNum(src) == getCTASplitNum(dst)` guard anywhere in the file.
* **The synchronisation is downgraded from cluster-wide to CTA-local.** The
  `convert_layout` lowering picks its barrier by asking whether the conversion
  crosses CTAs: `lib/Conversion/TritonGPUToLLVM/ConvertLayoutOpToLLVM.cpp:205-215`

  ```cpp
  bool isBlockSync = mlir::isCvtDimSync(srcLayout, dstLayout, kBlock);
  auto emitBarrier = [&]() {
    if (isWarpSync)        targetInfo.warpSync(loc, rewriter);
    else if (isBlockSync)  targetInfo.barrier(loc, rewriter, AddrSpace::Local);
    else                   targetInfo.clusterBarrier(loc, rewriter, sourceOp);
  };
  ```

  After the rewrite there is no `ConvertLayoutOp` left, so the only sync is what
  `MembarAnalysis` inserts, and `lib/Analysis/Membar.cpp:101-105` unconditionally
  creates `triton::gpu::BarrierOp`, which `MemoryOpToLLVM.cpp:262` lowers to
  `mlir::gpu::BarrierOp` -> `bar.sync` -- a **CTA-local** barrier. It has no
  cluster-wide form.

  Measured in the emitted PTX for the two arms of this hit:

  | | `barrier.cluster.arrive/wait` | `bar.sync` | `st.shared.b16` | `ld.shared::cluster.b16` | `mapa.shared::cluster` |
  |---|---|---|---|---|---|
  | reference (`convert_layout`) | 5 / 5 | 3 | 6 | 4 | 4 |
  | candidate (`local_alloc`+`local_load`) | 2 / 2 | 6 | 6 | 4 | 4 |

  The candidate still issues `mapa.shared::cluster` + `ld.shared::cluster`, i.e.
  it still reads *other CTAs'* shared memory, but three of the five cluster
  barriers are gone and were replaced by `bar.sync`, which orders nothing outside
  the reading CTA. A CTA reads a neighbour's shared memory before the neighbour
  has written it.

So: the pass replaces a cross-CTA data movement with a CTA-local shared-memory
round trip, keeps the source's (wrong) CTA split on the shared buffer, and loses
the cluster barrier that made the original conversion correct.

### 3. Where it reproduces

Measured on H100 (sm90). The judgement on how far it travels:

* It needs `num_ctas > 1`. At `num_ctas = 1` the pass produces the same result as
  the reference (`ir-identical` at this shape), and the whole CGA machinery is
  inert. Clusters are Hopper and newer, so **sm90+ only** in practice.
* It does not need any other Hopper-only construct: the failing IR has no wgmma,
  no TMA, no mbarrier, no warp specialization. It is an `mma.sync` (MMAv2)
  `tt.dot` plus `ttg.local_alloc`/`ttg.local_load`. The two ingredients are a
  cluster and a `convert_layout` into a dot operand.
* `--tritongpu-reduce-data-duplication` is in the **default** pipeline for both
  NVIDIA (`third_party/nvidia/backend/compiler.py:355`) and AMD
  (`third_party/amd/backend/compiler.py:295`).
* **Honest limit on reachability.** I could **not** reach it through the default
  pipeline on this kernel. Compiling the same kernel normally at `num_ctas`
  1/2/4 gives one identical answer, and the default TTGIR the pass sees already
  carries CGA layouts that match the dot (A replicated `CGALayout = [[0,0],[0,0]]`,
  B split along N `[[0,1],[0,2]]`), because `--triton-nvidia-gpu-plan-cta` runs
  before it (`compiler.py:304`). The fuzzed pipeline omitted `plan-cta`, so the
  operands kept the `convert-triton-to-tritongpu` default split on dim 0 and the
  pass carried that into shared memory. So today the defect is guarded by an
  invariant ("PlanCTA has already given every dot operand a CGA layout the dot
  can use") that is nowhere written down and nowhere checked -- and note that
  `PlanCTA.cpp` itself carries a `TODO(Qingyi): Move PlanCTAPass to the front of
  CoalescePass`, i.e. that ordering is expected to move.

### 4. Plain-language explanation

With more than one CTA in a cluster, a tile can be spread over several CTAs. The
old code knew that and, when it shuffled such a tile into the shape the matrix
unit wants, it used a **cluster-wide** wait so that every CTA had finished
writing before anybody read. This pass rewrites that shuffle into "write my part
to shared memory, then read the whole tile back". It keeps "read the whole tile"
-- including the parts that live in other CTAs -- but it drops the cluster-wide
wait and leaves only a wait inside one CTA. So a CTA can read a neighbour's
shared memory before the neighbour has put anything there. On top of that it
gives the shared buffer the same split the data had when it was loaded, which for
the second matrix operand is the wrong split: every CTA needs the whole operand,
not a quarter of it.

### 5. Can an SMT solver model this?

**Verdict: `needs a concurrency / memory-ordering model`.**

The value semantics of the two programs are the same. `ttg.convert_layout` and
`ttg.local_alloc` + `ttg.local_load` are, as *functions*, both the identity on
the tile; a functional equivalence check that models a tile as a value and
`local_alloc`/`local_load` as store-then-load of that value will prove them
equal, correctly, and see nothing. The bug is entirely in *when* the read is
allowed to happen relative to another CTA's write.

To catch it a model would need, at minimum:

* **shared memory as a second address space with a CTA index** -- not one flat
  array but `smem[cta][offset]`, because the whole point is that `local_load`
  reads `smem[other_cta]`;
* **layouts as index maps that include the block/CTA dimension** -- the
  `CGAEncodingAttr` linear layout maps a block id to a tile offset, and the bug
  is that the store map (from `getCGALayout(srcEncoding)`) and the load map (from
  the dot operand) disagree. This part *is* pure index algebra and an SMT model
  could check it directly: emit `store_map(cta, lane) == load_map(cta, lane)` as
  a side condition on every `local_alloc`/`local_load` pair and it is UNSAT here.
  That check alone would have caught this hit and needs no concurrency model at
  all.
* **a happens-before relation with barrier scopes** -- `bar.sync` orders only
  within a CTA, `barrier.cluster.arrive/wait` orders the cluster. Catching the
  *general* form of the bug (right split, missing barrier) needs the model to
  know that a read of `smem[c']` from CTA `c != c'` must be preceded by a
  cluster-scope barrier. That is a memory-ordering property, not a value
  property, so it is outside a functional input->output equivalence check.

FP axiom profile: irrelevant. The difference shows up on whole-number inputs
where every operation is exact, so even the weakest (reassoc-allowed)
uninterpreted-FP profile distinguishes the two answers -- *if* the model can see
the memory ordering at all. The abstraction that hides this bug is not the FP
abstraction, it is treating shared memory as a single-writer single-reader value.

Cost: the index-map side condition is tiny -- two linear layouts over
`(cta, warp, lane, reg)`, a few dozen bits, UNSAT in milliseconds. The full
happens-before formulation is the expensive one, because it needs a schedule
variable per CTA.

### 6. Confidence

**High that the candidate is wrong; high that the pass is at fault; medium that
a user can hit it today.**

* That the candidate is wrong is settled without any reference: it disagrees with
  itself across `num_ctas`, which is semantics preserving, on whole-number inputs
  where no rounding is possible, deterministically (4/4 identical runs per arm),
  and it survives a 28 KiB heap shift and `ptxas -O0`.
* That the pass is at fault is supported by the PTX barrier counts (5 cluster
  barriers -> 2) and by the source: the pass copies `getCGALayout(srcEncoding)`
  with no check against the destination, and `MembarAnalysis` has no cluster-scope
  barrier to insert.
* What is *not* settled: whether the shipping pass order can ever hand this pass
  a CGA-mismatched `convert_layout`. I tried the default pipeline on this kernel
  and it cannot. Settling that needs either a kernel where `plan-cta` leaves a
  mismatched conversion behind, or a maintainer's statement that the invariant is
  intended. A cheap first step for whoever picks this up: add an assert in
  `ReduceDataDuplication.cpp` that `getCTASplitNum(srcEncoding) ==
  getCTASplitNum(dstEncoding)` and run the test suite with `num_ctas > 1`.

## Numerics-change context (a label, not a verdict)

The culprit pass is classified `layout` by `fz/passes.py`. Reduction or dot
present in the reference IR: `True`. A `numerics` class pass
(`accelerate-matmul`, `F32DotTC`, `triton-combine`, `optimize-thread-locality`)
is *expected* to change FP results, and a layout-family pass on a kernel with a
reduction can legitimately change the summation order. Neither is a reason to
drop the finding; both are recorded so a reviewer can filter with all results in
hand. The small-whole-number control above is the cheap discriminator: if the
difference persists there, reassociation of an fp32 sum does not explain it.
