## Review

Reviewed against `tv/bug-report/REVIEW-CRITERIA.md`. Kept. No criterion in Group
A or Group B explains it. It is a genuine wrong answer, but the honest root cause
is **ptxas, not Triton**: with `DISABLE_PTXAS_OPT=1` (ptxas `-O0`) the difference
disappears completely.

### 1. Root cause in the source

There is no wrong Triton transformation here. `--triton-loop-aware-cse` does a
plain, correct common-subexpression elimination on this kernel. Checked line by
line against `artifacts/HIT-0024/input.ttgir` and `output.ttgir`:

* `%9 = tt.make_range {end = 128, start = 0} : tensor<128xi32, #blocked2>` is
  removed and its uses redirected to `%2`, which is the *same* op
  (`tt.make_range {end = 128, start = 0} : tensor<128xi32, #blocked2>`);
* the duplicate `ttg.convert_layout %11 : #blocked4 -> #blocked1` (five copies,
  `%12`..`%16`) collapse to one;
* the duplicate `arith.muli %7, %cst_2` (`%17`, `%27`) collapse to one;
* the duplicate `tt.broadcast %8` collapse to one.

`convert_layout` count goes 25 -> 14. Every merge is between two textually
identical ops with identical operands and identical result types. The
optimisation is sound and the two TTGIR modules are semantically the same
program.

The wrong answer is created after that:

* Both arms lower through the identical TTGIR->LLVM->PTX path and get the same
  shared-memory budget (`shared = 16384` on both).
* PTX op counts: the reference has 592 `st.shared.v4.b32`, 64 `ld.shared.v4.b32`
  and 97 `bar.sync`; the candidate has 336 `st.shared.v4.b32`, the **same** 64
  `ld.shared.v4.b32`, and 66 `bar.sync`. Fewer stores is expected (the duplicate
  conversions are gone); the point is that the two PTX files are both plausible
  and both are the same program.
* Setting `DISABLE_PTXAS_OPT=1` (`python/triton/knobs.py:508`, which drops ptxas
  to `-O0`) makes **both arms and all four `num_warps` settings agree**. So the
  divergence is introduced by the ptxas optimiser on the candidate's PTX.

I could not narrow it further than "ptxas at -O3 miscompiles the CSE'd PTX at
`num_warps = 2` for this kernel". I have not isolated which SASS transformation
does it, and I am explicitly **not** inventing one.

### 3. Where it reproduces

H100 / sm90, with this machine's ptxas. The failing IR is generic: `#blocked`
layouts, `tt.load`, `tt.reduce`, `arith.*`, `libdevice.rsqrt`, `tt.store`. No
wgmma, no TMA, no mbarrier, no cluster, no warp specialization, `num_ctas = 1`.
So the *Triton* side would behave the same on any NVIDIA target. But since the
fault is in ptxas, "where it reproduces" is really "which ptxas version", and I
have only tested the one in this checkout. It should be re-checked against a
newer CUDA toolkit before anything is reported upstream -- if it is already fixed
there, this report is closed.

### 4. Plain-language explanation

Triton removed some repeated work -- it noticed the same index calculation was
being done twice and kept one copy. That is a safe change and the two programs
are the same. But the shorter program, when NVIDIA's assembler (`ptxas`) compiles
it with optimisation on, at exactly two warps per block, gives different numbers.
Turn the assembler's optimiser off and both give the same, correct numbers. So
the mistake is not Triton's; it is one step further down, in the tool that turns
PTX into machine code.

### 5. Can an SMT solver model this?

**Verdict: `below the IR level`. No IR-level translation validator can ever catch
this, and that is the useful thing this report says.**

The two TTGIR modules are semantically equal and an SMT equivalence check would
correctly prove them equal -- that is the *right* answer at the IR level. The
divergence appears only in the PTX->SASS step, which is closed-source and below
anything a Triton-IR checker models. Concretely:

* the ops in the diff are `tt.make_range`, `ttg.convert_layout`, `arith.muli`,
  `tt.broadcast` -- all pure, all value-semantics, all trivially modelled;
* an equivalence checker that proved "input.ttgir == output.ttgir" would be
  *correct* and would still leave the user with a wrong answer.

This is worth recording for the translation-validation project as a concrete
ceiling: proving the IR transformation correct is necessary but not sufficient;
the same class would need a SASS-level or a hardware-level model, or a
differential-testing layer under the IR checker (exactly what this campaign is).
An SMT model would only help here in the negative direction -- it can *rule out*
the IR passes as the culprit, which is what turns "some pass is wrong" into
"the backend is wrong", and that is genuinely useful triage.

FP axiom profile: not the deciding factor. Under exact-integer inputs the
arithmetic is exact, so even a reassoc-allowed profile would demand the two
answers be equal.

### 6. Confidence

**High that this is a real wrong answer. High that Triton's IR passes are not at
fault. Medium on the exact ptxas mechanism, which I did not isolate.**

What is settled: the two IRs are the same program (checked op by op); the
candidate at `num_warps=2` disagrees with three other `num_warps` settings of the
same program on exact-integer inputs, on three seeds; both arms are deterministic;
`enable_fp_fusion=False` does not remove it; `ptxas -O0` does.

What would settle the rest: reduce the PTX to a minimal kernel and file it with
NVIDIA, and re-test on a newer ptxas. If a newer ptxas fixes it, close the report.
The one alternative I cannot fully exclude is that Triton emits PTX that is
under-synchronised in a way only `-O3` exposes; the `bar.sync` counts (97 vs 66)
are consistent with the CSE legitimately removing shared round trips, but I did
not prove the remaining barriers are sufficient.

## Numerics-change context (a label, not a verdict)

The culprit pass is classified `bit` by `fz/passes.py`. Reduction or dot
present in the reference IR: `True`. A `numerics` class pass
(`accelerate-matmul`, `F32DotTC`, `triton-combine`, `optimize-thread-locality`)
is *expected* to change FP results, and a layout-family pass on a kernel with a
reduction can legitimately change the summation order. Neither is a reason to
drop the finding; both are recorded so a reviewer can filter with all results in
hand. The small-whole-number control above is the cheap discriminator: if the
difference persists there, reassociation of an fp32 sum does not explain it.
