## Review

Reviewed against `tv/bug-report/REVIEW-CRITERIA.md`. Kept under section 2, last
bullet ("compile failure, crash ... keep it"), but read section 6 before acting
on it: unlike `HIT-0037`, this assertion is a **documented precondition the
harness violated**, not a logic error. Occurrence count 2: `r2-corpus/HIT-0020`
is the same assertion from a different pass list and was rejected as a B4
duplicate.

### 1. Root cause in the source

`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp:238-242`, inside
`CTAPlanner::processDot`:

```cpp
funcOp.walk([&](triton::DotOp dot) {
  auto aTy = cast<RankedTensorType>(dot.getA().getType());
  auto bTy = cast<RankedTensorType>(dot.getB().getType());
  auto dTy = cast<RankedTensorType>(dot.getD().getType());

  assert(isa<ttg::DotOperandEncodingAttr>(aTy.getEncoding()) &&
         isa<ttg::DotOperandEncodingAttr>(bTy.getEncoding()) &&
         isa<ttg::BlockedEncodingAttr>(dTy.getEncoding()) &&
         "PlanCTAPass should follow immediately after CoalescePass");
```

The pass requires the dot's accumulator `D` to still carry a **blocked**
encoding. The reference pipeline for this hit already ran
`--tritongpu-accelerate-matmul`, which is precisely the pass that turns `D` into
an `#ttg.nvidia_mma` encoding. So the assertion fires, and the message names the
cause itself.

Two things are wrong, in different senses:

* **The harness's fault.** It built a pass order the compiler documents as
  invalid. In the shipping NVIDIA pipeline (`third_party/nvidia/backend/compiler.py`)
  `plan_cta` is at line 304 and `accelerate_matmul` at line 307 -- plan-cta first.
  So this ordering cannot occur in a real compile.
* **The compiler's fault, and this is the part worth fixing.** The precondition
  is enforced only by an `assert`, which is compiled out in a release build
  (`NDEBUG`). In a release build the three `cast<...>` calls that follow it
  (lines 244-246) become unchecked casts on the wrong attribute types, so instead
  of a clean diagnostic the pass reads garbage. A pass with a hard precondition
  on pipeline position should either state it in the pass's TableGen
  documentation and check it with a real `emitError` + `signalPassFailure`, or be
  written to bail out (`return`) on a dot it cannot handle.

### 3. Where it reproduces

Anywhere: a host-side MLIR pass, no GPU needed, no Hopper- or Blackwell-only
construct in the IR (the dot is an MMAv2 `tt.dot` on fp16). It needs
`num_ctas > 1` (this draw is `cta2`) so that `PlanCTAPass` does not return early,
a `tt.dot` in the module, and any pass before it that has already replaced the
accumulator's blocked encoding -- in practice `--tritongpu-accelerate-matmul`.

It is **not reachable through the shipping pipeline**, by construction: the
shipping order puts `plan_cta` before `accelerate_matmul`.

### 4. Plain-language explanation

This pass only knows how to look at a matrix multiply whose output still has the
plain "blocked" description it gets right after the first layout pass. Here an
earlier pass had already rewritten that output to the tensor-core description, so
the pass found something it did not expect and aborted. The abort message says so.
The real complaint is that the check is only an `assert`: in a build with asserts
turned off the pass would carry on and reinterpret the layout as the wrong type.

### 5. Can an SMT solver model this?

**Not applicable.** A compile-time abort produces no second program, so there is
nothing for an equivalence check to compare.

The right tool for this class is a pass-precondition check inside the compiler --
a `PassManager` invariant or a declared dependency, not an SMT query. It is worth
noting for the translation-validation project that a validator built on
"run pass P on IR, compare before and after" has to survive being handed IR that
P was never meant to see; a validator that drives passes in arbitrary orders will
hit this class constantly and should treat a crash as "pass not applicable here"
rather than as a finding, unless the pass's precondition is actually documented.

### 6. Confidence

**Certain that the assertion fires; low that this is a bug a user can hit.**

The assertion text itself names the required pipeline position, and the shipping
pipeline honours it. So this is a robustness complaint, not a miscompile: the
only concrete defect is that a documented precondition is enforced by an `assert`
that disappears under `NDEBUG`, leaving three unchecked `cast<>`s behind it.

What would settle it: a maintainer saying whether `PlanCTAPass` is meant to be
runnable at other points in the pipeline. If yes, `processDot` needs to handle a
non-blocked accumulator; if no, the assert should become a real diagnostic and
the precondition should be written into the pass documentation.
