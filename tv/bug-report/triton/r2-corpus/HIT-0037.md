### 1. Root cause in the source

Bisected to a **single pass**: `--triton-nvidia-gpu-plan-cta` alone crashes on
the reference IR. The other three passes in the report's pass list run clean.

```

  llvm::SmallVectorTemplateCommon<long>::operator[](size_type):
  Assertion `idx < size()` failed.
```

Symbolised backtrace, innermost first:

```

        unsigned numWarps, unsigned numThreads, CGAEncodingAttr)
```

`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp`, lines 65-83:

```cpp
ttg::DistributedEncodingTrait
replaceCGALayout(ttg::DistributedEncodingTrait layout,
                 llvm::ArrayRef<int64_t> shape, int numWarps,
                 ttg::CGAEncodingAttr newCGALayout) {
  if (auto blockedLayout = mlir::dyn_cast<ttg::BlockedEncodingAttr>(layout)) {
    return ttg::BlockedEncodingAttr::get(                      // line 70
        layout.getContext(), shape, blockedLayout.getSizePerThread(),
        blockedLayout.getOrder(), numWarps, 32, newCGALayout);
  } else if (auto sliceLayout =
                 mlir::dyn_cast<ttg::SliceEncodingAttr>(layout)) {
    return ttg::SliceEncodingAttr::get(
        layout.getContext(), sliceLayout.getDim(),
        replaceCGALayout(sliceLayout.getParent(), shape, numWarps,  // line 77
                         newCGALayout));
  }
  ...
```

**Line 77 is the bug: it recurses into the slice layout's *parent* but passes the
*slice's* shape unchanged.** A `#ttg.slice<{dim = d, parent = P}>` on a rank-`N`
tensor has a parent of rank `N+1`. So the recursive call reaches line 70 with a
rank-1 `shape` and a rank-2 `sizePerThread`/`order` taken from the parent, and
`BlockedEncodingAttr::get` indexes `shape[i]` for `i` up to the parent's rank and
walks off the end of the array. The fix has to expand the shape at `sliceLayout.getDim()`
(insert 1, or the parent's real extent) before recursing.

The trigger in this kernel is `PlanCTA.cpp:609` in `processLoadStore`, on this
op in the reference IR (line 131):

```mlir
%47 = tt.load %44, %46, %cst_5 : tensor<32x!tt.ptr<f32>, #ttg.slice<{dim = 0, parent = #blocked}>>
```

a **1-D load whose layout is a slice of a 2-D blocked layout** -- exactly the
rank-mismatch case.

`HIT-0038` is the same crash: same input IR, same single pass, same assertion,
same stack.

### 3. Where it reproduces

Anywhere. This is a host-side MLIR pass; no GPU is involved and no GPU-specific
construct is needed. The only requirements are:

* `num_ctas > 1` (this draw is `cta4`), because `PlanCTAPass` returns early
  otherwise, and
* an op that `processLoadStore` visits whose tensor carries a `#ttg.slice`
  layout -- i.e. any 1-D `tt.load`/`tt.store` that has been folded into a slice
  encoding.

**Reachability through the shipping pipeline: not demonstrated.** In the real
NVIDIA pipeline `plan_cta` runs at `third_party/nvidia/backend/compiler.py:304`,
right after `coalesce` and `f32_dot_tc` and *before* `remove_layout_conversions`.
At that point a 1-D `tt.load` still has a plain rank-1 blocked layout, not a
slice; slice-layout loads appear after `remove-layout-conversions` folds a
conversion into the load. I checked directly: running the real prefix
`--tritongpu-coalesce --tritongpu-F32DotTC --triton-nvidia-gpu-plan-cta` on the
*root* TTGIR of this kernel does **not** crash. So today the pass is protected by
its position in the pipeline. That protection is not written down as a
precondition, is not asserted, and `PlanCTA.cpp` carries a
`TODO(Qingyi): Move PlanCTAPass to the front of CoalescePass` -- the position is
expected to change. The fix is three lines and removes a latent crash.

### 4. Plain-language explanation

A "slice" layout describes a 1-D tensor by saying "I am one row of this 2-D
layout". When this pass rewrites layouts for multi-block clusters, it walks from
the slice to the 2-D layout it points at -- but it forgets to grow the shape from
1-D to 2-D while doing so. The code then reads the second dimension of a
one-element list and the compiler aborts.

### 5. Can an SMT solver model this?

**Not applicable.** This is a compile-time crash, not a difference in computed
values, so the question "could an equivalence check see it" does not arise: there
is no second program to compare against -- the compiler never produces one.

For completeness, the class of tool that *would* catch it is a different one: an
IR verifier invariant or a type-level rank check ("the shape handed to
`BlockedEncodingAttr::get` must have the same rank as its `sizePerThread` and
`order`"), i.e. a static assertion inside the compiler, not an SMT equivalence
query. Note this is exactly what the campaign's R4 line (`r2-compile`,
`--verify-each`) is for.

### 6. Confidence

**Very high that the code is wrong.** The rank mismatch at `PlanCTA.cpp:77` is
visible by reading the function, and the backtrace lands exactly there. There is
no interpretation involved.

**Low-to-medium that a user hits it today**, for the reason in section 3: the
shipping pipeline does not currently feed the pass a slice-layout load. The
remaining doubt is only about reachability, and a maintainer can settle it in one
sentence ("PlanCTA is documented to run before remove-layout-conversions"), after
which the right outcome is still to fix the recursion rather than rely on the
ordering.
