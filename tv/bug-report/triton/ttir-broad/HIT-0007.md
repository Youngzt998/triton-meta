Summary: the kernel `_conv_transpose2d_stride2_pad1_3x3_kernel_312550c9` is compiled twice from the *same* root TTIR.
The only difference is that the candidate side runs `--triton-combine` first.
Both sides then go through --convert-triton-to-tritongpu, then make_llir / make_ptx / make_cubin -- the identical code. On the same inputs,
in the same device buffers, the two builds write different bits.

What is claimed here, and nothing more: **two compilations that differ only in
the pass set produce different bits on the same input.** Whether that counts as
a bug is a judgment call and is left to a human; the `Labels:` block above
carries everything needed to make it.

## What is and is not claimed

The scope of this round is **bit-equivalence only**. The finding is: the
reference side runs **zero** TTIR passes, the candidate runs `--triton-combine`, and
the two builds write different bits for the same inputs in the same buffers.
No claim is made here that this is a compiler bug.

The judgment inputs a reviewer needs are recorded as labels, not used to filter:

  - pass-class: numerics-changing -- --triton-combine (rewrites tt.dot/tt.reduce/tt.dot_scaled: Combine.cpp CombineDotAddFPattern / CombineBroadcastMulReducePattern)
  - layout-reorders-reduction: same layouts here, but this kernel's result is already layout sensitive (minimal vs production lowering of the same TTIR disagree)
  - magnitude: 845450/988160 elements (85.5580%), max_abs_diff=4.57764e-05, max_rel_diff=0.178743, nan-vs-number 0, inf-vs-finite 0, first bits 0x406efeb7 -> 0x406efeb3
  - exact-int-control: no difference under exact-integer inputs over 3 draws (consistent with, but not proof of, reassociation)

Background for the reviewer: the only TTIR pass in this build documented to
change floating-point results is `--triton-combine` (`Combine.cpp`:
`CombineDotAddFPattern` folds an add into the dot accumulator,
`CombineBroadcastMulReducePattern` turns a reduction into a `tt.dot`). Every
other pass here -- canonicalization, CSE, DCE, code motion, structural rewrites
-- is meant to preserve values. Everything below the TTIR is identical code on
both sides.

Data races are out of scope by decision (a race is undefined behaviour), which
is why non-deterministic kernels are dropped from the corpus rather than
reported. This kernel is deterministic; see the evidence above.
