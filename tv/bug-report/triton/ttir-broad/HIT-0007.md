# HIT-0007: `--triton-combine` turns NaN into Inf by moving the accumulator into the dot

Verdict: **CONFIRMED — NaN on one side, Inf on the other**
Line:    ttir-broad
Arch:    generic (no Hopper- or Blackwell-only construct anywhere in the IR)
Culprit pass: `--triton-combine`, pattern `CombineDotAddFPattern`
Reviewed: 2026-08-17

## What goes wrong, in one sentence

`--triton-combine` rewrites `dot(a, b, 0) + acc` into `dot(a, b, acc)`, which
moves `acc` from the end of the K-length summation chain to its front; when the
chain contains `+inf` and `-inf`, one order produces `NaN` and the other
produces `±Inf`.

---

## 1. Root cause in the source

Public Triton `3.8.0+git3277063a`.

**Step 1 — the rewrite.**
`lib/Dialect/Triton/Transforms/Combine.cpp:249-284`,
`CombineDotAddPattern<DotOp, arith::AddFOp>`:

```cpp
if (!dotOp->hasOneUse())      return failure();
if (!isZero(dotOp.getC()))    return failure();
if (dotOp.getMaxNumImpreciseAcc() != 0) return failure();
rewriter.modifyOpInPlace(dotOp, [&] {
  dotOp.getCMutable().assign(isDotLHS ? addOp.getRhs() : addOp.getLhs());
  dotOp->moveBefore(addOp);
});
rewriter.replaceAllUsesWith(addOp, dotOp.getResult());
```

The only guard on the numerics is `isZero(dotOp.getC())`. That is sound in
exact real arithmetic (`x + 0 = x`), but it says nothing about where `C` enters
the floating-point sum.

The TTIR diff for this kernel is exactly that one rewrite:

```diff
-%144 = tt.dot %140, %143, %cst_4, inputPrecision = tf32x3 : ... -> tensor<64x16xf32>
-%145 = arith.addf %arg8, %144 : tensor<64x16xf32>
-scf.yield %145 : tensor<64x16xf32>
+%144 = tt.dot %140, %143, %arg8, inputPrecision = tf32x3 : ... -> tensor<64x16xf32>
+scf.yield %144 : tensor<64x16xf32>
```

and it survives into TTGIR unchanged (`artifacts/HIT-0007/reference.ttgir` vs
`candidate.ttgir` differ in three lines only: `%192` converts `%cst_4` instead
of `%arg8`, and the trailing `arith.addf` disappears).

**Step 2 — what `C` means at codegen.** The dot's result layout here is a plain
`#ttg.blocked`, not `#mma`, so it is lowered by the FMA dot path,
`lib/Conversion/TritonGPUToLLVM/DotOpToLLVM/FMA.cpp`:

```cpp
Value accum = c;                                        // line 22
for (each k)
  accum = LLVM::FMulAddOp::create(builder, loc, aElem, bElem, accum);  // line 36
```

So `C` is the **seed** of the K-long `fmuladd` chain.

Put together, for `K = 16`:

| side | what is computed |
|---|---|
| reference | `t = fma(a15,b15, ... fma(a0,b0, 0))` then `arg8 + t` |
| candidate | `fma(a15,b15, ... fma(a0,b0, arg8))` |

`arg8` moved from the last position to the first. In real arithmetic these are
equal. In IEEE-754 they are not, and the interesting case is not rounding:

* if the partial products contain a `+inf` and the running term is `-inf`
  (or the reverse), the addition yields **NaN**;
* moving `arg8` changes *when* the two opposite infinities meet, so one order
  hits `inf + (-inf)` and the other does not.

That is what is observed: on inputs containing infinities the reference writes
`NaN` (`0x7fffffff`) and the candidate writes `+Inf` or `-Inf`.

**Note on `tf32x3`.** The dot carries `inputPrecision = tf32x3`. The
`TF32x3` expansion in `lib/Dialect/TritonGPU/Transforms/F32DotTC.cpp:146-201`
already has to defend against exactly this class of problem — line 192
`replaceNansWithZeros(dot2)`, with the comment "+infinity * 0.0 = NaN ... we
must override any accumulated result if the last partial product is
non-finite". In this kernel that pass does not fire (the `tt.dot` still carries
`inputPrecision = tf32x3` in the final TTGIR), but it shows the Triton
developers already know that moving terms around a dot is not NaN/Inf safe.
`CombineDotAddPattern` has no such guard.

## 3. Where it reproduces

**Any target.** Nothing in this is Hopper-specific:

* `CombineDotAddFPattern` lives in `lib/Dialect/Triton/Transforms/`, the
  target-independent TTIR layer, and `--triton-combine` runs in every backend's
  `make_ttir`.
* The FMA dot lowering in `lib/Conversion/TritonGPUToLLVM/DotOpToLLVM/FMA.cpp`
  is the shared TritonGPU-to-LLVM path, used whenever the dot's result layout
  is `#blocked` rather than a hardware MMA layout — i.e. small dots like this
  `64x16 * 16x16` one, on any GPU.
* The IR contains no wgmma, TMA, mbarrier, cluster or warp-specialize op.
* On an MMA layout the same rewrite would put `acc` into the tensor-core
  accumulator instead, which is a different (hardware) summation order but the
  same class of change. That variant is **not** tested here.

Tested on: one H100 (sm_90a), Triton `3.8.0+git3277063a`, CUDA 12.9 ptxas. Not
tested on other architectures or on AMD.

## 4. Plain-language explanation

The kernel adds up 16 products and then adds a running total from earlier
loop steps. The optimizer notices it can start the 16-product sum *from* the
running total instead of adding it at the end, which saves one instruction.

For ordinary numbers those two orders agree to within rounding. For infinity
they do not: `(+infinity) + (-infinity)` is "not a number", and whether the two
infinities ever meet depends on the order you add things in. So one build says
"not a number" and the other says "infinity" for the same input.

---

## 5. Can an SMT solver model this?

**Yes, but only with a bit-exact floating-point model that includes the special
values.** This is a deterministic, single-program-instance value difference —
no grid, no concurrency, no memory ordering, one output element is enough to
see it.

The catch is which FP model the checker uses:

* An **uninterpreted-function** FP model (each fp op an opaque function, plus a
  few axioms) is blind to this. It has no notion of Inf, so `add(x, y)` is just
  a term; the checker would report EQUIVALENT and be wrong about the hardware.
* An FP model that **allows reassociation** — the natural profile for accepting
  a compiler's reordering of a sum — is also blind to it, and for the *finite*
  inputs it should be: on `randn` / `small` the difference is 1 ulp and is a
  reassociation the pass is entitled to make. But such a profile would also
  accept the NaN case, which is the part that is not just rounding.
* A **bit-exact IEEE-754 model** (`fp.add`, `fp.fma` in SMT-LIB `FloatingPoint`
  theory, with NaN and Inf) captures the finding exactly. The obligation is
  `fma_chain(a, b, 0) + acc == fma_chain(a, b, acc)` for `K = 16`, one output
  element, all inputs free 32-bit floats. That is 33 free fp32 variables and 32
  fused operations, which a bit-blasting FP solver can handle for a
  counterexample search (finding a SAT witness is usually much easier than
  proving UNSAT here). It would return SAT with the two infinities.

So the practical answer for a translation validator: **this bug is exactly the
case that distinguishes the two FP axiom profiles.** Under "reassociation
allowed" it is invisible; under "exact bit-to-bit" it is found immediately, and
found on a single element with a small formula. It is a good regression test
for the exact-mode solver.

## 6. Confidence

**High that the two builds really disagree NaN-vs-Inf; medium on whether Triton
would call it a bug.**

Solid:

* The rewrite is one pattern, quoted above, and the TTIR/TTGIR diffs contain
  nothing else — three lines in TTGIR.
* The lowering fact that `C` seeds the fmuladd chain is one line of source
  (`FMA.cpp:22`).
* The NaN-vs-Inf outcome reproduces on three independent seeds of the `mixed`
  profile, always in the same direction (reference NaN, candidate Inf), and it
  is not ptxas: it survives `DISABLE_PTXAS_OPT=1`.
* The kernel is not UB: the scope-aware scanner reports its single `tt.store`
  address chain as
  `tt.addptr <- arith.addi <- tt.broadcast <- tt.expand_dims <- arith.addi <- tt.splat <- arith.remsi <- tt.get_program_id`,
  with no `tt.load` in it (see `ttir-broad/UB-GATE-AUDIT.md`). Both builds are
  bit-identical to themselves across repeated launches.

The honest counter-argument, stated so a reader can weigh it:

* On finite inputs this is plain reassociation of an fp32 sum, the difference
  is 1-4 ulp, and it vanishes entirely on exact-integer inputs (`intvals`
  profile, and my own exact `3+a`/`3-a` control). By criterion B1 alone that
  half of the finding would be rejected: the pass holds an explicit licence to
  fuse `dot+add` into the accumulator.
* Triton's `tt.dot` does not document a summation order, so a Triton developer
  may well answer "reassociating a dot accumulation is allowed, and IEEE
  special-value behaviour is not preserved across reassociation — working as
  intended".
* What keeps this report is that the change is not a rounding change: a NaN
  becoming an Inf is a change of *kind*, and a downstream `isnan` check or a
  masked-out-with-NaN idiom would behave differently. The review criteria list
  "NaN or Inf appears on one side only" as a keep with no exception.

What would settle the remaining doubt:

* An upstream answer on whether `CombineDotAddFPattern` is meant to be
  NaN/Inf preserving. `F32DotTC.cpp:192` shows the codebase does care about
  this in at least one place, which is an argument that it should here too.
* Testing the same rewrite when the dot lands on an `#mma` layout (larger
  tiles), to see whether the tensor-core accumulator shows the same NaN-vs-Inf
  flip. Not done here.
* Narrowing to a single 64x16 tile with hand-picked `±inf` operands, to show
  the exact pair of infinities involved. I established the mechanism from the
  lowering, not from an isolated operand pair.
