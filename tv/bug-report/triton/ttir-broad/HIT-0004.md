# HIT-0004: ind::triton_per_fused_mean_std_var_0_fdf7c466 miscompiles under `--triton-loop-aware-cse`
Verdict: needs-review
Arch:    generic
Culprit: --triton-loop-aware-cse
Arm:     B

Summary: the kernel `triton_per_fused_mean_std_var_0_fdf7c466` is compiled twice from the *same* root TTIR.
The only difference is that the candidate side runs `--triton-loop-aware-cse` first.
Both sides then go through the production make_ttgir, then make_llir / make_ptx / make_cubin -- the identical code. On the same inputs,
in the same device buffers, the two builds write different bits.
Gate note: this kernel already gives different results under the minimal vs the production lowering of the same TTIR, i.e. its float result is layout sensitive

## Determinism evidence

* corpus pre-screen: 3 runs per input profile on 3 profiles, both lowering
  arms, all bit-identical -- otherwise the kernel would have been dropped;
* at triage: reference side 3/3 self-identical, candidate side 3/3
  self-identical, reference-vs-candidate mismatch reproduced 3/3;
* both sides run on the *same* device buffers at the same addresses
  (fill -> snapshot -> run reference -> read -> restore -> run candidate),
  so an out-of-bounds read cannot make them differ by accident.

## Why this is NOT an expected numerics change

The reference side runs **zero** TTIR passes and the candidate runs
`--triton-loop-aware-cse`. Those passes are canonicalization, CSE, DCE, code motion and
structural rewrites; none of them is licensed to change a floating-point
result. Everything below the TTIR is the identical code on both sides.
The by-design gate DID fire here: this kernel already gives different results under the minimal vs the production lowering of the same TTIR, i.e. its float result is layout sensitive -- so this is filed as needs-review, not as a confirmed bug.
