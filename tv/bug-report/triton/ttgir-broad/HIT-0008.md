# HIT-0008: ptxas 12.9 puts 4096 global stores at the wrong address in an unoptimized TTGIR softmax-backward kernel

Verdict: **CONFIRMED — invalid generated code** (out-of-bounds writes, and 4096
         in-range elements never written)
Line:    ttgir-broad
Arch:    any NVIDIA target built with CUDA 12.9 ptxas; the IR is generic
Culprit: **not a Triton MLIR pass.** The fault is in `ptxas` V12.9.86 at
         `--opt-level 2` and above. `--triton-loop-aware-cse` (the pass this
         report was filed against) only perturbs the PTX enough that ptxas
         stops mis-optimising it.
Reviewed: 2026-08-17; re-checked 2026-08-17 against the amended review criteria
Occurrences: 3 — this report, ttgir-broad HIT-0042 (byte-identical reference IR,
         different culprit-pass label) and ttgir-broad HIT-0059 (byte-identical
         `input.ttgir`, `output.ttgir` **and** `spec.json`, same culprit pass).
         Both were rejected as duplicates under criterion B4.

**Re-check against the amended criteria (2026-08-17).** The criteria gained an
exception to the one-sided NaN/Inf keep rule: reject if the difference goes away
once fast math is removed. It does not touch this report, which is kept under a
different bullet — "invalid generated code" — and involves no NaN or Inf at all.
Checked anyway: with `TRITON_DEFAULT_FP_FUSION=0` the minimized repro still
writes 3968 elements out of range (`written 32640 max 62719`), and it is still
fixed only by `DISABLE_PTXAS_OPT=1` (`written 32768 max 32767`). The finding is
an address error, not an arithmetic one, so no floating-point flag can explain
it. **Keep stands.**

## What goes wrong, in one sentence

The reference build of this kernel writes 3968 elements **past the end of the
output tile** and never writes 4096 elements inside it, because ptxas 12.9
computes a wrong row offset for one register block of the store.

---

## 1. Root cause

### The two sides

Reference = the raw root TTGIR of
`ind:triton_per_fused__softmax_backward_data_0_351b228a`, straight out of
`--convert-triton-to-tritongpu`, no optimization at all
(`HIT-0008/input.ttgir`). Candidate = the same IR plus
`--triton-loop-aware-cse` (`HIT-0008/output.ttgir`). The pass removes duplicate
`ttg.convert_layout` / `tt.broadcast` / `arith.muli` copies of the *same*
index and mask expressions; it changes no arithmetic.

### It is the reference that is wrong, not the candidate

The kernel is exactly computable with integer inputs — it is
`tmp4 = a*b`, `tmp8 = sum(tmp4, axis=1)` over 512 columns, then
`tmp10 = fma(-b, tmp8, tmp4)` — so with `|a|,|b| <= 8` every fp32 accumulator
stays under `2^24` and there is a ground truth. Filling the output with NaN
first and comparing against a torch fp32 model:

```
ref : written=32640  in-range=28672/32768  OUT-OF-RANGE=3968  (max idx 62719)
      bit-equal to the torch model on the 28672 it did write
cand: written=32768  in-range=32768/32768  OUT-OF-RANGE=0     (max idx 32767)
      bit-equal to the torch model on all 32768
```

The kernel's own store is
`tl.store(out_ptr1 + (r0_1 + 512*x0), tmp11, xmask)` with `x0 in [0,64)` and
`r0_1 in [0,512)`, so index 32767 is the largest legal one. Index 62719 is
`122*512 + 255`: the row index used was `58 + 64` instead of `58`.

The corrupted set is exactly one register block of the store: rows where
`(row // 4) % 2 == 0` crossed with columns `128..255` — 32 x 128 = 4096
elements, all shifted by `+64` rows (`+32768` elements). Everything else is
correct.

### The fault is in ptxas, not in Triton's MLIR

Same PTX, different ptxas settings, same input:

| ptxas | opt level | result |
|---|---|---|
| V12.9.86 (Triton's `TRITON_PTXAS_PATH`) | `--opt-level 0` | correct, 32768 in range |
| V12.9.86 | `--opt-level 1` | correct |
| V12.9.86 | `--opt-level 2` | **wrong**, 3968 out of range |
| V12.9.86 | `--opt-level 3` (Triton's default) | **wrong**, 3968 out of range |
| V13.1.80 | `--opt-level 0` and `3` | correct |

The SASS has 256 `STG` instructions at every optimization level and the PTX has
256 `st.global`, so no store is added or dropped — only the address of 32 of
them changes.

The PTX has no detectable undefined behaviour that would let ptxas do this
legally:

* `compute-sanitizer --tool racecheck`: **0 hazards** — the shared-memory
  round-trips that `ttg.convert_layout` performs are properly separated by
  `bar.sync`.
* `compute-sanitizer --tool initcheck`: **0 errors** — nothing uninitialised is
  read.
* `compute-sanitizer --tool memcheck`: **0 errors** — the stray writes land
  inside the (much larger) allocation, so they are silent.

Inserting an explicit `ttg.barrier local` before the store's
`ttg.convert_layout` does **not** change the outcome, which also rules out a
missing membar in Triton.

### What in the IR triggers it

Reduced by hand from the reference (`HIT-0008/minimized.ttgir`, 34 lines):

* the store address chain **alone** is correct;
* the store address chain plus **one** masked `tt.load` (with its own
  `64x512xi32` and `64x512xi1` layout conversions) is correct;
* the store address chain plus **two** such loads reproduces the bug exactly
  (32640 written, max index 62719, 3968 out of range);
* dropping the `tt.reduce` / `math.fma` epilogue does not matter.

So the trigger is having several `ttg.convert_layout`s of a `64x512` tensor
from `#blocked1` (`threadsPerWarp = [32,1]`, `warpsPerCTA = [4,1]`) to
`#blocked` (`threadsPerWarp = [1,32]`, `warpsPerCTA = [1,4]`) — each a 128 KiB
shared-memory transpose — before the store. The unoptimized IR has ten scratch
users, all assigned `allocation.offset = 0`; `--triton-loop-aware-cse` folds
them to five and the problem disappears.

### Honest limit of the root cause

I have **not** identified the ptxas transformation that goes wrong, and I
cannot: ptxas is closed source. What is established is where the fault is
(between PTX and SASS), which ptxas versions and optimization levels have it,
and a 34-line PTX-producing input that triggers it. Whether NVIDIA would call
this a ptxas bug or point at something in the PTX I could not see is the one
open question.

## 3. Where it reproduces

**Any NVIDIA GPU whose cubin is produced by CUDA 12.9 ptxas at `-O2` or above.**

* The TTGIR is completely generic: `tt.load`, `tt.store`, `tt.reduce`,
  `math.fma`, `arith.*`, `ttg.convert_layout` between two `#ttg.blocked`
  layouts. No wgmma, no TMA, no mbarrier, no cluster, no warp specialization,
  no Hopper- or Blackwell-only token appears anywhere in the diff.
* It is therefore *not* an sm_90 story in the way a warp-specialization bug is.
  What I actually tested is one machine (H100, sm_90a) and one ptxas pair
  (12.9.86 vs 13.1.80). I have **not** tested another architecture, another
  CUDA minor version, or an AMD build. The claim I can support is: "on sm_90a
  with ptxas 12.9.86 at `-O2`/`-O3`, this happens"; the claim that all sm_XX are
  affected is a guess and is not made here.
* Because the trigger is a *shape* of PTX rather than anything Triton-specific,
  any Triton kernel that ends up with several large `#blocked -> #blocked`
  layout conversions before a masked store is a candidate. That is a large
  class, and it is worth a sweep.

## 4. Plain-language explanation

The kernel writes a 64 x 512 block of numbers. Each thread writes several
pieces of that block, and for every piece it works out "which row, which
column" and turns that into an address.

For one of those pieces, the low-level assembler (ptxas, NVIDIA's tool that
turns PTX into machine code) works out the row wrong: it adds 64 rows too many.
So a quarter of the block is written 64 rows below where it belongs — past the
end of the block — and the places where it should have gone are left untouched.

The numbers themselves are all correct. Only the destinations of some of them
are wrong. Turning off the assembler's optimization, or using a newer
assembler, makes it correct again.

## 5. Can an SMT solver model this?

**No — this one is out of reach of any IR-level checker, and that is the
interesting part of it.**

The two things being compared (`input.ttgir` and `output.ttgir`) *are*
semantically equivalent. A perfect TTGIR-level equivalence checker would prove
them equal, and it would be right to. The programs that actually disagree are
the two cubins, and they disagree because a closed-source tool below the IR
translated one of them wrongly.

So the failure lives strictly below the level any Triton IR checker models:

* Not a value-semantics difference in the IR — the IR pair is equivalent.
* Not reassociation, contraction, or precision — the data is exact integers and
  the written values are bit-perfect on both sides.
* Not a concurrency or memory-ordering question — racecheck is clean and the
  behaviour is deterministic across runs.
* Not whole-grid — the grid is `(1,1,1)`, one program instance.

To catch this you would need to verify PTX against SASS, i.e. a checker for
ptxas, which is a different tool with a different (and undocumented) input
language. An IR-level translation validator cannot see it, and should not
pretend to.

There is one useful corollary for the validator project: an equivalence checker
that says "these two IRs are equal" while the two binaries differ is *evidence
that the fault is below the IR*. That is a real diagnostic capability, and this
finding is a concrete test case for it — the expected verdict is EQUIVALENT,
and the disagreement on hardware is then attributable to the backend.

## 6. Confidence

**High that the generated code is invalid; medium-high that ptxas is the
component at fault.**

Solid:

* The out-of-bounds behaviour is directly measured, not inferred: the output
  buffer is pre-filled with NaN, and afterwards 3968 non-NaN values sit at
  indices 32768..62719 that the kernel's own index expression can never reach.
* There is a ground truth (integer inputs, exact accumulator) and the reference
  build disagrees with it while the candidate matches it bit for bit.
* Deterministic: the same build gives the same wrong answer every run, and the
  campaign's heap-shift control is irrelevant here because nothing is being
  read out of bounds.
* The bisect over ptxas optimization level (0,1 good; 2,3 bad) and over ptxas
  version (12.9 bad, 13.1 good) is a direct experiment on a fixed PTX file.
* racecheck / initcheck / memcheck are all clean, which removes the three
  obvious ways the PTX could have been the guilty party.

What would settle the remainder:

* Reading the SASS for the 32 bad `STG` instructions and showing the address
  register is off by `64*512*2` bytes. I counted the `STG`s (256, unchanged at
  every level) but did not diff the address arithmetic.
* Reducing the PTX further, by hand, to something small enough to hand to
  NVIDIA without Triton in the loop. The current minimal case is a 34-line
  TTGIR that expands to 8919 lines of PTX.
* Checking a third ptxas (12.8, 13.0) to bracket exactly when it was fixed.
