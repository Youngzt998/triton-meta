# HIT-0071: a layout pass reorders a `tl.sum` and turns `-inf` into `NaN`

Verdict: **CONFIRMED BUG — kept.** NaN/Inf on one side only (section 2 of the
         review criteria). The keep was borderline against criterion B1 and was
         escalated; the project owner ruled on 2026-08-18 that a licensed
         reassociation crossing an overflow boundary **is** a bug, and named this
         report as the reference case for the class. Settled — see section 6; do
         not re-litigate.
Line:    ttgir-broad
Arch:    generic (no Hopper- or Blackwell-only construct in the IR)
Culprit: `--triton-licm --tritongpu-coalesce --tritongpu-remove-layout-conversions --canonicalize`
         (class: layout). The load-bearing pass is
         `--tritongpu-remove-layout-conversions`.
Reviewed: 2026-08-17; owner ruling recorded 2026-08-18
Occurrences: 4 — this report plus three duplicates rejected under criterion B4:

  * **ttgir-broad/HIT-0057** — the same kernel with the same culprit set minus
    `--triton-licm`, showing the identical signature (`extreme` seed 777: 7
    elements differ, 1 of them a one-sided NaN/Inf). It was rejected earlier
    under B1 + B2 before I had run the NaN/Inf sweep; its quarantine entry has
    been corrected to B4 pointing here.
  * **ttgir-broad/HIT-0078** — a *different* kernel
    (`ind:triton_per_fused_native_layer_norm_native_layer_norm_backward_1_fca6977e`,
    `sum(a*((b-mean)*rstd))` over 16) but the same load-bearing pass and the
    same mechanism: the `tt.reduce` operand keeps the spelling
    `tensor<1024x16xf32, #blocked>` while `#blocked` moves from
    `threadsPerWarp = [2,16], order = [1,0]` (reduced axis across 16 lanes) to
    `threadsPerWarp = [32,1], order = [0,1]` (axis inside one lane's registers,
    `reduceLaneIdMask = 0`). Outcomes are the same overflow-crossing signature
    at values just under `FLT_MAX`: `-2.99e+38 -> -inf`, `2.99e+38 -> inf`,
    `nan -> -inf`. Fast math ruled out the same way.
  * **ttgir-broad/HIT-0082** — the same kernel as HIT-0078, reached by a
    *different pass route* (`--tritongpu-coalesce --tritongpu-remove-layout-conversions
    --tritongpu-fuse-nested-loops` from the raw root, instead of adding
    `--tritongpu-remove-layout-conversions` on top of a coalesced reference).
    Its `output.ttgir` is **byte-identical** to HIT-0078's, and the measured
    outcomes match bit for bit.

  Two things these duplicates establish. First, the class is a property of the
  pass and the reduction shape, not of one corpus entry — HIT-0078 and HIT-0082
  are on a different kernel from this report. Second, and practically: because
  several pass combinations converge on the same candidate layout, the fuzzer
  will keep re-finding this one as it explores the pass space. A duplicate here
  is expected rather than new information; the thing to check on each is only
  whether the reduce operand's `#blocked` makes the same lane-to-register move.

## What goes wrong, in one sentence

Changing the tensor layout changes the shape of the summation tree that
`tl.sum` is lowered to, and with one `-inf` summand and three summands within a
factor of 32 of `FLT_MAX`, one tree overflows an intermediate partial sum to
`+inf` before absorbing the `-inf` (giving `NaN`) while the other does not
(giving `-inf`).

---

## 1. Root cause in the source

Public Triton `3.8.0+git3277063a` (commit `3277063a6`).

### The kernel

`ind:triton_per_fused_mul_sum_0_f904167e`, a plain reduction with no division,
no `exp`, no Welford:

```python
tmp3 = tmp1 * tmp2          # tmp2 = in_ptr2[r0_1]
tmp4 = tmp0 * tmp3
tmp7 = tl.where(xmask, tl.broadcast_to(tmp4, [XBLOCK, R0_BLOCK]), 0)
tmp8 = tl.sum(tmp7, 1)[:, None]
tl.store(out_ptr0 + x0, tmp8, xmask)
```

`xnumel = 768`, `r0_numel = 32`, so each output element is a sum of 32 products.

### What the passes change

Both IRs contain the *same* `tt.reduce` on a tensor spelled the same way:

```mlir
%44 = "tt.reduce"(%43) <{axis = 1 : i32}> ({
^bb0(%arg6: f32, %arg7: f32):
  %51 = arith.addf %arg6, %arg7 : f32
  tt.reduce.return %51 : f32
}) : (tensor<512x32xf32, #blocked>) -> tensor<512xf32, #ttg.slice<{dim = 1, parent = #blocked}>>
```

but `#blocked` denotes a different layout on each side:

| | `#blocked` for the reduce operand | where the 32 reduced elements live |
|---|---|---|
| reference | `threadsPerWarp = [1, 32], warpsPerCTA = [4, 1], order = [1, 0]` | axis 1 spread across **32 lanes** of a warp |
| candidate | `threadsPerWarp = [32, 1], warpsPerCTA = [4, 1], order = [0, 1]` | axis 1 entirely **within one lane's registers** |

### Why that decides the summation order

`lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp`, `reduceWithinWarps`
(line 321) derives the cross-lane reduction mask straight from the layout:

```cpp
const auto &laneBases = layout.getBases().lookup(kLane);
unsigned reduceLaneIdMask = 0;
for (unsigned bit = 0; bit < laneBases.size(); ++bit) {
  if (laneBases[bit][op.getAxis()] != 0) {
    reduceLaneIdMask |= 1u << bit;
  }
}
if (reduceLaneIdMask == 0) {
  return {std::move(layout), std::move(accs)};   // nothing to do across lanes
}
```

and `warpReduce` (line 354) then folds with a butterfly over exactly those bits:

```cpp
for (int bit = llvm::Log2_32(warpSize) - 1; bit >= 0; --bit) {
  unsigned mask = 1u << bit;
  if ((reduceLaneIdMask & mask) == 0) continue;
  shfl[i] = targetInfo.shuffleXor(rewriter, op.getLoc(), acc[i], mask);
  accumulate(op.getLoc(), rewriter, op.getCombineOp(), acc, shfl);
}
```

So:

* **reference** — the axis occupies all five lane bits, `reduceLaneIdMask =
  0b11111`, and the sum is a 5-level balanced butterfly across lanes;
* **candidate** — the axis occupies no lane bit, `reduceLaneIdMask = 0`, the
  cross-lane phase is skipped entirely, and the 32 values are folded in
  registers instead (the loop above `reduceWithinWarps`).

Two different association orders for the same 32 fp32 values. Nothing in
`ReduceOpToLLVM.cpp` is wrong in isolation — it faithfully implements whatever
tree the layout implies. The behaviour change comes from the layout choice made
by `--tritongpu-remove-layout-conversions`.

### Why the order is observable as NaN

I extracted the 32 summands feeding the differing output element (script inline
in section 2). For `out[128]` at the `extreme` fill, seed 777:

```
summands: 0 x +inf, 1 x -inf, 0 x NaN, 3 finite with |v| > 1e37, 32 total
reference build : -inf
candidate build : nan
```

With three summands near `FLT_MAX = 3.4e38`, a partial sum that happens to add
two or three of them together overflows to `+inf`. If that overflow happens
*before* the `-inf` is folded in, the next add is `(+inf) + (-inf) = NaN`; if
the `-inf` is absorbed first, everything after it stays `-inf`. Which of those
happens is exactly what the tree shape decides.

Two neighbouring elements of the same output show the finite version of the same
effect — `out[23]` is `2.0308375e+38` against `2.0308377e+38`, an ordinary
rounding difference in the same overflow-adjacent regime.

### It is not fast math and not ptxas

* `TRITON_DEFAULT_FP_FUSION=0` (LLVM contraction off **and** ptxas
  `--fmad=false`): identical results — `extreme`/777 still `-inf -> nan`,
  `extreme`/2222 still `nan -> inf` and `-inf -> nan`. This removes all 64
  `fma.rn.f32` from the candidate and changes nothing about the outcome.
* `ptx.count(".ftz") == 0` on both sides in every configuration, so the
  flush-to-zero route to a manufactured NaN (the section-2 exception) is not
  present at all.
* The difference survives `DISABLE_PTXAS_OPT=1`, so it is not a ptxas
  mis-optimisation like ttgir-broad/HIT-0008.

## 3. Where it reproduces

**Any NVIDIA target; nothing here is Hopper-specific.**

* The two passes involved, `--tritongpu-coalesce` and
  `--tritongpu-remove-layout-conversions`, are core TritonGPU passes that every
  backend runs.
* `ReduceOpToLLVM.cpp` is the shared TritonGPU-to-LLVM reduction lowering, and
  `warpReduce` falls back to a `shuffleXor` butterfly on any target that does not
  provide `targetInfo.warpReduce`.
* The IR contains no wgmma, TMA, mbarrier, cluster or warp-specialize op; the
  `tt.reduce` is a plain `arith.addf` combine over `tensor<512x32xf32>`.
* Tested on: one H100 (sm_90a), Triton `3.8.0+git3277063a`, CUDA 12.9 ptxas.
  Not tested on another architecture or on AMD — but since the mechanism is
  "layout decides the reduction tree", any target where a layout pass can pick a
  different tree is exposed.

The **input** requirement is narrow and worth stating: the summands must contain
an infinity (or values that overflow when grouped) together with finite values
large enough that a partial sum can cross `FLT_MAX`. Ordinary data never
triggers the NaN; it only shows the last-bit version.

## 4. Plain-language explanation

The kernel adds up 32 numbers. The compiler is free to choose the order — add
them in pairs, or one after another — and it picks the order based on how it
decided to spread the data across the GPU's threads.

Normally the order only changes the last digit. Here one of the 32 numbers is
"minus infinity" and three of the others are enormous. Add the enormous ones
together first and they overflow to "plus infinity"; plus infinity added to
minus infinity is "not a number". Absorb the minus infinity early instead and
the answer stays minus infinity.

So the same kernel on the same data answers `-inf` with one layout and `NaN`
with the other, purely because the addition order moved.

## 5. Can an SMT solver model this?

**Yes, and it is precisely the case that separates this project's two FP axiom
profiles.**

`tv/CLAUDE.md` records the locked decision to support two profiles: *exact
bit-to-bit* and *reassoc-allowed*. This finding is the discriminator between
them:

* Under **reassoc-allowed**, the checker is told that `+` may be reassociated,
  so the two programs are equivalent by construction and the verdict is
  EQUIVALENT — correctly, on that reading of the semantics.
* Under **exact bit-to-bit**, they are not equivalent, and the counterexample is
  exactly what the hardware shows.

To produce the counterexample the model needs real IEEE-754 semantics, not the
current abstract mode. `tv/semantics/AbstractFp.*` today makes each FP value an
opaque `BitVec` with five axioms — including *commutativity* of `add`, but
deliberately no associativity. Commutativity alone does not distinguish these
two trees, and an uninterpreted `add` has no notion of overflow or of `inf`, so
abstract mode would report the two sides equal and miss this entirely.

What a bit-exact model needs here is modest:

* `fp.add` over `Float32` with the default rounding mode, including `inf` and
  `NaN` — SMT-LIB's `FloatingPoint` theory has this directly.
* One output element, 32 free `Float32` inputs, and the two concrete association
  trees as two terms. Asking whether they can differ is a 32-add formula; a
  bit-blasting solver finds the SAT witness quickly (finding a counterexample is
  much easier than proving UNSAT, which matches this project's measured
  experience that SAT cases are the hard ones only when the tile is wide).
* No concurrency model, no whole-grid modelling, no memory ordering. It is a
  deterministic, single-program-instance value question, and the grid here is
  only `(2,1,1)`.

The one thing an IR-level checker must additionally know is **which tree each
layout implies** — the mapping from `#ttg.blocked` to `reduceLaneIdMask` and the
register fold. That is squarely the job of the planned `tile-gpu-smt` layer
(layouts and `convert_layout`); without it, a TTGIR-level checker sees two
identical-looking `tt.reduce` ops on `tensor<512x32xf32, #blocked>` and cannot
tell them apart, because the difference is entirely inside what `#blocked`
means.

So: **capturable in principle, cheaply, but only by a checker that models both
bit-exact FP and the layout-to-reduction-tree mapping.** It is a good end-to-end
test case for `tile-gpu-smt` precisely because it needs both halves.

## 6. Confidence

**High that the behaviour is real and fully explained. Genuinely uncertain
whether it should count as a bug — and that is a criteria question, not a
measurement question.**

What is solid:

* The layout change is visible in the checked-in IR pair, and the IR pair
  regenerates exactly from `triton-opt`.
* The link from layout to summation tree is two quoted functions in
  `ReduceOpToLLVM.cpp` (`reduceWithinWarps` line 321, `warpReduce` line 354),
  where `reduceLaneIdMask` is computed from the layout's lane bases.
* The differing element's 32 summands were extracted and counted: one `-inf`,
  three finite above `1e37`. That is a sufficient condition for the two trees to
  disagree, and the neighbouring elements show the finite version of the same
  effect.
* Fast math is ruled out by direct re-run, not by argument, and no `.ftz`
  instruction exists in either PTX. ptxas is ruled out by `-O0`.
* Both builds are self-deterministic; the kernel has no scatter store, no
  atomics, and its single store address does not touch the loop's block
  arguments.

**The honest counter-argument, which a reader should weigh:**

By criterion B1 this is a rejection. The culprit is a layout pass, the report's
own label is `layout-reorders-reduction`, and reordering an fp32 reduction is
that pass's licence. B2's consistency test passes perfectly — every input where
the sum is exact gives bit-identical output. On that reading the NaN is not a
second phenomenon at all: it is the *same* reassociation, observed on inputs
where the reassociation crosses an overflow boundary instead of a rounding one.
I have rejected ten other `layout-reorders-reduction` findings in this campaign
on exactly that basis; the only thing different here is that the fuzzer's
`extreme` distribution happened to supply an infinity.

I kept it because section 2 of the review criteria says a one-sided NaN/Inf is a
keep and lists exactly one exception — fast math — which I tested and ruled out.
Overriding an explicit, owner-controlled rule on my own judgement is not mine to
do, and a wrong rejection is silent and permanent while a wrong keep costs one
file. I flagged the tension and escalated it rather than deciding it.

### Resolved: owner ruling, 2026-08-18

**The question above is settled and must not be re-litigated.** I proposed
adding "reassociation made visible by overflow" as a second exception, so that
this report and HIT-0057 would become B1 rejections. That proposal was
**considered and rejected** by the project owner. `REVIEW-CRITERIA.md` (sha1
`e6c6959383bad0fb`) now states the rule explicitly and names this report as the
reference case for the class:

> **a licensed reassociation that crosses an overflow boundary still counts —
> keep it.** If a reduction reorder makes an intermediate partial sum overflow to
> `±inf` so that a later `(+inf) + (−inf)` yields `NaN`, that is a **bug**, even
> though the reorder itself is licensed and B2's exact-integer test passes.
> [...] turning a finite or `±inf` result into `NaN` is a change of kind, not of
> precision, and `NaN` poisons everything downstream.

So the counter-argument above is recorded for context, not as an open question.
The line it draws is the one that matters going forward: **the NaN/Inf outcome is
the discriminator.** The same layout-driven reduce reordering *without* a NaN/Inf
outcome remains an ordinary B1 + B2 rejection — which is how ttgir-broad
HIT-0069, 0070, 0072, 0073, 0074 and 0075 were disposed of, all in this same
family and all measured to have zero one-sided NaN/Inf.

**Status of the related reports:** this one stands as the kept representative;
ttgir-broad/HIT-0057 (same kernel, same mechanism, same signature) stays rejected
as a B4 duplicate of this report.

A remaining question of fact, which the ruling does not depend on: whether Triton
intends `tl.sum` to have a layout-independent result. Nothing documents an
ordering guarantee, which is evidence that it does not — but under the ruling
that does not change the disposition, because the objection is to the NaN, not to
the reordering.
