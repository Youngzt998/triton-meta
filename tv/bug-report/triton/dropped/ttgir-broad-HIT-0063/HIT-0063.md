# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the text the fuzzing line
wrote; **none of it has been corrected**, including any statement this banner
contradicts.

**Criterion: B1 + B2** -- a licensed reduction reorder. The culprit is a layout
pass, and reshaping the `tt.reduce` tree is that pass's own licence.

**The measurement that settled it:** the automatic exactness control was
**invalid on this kernel**, so a valid one had to be built by hand and then run.
The body is `sum(exp(x - m))` over 100 elements with `libdevice.exp` inside the
loop, so whole-number inputs do **not** give an exact accumulator -- `exp` of an
integer is irrational. The valid exact control here is *all inputs equal*: then
`tmp0 - tmp1 = 0` and `exp(0) = 1.0` exactly, every partial sum is a small
integer, and evaluation order cannot matter. Under that control -- the all-equal
`constint` fill at both seeds, plus `zeros` and `onesish` -- the two arms are
**bit-identical**, while every fill that leaves the summands irrational
(`randn`, `randn2`, `uniform`, `intval`, `smallint`, the `3+a`/`3-a` pair)
differs. Magnitude 2 ulp throughout.

**This report is here because its own automatic label was wrong.** It is labelled
`differs-with-small-integer-inputs (... so reassociation of an fp32 sum does not
explain it)`, which reads as a keep signal, and reassociation explains it
perfectly well. The generalised trap: **any transcendental in the chain
invalidates the plain integer control** -- the same trap as the mean / variance /
norm kernels, one step further out.

**The licence is visible in the IR:** the diff shows `#blocked` order flipping
`[1, 0]` -> `[0, 1]`, which reshapes the `tt.reduce` tree.

**The alternatives were ruled out, not assumed.** The difference survives ptxas
`-O0`, so it is IR-level reordering and not fma contraction. A1 clear (the
report's own repro reproduces), A3 clear (both builds self-deterministic), A4
clear by a loop-aware backward walk from store `%29` (13 values; the `scf.for`
`iter_args` is the fp accumulator, not an address, and no load is reached),
A5 clear.

## Numerics-change context (a label, not a verdict)

The culprit pass is classified `layout` by `fz/passes.py`. Reduction or dot
present in the reference IR: `True`. A `numerics` class pass
(`accelerate-matmul`, `F32DotTC`, `triton-combine`, `optimize-thread-locality`)
is *expected* to change FP results, and a layout-family pass on a kernel with a
reduction can legitimately change the summation order. Neither is a reason to
drop the finding; both are recorded so a reviewer can filter with all results in
hand. The small-whole-number control above is the cheap discriminator: if the
difference persists there, reassociation of an fp32 sum does not explain it.
