# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the text the fuzzing line
wrote; **none of it has been corrected**, including any statement this banner
contradicts.

**Criterion: A3** -- the kernel is not deterministic under a **single** binary.
That is undefined behaviour, so there is nothing to compare between two binaries.

**The measurement that settled it:** the **reference build was compared against
itself**, and it disagreed with itself **more often than it disagreed with the
candidate**. Over 20 reps: reference-vs-reference **6 of 20**,
reference-vs-candidate **3 of 20**, candidate-vs-candidate **0 of 20**. A binary
that is less consistent with itself than with the other binary cannot support a
finding about the other binary.

**The mechanism the difference was made of:** the whole reported difference is
1-2 elements of 1048576 that are `+0.0` on one side and `-0.0` on the other
(`max_abs_diff` exactly 0.0), and **the element moves between reps** (index
101420, then 641289). A fixed miscompile does not move.

**The method note that matters more than the verdict.** The determinism check
only sees this if the input buffers from earlier reps are **kept alive**, so that
addresses drift the way `harness/repro.py` actually makes them drift. A
determinism check that frees each rep's buffers before the next shows **0 of 39**
here and misses the bug completely. The report's own `reproduced: 0/3`,
`heap-shift-survives: 2/3` and `suspect-unstable: true` were all pointing at it.

**Independently B2 also fires:** the integer-input control is equal, and its
exactness argument holds (one dot plus a cast, `|acc| <= 8*8*K = 65536 < 2^24`),
so even a stable version of this difference would have been a licensed one.

This is the **fourth** instance of the same pattern on warp-specialized `mm_tma`,
after `ttgir-deep/HIT-0015`, `HIT-0018` and `HIT-0019`.

## Why this is NOT an expected numerics change
*(evidence, not a verdict -- the call is the reviewer's)*

Groups of the culprit passes: ['layout', 'sched'].
No culprit pass is in the numerics-changing group (accelerate-matmul, f32-dot-tc, optimize-thread-locality, optimize-accumulator-init, tmem-load-reduce).  The remaining passes only move data, change layouts, schedule, or lower to hardware.
A layout-family pass is in the culprit set and the kernel contains tt.dot / tt.reduce, so the layout can legitimately change the summation tree.

### Integer-input control

With inputs that are integers in `[-8, 8]`, every fp32 accumulator in family
`mm_tma` stays below `2^24 = 16777216` (bound here: `65536`,
exactness `yes`), so every accumulator add is exact and the
summation ORDER cannot change the result. the whole kernel is one dot plus a cast; with inputs in [-8, 8] the fp32 accumulator is an integer with |acc| <= 8*8*K

Result of re-running this comparison on integer-valued inputs:
**`equal`**.

The control holds but the integer-valued inputs do NOT reproduce the difference, so this one is only visible on inputs where reassociation is also possible.

### Allocator perturbation (heap shift)

The comparison was repeated 3 times with the GPU allocator perturbed, so the
buffers land at different addresses with identical values. The difference
survived **2/3** of those runs. A difference caused
by an out-of-bounds or uninitialised read usually moves or disappears; a value
difference does not.
