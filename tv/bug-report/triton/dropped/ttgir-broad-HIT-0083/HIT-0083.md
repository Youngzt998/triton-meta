# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the text the fuzzing line
wrote; **none of it has been corrected**, including any statement this banner
contradicts.

**Criterion: B1 + B2** -- dot+add accumulator fusion, the fourth licensed
mechanism seen on this side. `--triton-combine` fires `CombineDotAddPattern`
(`lib/Dialect/Triton/Transforms/Combine.cpp:250` in the checkout under test,
`/home/youngzt/fuzz/triton-public` @ `3277063a6`; the `CombineDotAddFPattern`
alias is at `:291` and it is registered at `:305`). REVIEW-CRITERIA B1 names
"fuse into an accumulator (e.g. dot+add)" verbatim.

**The measurement that settled it:** the rewrite is visible in the 17-line diff,
and the exactness control passes on it. The diff is

```
-%78 = tt.dot %76, %77, %cst_1, inputPrecision = tf32
-%79 = arith.addf %arg15, %78
+%78 = tt.dot %76, %77, %arg15, inputPrecision = tf32
```

plus SSA renumbering of the pointer-advance ops -- the loop-carried accumulator
moves into the dot's `C` operand. Then B2: only `randn` / `randn2` / `uniform`
differ (59058-59414 of 3145728), while **all six exact-integer fills plus
`denorm`, `extreme` and `extreme2` are bit-identical**.

**Three alternatives were ruled out by measurement, not by shape.**

1. *Not a reduction reorder.* The kernel contains **no `tt.reduce` at all** and
   `#blocked` is unchanged between the two IRs, so the layout-family check does
   not apply.
2. *Not contraction.* The difference survives ptxas `-O0` with `fma.rn.f32`
   unchanged at **1024 vs 1024**; the only PTX change is the trailing `add.f32`
   count going **32 -> 0**, which is the fused add disappearing.
3. *Not a precision change.* `inputPrecision = tf32` is identical on both sides
   -- the rewrite only moves the `C` operand.

**The keep/reject line inside this one mechanism.** This dot lands on a
`#blocked` FMA-lowered dot, the same code path as the **kept**
`ttir-broad/HIT-0007`, so the NaN/Inf sweep was run rather than assumed:
**zero one-sided NaN/Inf across all 24 fill/seed combinations**, with `extreme`
and `extreme2` both bit-identical. REVIEW-CRITERIA §2's NaN/Inf bullet therefore
never engages, and this is an ordinary B1 + B2 rejection with no B4 relationship
to the kept report. Ninth report of this pattern: four with a NaN/Inf outcome
(one kept, three B4), five without (B1 + B2).

## Numerics-change context (a label, not a verdict)

The culprit pass is classified `numerics` by `fz/passes.py`. Reduction or dot
present in the reference IR: `True`. A `numerics` class pass
(`accelerate-matmul`, `F32DotTC`, `triton-combine`, `optimize-thread-locality`)
is *expected* to change FP results, and a layout-family pass on a kernel with a
reduction can legitimately change the summation order. Neither is a reason to
drop the finding; both are recorded so a reviewer can filter with all results in
hand. The small-whole-number control above is the cheap discriminator: if the
difference persists there, reassociation of an fp32 sum does not explain it.
