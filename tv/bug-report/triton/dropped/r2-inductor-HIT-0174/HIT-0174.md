# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the text the fuzzing line
wrote; **none of it has been corrected**, including any statement this banner
contradicts.

**Criterion: A4** -- a write-write race. Two lanes of one `tl.store` write
**different** values to the same address, so the kernel is undefined behaviour
and the comparison between the two builds carries no information.

**The measurement that settled it:** the store index map was evaluated by hand
over the whole launch domain. Both stores use `r0_1 + ks0*x0`, and the draw is
`ks0 = 63` with `r0_numel = 128` -- **the row stride is half the row length, so
consecutive rows overlap**. Result: **1073 distinct addresses written by 2048
lanes, 947 of them by two or three lanes each**, and the values genuinely differ
per row because each row is its own `tl.associative_scan`. The same buffer is
also the input (`in_out_ptr0` is loaded at the same overlapping addresses), so it
is a read-write race as well.

**This is the most important example in this directory, because it defeated
every automatic control.** It **survived the all-inputs-equal exactness control**
(16 value differences, `max_abs` 63.0, at iteration 3) and it **survived
`DISABLE_PTXAS_OPT=1`**. On the printed labels it reads as a keep: a difference
that no exactness control removes and that is not made by the assembler is
exactly the fingerprint of the two ptxas classes the review *did* keep. Nothing
but working out the store index by hand separates it from them.

**Why the automatic screen missed it.** `fz/storeidx.py` returned `unknown`
("nested for block") for this report, so the harness never applied the
injectivity test. A screen that answers `unknown` is not a pass -- it is a
request for manual work, and this report is what happens when that request is
skipped.

**Note that the collision is manufactured by the harness, not by the kernel.**
`ks0` is a scalar the shape draw patches. The kernel as its author wrote it is
fine; the draw gave it a row stride that makes its own rows overlap. That is the
single largest source of false findings on this side of the campaign -- see the
README.

## Numerics-change context (a label, not a verdict)

The culprit pass is classified `bit` by `fz/passes.py`. Reduction or dot
present in the reference IR: `True`. A `numerics` class pass
(`accelerate-matmul`, `F32DotTC`, `triton-combine`, `optimize-thread-locality`)
is *expected* to change FP results, and a layout-family pass on a kernel with a
reduction can legitimately change the summation order. Neither is a reason to
drop the finding; both are recorded so a reviewer can filter with all results in
hand. The small-whole-number control above is the cheap discriminator: if the
difference persists there, reassociation of an fp32 sum does not explain it.
