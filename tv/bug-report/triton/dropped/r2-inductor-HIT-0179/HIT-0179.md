# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the text the fuzzing line
wrote; **none of it has been corrected**, including any statement this banner
contradicts.

**Criterion: B3** -- floating-point contraction (`mul + add -> fma`). That is a
licence held by the whole compiler, not by any one pass, so *any* change that
merely reshapes the IR can trigger it.

**The measurement that settled it:** the draw has `enable_fp_fusion = True`, and
with the config overridden to `enable_fp_fusion = False` the two arms are
**equal**. With fusion off, Triton puts `--fmad=false` on the ptxas command line
and the licence is withdrawn; the difference goes with it.

**Why this is the cleanest B3 in the set: the competing licence is not even
available.** The kernel has **no reduction at all** -- `reduce/scan = False`, and
the layout screen finds **zero** `tt.reduce` ops. So there is no reduction tree
to reorder and criterion B1 cannot apply. Contraction is the only licensed
mechanism left, and turning it off removes the difference. Both the exact-integer
and the all-inputs-equal controls also go equal, independently.

**The order of checks this report pins down.** `--triton-loop-aware-cse` is a
`bit`-class pass with no numeric licence of its own, and the difference is 1
element of 229376 at 1 ulp. On the labels it looks like a pass with no licence
producing a difference, which REVIEW-CRITERIA §2 lists as a **keep**. It is not:
the pass reshaped the IR and the *compiler's* contraction licence did the rest.
**Check `enable_fp_fusion` before concluding a pass has no licence.**

## Numerics-change context (a label, not a verdict)

The culprit pass is classified `bit` by `fz/passes.py`. Reduction or dot
present in the reference IR: `False`. A `numerics` class pass
(`accelerate-matmul`, `F32DotTC`, `triton-combine`, `optimize-thread-locality`)
is *expected* to change FP results, and a layout-family pass on a kernel with a
reduction can legitimately change the summation order. Neither is a reason to
drop the finding; both are recorded so a reviewer can filter with all results in
hand. The small-whole-number control above is the cheap discriminator: if the
difference persists there, reassociation of an fp32 sum does not explain it.
