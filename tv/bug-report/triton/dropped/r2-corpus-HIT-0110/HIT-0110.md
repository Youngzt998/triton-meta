# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the text the fuzzing line
wrote; **none of it has been corrected**, including any statement this banner
contradicts.

**Criterion: A2** -- an out-of-bounds store, made by the harness's shape draw,
not by the compiler.

**The measurement that settled it:** the per-arm write map was measured, not
inferred. The draw patches the scalar `N` from 32 to 48 while `ptr_o` is still
the `(32, 16, 256, 256)` tensor the corpus captured, and the kernel's final
`tl.store` is **unmasked**: `offset_o = ((n*C + c)*OH + oh)*OW + ow` with `n`
running to `N-1 = 47` reaches element **50,272,255** while the slot holds
**33,554,432** fp16 elements -- 16,717,824 past the end. Both arms were then
observed to write **1,021,643 fp16 words into slot 1**, which is `ptr_i`, **the
kernel's own input**, at indices 4..16,717,826 -- exactly the predicted overflow.

**The overflow fully accounts for the recorded difference.** The report's
`ref_bits 0x7fff` (a NaN) against `cand_bits 0xb392` (finite) is one arm reading
a byte that the other arm's store had already overwritten. The kernel destroys
the data it is still loading, across program instances, which is undefined.

**A2 and not A3:** both arms are self-deterministic 6 of 6. The kernel is not
flaky; it is reading memory it already clobbered in a fixed pattern.

**Why the automatic gate missed it, which is the real lesson.** A2's stated test
is the 28 KiB heap shift, and the heap shift **cannot see this**: it moves every
slot together, so a store that lands inside a *neighbouring slot of the same
pool* still lands there after the shift. A label is evidence, never a verdict.

**One more sign the draw is off the kernel's contract**, recorded because it
would have been the next thing to chase: with `grid=(6,24,1)` and
`ow = (pid_x*64 + arange(64)) % 256`, program ids 4 and 5 recompute the same `ow`
as 0 and 1, so pairs of programs write the same addresses. Benign here -- the
stored value depends only on `ow` -- but it is a second symptom of the same bad
draw.

heap shift, the determinism gate, the measurements, and `fz.repro`) replays
**this** draw, not draw 0.

## Numerics-change context (a label, not a verdict)

The culprit pass is classified `bit` by `fz/passes.py`. Reduction or dot
present in the reference IR: `False`. A `numerics` class pass
(`accelerate-matmul`, `F32DotTC`, `triton-combine`, `optimize-thread-locality`)
is *expected* to change FP results, and a layout-family pass on a kernel with a
reduction can legitimately change the summation order. Neither is a reason to
drop the finding; both are recorded so a reviewer can filter with all results in
hand. The small-whole-number control above is the cheap discriminator: if the
difference persists there, reassociation of an fp32 sum does not explain it.
