# HIT-0001: `tl.cumsum` drops the carry between CTAs, so with `num_ctas > 1` a prefix sum silently restarts at every CTA boundary

Verdict: CONFIRMED — kept
Oracle:  O1 (interpreter versus compiled, **default pipeline**)
Arch:    sm_90 and newer (`num_ctas > 1` is rejected below sm_90)
Line:    r2-oracle (R3)
Culprit: `ConvertTritonGPUToLLVM` — the `tt.scan` lowering, plus the two
         cross-CTA helper lists that do not mention `ScanOp`
Occurrences: 6 in this line — the original draw, 2 further draws of
         `moe_align_block_size_stage2_vec`, 2 draws of
         `moe_align_block_size_stage3` (recorded as HIT-0003, rejected as a B4
         duplicate), and 1 more; **every one of them had `num_ctas` 2 or 4**.

Summary: `tl.cumsum` on a tensor whose only axis is spread over the CTAs of a
Hopper cluster produces a **per-CTA** prefix sum. Each CTA scans its own slice
and never adds the total of the CTAs before it, so the running sum restarts
from zero at every CTA boundary. There is no error and no warning. The same
tensor under `tl.sum` is correct, because reduce has a cross-CTA path and scan
does not. On tiles of 256 elements or more the same gap turns into a compiler
assertion instead of a wrong number.

This is a bug in the **stock pipeline**: no pass was toggled, nothing unusual
was asked for beyond `num_ctas`, which is an ordinary `@triton.jit` /
`triton.Config` knob.

---

## 1. Root cause in the source

Checkout: `/home/youngzt/fuzz/triton-public`, commit `3277063a6` (public
triton-lang, version `3.8.0+git3277063a`).

When `num_ctas > 1`, a tensor's layout carries a **CGA layout** — the part of
the layout that says which CTA of the cluster holds which elements. For a 1-D
tensor there is only one dimension to split, so that dimension gets split, and
for a `tt.scan` that dimension *is* the scan axis:

```mlir
#blocked = #ttg.blocked<{sizePerThread = [1], threadsPerWarp = [32],
                         warpsPerCTA = [4], order = [0],
                         CGALayout = [[1], [2]]}>     // <- split 4 ways
```

Reduce and scan then go different ways.

**Reduce knows about this and handles it.**

* `lib/Analysis/Utility.cpp:82-87` — `ReduceOpHelper::isReduceWithinCTA()`
  returns `getCTASplitNum(srcEncoding)[axis] == 1`, i.e. it answers "is the
  reduce axis inside one CTA?".
* `lib/Analysis/Allocation.cpp:157-158` — `hasCrossCTAScratch()` calls it and
  gives the reduce distributed shared-memory scratch when the answer is no.
* `lib/Analysis/Utility.cpp:1323-1324` — `needsClusterBarrier()` calls it and
  inserts a cluster barrier.

**Scan has none of the three, and nothing rejects the split either.**

* `lib/Analysis/Utility.cpp:496-502` — `ScanLoweringHelper::isSupported()` is
  the only gate on the scan lowering, and its whole body is:

  ```cpp
  bool ScanLoweringHelper::isSupported() {
    // TODO: Support the following cases:
    // 1. Scan on non-blocking encodings
    if (!isa<BlockedEncodingAttr>(legacyEncoding))
      return false;
    return true;
  }
  ```

  It never looks at `getCTASplitNum(...)[axis]`. There is no
  `isScanWithinCTA()` anywhere in the tree.
* `lib/Analysis/Allocation.cpp:149-172` — `hasCrossCTAScratch()` lists
  `ConvertLayoutOp`, `ReduceOp`, `AtomicPollOp` and the atomics. **No
  `ScanOp`.** So the scan gets ordinary CTA-local shared memory
  (`ScanLoweringHelper::getScratchSizeInElems()`, `Utility.cpp:504-511`, sizes
  it from `product(getEncoding().getWarpsPerCTA())` — warps in *one* CTA, with
  no CTA term at all).
* `lib/Analysis/Utility.cpp:1319-1326` — `needsClusterBarrier()` lists the same
  set. **No `ScanOp`.** So no cluster barrier is emitted either.
* `lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp:278-282` — `PlanCTA`, the
  pass that picks the CGA layout (in the default pipeline at
  `third_party/nvidia/backend/compiler.py:304`, skipped when `num_ctas == 1`),
  has a `processReduce` that walks `triton::ReduceOp`. There is **no
  `processScan`** and no walk over `triton::ScanOp`, so a scan never gets a say
  in how its axis is split.
* `lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp:459-570` — `emitFastScan`
  therefore proceeds, and every step it takes is inside one CTA: thread-local
  (`scanThreadContiguousElements`), then warp shuffles (`warpScan`), then
  CTA-local shared memory (`AddPartialReduce`, which uses
  `helper.getNonAxisNumThreadsPerCTA()` at lines 103 and 142 and
  `srcEncoding.getWarpsPerCTA()` at line 396). Nothing in the function ever
  reads another CTA's data.

**The specific step that is wrong:** the lowering treats the value it has
computed for its own CTA's slice as the final answer for those elements. The
correct lowering must, after the intra-CTA scan, add the sum of all slices held
by lower-numbered CTAs — through distributed shared memory and a cluster
barrier, exactly as the reduce path does. That step does not exist, so the
carry is silently zero.

Proof that no cross-CTA traffic is emitted, from the generated PTX for the same
8-element tensor at `num_ctas=4`:

| kernel | PTX lines with `mapa` / `::cluster` (distributed shared memory) |
|---|---|
| `tl.sum` (`tt.reduce`) | 2 |
| `tl.cumsum` (`tt.scan`) | **0** |

**Second face of the same gap.** Because the scratch size is computed with no
CTA term, a bigger tile makes the element count disagree with what
`AddPartialReduce` expects, and the compiler dies on
`ScanOpToLLVM.cpp:157-159`:

```
numScanBlocks * numParallelBlocks * parallelElementsPerThread *
    scanElementsPerThreads == srcValues.size()
```

That assertion is already recorded, without a root cause, by the compile-only
line as `triton/r2-compile/HIT-0017` (25 occurrences, sm_90 only,
`ScanOpToLLVM.cpp:159`) and `triton/r2-compile/HIT-0016` (12 occurrences,
`ScanOpToLLVM.cpp:265`), on `cumsum` / `cummax` / `cumprod` / `logcumsumexp`
kernels. I believe those are the loud form of this same defect. I did **not**
reject this report as a B4 duplicate of them: they report a crash, this reports
silently wrong data, and REVIEW-CRITERIA §2 treats a crash as a different shape
of finding. Whoever reviews r2-compile HIT-0016/0017 should read this section.

No RNG seed is needed: an all-ones input is enough. Step 4 seeds

value class the fuzzer's `exactint` fill uses for integer buffers
(`fz/modes.py:30`, `fz/argsgen.py:293-302`).

**Which side is wrong: the compiler.** Three independent references agree with
each other and disagree with the compiled kernel — `torch.cumsum`, Triton's own
interpreter, and Triton itself at `num_ctas=1`:

```bash

TRITON_INTERPRET=1 python -c "..."   # step 1 of repro.py
#   interpreter num_ctas=4 : [1, 2, 3, 4, 5, 6, 7, 8]
#   compiled    num_ctas=4 : [1, 2, 1, 2, 1, 2, 1, 2]
```

**The fuzzer's original draw.** Corpus `bench`, kernel
`bch:moe_align_block_size_stage2_vec_88dc7283`, grid `(6,1,1)`, fill `exactint`,
seed `674081`, config `num_warps=8 num_stages=8 num_ctas=4 maxnreg=None
default_dot_input_precision=ieee sanitize_overflow=True enable_fp_fusion=False`,
36 of the 48 written `int32` cells differed, first at index 24 (interpreter 16,
compiled 7). `python -m fz.repro --hit HIT-0001` reproduced it 1/1 while I was
reviewing, before the fuzzer's own artifact directory was cleared at 18:06; the
self-contained `repro.py` above replaces it and does not depend on the fuzzer.

**Why exact bit equality was a fair demand here — checked independently.** The
kernel is `*i32` end to end: `tt.make_range`, `arith.addi`, `arith.muli`,
`tt.load`, `tt.scan` with an `arith.addi` combine, `tt.store`. There is no
float value anywhere, no divide, no transcendental, no reduced-precision
accumulator between input and output. Two's-complement add and multiply are
exact and associative, so evaluation order cannot change a single bit, and the
`< 2^24` accumulator argument is not even needed. I confirmed this on the TTGIR
(`HIT-0001/scan_num_ctas4.ttgir`) rather than trusting the fuzzer's label. The
report's own justification said "integer kernel", which is right for this
kernel — but note that the same analysis wrote "exactness kind: integer,
distinct floating point formats: []" for the fp16 kernel in HIT-0004, so the
label is not by itself trustworthy and has to be re-derived per report.

## 3. Where it reproduces

**sm_90 (Hopper) and newer, only.** `num_ctas > 1` is the sole trigger, and
Triton refuses it below sm_90 — compiling for `cuda:80` or `cuda:89` raises
`ValueError: num_ctas > 1 requires NVIDIA SM90+ (Hopper)`. Compiling for
`cuda:100` (Blackwell) is accepted; I could not run it, since this box is 8×
H100 (PLAN.md §11 also warns that the local ptxas is version-skewed for sm_100).

What this rests on: the missing code is **not** Hopper-specific. It is in
`lib/Analysis/` and `lib/Conversion/TritonGPUToLLVM/`, which are shared by every
NVIDIA target, and the failing construct is a plain `tt.scan` on a
`#ttg.blocked` layout — no wgmma, no TMA, no mbarrier, no warp specialization
appears anywhere in the failing IR. The arch limit comes only from the fact
that a CGA layout that splits a tensor across CTAs cannot exist without hardware
clusters. So: any NVIDIA target with thread-block clusters, which today means
sm_90 and sm_100+.

Independent of `num_warps` (wrong at 1, 4 and 8 alike) and independent of
`num_stages`, `maxnreg`, `launch_cooperative_grid` and `sanitize_overflow` —
all 6 recorded occurrences differ in those and agree in `num_ctas > 1`.

## 4. In plain words

On an H100 you can ask Triton to run one program as a *cluster* of several
thread blocks that cooperate (`num_ctas=4`). Triton then cuts the tile into
pieces and gives one piece to each block.

`tl.cumsum` is a running total: element *i* of the answer is the sum of
everything up to *i*. Each block correctly totals up its own piece — but nobody
tells it what the blocks before it added up to, so it starts counting from zero
again. Ask for the running total of eight ones and you get `1 2 1 2 1 2 1 2`
instead of `1 2 3 4 5 6 7 8`.

`tl.sum`, the plain total, was written with clusters in mind: the blocks swap
their partial totals and wait for each other. Nobody did that work for
`tl.cumsum`, and nobody added a check to say "I cannot do this" — so instead of
an error you get a wrong number.

## 5. Can an SMT solver model this?

**Verdict: `SMT-decidable in principle`, but only for a checker that looks at
the TTGIR → LLVM step and models the CTA dimension of a layout.**

1. **Root cause in semantic terms.** The construct is `tt.scan` (axis 0, combine
   region `arith.addi`) on `tensor<8xi32, #ttg.blocked<..., CGALayout =
   [[1],[2]]>>`. The semantic error: the lowering realises the scan as a prefix
   sum *within each CTA's slice of the layout* instead of over the whole tensor
   axis, i.e. it drops the term `sum of all elements held by CTAs with a lower
   block index`.

2. **Is the difference a pure input→output function difference?** Yes.
   The wrong output follows deterministically from the input of a single
   program instance — I got byte-identical wrong answers at `num_warps` 1, 4 and
   8 and across repeated runs. This is *not* a race and *not* a scheduling
   hazard. It only looks concurrency-flavoured because the missing fix would be
   a barrier; the defect itself is a missing arithmetic term.

3. **Fundamental verdict: `SMT-decidable in principle`.** With one sharp caveat
   that matters more than the verdict: **the TTIR and the TTGIR are both
   correct**. `tt.scan` in the TTGIR still means "prefix sum over axis 0"; the
   CGA layout is a legal way to place the data. So a TTIR ↔ TTGIR equivalence
   check — the boundary a tile-level validator is most likely to attack first —
   would prove these equivalent and would be *right* to. The wrong step is the
   TTGIR → LLVM lowering. A checker only catches this if its bottom end is
   below TTGIR.

4. **Minimum semantic vocabulary required.**
   - A layout as an index map from `(block, warp, lane, register)` to a tensor
     index — with **`block` (the CTA within the cluster) as a real dimension**,
     not folded away. A model that treats a layout as a within-CTA map only, and
     assumes one CTA per program instance, is blind here by construction.
   - `tt.scan` as a prefix reduction over one tensor axis with an associative
     combine region, defined over the *whole* axis.
   - Two address spaces at the LLVM end: CTA-local shared memory, and cluster
     distributed shared memory (`mapa`), with the second reachable only after a
     cluster barrier. That is what makes "the lowering never reads another CTA's
     data" a statement the model can express and therefore refute.
   - A program instance that spans several CTAs. Note this is *not* the same as
     "whole-grid modelling": one cluster is still one program instance and the
     grid stays symbolic.

5. **Would the abstraction hide it?** No, and not even a weak one would. The
   values are `i32` and the combine is `arith.addi`, so no FP axiom profile is
   involved at all. Even for a float `tl.cumsum` both profiles would catch it,
   including **reassoc-allowed**: the wrong answer is missing whole *terms*, not
   the same terms added in a different order, so it is not inside the licence
   that a reassociation profile grants. This is a clean case where the abstract
   (uninterpreted-function) FP encoding loses nothing — the counterexample
   survives under any FP profile.

6. **Inherent cost.** Tiny. The smallest failing instance is 8 `i32` values on
   4 CTAs: 8 symbolic 32-bit words, one `addi` chain of length 8 per side. A
   SAT (find-the-difference) query at that size is trivial, which is the good
   case — the general rule that non-equivalence is expensive bites on large
   tiles, and here the bug is fully visible at the smallest tile that can be
   split at all.

## 6. Confidence

**Very high that this is a genuine compiler bug.** The evidence is not one
measurement but a closed chain: (a) the compiled kernel contradicts three
independent references — `torch.cumsum`, Triton's own interpreter, and Triton
itself at `num_ctas=1`; (b) the wrong answer has exactly the shape the source
predicts, restarting with period `N / num_ctas`; (c) the source shows the three
places where `ScanOp` is missing from a list that `ReduceOp` is in; (d) the PTX
contains zero distributed-shared-memory instructions for the scan and two for
the reduce on the same tensor; (e) the same gap crashes the compiler on larger
tiles, and that crash is already logged 37 times by an unrelated line.

**The remaining doubt is not "is it wrong" but "is it in scope".** Nobody has
written down that `tl.cumsum` supports `num_ctas > 1`. `PlanCTA` has no lit
tests at all (r2-compile's rollup makes the same point about four other defects
in that pass), so it is possible the maintainers consider clusters plus scan an
untested corner rather than a promise. That does not change the report: Triton
accepts the configuration, compiles it without a word, and returns wrong data.
Silence is the bug.

What would settle it: an upstream issue asking whether cross-CTA `tt.scan` is
meant to work. Either answer produces a fix — implement the cross-CTA carry, or
make `ScanLoweringHelper::isSupported()` return false when
`getCTASplitNum(encoding)[axis] != 1` so the user gets a clear error instead of
a wrong number. The second is a two-line change and would also remove the
`ScanOpToLLVM.cpp:159` assertion class.
