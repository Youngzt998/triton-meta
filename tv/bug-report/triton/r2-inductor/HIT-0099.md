# HIT-0099: a `tt.reduce` result is not the same in every lane, so removing a `convert_layout` changes it from a number to NaN

Verdict: **CONFIRMED BUG — kept.** An integer output differs (`0` vs
         `-2147483648`), and the float behind it is **NaN on one side and an
         ordinary finite number on the other** — REVIEW-CRITERIA §2, two
         separate bullets. The fast-math exception does not apply
         (`enable_fp_fusion = False` in the draw).
Line:    r2-inductor
Arch:    **generic.** The IR diff contains no wgmma, TMA, mbarrier, cluster or
         warp-specialization construct — only `#ttg.blocked` / `#ttg.slice`
         layouts, `tt.reduce`, `ttg.convert_layout` and `arith` ops. It should
         reproduce on any NVIDIA target whose warp is 32 lanes.
Culprit: `--tritongpu-remove-layout-conversions`, but see §1: the pass is only
         the *exposer*. The defect is in the reduce lowering,
         `lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp`.
Reviewed: 2026-08-19
SMT verdict: **needs bit-exact FP, and a model in which a `tt.reduce` result is
         a per-lane value rather than one tensor element** — see §5.

## What goes wrong, in one sentence

After `tt.reduce`, the lanes that the result's layout declares to be **copies of
one value** in fact hold **different** values (`+inf` in some, `NaN` in others),
so deleting the `ttg.convert_layout` that followed the reduce changes which copy
every consumer reads, and one whole row of the output flips between a finite
number and NaN.

---

## 1. Root cause in the source

### The two arms are the same program

Reference = the root TTGIR of
`gen:triton_red_fused__to_copy_linalg_vector_norm_native_layer_norm_0_76472cad`.
Candidate = the same IR plus `--tritongpu-remove-layout-conversions`. I read the
whole diff. The pass does three things, all of them ordinary and all of them
value-preserving on paper:

* it deletes seven identical `ttg.convert_layout %11 : #blocked4 -> #blocked`
  copies (`%12`…`%18` in `input.ttgir`) and rewrites the users to one of them —
  hence the cosmetic `%14 → %13` change on the `in_ptr1` address;
* it moves the mean / variance arithmetic (`divf`, `addf`, `__nv_rsqrtf`) from
  `#blocked1` (`threadsPerWarp = [32,1]`, `warpsPerCTA = [4,1]`) to `#blocked`
  (`threadsPerWarp = [1,32]`, `warpsPerCTA = [1,4]`);
* **it deletes the `convert_layout` chain that sat directly on the reduce
  result.** In the reference:

  ```mlir
  %43:3 = "tt.reduce"(%37, %cst_5, %42) <{axis = 1}> ... ->
              tensor<32xf32, #ttg.slice<{dim = 1, parent = #blocked}>> x3
  %45 = ttg.convert_layout %43#0 : ...#ttg.slice<{dim=1,parent=#blocked}>-> tensor<32xf32, #blocked2>
  %46 = ttg.convert_layout %45   : #blocked2 -> #ttg.slice<{dim=1,parent=#blocked3}>
  %47 = tt.expand_dims %46       : -> tensor<32x1xf32, #blocked3>
  %48 = ttg.convert_layout %47   : #blocked3 -> tensor<32x1xf32, #blocked1>
  ```

  in the candidate:

  ```mlir
  %34:3 = "tt.reduce"(%29, %cst_5, %33) <{axis = 1}> ...   // identical operands, identical layout
  %35 = tt.expand_dims %34#0 {axis = 1} : -> tensor<32x1xf32, #blocked>
  ```

Note what did **not** change: the `tt.reduce` operand is `tensor<32x128xf32,
#blocked>` in *both* arms, with the same `#blocked`. So the reduction tree is
identical — this is **not** the reduce-reorder class of the kept
`ttgir-broad/HIT-0071` (whose duplicate screen is "did the `tt.reduce` operand
layout change at all"; here it did not).

### The lanes disagree — measured, not inferred

`probe_lane_disagree.py` (shipped with this report) re-runs both arms with one
edit: the value stored to the i32 output is replaced by the **broadcast
`rsqrt(m2/2048 + 1e-5)` of the row**, bit-cast to i32. That is one number per
row, so every column of a row must print the same thing. It does not:

```
--- row 99: broadcast rstd, one value per column ---
   r0= 0  ref=nan  cand=nan
   r0= 1  ref=nan  cand=nan
   r0= 2  ref=nan  cand=nan
   r0= 3  ref=nan  cand=0.0      <-- lane 3
   ...
   r0= 7  ref=nan  cand=0.0      <-- lane 7
   r0=11  ref=nan  cand=0.0
   r0=15  ref=nan  cand=0.0
   r0=19  ref=nan  cand=0.0
   r0=23  ref=nan  cand=0.0
```

`0.0` is `rsqrt(+inf)`; `nan` is `rsqrt(NaN)`. Under `#blocked` with
`threadsPerWarp = [1,32]`, column `c` lives in lane `c`, so the candidate's
per-row scalar is `+inf` in lanes ≡ 3 (mod 4) and `NaN` in the rest. **One
tensor element is holding two different values at the same time.** In the
reference the deleted `convert_layout` chain routes the value through shared
memory, which picks a single lane's copy — a NaN one — for the whole row.

### Where the copies come from apart

`lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp`:

* `reduceWithinWarps` (line 321) reduces along the lane dimension by calling
  `warpReduce` (line 354) and then, at line 348, calls
  `ReduceOpHelper::zeroBasesAlongDimAndReorder(...)` — this is the line that
  *records in the layout* "these lanes now all hold the same value".
* `warpReduce` (lines 354–383) is a **butterfly**: for each set bit of
  `reduceLaneIdMask` it does
  `shfl[i] = shuffleXor(acc[i], mask)` (line 379) and then
  `accumulate(loc, rewriter, op.getCombineOp(), acc, shfl)` (line 381).
  Lane `L` computes `combine(acc_L, acc_{L^mask})`; lane `L^mask` computes
  `combine(acc_{L^mask}, acc_L)`. The two lanes end equal **only if the combine
  region is associative and commutative on the actual values**.

The combine region here is TorchInductor's Welford step
(`torch/_inductor/runtime/triton_helpers.py:300`):

```python
def welford_combine(mean_1, m2_1, weight_1, mean_2, m2_2, weight_2):
    delta = tl.where(mean_1 == mean_2, 0.0, mean_2 - mean_1)
    new_weight = weight_1 + weight_2
    w2_over_w = tl.where(new_weight == 0.0, 0.0, weight_2 / new_weight)
    return (mean_1 + delta * w2_over_w,
            m2_1 + m2_2 + delta * delta * weight_1 * w2_over_w,
            new_weight)
```

With the `wide` input class the row holds values up to ~1e30, so `delta*delta`
overflows to `+inf`; and 103 of the 128 lanes are masked off, so their
`weight` is `0`, which makes `w2_over_w` exactly `0`. The `m2` term is then
`((+inf) * weight_1) * 0` = **NaN**. Whether a given lane's butterfly step pairs
the overflowing partial with an empty partner depends on the lane, so some lanes
finish with `m2 = +inf` and others with `m2 = NaN`. Line 348 then declares them
copies of each other anyway.

### So who is at fault

`tl.reduce`'s docstring (`python/triton/language/core.py:2879`) says "The
reduction operation should be associative and commutative", and in floating
point this combine is not — in the overflow regime it is not even close. That is
the honest counter-argument and I state it plainly. Three reasons it does not
make this a non-bug:

1. **No floating-point combine is associative**, `tl.sum` included. Triton
   nonetheless has to produce *one* value per output element; the reordering
   licence is a licence to round differently, not a licence for a single tensor
   element to hold two values at once.
2. `--tritongpu-remove-layout-conversions` is a **semantics-preserving** pass.
   Whatever the reduce computed, changing the layout of the consumers must not
   change the answer. Here it turns a finite number into NaN.
3. **The invariant is Triton's own.** Line 348 asserts the lanes are broadcast
   copies; line 381 does not establish that. Either the lowering must make them
   equal (broadcast one lane's result after the butterfly, as the shared-memory
   path effectively does) or `tt.reduce` must stop claiming a broadcast layout.
   The first costs one shuffle.

**Distinct from `ttgir-broad/HIT-0071`** (same culprit pass, so B4 was checked):
HIT-0071 is a *reduce-tree* change — the `tt.reduce` operand layout moves
(`threadsPerWarp` / `order`), so the summation order changes and an
intermediate crosses the overflow boundary. Here the operand layout and the tree
are byte-identical between the arms; what changes is which of several disagreeing
copies of the *result* is consumed. Fixing HIT-0071 would not fix this, and vice
versa.

## 3. Where it reproduces

* **Generic NVIDIA.** Nothing in either IR is Hopper- or Blackwell-only; the
  mechanism is a 32-lane butterfly `shfl.sync.bfly` plus blocked/slice layouts,
  which exist on every supported NVIDIA target. `warpReduce` has a fast path
  (`targetInfo.warpReduce`, line 366) for targets with a hardware `redux` op —
  that path is for integer min/max/and/or/xor, so a 3-operand float combine like
  Welford's always takes the butterfly.
* **`num_ctas = 1`, `num_warps = 4`** — no cluster involvement, so this is not a
  member of the campaign's `num_ctas > 1` family.
* **Any kernel whose `tl.reduce` combine can produce different values in
  different lanes.** That is not exotic: it needs (a) a combine that is not
  bit-exactly associative in some regime, and (b) inputs that reach that regime.
  Welford is the standard TorchInductor mean/variance reduction, so every
  `layer_norm` / `var_mean` / `std` kernel inductor emits carries the same
  combine. What makes this draw special is only the `wide` input class, which
  the round-2 plan added.
* Not observed below the overflow regime: with `randn`, `intval`, `smallint`,
  `onesish` the arms agree. The bug needs `m2` to reach `inf`.

## 4. Plain-language explanation

The kernel wants one average and one variance per row. Triton computes them by
having the 32 lanes of a warp swap partial results with each other until every
lane has the whole row's answer. That trick only gives every lane the *same*
answer if adding the partials in a different order gives the same number. With
very large inputs it does not: some lanes end up with "infinity" and some with
"not a number", because "infinity times zero" appears in one order and not the
other.

Triton then treats those 32 lanes as 32 copies of one number. They are not. So
the answer the rest of the kernel sees depends on *which lane it happens to read
from* — and that is decided by the layout. One optimization pass changes the
layout, the kernel starts reading a different lane, and a whole row of output
flips from a real number to "not a number".

## 5. Can an SMT solver model this?

**Yes in principle, but only with two things most tensor-level models leave
out.** Ranking the required vocabulary:

1. **Bit-exact IEEE floating point, including inf and NaN.** Under an abstract
   (uninterpreted-function) FP encoding the two arms are identical — both
   compute `reduce(welford_combine, x)` — and the checker would report
   "equivalent" and be wrong. The whole difference lives in `inf * 0 = NaN`, so
   the axiom profile has to be the exact bit-to-bit one, not the
   reassoc-allowed one. This is also the case that shows why the two profiles
   are not interchangeable: under `reassoc-allowed` this difference is *supposed*
   to be invisible, yet it changes a finite number into NaN.
2. **A `tt.reduce` result modelled as a per-lane value, not as one tensor
   element.** This is the harder requirement and the interesting one. Almost
   every tensor-semantics model — including the one `tv/doc/tile-smt-design.md`
   sketches — treats a reduce as a *function of the input tile* producing a
   value per output index, exactly what the MLIR type says. Under that model the
   two arms are equal by construction, because the difference is *below* the
   tensor abstraction: it is disagreement between physical copies of one logical
   element. To see it, the model needs layouts as index maps from
   (register, lane, warp, block) to tensor index **and** it must allow the
   contents of two positions that map to the same tensor index to differ — i.e.
   the reduce's result is a lane-indexed array plus a claim of uniformity, and
   `convert_layout` is a *choice function* over that array.

That second point is the useful message for the tv project: the abstraction
"reduce returns one value per output index" is precisely the abstraction that
hides this bug. A checker built on it would be sound for well-behaved combines
and silently blind here.

Two things it does **not** need. It is **not** a concurrency bug: there is no
race, no shared-memory hazard and no ordering question — the butterfly is a
`shfl.sync` within one warp and the result is deterministic (4/4 identical runs
per arm). And it is **not** whole-grid: a single program instance, indeed a
single warp, shows the whole thing.

**Cost.** Cheap, if the vocabulary is there. The tile is 32x128 and the
reduction is over 128 with a 3-operand combine; the interesting part is one
warp, 32 lanes, 5 butterfly steps. Proving the *difference* (a SAT query) needs a
witness input that overflows, which is easy to reach — `x ≥ 2^64` in one lane and
an empty partner is enough. A checker that models the lanes and uses exact FP
finds this quickly.

## 6. Confidence

**High that the arms genuinely disagree and that the disagreement is not
licensed rounding; medium-high on the exact chain inside `warpReduce`.**

Solid:
* the difference reproduces (`fz.repro`, plus a from-IR `triton-opt` check);
* it is not measurement noise — heap shift, determinism, store injectivity,
  read-own-output and load-bounds controls are all clean, and `DISABLE_PTXAS_OPT=1`
  rules out the backend;
* the one-arm probe is decisive on the load-bearing claim: **a per-row scalar
  has different values in different columns of the same row.** No reordering
  licence permits that, and it needs no comparison between arms to see;
* the reduce operand layout is byte-identical between the arms, which rules out
  the ordinary reduce-reorder explanation and separates this from
  `ttgir-broad/HIT-0071`.

Not fully pinned:
* I inferred *which* butterfly step first produces the NaN from the shape of the
  pattern (lanes ≡ 3 mod 4) and from reading `warpReduce`; I did not dump the
  per-lane `m2` after each of the five steps. Doing so would name the exact
  step. It would not change the verdict — the disagreement is measured
  directly — but it would make a patch easier to argue.
* I did not check whether the shared-memory cross-warp path
  (`convertLayoutValues` + a second `reduceWithinWarps`, `ReduceOpToLLVM.cpp`
  lines 72–86) has the same hole for the warp dimension. It very likely does,
  by the same argument.
* Whether the maintainers would call this a Triton bug or an inductor bug is a
  judgement I cannot make for them; §1 gives both readings and my reasons for
  the first. If they take the second, the actionable output is still real: the
  layout passes must not be free to change which lane a reduce result is read
  from.

What would settle the remainder: instrument `warpReduce` to store `acc` after
each butterfly step, and re-run the probe. That is a small patch to
`ReduceOpToLLVM.cpp` plus one rebuild.

They were separated from the reduce-reorder class (`ttgir-broad/HIT-0071`) by
this report's own duplicate screen and then matched to this one on three facts,
in this order:

1. **The `tt.reduce` operand layout is byte-identical between the two arms** in
   all three — so "the layout pass reordered the reduction" is not available as
   an explanation. (32 of the 56 bit-difference reports in the previous pass
   were CHANGED; these are the other kind.)
2. **The reduce is a three-operand Welford combine**
   (`delta = m_b - m_a; n = n_a + n_b; w = n_b/n; m = m_a + delta*w;
   M2 = M2_a + M2_b + delta*delta*n_a*w`), which is **not** bit-exactly
   commutative — swapping the two operands negates `delta` and changes `w`, so
   the two orders round differently. That is what makes the lanes disagree after
   `warpReduce`'s shuffle-xor butterfly, exactly as §1 describes for the
   `+inf` / `NaN` case here. A plain `arith.addf` or `arith.maxnumf` combine
   *is* commutative and does not have this property, which is why the class does
   not fire on every reduce.
3. **The pass deletes the `ttg.convert_layout` sitting directly on the reduce
   result** — 3 → 1 on HIT-0177, 3 → 0 on HIT-0187, 2 → 0 on HIT-0191 — which is
   the step that changes which "copy" each consumer reads.

Their outcome is milder than this report's: 27 to 4394 elements at 1 to 3328
ulp, no NaN and no integer output, so on their own they would not have been
kept. What they add is that the mechanism is **not** confined to the extreme
`+inf` / `NaN` draw: with an ordinary input the same non-uniform reduce result
shows up as a last-bits disagreement. HIT-0187 and HIT-0191 also survive the
exact-integer control and survive `DISABLE_PTXAS_OPT=1`, so the difference is
above the assembler; `enable_fp_fusion = False` on all three.
