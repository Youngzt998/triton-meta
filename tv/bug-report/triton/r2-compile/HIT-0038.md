# HIT-0038: the default CGA layout puts the same split at a different CTA bit for different ranks, so a `tt.reshape` across ranks stops being free and the LLVM lowering asserts

Verdict: **CONFIRMED — kept**
Arch:    sm_90 and newer (`num_ctas > 1` needs Hopper thread-block clusters), and
only when `num_ctas >= 4`
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    assertion failure inside `ConvertTritonGPUToLLVM` (compiler abort, not a diagnostic)
Culprit: **`include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td:869-894`**
(the `BlockedEncodingAttr::get(..., numCTAs)` builder), applied per tensor type by
**`lib/Conversion/TritonToTritonGPU/TritonGPUConversion.cpp:28-38`**; tripped at
**`lib/Conversion/TritonGPUToLLVM/ViewOpToLLVM.cpp:244-248`**

Input realism: **the kernel keeps its own pointer dtypes.** The bench kernel
`mode_kernel` is unchanged (`*f16`, `*i64`). The only unusual thing the user has
to do is pass `num_ctas=4` or more.

Occurrences: **2** as of 2026-08-19 19:00, sm_90 only, on
`bch:mode_kernel_b978d037`. The count is low but the defect is not narrow: the
9-line TTIR file in §2 shows it needs nothing but a rank-2 ↔ rank-1
`tt.reshape`, which is what `[:, None]` / `[None, :]` indexing produces in almost
every reduction kernel.

---

## 1. Root cause in the source

Checkout: `/home/youngzt/fuzz/triton-public`, commit `3277063a6` (public
triton-lang, version `3.8.0+git3277063a`).

### The wrong step

`ConvertTritonToTritonGPU` gives every tensor type its layout through a type
converter that looks at **one type at a time**
(`lib/Conversion/TritonToTritonGPU/TritonGPUConversion.cpp:28-38`):

```cpp
addConversion([this](RankedTensorType tensorType) -> RankedTensorType {
  if (tensorType.getEncoding()) return tensorType;
  ArrayRef<int64_t> shape = tensorType.getShape();
  triton::gpu::BlockedEncodingAttr encoding =
      getDefaultBlockedEncoding(this->context, shape, this->numWarps,
                                this->threadsPerWarp, this->numCTAs);
  return tensorType.cloneWithEncoding(encoding);
});
```

`getDefaultBlockedEncoding` (`lib/Dialect/TritonGPU/IR/Dialect.cpp:676-687`)
just fixes `sizePerThread = 1` and `order = reverse(iota(rank))` and hands the
rest to the `BlockedEncodingAttr` builder,
`include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td:869-894`:

```tablegen
unsigned remainingCTAs = numCTAs;
// starting from the most strided dimension
for (int d = rank - 1; d >= 0; --d) {
  unsigned i = order[d];
  CTAsPerCGA[i] = std::clamp<unsigned>(remainingCTAs, 1,
                       std::max<unsigned>(1, shape[i] / sizePerThread[i]));
  CTASplitNum[i] = CTAsPerCGA[i];
  remainingCTAs /= CTAsPerCGA[i];
}
CTAsPerCGA[rank - 1] *= remainingCTAs;   // line 890: "wrap at CTA level"
CGAEncodingAttr CGALayout =
    CGAEncodingAttr::fromSplitParams(context, CTAsPerCGA, CTASplitNum, CTAOrder);
```

Line 890 is where it goes wrong. When the tensor is too small to use all the
CTAs, the leftover is dumped onto **dimension index `rank - 1`** — not onto the
last dimension in `order` — and `CTASplitNum` is *not* updated, so the leftover
becomes **replication**: several CTAs holding the same elements. Where those
replicated (all-zero) CTA bases land in the CTA index depends on `rank` and on
`order`, and that placement is decided independently for every tensor type.

For a rank-1 tensor the real split base comes **first** and the replication after
it. For a rank-2 tensor whose trailing dimension has extent 1 the replication is
attached to that trailing dimension, which `order = [1, 0]` makes the fastest CTA
dimension, so the replication comes **first** and the real split base last.

### What that produces

`ConvertTritonToTritonGPU` on a bare `tensor<2xi32> ↔ tensor<2x1xi32>` reshape,
measured with `triton-opt` (§2):

| `num_ctas` | rank-1 `tensor<2xi32>` | rank-2 `tensor<2x1xi32>` | `block` free-variable mask | result |
|---|---|---|---|---|
| 1 | `CGALayout = []` | `CGALayout = []` | 0 vs 0 | compiles |
| 2 | `[[1]]` | `[[1, 0]]` | 0 vs 0 | compiles |
| 4 | `[[1], [0]]` | `[[0, 0], [1, 0]]` | **2 vs 1** | **abort** |
| 8 | `[[1], [0], [0]]` | `[[0, 0], [0, 0], [1, 0]]` | **6 vs 3** | **abort** |

At `num_ctas >= 4` the two layouts split dimension 0 across a **different bit of
the CTA index**. Concretely at `num_ctas = 4`: in the rank-1 layout, element 1
lives in CTAs {1, 3}; in the rank-2 layout the same element lives in CTAs {2, 3}.
The reshape is therefore a real data movement between CTAs, not a relabelling.

`isExpensiveView` (`lib/Dialect/TritonGPU/IR/Dialect.cpp:206-219`) says so
correctly — it compares the free-variable masks of the two linear layouts and
returns true as soon as they differ:

```cpp
for (auto [srcMask, dstMask] :
     llvm::zip(llSrc.getFreeVariableMasks(), llDst.getFreeVariableMasks())) {
  assert(srcMask.first == dstMask.first);
  if (srcMask.second != dstMask.second) return true;
}
```

(Both sides have one element per thread, so the second test —
`getTotalElemsPerThread` — is *not* what fires. It is purely the position of the
replicated CTA bits.)

### Why nobody repairs it

`isExpensiveView` is only ever consulted as a **guard on an optimization** — a
reason not to fold, not to rewrite, not to accept a layout hint:

* `lib/Dialect/TritonGPU/IR/Ops.cpp:132` and `:315` — do not fold
  `cvt(reshape)`;
* `lib/Dialect/TritonGPU/Transforms/Utility.cpp:676` — do not propagate a layout
  through it;
* `lib/Dialect/TritonGPU/Transforms/OptimizeThreadLocality.cpp:80` — do not pick
  this rewrite;
* `lib/Dialect/TritonGPU/IR/Dialect.cpp:3520` — in `inferReshapeOpEncoding`,
  accept a caller's destination hint only if the view is cheap.

**No pass ever inserts a `ttg.convert_layout` to make an expensive reshape
cheap.** `TritonGPURemoveLayoutConversions` moves and cancels
`ttg.convert_layout` ops; a `tt.reshape` is not one, so it is left exactly as it
is.

The lowering then assumes the invariant that nothing established
(`lib/Conversion/TritonGPUToLLVM/ViewOpToLLVM.cpp:244-248`):

```cpp
  matchAndRewrite(ReshapeOp op, OpAdaptor adaptor,
                  ConversionPatternRewriter &rewriter) const override {
    assert(!isExpensiveView(op.getSrc().getType(), op.getType()));
    rewriter.replaceOp(op, adaptor.getSrc());     // <- pure relabelling
    return success();
  }
```

`replaceOp(op, adaptor.getSrc())` hands the source registers straight through.
That is only correct when the two layouts place every element in the same place.
When they do not, the assert fires — and in a build with `NDEBUG` the assert is
compiled out and the compiler would **silently emit wrong code**, because each
CTA would keep its own copy instead of the one the reshape asked for. I did not
verify that second half (it needs an assertions-off build), so treat it as a
consequence to check, not a measurement.

### Where the pass boundary sits

I dumped the IR before every pass (`MLIR_ENABLE_DUMP=1`) on the original draw.
The mismatched pair is already present in the **first** TTGIR module, the one
`TritonGPUCoalesce` receives, i.e. it comes straight out of
`ConvertTritonToTritonGPU`. It is **not** `PlanCTA`: the two layouts are
unchanged across that pass (`PlanCTA` only drops the third, unused layout).
That distinguishes this from HIT-0001 / HIT-0003 / HIT-0005 / HIT-0006 /
HIT-0019, which are all defects *inside* `PlanCTA`.

## 3. Where it reproduces

**sm_90 (Hopper) and newer, and only at `num_ctas >= 4`.** Triton refuses
`num_ctas > 1` below sm_90. Both recorded occurrences are sm_90.

What that judgement rests on: the failing IR contains **no** Hopper-only
construct — no `wgmma`, no TMA, no `mbarrier`, no cluster intrinsic, no warp
specialization. The minimal reproducer is `tt.make_range`, two `tt.reshape` and a
`tt.store`. Both wrong pieces of code are target-independent: the CGA-layout
builder is in `include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td` and the
lowering is in `lib/Conversion/TritonGPUToLLVM/`, shared by every NVIDIA target.
The arch limit comes only from clusters being a Hopper-and-later feature. So: any
NVIDIA target with thread-block clusters. Blackwell (sm_100) is a prediction from
the source; I could not test it on this box.

Independent of `num_warps`, `num_stages`, `maxnreg` and the pointer dtypes —
the minimal file has no pointers worth speaking of and still fails.

**A note on how easy this is to hit.** The count is only 2, but that is about how
often the fuzzer drew `num_ctas >= 4` together with a rank-changing reshape, not
about how narrow the defect is. Any kernel that mixes a 1-D tensor with its
`[:, None]` form — every reduction written in the usual inductor style — has this
reshape.

## 4. In plain words

On an H100 you can run one program as a *cluster* of several thread blocks
(`num_ctas=8`). Triton must then decide which block holds which part of each
tile.

For a small tile there are more blocks than pieces, so several blocks end up
holding the same data. Triton picks that arrangement one tile at a time, with no
memory of what it chose for the others. For a flat list of 2 numbers it decides
"block number bit 0 picks the element; the other bits are copies". For the same
2 numbers written as a 2-by-1 table it decides the opposite: "the first bits are
copies; the last bit picks the element".

Reshaping the list into the table is supposed to be free — the same numbers,
described differently. With those two arrangements it is not free: the number
that block 1 holds in one form is held by block 2 in the other. The final code
generator assumes the reshape is free, notices its own assumption is broken, and
aborts. The user gets a C++ file name.

## 5. Can an SMT solver model this?

**Verdict: not expressible as an equivalence query, because one side does not
exist — but it is a clean, cheap layout-compatibility obligation on exactly the
IR a GPU-level checker would already carry, and that framing settles the whole
class.**

1. **No second program to compare.** The compiler aborts inside
   `ConvertTritonGPUToLLVM`, so there is no "after" module. Same reasoning as
   `tv/bug-report/tilelang/CODEGEN-0001`.

2. **The obligation that would catch it.** Model a TTGIR layout the way
   `tv/doc/tile-smt-design.md` wants for the GPU layer: a map
   `(block, warp, lane, register) -> tensor index`. Then `tt.reshape`'s
   lowering has a precise precondition, and it is *stateable*:

   ```
   for every reshape from (S_src, L_src) to (S_dst, L_dst) that the lowering
   turns into a no-op:
       forall b, w, l, r:  flatten(L_src(b,w,l,r), S_src)
                        == flatten(L_dst(b,w,l,r), S_dst)
   ```

   i.e. the register in hardware slot `(b,w,l,r)` must hold the same logical
   element before and after. For this bug the two sides differ as soon as
   `b`'s bits are permuted, so the obligation is refuted with a two-element
   counterexample. This is a **finite, quantifier-free bit-vector query** once
   the shapes are fixed, and a linear-integer query over the layout bases if you
   want it for all shapes at once.

3. **Would it also catch the silent-miscompile form?** Yes, and that is the
   point. The assert is a debug-build courtesy; with `NDEBUG` the same reshape
   becomes a wrong-data bug, and the obligation above is exactly the check that
   distinguishes "relabelling" from "data movement". This is one of the cases
   where an IR-level checker is strictly better than the crash, because the crash
   only appears in one build mode.

4. **Minimum vocabulary.** The **CTA (`block`) dimension of a layout must be a
   real dimension**, including its *replicated* bases. A model that folds
   broadcast bases away — a very natural simplification, since replicated bases
   carry no data — loses precisely the information this bug lives in: *which*
   CTA-index bits are the replicated ones. That is the same blind spot as
   HIT-0016, seen from a different side.

5. **What is not needed.** No concurrency or memory-ordering model (nothing runs;
   no shared memory is involved in the failing op). No floating point at all —
   the minimal reproducer is `i32`. No whole-grid modelling — one cluster is one
   program instance.

6. **Cost.** Trivial: 2 elements, 8 CTAs, one equality per hardware slot.

## 6. Confidence

**Very high that this is a genuine compiler bug.**

* (a) A 9-line TTIR file with two `triton-opt` passes reproduces it. No Python,
  no corpus, no fuzzer.
* (b) The mechanism predicts the `num_ctas` threshold *before* measuring it: the
  CTA-base arithmetic in `TritonGPUAttrDefs.td:880-890` says the two layouts
  agree at `num_ctas` 1 and 2 and disagree from 4 up, and the measured
  compile/abort boundary is exactly there — on the real kernel and on the
  minimal file alike.
* (c) The printed layouts match the predicted bases element for element
  (`[[1],[0]]` vs `[[0,0],[1,0]]` at 4; `[[1],[0],[0]]` vs
  `[[0,0],[0,0],[1,0]]` at 8).
* (d) An `assert` is by construction the compiler's own invariant about itself.
  `isExpensiveView` returning true is the compiler agreeing that the reshape is
  not free.
* (e) A pass-by-pass IR dump places the bad pair at the output of
  `ConvertTritonToTritonGPU`, so the attribution is measured, not guessed.

**Remaining doubt, and it is about the fix, not the defect.** Which side is
"wrong" is a design question I cannot settle from outside: either
(i) the CGA-layout builder should place replicated CTA bases at a
rank-independent position so that shapes connected by a reshape stay compatible,
or (ii) the TTGIR pipeline should insert a `ttg.convert_layout` whenever
`isExpensiveView` holds, or (iii) `ReshapeOpConversion` should fall back to a
shared-memory round trip instead of asserting. Upstream's own comments suggest
(ii) was the intent — every other use of `isExpensiveView` is a guard that
assumes somebody else will handle the expensive case — but nobody does.

The one thing I would check next, and could not here: build with `NDEBUG` and
confirm that the assert's absence turns this into silently wrong data rather than
a different failure. If it does, this class is more serious than its occurrence
count of 2 suggests, because released wheels are built without assertions.
