# HIT-0006: PlanCTA calls `markTiled()` once per `tt.dot`, so any kernel with two matmuls aborts under `num_ctas > 1`

Verdict: **CONFIRMED — kept**
Arch:    hopper-only (sm_90; `num_ctas > 1` needs Hopper clusters)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    `assert` failure — the process aborts (SIGABRT)
Culprit: **`TritonGPUPlanCTAPass`** — `lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp:211`
(`CTAPlanner::markTiled`), called from `CTAPlanner::processDot` at line 255

Input realism: **the kernel keeps its own pointer dtypes.** The failing kernel is
a real torch-inductor flex-attention backward kernel. The only unusual thing a
user has to do is pass `num_ctas=2`.

Occurrences: **12**, sm_90 only, across at least 4 distinct kernels
(`ind:triton_flex_attention_backward_2c768ac2`,
`bch:_conv_transpose2d_residue_kernel_bc97b619`,
`ind:triton_flex_attention_65dbdfce`, …) — all of them multi-matmul kernels,
which is the pattern.

---

## 1. Root cause in the source

`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp`. The planner has one flag,
`bool tiled`, meaning "I have already decided how to split the tile across the
cluster". It is set through:

```cpp
void CTAPlanner::markTiled() {
  assert(!tiled && "CTA tiling is already determined");     // line 211
  tiled = true;
}
```

Every caller but one guards the call. `processReduce` (line 328) does
`if (!tiled) markTiled();`. `processStoreLikeOps` (lines 373, 383) does
`if (!tiled)` both times. **`processDot` does not:**

```cpp
funcOp.walk([&](triton::DotOp dot) {              // line 227 — once per dot
    ...
    unsigned splitM, splitN;
    std::tie(splitM, splitN) = getCTATiling(M, N, K, ttg::getNumCTAs(dLayout));
    // FIXME: Should consider IR with more than one DotOps
    markTiled();                                  // line 255 — unguarded
    ...
});
```

The `FIXME` on line 254 says exactly what is wrong. `funcOp.walk` visits **every**
`tt.dot` in the function, so the second one re-enters `markTiled()` with
`tiled == true` and line 211 fires.

The failing module has **7** `tt.dot` ops (counted in
`HIT-0006/pre-plan-cta.ttgir`), so the abort happens on the second one. Any
kernel with two or more matmuls in one function is affected: attention forward
(QK then PV), attention backward, fused MLPs, back-to-back GEMMs.

The bug is not only the assert. Even with the assert removed, the loop body
would keep recomputing `splitM`/`splitN` per dot and overwriting the previous
dot's decision, so the last dot silently wins — which is presumably why the
`FIXME` is there. A correct fix has to pick one tiling for the whole function
(or refuse), not just stop asserting.

## 3. Where it reproduces

**Any NVIDIA target that accepts `num_ctas > 1`, i.e. sm_90 and later.**

- `PlanCTAPass::runOnOperation` returns immediately when `getNumCTAs(mod) == 1`
  (PlanCTA.cpp:986), so the default configuration never reaches this code.
- The minimal repro uses only `tt.dot` on `#ttg.dot_op` / `#ttg.blocked`
  layouts — no wgmma, no TMA, no mbarrier, no cluster op, no warp
  specialization. The arch dependence is purely the `num_ctas` gate.
- `markTiled` and the `funcOp.walk` make no target query.

R4 saw it on sm_90 only, having swept sm_80/sm_89 too, where `num_ctas > 1` is
rejected earlier.

**On user reachability:** two matmuls in one kernel is the norm, not the
exception — flash attention has two, and both flex-attention kernels in this
class are stock torch-inductor output. Anyone enabling clusters on an attention
model hits this immediately.

## 4. Plain-language explanation

When you ask for a cluster of thread blocks, the compiler has to choose one way
to split the tile between them, and it wants to make that choice exactly once.
It keeps a flag that says "already chosen", and it checks that flag before
setting it.

The code that chooses from a matrix multiply forgot the check. It runs once for
*every* matrix multiply in the kernel. So a kernel with one matmul is fine, and a
kernel with two — which is every attention kernel — sets the flag twice and the
compiler aborts. There is a `FIXME` comment on the line right above saying this
case was never handled.

## 5. SMT reachability analysis

**Outside the equivalence question — but with a real value-level question hiding
just behind it, which is worth stating because that one an SMT checker *could*
answer.**

1. **Root cause in semantic terms.** The construct is `tt.dot`, and the state is
   a per-function CGA tiling choice `(splitM, splitN)` attached to a
   `#ttg.blocked` layout. The error is a broken internal invariant — "tiling is
   chosen at most once" — not a wrong meaning for any op.
2. **Is the difference a pure input→output function difference?** No difference
   exists; the process dies. Nothing depends on runtime inputs, scheduling, or
   hardware.
3. **Fundamental verdict.** **Outside the equivalence question** for the crash as
   observed. But note what the `FIXME` implies: if the assert were simply
   deleted, the loop would compute a tiling for each dot and let the last one
   win, silently, while the earlier dots keep layouts chosen for a different
   split. *That* would be a value-level bug, and it would be
   **`needs whole-grid modeling`** — a CGA is several CTAs cooperating on one
   tile, so "each dot is split differently across the cluster" is a statement
   about several program instances at once, not about one instance's
   input→output function. A single-instance equivalence check would not see it.
4. **Minimum semantic vocabulary required.** For the hypothetical silent version:
   layouts as index maps from (CTA, warp, lane, register) to tensor coordinates,
   with the CTA index ranging over the cluster rather than being fixed; `tt.dot`
   as a contraction whose operand and result index maps must agree; and a notion
   of the whole cluster's combined result. That is the `tile-gpu-smt` layer, not
   the hardware-neutral core. It is expressible, and it is not obviously
   expensive, because the property is about index maps rather than about values.
5. **Would the abstraction hide it?** For the crash, the FP profile is
   irrelevant. For the hypothetical silent version, an abstract
   (uninterpreted-function) FP encoding would be *enough* — a mis-split matmul
   moves data to the wrong CTA, which shows up as different operands feeding the
   contraction, not as a rounding difference. So this is one of the cases where
   the cheap FP profile suffices and the expensive bit-exact one is not needed.
6. **Inherent cost.** Zero for the crash. For the hypothetical: proving
   equivalence would be cheap; finding the counterexample would need a small tile
   (the usual UNSAT-cheap / SAT-expensive asymmetry), so shrink to 16×16 before
   asking.

**What would catch this class instead:** an assertion-reachability sweep, which
is what R4 is. Cheaper and targeted: a lit test with two `tt.dot`s and
`num_ctas = 2`. The `FIXME` on line 254 already names the missing case, so this
is a known gap that no test pins.

## 6. Confidence

**High.** The assert text names file, line and condition. The source shows the
one unguarded `markTiled()` call inside a `funcOp.walk` over `tt.dot`, with the
other three call sites guarded by `if (!tiled)`. The failing module has 7
`tt.dot`s. A hand-written 13-line module with two dots aborts identically, and
the same module with one dot passes — so the trigger is the dot count and
nothing else.

Remaining doubt is about the *fix*, not the bug: I do not know what tiling Triton
would want for a multi-dot kernel — the first dot's, the largest dot's, or a
refusal to use clusters at all. That is a design question for the owner of the
pass, and it is the reason the `FIXME` is still there. My report does not need to
answer it.
