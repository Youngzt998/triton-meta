# HIT-0049: PlanCTA cannot give a loop-carried value two different CTA layouts, and calls report_fatal_error

Verdict: **CONFIRMED — compiler crash** (`LLVM ERROR: Layout conflict for block arg`,
         then `RuntimeError: PassManager::run failed`)
Arch:    **sm_90 only in practice** — the pass returns immediately when
         `num_ctas == 1` (`PlanCTA.cpp:986`), and `num_ctas > 1` (Hopper
         thread-block clusters) is gated to sm_90+. The mistake itself is
         target-independent.
Line:    r2-compile (R4, compile-only, no GPU)
Culprit: `TritonGPUPlanCTAPass`
         (`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp:937`)
Class:   R4 `crash-assert`, rule `F4`, signature
         `llvm-error:Layout conflict for block arg`
Occurrences: 2 at the time of review, both sm_90, both in the `ttgir` stage,
         example kernel `bch:bmm_kernel_a62513ac`.
Review:  **KEPT** under REVIEW-CRITERIA §2, last bullet ("compile failure,
         crash, or invalid generated code — keep it"). This is the **eighth**
         defect in the `num_ctas > 1` family and the sixth inside `PlanCTA`.
SMT verdict: **not applicable / out of scope** — a compile-time crash, not a
         value difference.

## What goes wrong, in one sentence

A value carried by an `scf.for` loop is used twice inside the loop body — once
by a `tt.load`, once by the `tt.addptr` that advances it — the two uses need
two different CTA (CGA) layouts, and `PlanCTA` can only give a value two
layouts by cloning the op that produced it, which a loop argument does not
have.

---

## 1. Root cause in the source

`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp`.

`CTAPlanner` propagates CTA layouts by walking a worklist of temporary
`CastOp`s. `propagateBackward` (line ~390) looks at the value feeding a cast
and splits on how many users that value has:

* **one user** (line 398): dispatch on the defining op. A block argument is
  handled here, by `processBlockArgBackward` (line 843), which walks into the
  parent `scf.for`. That path works.
* **more than one user** (line 439): `processMultiUsersBackward`.

`processMultiUsersBackward` (lines 903–958) groups the users by the type each
one asks for (`typeToIndices`). The first group keeps the original value. Every
later group needs its **own** producer, and the only way the pass knows to make
one is to clone the defining op:

```c++
    Value newInput = input;
    if (!first) {
      if (Operation *defOp = input.getDefiningOp()) {
        builder.setInsertionPointAfter(defOp);
        Operation *clonedOp = builder.clone(*defOp);
        newInput = clonedOp->getResult(0);
      } else {
        llvm::report_fatal_error("Layout conflict for block arg"); // TODO
        return false;
      }
    }
```
(`PlanCTA.cpp:930-941`; the `// TODO` is in the source.)

A block argument has no defining op. There is nothing to clone, so the pass
kills the process. The fix shape is the one `processBlockArgBackward` already
knows for the single-user case — push the second layout through the loop's
`init` operand and add a second iteration argument, or leave one user behind a
`ttg.convert_layout` — but neither is implemented, and the `// TODO` says so.

**Why it is reached here.** In the failing kernel the `scf.for` carries
`%arg12 : tensor<32x32x!tt.ptr<f16>, #blocked>` (the A-operand pointer block)
and uses it twice in the body — `ttg.convert_layout %arg12 -> #blocked6`
feeding `tt.load`, and `tt.addptr %arg12, %cst_1` advancing it for the next
iteration. `tt.dot` forces the loaded value into a `dot_op` layout whose CTA
split differs from the one the pointer arithmetic keeps, so the two users land
in two groups of `typeToIndices`, and the second group hits line 937. Both
carried pointer blocks (`%arg12`, `%arg13`) have this shape; see
`planCTA-blockarg-prepass.ttgir`.

**Distinct from the other kept `PlanCTA` reports.**

| kept report | where | what fires |
|---|---|---|
| HIT-0001 | `processReduce` | leftover CTA count applied twice |
| HIT-0003 | `:849` | block arg whose parent is not `scf.for` (`scf.while`) — the *single*-user path, different message |
| HIT-0005 | store scan | `assert stores.size() > 0` |
| HIT-0006 | `markTiled()` | 2+ matmuls |
| HIT-0019 | `:164` | 10000-step worklist budget |
| HIT-0045 | `:373` | first store's CGA layout reused on a later store of another rank |
| r2-corpus/HIT-0037 | `:77` | recursive `replaceCGALayout` on a slice |
| **this** | **`:937`** | **multi-user block arg needing two layouts** |

HIT-0003 is the closest neighbour and is genuinely a different case: it is the
`numUsers == 1` branch, its message is `Unexpected parent op of block argument`,
and it needs an `scf.while`. This one has an ordinary `scf.for` and needs the
block argument to have **two** users wanting **two** layouts.

## 3. Where it reproduces

Any host with this Triton checkout. The pass is target-independent C++ and runs
long before code generation, so no GPU is involved and the crash is not
machine-specific.

It is **sm_90-and-later in practice, and only there**, for one reason:
`PlanCTAPass::runOnOperation` returns immediately when `num_ctas == 1`
(`PlanCTA.cpp:986`), and `num_ctas > 1` needs Hopper thread-block clusters. The
IR itself holds no Hopper-only construct — no wgmma, no TMA, no mbarrier, no
warp specialization; it is `#ttg.blocked` layouts, `tt.load`, `tt.dot`,
`scf.for`, `tt.store`. A backend that offered clusters on another target would
reach the same line.

## 4. Plain-language explanation

When a kernel is compiled for more than one thread block per cluster, Triton
must decide, for every tensor, how its elements are split across those blocks.
It decides by walking the program and pushing that choice from each use back to
where the value was made.

This kernel has a pointer block that lives across the loop: each round it is
read from, and then bumped forward for the next round. Those two uses want the
data split two different ways. Triton's answer to "one value, two splits" is to
duplicate the instruction that made the value, once per split. But this value
is not made by an instruction — it is the loop's own carried value, handed in
at the top of each round. There is nothing to duplicate, so the pass stops the
compiler dead. The comment on that line says `TODO`, so the gap is known.

## 5. Can an SMT solver model this?

**Not applicable.** This is a compile-time abort, not a difference between two
computed values, so there is no pair of programs to prove equal or unequal. An
equivalence checker never gets an output to compare, because the compiler never
produces one.

The useful thing to record for the translation-validation project is the
negative one: a validator sitting after this pass sees nothing at all, and the
whole `num_ctas > 1` family — now eight defects — is invisible to it for the
same reason, because six of the eight are crashes. Only `r2-oracle/HIT-0001` in
that family produces wrong data, and that one an IR-level checker could in
principle catch, but only with whole-grid, cross-CTA semantics.

## 6. Confidence

**High that it is a genuine defect.** The abort is unconditional, the message
and the `// TODO` are in the source, the failing case is an ordinary
`scf.for`-carried pointer block in a batched matmul, and the same program
compiles cleanly at `num_ctas = 1`. No user-facing diagnostic is produced — the
user gets `RuntimeError: PassManager::run failed` with no source location.

**The remaining doubt is severity, not existence.** `num_ctas > 1` has no lit
test anywhere in this pass (the file's closing TODO list ends with "Add some
lit tests for this pass"), so it is possible this configuration is understood
internally as not-yet-supported rather than broken. What would settle it: a
statement from the Triton owners on whether `num_ctas > 1` is a supported
option. If it is, this is a bug with an obvious fix shape. If it is not, the
honest report is that the option should be refused up front with a message
naming the unsupported case, instead of `report_fatal_error` in the middle of a
pass.
