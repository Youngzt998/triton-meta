# HIT-0004: fp8 arithmetic survives to `ConvertTritonGPUToLLVM`, which converts fp8 to `i8` and then emits float LLVM ops on integers

Verdict: **CONFIRMED — kept**
Arch:    sm_89 and sm_90 observed; the mechanism is generic to the NVIDIA backend
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    invalid LLVM-dialect IR emitted by a pass, and one hard `report_fatal_error`
Culprit: **`ConvertTritonGPUToLLVM`** — the elementwise lowering, together with
the fp8→`i8` rule in the type converter
(`include/triton/Conversion/TritonGPUToLLVM/TypeConverter.h:31-36`)

Input realism: **the fuzzer swapped a pointer dtype** — it drew `*fp8e4nv` for a
pointer whose corpus author used another type. Weigh it lower: nobody wrote this
exact program. But `tl.float8e4nv` is a first-class Triton dtype with a real MLIR
float type behind it, the TTIR and TTGIR that Triton builds from it **verify
clean**, and the compiler only falls over at the last lowering step. Triton owes a
diagnostic there, not invalid IR and not an abort.

Occurrences: **16** = 5 `llvm.fcmp` (this report) + 3 `llvm.fmul` (HIT-0010,
rejected B4 duplicate) + 8 `packLLElements` (HIT-0012, rejected B4 duplicate).
R4 later filed a fourth signature for the same thing, `llvm.fsub` (HIT-0018,
count 4, outside this review's backlog) — the class keeps splitting one more time
for every arithmetic op someone happens to apply to an fp8 tensor. Archs sm_80,
sm_89, sm_90 across the merged set; at least 6 distinct kernels.

---

## 1. Root cause in the source

**Step 1 — LLVM has no fp8 type, so Triton converts all four MLIR fp8 types to
`i8`.** `include/triton/Conversion/TritonGPUToLLVM/TypeConverter.h:31-36`:

```cpp
template <typename... T> void convertFP8Type() {
  (addConversion([&](T type) -> std::optional<Type> {
     return IntegerType::get(type.getContext(), 8);
   }),
   ...);
}
```

registered in `lib/Conversion/TritonGPUToLLVM/TypeConverter.cpp:43-44` for
`Float8E4M3FNUZType, Float8E4M3FNType, Float8E5M2Type, Float8E5M2FNUZType`.
So after conversion an fp8 value is an `i8` bag of bits, and all real fp8
arithmetic has to be done by first converting to f16/f32 — which is what
`FpToFpOpConversion` exists for.

**Step 2 — but the elementwise lowering maps `arith.<float op>` to
`llvm.<float op>` with no fp8 check.**
`third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/ElementwiseOpToLLVM.cpp:896-900`:

```cpp
#define POPULATE_OP(SRC_OP, DST_OP)                                            \
  patterns.add<ElementwiseOpConversion<SRC_OP, DST_OP>>(                       \
      typeConverter, axisInfoAnalysis, benefit)

  POPULATE_OP(arith::SubFOp, LLVM::FSubOp);
  POPULATE_OP(arith::AddFOp, LLVM::FAddOp);
  POPULATE_OP(arith::MulFOp, LLVM::FMulOp);
```

and the shared base, `include/triton/Conversion/TritonGPUToLLVM/ElementwiseOpToLLVMBase.h:116-131`:

```cpp
auto resultElementTy = getElementTypeOrSelf(resultTy);
Type elemTy = this->getTypeConverter()->convertType(resultElementTy);  // fp8 -> i8
...
auto loweredOps = static_cast<const ConcreteT *>(this)->createDestOps(
    op, adaptor, rewriter, elemTy, MultipleOperandsRange(it, end), loc);
```

The operands arrive already converted (i8) and `elemTy` is the converted result
type (i8), so `LLVM::FMulOp::create(rewriter, loc, i8, i8_a, i8_b)` is built.
The LLVM dialect verifier rejects it:

```
error: 'llvm.fmul' op operand #0 must be floating point LLVM type or
       LLVM dialect-compatible vector of floating point LLVM type, but got 'i8'
```

Comparison takes the same route through a hand-written pattern,
`lib/Conversion/TritonGPUToLLVM/ElementwiseOpToLLVM.cpp:94-108`:

```cpp
static SmallVector<LLVM::FCmpOp>
createDestOps(arith::CmpFOp op, OpAdaptor adaptor, ..., Type elemTy,
              MultipleOperandsRange operands, Location loc) {
  return {LLVM::FCmpOp::create(rewriter, loc, elemTy,
                               ArithCmpFPredicateToLLVM(op.getPredicate()),
                               operands[0][0], operands[0][1])};
}
```

Here `elemTy` is `i1` (the compare's own result type) so it looks fine, but
`operands[0][0]` and `[0][1]` are the converted i8 values:

```
error: 'llvm.fcmp' op operand #0 must be floating point LLVM type ..., but got 'i8'
```

**Step 3 — the third symptom.** The merged HIT-0012 fails a little earlier, at
`lib/Conversion/TritonGPUToLLVM/Utility.cpp:1087-1090`:

```
error: invalid element type in packLLElements. Expected 'i8' but got 'f8E4M3FN'
LLVM ERROR: element type mismatch when packing elements for LLVM struct
```

i.e. some lowering handed the packer values still typed `f8E4M3FN` while the
converted struct type is a struct of `i8` — the same fp8-vs-i8 disagreement,
seen from the other side. That module's fp8 arithmetic lives inside a `tt.reduce`
combine region (`arith.addf %arg2, %arg3 : f8E4M3FN`), where the region body is
cloned rather than run through `ElementwiseOpConversionBase`, so the values keep
their original fp8 type. **I did not pin that pattern to an exact line** — see §6.

**Why all three are one class.** Same pass, same mechanism: the TTGIR is valid
(MLIR's `arith` dialect accepts float ops on any `FloatType`, and `Float8E4M3FN`
is one), the type converter turns fp8 into `i8` for LLVM, and no part of the
elementwise lowering was taught that fp8 arithmetic must go through an
up-convert. One fix removes all of them — either reject fp8 arithmetic in the
frontend and force an explicit `.to(tl.float16)`, or make the elementwise
patterns up-convert fp8 operands the way `FpToFpOpConversion` already can. The
`llvm.fsub` signature R4 filed later (HIT-0018) is the same fix again.

Note also what does *not* fail: `ArithConstantSplatOpConversion`
(`lib/Conversion/TritonGPUToLLVM/ViewOpToLLVM.cpp:113-116`) has an explicit fp8
branch — *"Lower FP8 constant to int8 constant since FP8 types are not supported
on LLVM IR"*. So the problem is known in one place and not handled in the others.

## 3. Where it reproduces

**Every NVIDIA target from sm_89 up; almost certainly sm_80 too, and very likely
AMD.** The judgement rests on:

- The type-converter rule (fp8 → `i8`) is in target-independent code,
  `include/triton/Conversion/TritonGPUToLLVM/TypeConverter.h`, and applies to all
  four fp8 MLIR types.
- `CmpFOpConversion` is in shared code
  (`lib/Conversion/TritonGPUToLLVM/ElementwiseOpToLLVM.cpp`); only the
  `POPULATE_OP` list for add/sub/mul lives under `third_party/nvidia/`. The AMD
  backend has its own copy of that list, so the same shape of bug is expected
  there, but I did not test AMD.
- The failing IR uses **no** Hopper-only construct — no wgmma, no TMA, no
  mbarrier, no cluster, no warp specialization. It is `arith.cmpf` / `arith.mulf`
  on a blocked-layout tensor.
- The observed arch spread across the merged class is sm_80, sm_89 and sm_90
  (HIT-0012's occurrences cover all three). This report's own two symptoms were
  seen on sm_89 and sm_90 only, which fits the fact that `fp8e4nv` is gated to
  compute capability ≥ 89 (`ElementwiseOpToLLVM.cpp:458-461`) — on sm_80 the
  `fp8e4nv` draw is rejected earlier with a proper message, which is the correct
  behaviour.

## 4. Plain-language explanation

An 8-bit float type only exists inside Triton. LLVM, the layer below, has no
such type, so Triton stores those values as plain 8-bit integers and converts
them to a normal float whenever it needs to compute with them.

The catch is that Triton's Python layer lets you write `a * b` or `a < b`
directly on 8-bit floats without any conversion. That builds a float multiply
whose operand type is the 8-bit float. Every check up to the last step is happy,
because MLIR does have an 8-bit float type. Then the last step swaps the type for
a plain 8-bit integer — and now there is a float multiply on two integers, which
LLVM refuses.

So the compiler accepts the program for four or five passes and then produces
something it cannot accept itself. The user should have been told at the start:
"you must convert this to fp16 or fp32 before doing arithmetic on it."

## 5. SMT reachability analysis

**Outside the equivalence question. This one is a type-preservation bug, and it
is the clearest example in this batch of a defect that an equivalence checker is
structurally the wrong tool for.**

1. **Root cause in semantic terms.** The constructs are `arith.mulf`,
   `arith.cmpf`, `arith.addf`, `arith.subf` on a tensor whose element type is
   `f8E4M3FN`, plus the type conversion `f8E4M3FN → i8` applied on the way to the
   LLVM dialect. The semantic error is that the conversion is a **reinterpret**
   (same 8 bits, different meaning) while the operation is left as a *float*
   operation, so op and operand type stop agreeing. Nothing about tensor shape,
   layout, loop structure or memory is involved.
2. **Is the difference a pure input→output function difference?** No difference
   exists — compilation stops. Nothing depends on the kernel's runtime inputs, on
   scheduling, or on hardware.
3. **Fundamental verdict.** **Outside the equivalence question**, and worth
   being blunt about why. An SMT equivalence check answers "do these two programs
   agree on all inputs". Here the second program was never built. Worse, an SMT
   encoder pointed at the broken output would fail in exactly the same way the
   verifier did: it cannot build a term for `fmul : (i8, i8) -> i8`. The property
   violated is **type preservation across a lowering** — "if the input program is
   well-typed, the output program is well-typed" — which is a compiler-correctness
   property that type checking decides, not a value property that a solver
   decides.
4. **Minimum semantic vocabulary required.** For the type-preservation framing:
   the model needs the *type conversion function* itself as an object, so it can
   state "for every op in the output, the operand types are those the op's
   signature admits". MLIR already has this as the conversion-target/legality
   machinery, and the fix is to mark `LLVM::FMulOp` illegal on non-float operands
   — which the verifier does, one step too late to be useful.
   For the *hypothetical* value-level version of the question — "does an fp8
   multiply computed via up-convert to f16 give the same bits as one computed
   some other way?" — a model would need fp8 as a genuine 8-bit IEEE-like format
   with its own exponent bias and saturation rules, plus exact conversion
   semantics to and from f16/f32. That would need the **exact bit-to-bit FP axiom
   profile**; the reassoc-allowed profile would not see rounding differences of
   an 8-bit format, where almost every operation rounds.
5. **Would the abstraction hide it?** For the actual bug, the FP profile is
   irrelevant — no value is computed. For the hypothetical version above, an
   uninterpreted-function FP encoding would hide it completely: `fmul(a,b)` as an
   opaque function is the same term regardless of the width it was carried out
   in, so the checker would prove an fp8 multiply equal to an f32 multiply.
6. **Inherent cost.** Zero for the type check. The value-level version would be
   cheap too — fp8 is 8 bits, so exhaustive enumeration over a pair of operands
   is 65,536 cases and needs no solver at all.

**What would catch this class instead:** exactly R4's design — compile every
corpus kernel and never run it. Better still, a *dtype × operation matrix* in
Triton's own test suite: for each of the five fp8 names, build each `tl.`
arithmetic op and each reduction once and check the compile either succeeds or
fails with a Python-level message. That is a few hundred compiles and it would
pin all four signatures at once, including the one R4 has not yet filed.

## 6. Confidence

**High that fp8 arithmetic is unsupported and that Triton crashes instead of
saying so.** Read in the source and confirmed by running:

- the fp8→`i8` conversion registration, with all four fp8 types listed;
- `elemTy = convertType(resultElementTy)` in the elementwise base, so operands
  and result are already `i8` when the LLVM float op is built;
- the `POPULATE_OP` list mapping add/sub/mul straight to their LLVM float
  counterparts, with no fp8 branch;
- `CmpFOpConversion::createDestOps` building `LLVM::FCmpOp` on the converted
  operands;
- the contrast with `ArithConstantSplatOpConversion`, which *does* have an
  explicit fp8 branch and a comment explaining why — so the constraint is known
  in the codebase and simply not applied here;
- all three reproductions, each failing in `ConvertTritonGPUToLLVM` after a clean
  TTGIR.

**Medium on one detail of the merge.** For the `packLLElements` symptom
(HIT-0012) I did not pin the exact conversion pattern that hands the packer an
`f8E4M3FN` value; my reading is that it is the `tt.reduce` combine-region
lowering, which clones the region's ops instead of routing them through
`ElementwiseOpConversionBase`, so their fp8 result type survives the conversion.
That is the same fp8-vs-`i8` disagreement and the same fix, but it is inference,
not a line I read. If a maintainer wanted them filed separately that would be
defensible; I merged because one decision ("fp8 arithmetic is unsupported —
reject it in the frontend") deletes all three symptoms at once. What would settle
it: run the HIT-0012 reproduction under a debugger with a breakpoint on
`Utility.cpp:1087` and read the op off the stack.

## Original R4 material

### The exact error

```
<unknown>:0: error: 'llvm.fcmp' op operand #0 must be floating point LLVM type or LLVM dialect-compatible vector of floating point LLVM type, but got 'i8'
<unknown>:0: note: Pipeline failed while executing [`ConvertTritonGPUToLLVM` on 'builtin.module' operation]
```

The offending TTGIR op:

```mlir
arith.cmpf oeq, %arg6, %arg8 : f8E4M3FN     // inside the tt.reduce combine region
```

and, for the merged symptoms:

```mlir
arith.mulf %31, %31 : tensor<1x1xf8E4M3FN, #blocked>          // HIT-0010
arith.addf %arg2, %arg3 : f8E4M3FN                            // HIT-0012
arith.constant dense<0.000000e+00> : tensor<32x32xf8E4M3FN>   // HIT-0012
```

### Kernel and draw

`bch:argmin_kernel_f8fcbf2b`, sm_89, pointer types `inp: *fp8e4nv`,
`out_index: *i1`. The kernel is an argmin: `tl.min(x, axis=0,
return_indices=True)`, whose combine region compares two elements of the input
dtype directly.

### Determinism

Every point is a pure function of (seed, round, kernel index, arch). No GPU, no
random input data, `TRITON_ALWAYS_COMPILE=1` and a private `TRITON_CACHE_DIR`.
Re-running `repro.py` reproduces every time.
