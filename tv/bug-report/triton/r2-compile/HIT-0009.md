# HIT-0009: `Semantic.cast` routes every fp8 conversion to one `tt.fp_to_fp`, and the NVIDIA lowering aborts the process on any pair its table does not hold

Verdict: **CONFIRMED — kept**
Arch:    sm_80, sm_89, sm_90 observed; the mechanism is generic to the NVIDIA backend
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    `assert` failure and `llvm::report_fatal_error` — the process aborts
         (SIGABRT), no diagnostic a user can act on
Culprit: **`python/triton/language/semantic.py:829-832`** (`Semantic.cast` sends
every fp8-involving float cast to a single `tt.fp_to_fp`, with no staging through
f32) together with
**`third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/ElementwiseOpToLLVM.cpp:410-457`
and `:479-491`** (`FpToFpOpConversion`, which aborts instead of emitting an
error)

Input realism: **the fuzzer swapped a pointer dtype** — it drew `*fp8e5` and
`*fp8e4nv` for pointers whose corpus authors used other types. Weigh it lower.
But both failing programs are ones a user can write in two lines
(`tl.load(p_fp8e5).to(tl.float64)`, or store an fp8e5 value through an
`*fp8e4nv` pointer), and the response to an unsupported conversion must be a
message, not `abort()`.

Occurrences: **13** = 3 under the "rounding mode must be specified" assert (this
report) + 10 under the "Unsupported rounding mode for conversion." fatal error
(HIT-0011, rejected as a B4 duplicate — same one-line frontend cause, same
lookup table, see §1). Archs sm_80, sm_89, sm_90; at least 4 distinct kernels
(`bch:special_i1_kernel_7e502f07`, `ind:triton_poi_fused__softmax_4_04f5cb59`,
`bch:mhc_split_sinkhorn_kernel_hcmult_4`, `ind:triton_per_fused_mul_sum_0`).

---

## 1. Root cause in the source

**The frontend emits one `tt.fp_to_fp` for every fp8 conversion, whatever the
other type is.** `python/triton/language/semantic.py:829-832`:

```python
# Casting with customized floating types involved: fp8 <=> bf16, fp16, fp32, fp64
# and non-default rounding modes for downcasting
if (src_sca_ty.is_fp8() and dst_sca_ty.is_floating()) or \
   (src_sca_ty.is_floating() and dst_sca_ty.is_fp8()) or \
   use_custom_rounding:
    return self.tensor(
        self.builder.create_fp_to_fp(input.handle, dst_ty.to_ir(self.builder), fp_downcast_rounding), dst_ty)
```

Compare the branch immediately below it, which *does* stage a hard conversion
through fp32 (`semantic.py:835-837`):

```python
# bf16 <=> (not fp32)
if (src_sca_ty.is_fp16() and not dst_sca_ty.is_fp32()) or \
   (src_sca_ty.is_bf16() and not dst_sca_ty.is_fp32()):
    return self.cast(self.cast(input, tl.float32), dst_sca_ty)
```

fp8 gets no such staging. Everything is handed to the backend as one op.

**The backend has a small fixed table and aborts on a miss.**
`third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/ElementwiseOpToLLVM.cpp:410-445`,
`FpToFpOpConversion::getConversionFunc`, holds exactly eleven `(src, dst,
rounding)` triples:

| direction | pairs in the table |
|---|---|
| fp8 → wider | `f8E4M3FN→f16`, `f8E5M2→f16`, `f8E5M2→bf16`, `f8E4M3FN→bf16` |
| wider → fp8 | `f16→f8E4M3FN` (RTNE), `f16→f8E5M2` (RTNE, RTZ), `bf16→f8E5M2` (RTNE), `bf16→f8E4M3FN` (RTNE), `f32→f8E4M3FN` (RTNE), `f32→f8E5M2` (RTNE) |

There is **no `f64` anywhere**, and **no fp8 → fp8**. A miss is fatal
(lines 449-457):

```cpp
if (srcMap.count(key) == 0) {
  llvm::errs() << "Unsupported conversion from " << srcTy << " to " << dstTy;
  ...
  llvm::report_fatal_error("Unsupported rounding mode for conversion.");   // line 456
}
```

**Two ways the same hole is reached.** They are the two signatures R4 filed
separately:

*Symptom A — fp8 → fp8 (this report).* `Semantic.cast` sets a rounding mode only
for a *narrowing* float conversion, `semantic.py:813-816`:

```python
if dst_sca_ty.is_floating() and src_sca_ty.is_floating() \
        and dst_sca_ty.primitive_bitwidth < src_sca_ty.primitive_bitwidth:
    if fp_downcast_rounding is None: fp_downcast_rounding = ir.ROUNDING_MODE.RTNE
```

fp8 → fp8 is 8 bits to 8 bits, so the strict `<` is false and **no rounding mode
is attached**. In the backend, `createDestOps` then trips its own assert first
(`ElementwiseOpToLLVM.cpp:479-482`):

```cpp
if (llvm::isa<Float8E5M2Type, Float8E4M3FNType>(dstElementType)) {
  assert(roundingMode.has_value() &&
         "Rounding mode must be specified for convertsions to fp8");
```

Observed: `bch:special_i1_kernel_7e502f07` with `x_ptr: *fp8e5` and
`out_ptr: *fp8e4nv`; the failing op is
`tt.fp_to_fp %55 : tensor<512xf8E5M2, ...> -> tensor<512xf8E4M3FN, ...>` with no
`rounding =` attribute. Note that even with a rounding mode this would still
miss the table — there is no fp8 → fp8 entry — so the assert is an early trip on
the same absence.

*Symptom B — fp8 → f64 (merged HIT-0011).* No rounding mode is involved and the
lookup simply misses, so line 456 fires. Observed:
`ind:triton_poi_fused__softmax_4_04f5cb59` with `in_ptr1: *fp64` and
`in_ptr2: *fp8e5`; the division `tmp3 / tmp4` promotes the fp8e5 operand to f64
and builds `tt.fp_to_fp %15 : tensor<64xf8E5M2, ...> -> tensor<64xf64, ...>`.
The compiler prints `Unsupported conversion from f8E5M2 to f64` and aborts.

**Why these are one class.** Same one-line frontend decision
(`semantic.py:829-832` hands the backend an unstaged fp8 conversion), same
missing-table-entry mechanism, same abort-instead-of-diagnose response, and the
same fix at the frontend: stage fp8 conversions through f32 exactly as the
fp16/bf16 branch below already does. `fp8e5 → f64` becomes `fp8e5 → f32 → f64`,
both of which the table has; `fp8e5 → fp8e4nv` becomes `fp8e5 → f32 → fp8e4nv`
with RTNE, both of which the table has. A second, independent fix is needed
regardless: replace the `assert` and the `report_fatal_error` with
`op.emitError()` so an unsupported pair produces a message instead of killing the
process.

## 3. Where it reproduces

**Every NVIDIA target.** The judgement rests on:

- `Semantic.cast` is target-independent, so the unstaged `tt.fp_to_fp` is built
  on every backend.
- The table and both abort sites are in `third_party/nvidia/`, so the specific
  abort text is NVIDIA-only. AMD has its own `FpToFpOpConversion`; not tested.
- The table's contents vary a little with compute capability (some entries pick a
  different PTX sequence for `>= 89` or `>= 90`), but the *keys* do not — no
  capability adds an fp8→fp8 or an fp8→f64 entry. So the miss happens on every
  capability, which matches R4 seeing the merged class on sm_80, sm_89 and sm_90.
- The failing IR uses **no** Hopper-only construct — no wgmma, no TMA, no
  mbarrier, no cluster, no warp specialization. It is `tt.fp_to_fp` on a
  blocked-layout tensor.
- There is a separate, *correct* diagnostic right below the fatal error, for
  fp8e4m3nv below sm_89 (`ElementwiseOpToLLVM.cpp:458-462`). So the file already
  knows how to report an unsupported conversion — it just does not do it for a
  table miss.

## 4. Plain-language explanation

Triton has several 8-bit float formats. Converting one to a normal float, or the
other way, is done by a short list of hand-written GPU instruction sequences —
one entry per (from, to, rounding) combination.

The list covers 8-bit float against 16-bit and 32-bit floats. It does not cover
8-bit float against 64-bit float, and it does not cover one 8-bit float format to
another.

The Python layer does not know that. It happily builds "convert this 8-bit float
straight to a 64-bit float" as a single step. The backend looks it up, does not
find it, and calls `report_fatal_error`, which kills the compiler process with no
line number and nothing the user can fix.

The right answer is easy: go through 32-bit float in the middle, which is exactly
what Triton already does for 16-bit float conversions it cannot do directly. And
when a conversion really is unsupported, say so instead of aborting.

## 5. SMT reachability analysis

**Outside the equivalence question for the crash — but this entry has the most
interesting value-level shadow of the batch, and that one is squarely
`needs bit-exact FP`.**

1. **Root cause in semantic terms.** The construct is `tt.fp_to_fp` with an
   optional `rounding` attribute, on tensors of `f8E5M2`, `f8E4M3FN` and `f64`.
   The semantic error is that the frontend produced a conversion the backend has
   no rule for, and the backend responded by aborting rather than by reporting.
2. **Is the difference a pure input→output function difference?** No difference
   exists — the process dies. Nothing depends on runtime inputs, scheduling, or
   hardware.
3. **Fundamental verdict.** **Outside the equivalence question** as observed.
   But consider the fix: staging `fp8e5 → f32 → f64` in place of a direct
   `fp8e5 → f64`. Is that transformation sound? *That* is a genuine equivalence
   question, and the answer determines whether the obvious fix is correct. Its
   label is **`needs bit-exact FP`**: the claim "converting through f32 loses
   nothing" is true here only because f32 has more mantissa bits and a wider
   exponent range than f8E5M2, so the first step is exact — and an abstract,
   uninterpreted-function model of conversion cannot tell an exact widening from
   a lossy one. For the other direction it is *not* free: `f32 → fp8e5` staged as
   `f32 → f16 → fp8e5` rounds twice and can differ from a single rounding
   (classic double-rounding), which is exactly the kind of thing a bit-exact
   checker exists to catch.
4. **Minimum semantic vocabulary required.** For the crash: nothing. For the
   staging question: IEEE-754 semantics at four widths (8, 16, 32, 64 bits) with
   the correct fp8 variants — `f8E5M2` and `f8E4M3FN` differ in exponent bias and
   in what they do with the all-ones exponent — plus rounding modes as explicit
   parameters (RTNE, RTZ), plus subnormal and saturation behaviour, which is
   where the 8-bit formats differ most from each other.
5. **Would the abstraction hide it?** Yes, completely, under the
   reassoc-allowed / uninterpreted-function profile: `convert(x)` as an opaque
   function is the same term no matter what width it passes through, so a checker
   would "prove" the double-rounded path equal to the single-rounded one. Only
   the **exact bit-to-bit** profile can distinguish them. This is a good concrete
   example of a bug class where the cheap FP profile is not merely weaker but
   actively misleading.
6. **Inherent cost.** Zero for the crash. For the staging question the cost is
   negligible and no solver is needed at all: fp8 has 256 values, so
   `for x in range(256): check(direct(x) == staged(x))` decides the fp8→wider
   direction exhaustively. Only the wider→fp8 direction is large (2³² inputs for
   f32), and even there a solver handles single-instruction float conversion
   easily.

**What would catch this class instead:** the same dtype × dtype cast matrix
proposed in HIT-0007 — 19 dtypes, 342 ordered pairs, compile each and check for
either success or a clean Python-level error. That single test finds every gap in
this eleven-entry table at once, and it is cheap enough to run in CI. R4 found
two of the gaps by random draw; the matrix finds all of them.

## 6. Confidence

**High that both conversions are unsupported and that Triton aborts instead of
reporting.** Read in the source and confirmed by running:

- the table's eleven keys, containing no `f64` and no fp8→fp8 entry;
- `semantic.py:813-816`, whose strict `<` on bit width means fp8→fp8 gets no
  rounding mode;
- `semantic.py:829-832`, which hands the backend the unstaged conversion, in
  contrast to the fp16/bf16 branch three lines below that stages through f32;
- the assert at line 482 and the `report_fatal_error` at line 456;
- the printed `Unsupported conversion from f8E5M2 to f64`, which names the exact
  missing pair;
- both reproductions, each failing in `ConvertTritonGPUToLLVM` after a clean
  TTGIR.

**Medium on the merge.** A maintainer could reasonably want two tickets: "add
fp8→fp8" and "add fp8→f64" are two table entries. I merged them because they
share one frontend cause (`semantic.py:829-832` not staging through f32) and
because one frontend change fixes both without touching the table at all. If
upstream instead chooses to extend the table, the two become separate work items
— but the abort-instead-of-diagnose defect is still single and still shared.

Remaining doubt on a detail: for symptom A I did not verify by experiment that
the fp8→fp8 conversion would *also* miss the table if a rounding mode were
present. That follows from reading the eleven keys (none has an fp8 source and an
fp8 destination), but it is inference. A release build with `NDEBUG`, where the
assert vanishes, would show the `Unsupported conversion from f8E5M2 to f8E4M3FN`
message and settle it.
