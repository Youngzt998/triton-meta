# HIT-0001: PlanCTA gives a reduction a CGA layout with `num_ctas²` CTAs, so the pass emits invalid IR

Verdict: **CONFIRMED — kept**
Arch:    hopper-only (sm_90; `num_ctas > 1` needs Hopper clusters)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    invalid IR emitted by a pass (MLIR verifier error)
Culprit: **`TritonGPUPlanCTAPass`** — `lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp`, `CTAPlanner::processReduce`

Input realism: **the kernel keeps its own pointer dtypes.** Nothing about the
program is synthetic. The only unusual thing a user has to do is pass
`num_ctas=2`.

Occurrences: **23** = 15 under the `#ttg.slice<...>` signature (this report)
+ 8 under the `#ttg.blocked<...>` signature (HIT-0013, rejected as a B4
duplicate — same root cause; the two signatures differ only in whether the first
tensor the verifier reaches carries a slice or a blocked layout). sm_90 only,
across at least 6 distinct kernels (`bch:logsumexp_kernel_non_inner`,
`bch:_complete_svd_factor_kernel`, `ind:triton_unk_fused_amax_sum_0`,
`ind:triton_per_fused_native_layer_norm_native_layer_norm_backward_0`,
`bch:median_f16_strided_key_select_kernel`,
`bch:_cp_gather_indexer_quant_cache_kernel`).

---

## 1. Root cause in the source

`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp`, `CTAPlanner::processReduce`,
lines **294–325**. The pass picks how the CTAs of one CGA (cluster) are spread
over the axes of a `tt.reduce`. It does that in three steps, and the leftover
CTA count is applied **twice**:

```cpp
llvm::SmallVector<unsigned> CTAsPerCGA(rank, 0);
unsigned remainingCTAs = numCTAs;                       // line 296
for (int i = rank - 1; i >= 0; --i) {                   // step 1: fill each axis
  unsigned dim = order[i];
  if (dim == axis) {
    CTAsPerCGA[dim] = 1;                                // reduced axis gets 1
  } else {
    CTAsPerCGA[dim] = std::min<unsigned>(srcShape[dim] / sizePerThread[dim],
                                         remainingCTAs);
    remainingCTAs /= CTAsPerCGA[dim];                   // line 305
  }
}

for (int i = rank - 1; i >= 0; --i) {                   // step 2: put the
  unsigned dim = order[i];                              // leftover on the first
  if (dim != axis) {                                    // non-reduced axis
    CTAsPerCGA[dim] *= remainingCTAs;                   // line 312  <-- applied
    break;                                              //              once
  }
}

llvm::SmallVector<unsigned> CTASplitNum = CTAsPerCGA;

// If numCTAs > 1 and the only dimension is the reduced dimension, the
// loops above leave all CTAs unassigned. Put the remaining CTAs on that
// dimension so that they all collaborate in the reduction.
if (remainingCTAs > 0) {                                // line 320  <-- WRONG
  CTAsPerCGA[order[rank - 1]] *= remainingCTAs;         // line 321  applied
  CTASplitNum[order[rank - 1]] = CTAsPerCGA[order[rank - 1]];  //     AGAIN
}
```

**The bug is the guard on line 320.** `remainingCTAs` is an unsigned *count* of
CTAs, not a flag. After step 1 it is `>= 1` whenever the divisions came out even
— the normal case, because CTA counts are powers of two. The comment says the
block is for the case where "the loops above leave all CTAs unassigned", but
`remainingCTAs > 0` is true in that case **and** in the ordinary case where step
2 has already consumed the leftover. So step 2 multiplies one axis by
`remainingCTAs`, and then step 3 multiplies another axis by `remainingCTAs`
again.

Result: `product(CTAsPerCGA) == numCTAs * remainingCTAs`. When step 1 could place
nothing — every non-reduced axis has extent 1, which is exactly what a
`keep_dims=True` reduction produces — `remainingCTAs == numCTAs`, so the product
is **`numCTAs²`**.

Measured, on the minimal input `HIT-0001/plan-cta-min.mlir`:

| `ttg.num-ctas` | CTAs in the layout PlanCTA produced |
|---|---|
| 2 | 4 |
| 4 | 16 |
| 8 | 64 |

That layout is written into the IR by `insertCasts` and propagated to every
tensor the reduction touches, so the module fails verification at the end of the
pass:

```
error: Result has an invalid layout: #ttg.slice<{dim = 1, parent = #ttg.blocked<{
         sizePerThread = [1, 1], threadsPerWarp = [32, 1], warpsPerCTA = [4, 1],
         order = [1, 0], CGALayout = [[1, 0], [0, 1]]}>}>.
       Layout has 4 CTAs per CGA, but the context requires 2 CTAs per CGA.
```

The guard the code wants is "did steps 1 and 2 place nothing", i.e. a test on
`product(CTAsPerCGA) == 1` — or simply set `remainingCTAs = 1` once step 2
consumes it.

## 3. Where it reproduces

**Any NVIDIA target that accepts `num_ctas > 1`, i.e. sm_90 and later.** The
judgement rests on three things:

- `PlanCTAPass::runOnOperation` returns immediately when `getNumCTAs(mod) == 1`
  (PlanCTA.cpp:986). With the default `num_ctas=1` the pass never runs at all,
  which is why this has stayed hidden.
- The failing IR contains **no** Hopper-only construct — no wgmma, no TMA, no
  mbarrier, no cluster op, no warp specialization. It is a plain `tt.reduce` on a
  blocked layout. The arch dependence comes only from clusters (CGAs) being a
  Hopper feature, which is what gates `num_ctas > 1` in the first place.
- The arithmetic is on `unsigned` counts and `processReduce` makes no target
  query, so nothing in it can behave differently on sm_100.

R4 observed the class on sm_90 only, but it swept sm_80/sm_89/sm_90a and
`num_ctas > 1` is rejected before this pass on the first two. "sm_90 only" is
what the sweep *could* observe, not a property of the bug.

## 4. Plain-language explanation

With `num_ctas=2` you ask for a cluster of two thread blocks that work together
on one tile. The compiler has to decide how to split the tile across those two
blocks.

For a reduction it splits along the axes that are *not* being reduced. It does
this in two goes: first give each axis as many blocks as it can use, then put
whatever is left over on one axis. But it then runs a third piece of code that
was meant only for the special case "nothing got placed at all" — and that third
piece puts the leftover on an axis **a second time**. So the compiler ends up
describing a cluster of four blocks when you asked for two.

Nothing checks this until the end of the pass, where MLIR's verifier notices the
mismatch and compilation stops. The compiler contradicted itself; the user's
program is fine.

## 5. SMT reachability analysis

**Not applicable in the equivalence sense — and that is the useful answer.**

1. **Root cause in semantic terms.** The constructs are `tt.reduce` and a
   `#ttg.blocked` / `#ttg.slice` layout attribute carrying a `CGALayout`. The
   error is not in any value computation: the pass wrote a layout *attribute*
   whose CTA count disagrees with the module's `ttg.num-ctas` attribute. It is an
   internal consistency error in metadata, not a wrong value.
2. **Is the difference a pure input→output function difference?** There is no
   difference at all — compilation stops, so one side of the comparison does not
   exist and an equivalence checker has nothing to compare. Note also that the
   kernel's runtime inputs play no part: the fault is a pure function of
   (shape, `num_ctas`, layout), all known at compile time.
3. **Fundamental verdict.** None of the six labels fits cleanly, and saying so is
   more useful than forcing one. It is not `below the IR level` — the fault *is*
   in the IR. The honest label is **outside the equivalence question**: an SMT
   equivalence check compares two programs, and here the second program was never
   produced. Even a perfect model of tensor semantics would be asked "prove
   A ≡ B" and handed only A.
4. **Minimum semantic vocabulary required.** If one insists on an SMT framing,
   the property is not equivalence but **well-formedness**: "for every tensor
   type in the module, the CTA count implied by its layout attribute equals
   `ttg.num-ctas`." Expressing that needs layouts as first-class objects (index
   maps from (CTA, warp, lane, register) to tensor coordinates) plus
   quantification over all typed values in a module. That is a type-system
   property, and MLIR already has the right checker for it — the verifier, which
   did catch it. The gap is not detection power; the gap is that nobody runs the
   pass.
5. **Would the abstraction hide it?** The FP axiom profile is irrelevant: no
   floating-point value takes part in the fault. An uninterpreted-function FP
   encoding would hide nothing here, and an exact bit-to-bit encoding would add
   nothing.
6. **Inherent cost.** Zero solver cost. The check is a linear walk over the
   module's types.

**What would catch this class instead, cheaply:** exactly what R4 does — compile
the corpus with `num_ctas ∈ {2,4,8}` and `--verify-each`, and run nothing. 23
occurrences across 6+ kernels turned up in minutes of CPU time. A `num_ctas > 1`
row in Triton's own lit matrix would have caught it long ago; `PlanCTA.cpp` ends
with a TODO list whose last line is literally "Add some lit tests for this pass."

## 6. Confidence

**High.** Every step was read in the source and then measured:

- The double application was traced by hand through lines 296–322 and then
  confirmed by experiment — the produced CTA count is `numCTAs²` for
  `numCTAs ∈ {2,4,8}` on a 12-line input whose only content is one `tt.reduce`.
- The culprit pass is pinned by running that single pass alone.
- Both controls (`num_ctas=1`; no reduce) pass.
- The `numCTAs²` prediction independently explains the *other* signature
  (HIT-0013: `num_ctas=4`, layout with 16 CTAs), which R4 had filed as a separate
  class.

Remaining doubt is about **scope, not about the bug**: I did not check whether a
later pass would have repaired the layout had the verifier not stopped first —
i.e. whether `num_ctas>1` compilations that *do* survive are getting a silently
wrong CTA split rather than a hard error. That matters, because a wrong-but-valid
split would be a silent wrong-answer bug rather than a compile failure. The
experiment that settles it: build a `num_ctas=2` reduction kernel that does not
trip the verifier, run it, and compare against `num_ctas=1`. That needs a Hopper
GPU, which this line does not have.

### Kernel source

```python
@triton.jit
def logsumexp_kernel_non_inner_baaf36b4(output_ptr, input_ptr, M, N, K,
                                        TILE_N: tl.constexpr, TILE_K: tl.constexpr,
                                        ONE_TILE_PER_CTA: tl.constexpr):
    """Kernel for logsumexp when reduction dimension is not the innermost."""
    pid_m = ext_baaf36b4.program_id(0)
    pid_k = ext_baaf36b4.program_id(1)
    k_offsets = pid_k * TILE_K + tl.arange(0, TILE_K)[None, :]
    if ONE_TILE_PER_CTA:
        n_offsets = tl.arange(0, TILE_N)[:, None]
        inp_offset = pid_m * N * K + n_offsets * K + k_offsets
        mask = (n_offsets < N) & (k_offsets < K)
        input_ptrs = input_ptr + inp_offset
        inp = tl.load(input_ptrs, mask=mask, other=-float('inf')).to(tl.float32)
        m = tl.max(inp, axis=0, keep_dims=True)
        safe_m = tl.where(m == float('-inf'), tl.zeros_like(m), m)
        e = tl.exp(inp - safe_m)
        z = tl.sum(e, axis=0, keep_dims=True)
        out = safe_m + tl.log(z)
        out = tl.where(m == float('-inf'), m, out)
        out_offset = pid_m * K + k_offsets
        output_ptrs = output_ptr + out_offset
        tl.store(output_ptrs, out, mask=k_offsets < K)
    else:
        ...   # not taken: ONE_TILE_PER_CTA is truthy in this draw
```

`keep_dims=True` is what makes the non-reduced axis have extent 1, which is what
leaves `remainingCTAs == numCTAs` going into the buggy block.

### Determinism

Every point is a pure function of (seed, round, kernel index, arch). No GPU, no
random input data, `TRITON_ALWAYS_COMPILE=1` and a private `TRITON_CACHE_DIR`.
Re-running `repro.py` reproduces every time.
