# HIT-0045: PlanCTA reuses the first store's CGA layout on a store of a different rank, and the compiler aborts

Verdict: **CONFIRMED — compiler crash** (assertion / `PassManager::run failed`)
Arch:    **sm_90 only in practice** — the pass returns immediately when
         `num_ctas == 1`, and `num_ctas > 1` (Hopper thread-block clusters) is
         gated to sm_90+. The mistake itself is target-independent.
Line:    r2-compile (R4, compile-only, no GPU)
Culprit: `TritonGPUPlanCTAPass`
         (`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp`)
Class:   R4 `crash-assert`, rule `F2`, signature
         `assert@StorageUniquerSupport.h:180:succeeded( ConcreteT::verifyInvariants(...))`
Occurrences: 2 at the time of review.
Review:  **KEPT** under REVIEW-CRITERIA §2, last bullet ("compile failure,
         crash, or invalid generated code — keep it").
SMT verdict: **not applicable / out of scope** — a compile-time crash, not a
         value difference.

## What goes wrong, in one sentence

A kernel with two `tt.store`s of **different tensor rank** compiled with
`num_ctas > 1` aborts, because `PlanCTA` takes the CTA (CGA) layout of the
*first* store and then reuses that same layout — with its own rank — when it
rebuilds the layout of every later store.

---

## 1. Root cause in the source

`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp`,
`CTAPlanner::processStoreLikeOps`, lines 350–385:

```cpp
  ttg::CGAEncodingAttr CGALayout;
  for (Operation *store : stores) {
    ...
    if (auto tensorTy = dyn_cast<RankedTensorType>(val.getType())) {
      if (!tiled) {
        // Use CTA tiling of the first store-like op as global CTA tiling
        CGALayout = ttg::getCGALayout(tensorTy.getEncoding());   // line 373
        markTiled();
      }
      auto newLayout = replaceCGALayout(
          cast<ttg::DistributedEncodingTrait>(tensorTy.getEncoding()),
          tensorTy.getShape(), numWarps, CGALayout);             // line 376-378
      processElementwise(store, newLayout);
    }
  }
```

`CGALayout` is captured **once**, from the first store that has a tensor type
(line 373), and then handed to `replaceCGALayout` for **every** store (line
378). A `CGAEncodingAttr` is a per-dimension object: its fields have exactly the
rank of the tensor it came from. `replaceCGALayout` at line 70 then does

```cpp
    return ttg::BlockedEncodingAttr::get(
        layout.getContext(), shape, blockedLayout.getSizePerThread(),
        blockedLayout.getOrder(), numWarps, 32, newCGALayout);
```

with `shape` = the *second* store's shape. When the two stores have different
ranks, `BlockedEncodingAttr`'s own verifier fires:

```
error: BlockedEncodingAttr and CGALayout's fields must have the same rank.
Assertion `succeeded(ConcreteT::verifyInvariants(...))' failed.
```

The loop never checks that the later stores have the same rank as the first, and
it never rebuilds a rank-matched CGA layout for them. Nothing else in the
function guards it; `getCGALayout` is read once into a local and reused.

Symbolised stack from `triton-opt` (innermost first):

```
#10 mlir::triton::gpu::BlockedEncodingAttr::get(MLIRContext*, ArrayRef<long>,
        ArrayRef<unsigned>, ArrayRef<unsigned>, unsigned, unsigned,
        CGAEncodingAttr)                                  AttrDefs.cpp.inc:1008
#15 (anonymous namespace)::replaceCGALayout(...)          PlanCTA.cpp:70
#16 (anonymous namespace)::CTAPlanner::processStoreLikeOps(FuncOp&)
                                                          PlanCTA.cpp:379
#17 CTAPlanner::run(FuncOp&)                              PlanCTA.cpp:174
#20 PlanCTAPass::runOnOperation()                         PlanCTA.cpp:1001
```

**This is a different mistake from the already-kept `r2-corpus/HIT-0037`.**
That one is `replaceCGALayout` recursing into a `SliceEncodingAttr`'s *parent*
at line 77 while passing the slice's own (smaller) shape, and it dies inside
`SmallVector` before any verifier runs. Here there is no slice and no recursion:
`replaceCGALayout` is called once, directly, from line 379, and the rank
mismatch is between the caller's `shape` and the **cached** CGA layout. Fixing
one does not fix the other.

The corpus kernel that hits it,
`bch:_cp_gather_indexer_quant_cache_kernel_d5cecde2`, has exactly two stores:

```mlir
tt.store %86, %87, %88 : tensor<1x!tt.ptr<f32>, #blocked>          // rank 1
tt.store %104, %105, %106 : tensor<1x64x!tt.ptr<i8>, #blocked5>    // rank 2
```

with `#blocked` carrying `CGALayout = [[0], [0], [0]]` (rank 1) and `#blocked5`
carrying `CGALayout = [[0, 1], [0, 2], [0, 4]]` (rank 2). The rank-1 layout of
the first store is what the rank-2 store is rebuilt with.

## 3. Where it reproduces

* **Any target where `num_ctas > 1` is allowed**, i.e. sm_90 and later. It is
  not a Hopper *feature* bug: the failing code touches no wgmma, TMA, mbarrier
  or warp-specialization construct — only `BlockedEncodingAttr` and
  `CGAEncodingAttr`, which are generic TritonGPU layout attributes. The only
  reason it cannot be seen below sm_90 is that `num_ctas > 1` is rejected
  earlier there, and `PlanCTAPass` short-circuits at `num_ctas == 1`.
* **Any kernel with two or more store-like ops of different tensor rank**
  (`tt.store`, `tt.atomic_rmw`, `tt.atomic_cas`, or a descriptor store). That is
  an ordinary shape — a reduction that writes both a per-row vector and a
  per-row-per-column tile hits it. The minimal file in (a) contains nothing else.
* It needs an assertions-enabled build to `abort()` at the assert; in a release
  build the verifier still rejects the attribute, so the pipeline still fails —
  with the diagnostic instead of a crash.

## 4. Plain-language explanation

When a kernel runs with more than one thread block per cluster, Triton has to
decide how to split each tensor across the blocks of the cluster. It makes that
decision by looking at the kernel's stores. The code takes the splitting rule
from the **first** store it finds and then applies that same rule to all the
other stores. A splitting rule has one entry per dimension. So if the first
store writes a 1-D tensor and a later store writes a 2-D tensor, the 2-D store
is handed a 1-D rule, the shapes do not line up, and the compiler stops with an
internal assertion instead of a message the user can act on.

## 5. Can an SMT solver model this?

**No — out of scope, and not because of any modelling limit.** This is a
compile-time crash: the pass never produces a second module, so there is no
equivalence question to pose.

It is worth being precise about *what kind* of property it is, because that
bounds what an equivalence checker could ever do here. The bug is a **rank
invariant inside the compiler's own data structure** (a `BlockedEncodingAttr`'s
rank must equal its `CGAEncodingAttr`'s rank), broken by a pass. That is a
static well-formedness property of the IR the pass builds, not a property of the
values a program computes. MLIR's verifier already states it and already catches
it; the defect is that Triton reaches it through `assert` instead of returning a
diagnostic. A solver reasoning over program values would never look at it. The
right tools are the ones already in the tree: a lit test with two
different-rank stores at `num_ctas > 1`, and `getChecked` rather than `get` at
`PlanCTA.cpp:70`.

## 6. Confidence

**High.** The 13-line hand-written input isolates the mechanism with nothing
else in it: two stores, different rank, `num_ctas > 1`. The stack names the call
site (`PlanCTA.cpp:379` → `:70`), line 373 plainly caches one CGA layout for the
whole loop, and the `num_ctas = 1` control passes.

What is **not** settled: whether the intended fix is to rebuild a rank-matched
CGA layout per store, or to declare mixed-rank stores unsupported and emit a
proper error — I did not write a fix, so I cannot say which the maintainers
want. Also unknown is whether the same cached-`CGALayout` loop can produce a
*silently wrong* layout (rather than a crash) when the ranks match but the split
does not; that would be a wrong-answer bug behind the same lines and needs its
own experiment.

`PlanCTA.cpp` has no lit tests at all (the file's closing TODO list ends with
"Add some lit tests for this pass"), which is why this class keeps turning up.
This is the seventh distinct `num_ctas > 1` defect in the campaign: `r2-compile`
HIT-0001, 0003, 0005, 0006, 0019 and this one in `PlanCTA`, plus HIT-0016 in the
scan lowering and HIT-0038 in the default layout assignment, with
`r2-oracle/HIT-0001` as the silent-wrong-answer member of the family.
