# HIT-0063: an `fp8e4b15` dot operand at `num_ctas > 1` carries a CTA-split CGA layout into the wgmma shared-memory operand, and the descriptor builder asserts `block == 0`

Verdict: **CONFIRMED — kept**
Arch:    Hopper only (sm_90/sm_90a), and only at `num_ctas >= 2`
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    hard crash — `assert` / `abort()` in the TTGIR→LLVM lowering.
         Under `NDEBUG` the assert is gone and the pass silently builds a
         shared-memory descriptor that ignores the CTA index.
Culprit: **`lib/Dialect/TritonGPU/Transforms/AccelerateMatmul.cpp:192`**
         copies the register tensor's CGA layout into the wgmma operand's
         shared-memory allocation;
         **`third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/DotOpToLLVM/MMAHelpers.h:171`**
         is where it is detected, with `assert(block == 0)`.
Pass:    `ConvertTritonGPUToLLVM` (stage `llir`)
Oracle:  R4 compile-only (`crash-assert`, classifier rule `F2`)
SMT verdict: no — a lowering crash, not a value difference; and the thing that
         goes wrong is a *layout* fact, which sits below the value semantics an
         IR-level checker compares (§5)

Input realism: the fuzzer swapped one pointer dtype to `*fp8e4b15`. Weigh the
*draw* lower — but note two things. `fp8e4b15` is a type Triton still accepts and
only *warns* about ("deprecated on Hopper and later"), and the minimal
reproducer below is 16 lines of hand-written TTGIR with **no fp8 at all**: it is
a plain f16 wgmma whose shared operand has a non-trivial CTA dimension. The fp8
type is only how the fuzzer reached that layout, not what the bug is about.

Occurrences: **2**, both sm_90. De-duplication signature:
`assert@MMAHelpers.h:171:block == N`.

**Distinct from the classes already kept.** It is not one of the seven
`PlanCTA` defects (`HIT-0001/0003/0005/0006/0019/0045/0049` — different file,
different pass, PlanCTA runs to completion here), not `HIT-0016` (the scan
lowering), not `HIT-0038` (a rank-changing `tt.reshape`; there is no reshape
here), and not the fp8-is-storage-only family
(`HIT-0002/0004/0007/0008/0009` — those build float arithmetic on `i8`; here the
software fp8 conversion is emitted correctly and the crash is about CTA
addressing). `r2-compile/HIT-0062` is the **same** defect reached at a second
lowering site; it is folded into this report under B4.

## 1. Root cause in the source

### The chain

The kernel is an inductor `triton_mm`. Its `B` operand pointer is
`*fp8e4b15`, which Triton stores as `i8` and converts to `f16` in software.
That single fact changes which path the operand takes into the tensor core:

1. **The `i8` global load gets a CTA-split blocked layout.** The default CGA
   layout assignment (already present before `TritonGPUCoalesce`) gives the load
   `#ttg.blocked<{..., CGALayout = [[1, 0]]}>` — dimension 0 (the `K` axis, 32
   rows) is split across the 2 CTAs of the CGA. The `A` operand, a real
   `fp8e4nv`, gets `CGALayout = [[0, 0]]` — no split.

2. **The software conversion keeps that layout.** `fp8e4b15 -> f16` is a
   `tt.elementwise_inline_asm`, so the converted `f16` tensor stays in registers
   with the same `#blocked1`:

   ```mlir
   %99  = ttg.local_load %98 : !ttg.memdesc<32x256xi8, #shared1, #smem, mutable>
                             -> tensor<32x256xi8, #blocked1>
   %101 = tt.elementwise_inline_asm "..." %99
            : tensor<32x256xi8,  #blocked1> -> tensor<32x256xf16, #blocked1>
   ```

3. **`TritonGPUAccelerateMatmul` copies the CGA layout into shared memory.**
   To feed wgmma it must put that `f16` tensor back into shared memory, and it
   builds the shared layout from the *register* layout:

   ```c++
   // lib/Dialect/TritonGPU/Transforms/AccelerateMatmul.cpp:190-199
   //   getSharedMemoryMMAOperand(...)
   auto CGALayout = getCGALayout(argType.getEncoding());     // <-- [[1, 0]]
   auto newLayout = NVMMASharedEncodingAttr::get(
       argType.getContext(), argType.getShape(), newOrder, CGALayout,
       argType.getElementType(), isMMAv5Fp4Padded);
   ...
   return LocalAllocOp::create(rewriter, arg.getLoc(), newType, arg);
   ```

   The result, confirmed by `MLIR_ENABLE_DUMP` (first module that contains it is
   the one dumped *before* `TritonNvidiaGPUCheckMatmulTwoCTAPass`, i.e. the pass
   immediately before it produced it):

   ```mlir
   #shared2 = #ttg.nvmma_shared<{swizzlingByteWidth = 32, transposed = true,
                                 elementBitWidth = 16, CGALayout = [[1, 0]]}>
   %102 = ttg.local_alloc %101 : (tensor<32x256xf16, #blocked1>)
                               -> !ttg.memdesc<32x256xf16, #shared2, #smem>
   %103 = ttng.warp_group_dot %100, %102, %arg6 {isAsync = true} : ...
   ```

4. **The wgmma descriptor cannot express a CTA index, so the lowering asserts.**

   ```c++
   // third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/DotOpToLLVM/MMAHelpers.h:167-172
   auto offsetBlock = ll.apply({{dims[0], a}, {dims[1], b}});
   int32_t offsetElems = offsetBlock[0].second;
   int32_t block       = offsetBlock[1].second;
   assert(block == 0);
   int32_t smemByteOffsetb8 = offsetElems * desc.bitwidth / 8;
   ```

   A Hopper wgmma shared-memory descriptor is a 64-bit word holding a base
   address inside **this CTA's** shared memory, a leading/stride byte offset and
   a swizzle mode. There is no field for "which CTA of the cluster". So a shared
   layout whose `block` component is non-zero cannot be encoded at all, and
   `smemLoad` gives up with an assert.

### Which step is wrong

Step 3. `getSharedMemoryMMAOperand` builds an operand that the only consumer of
that operand — `DotOpMmaSmemLoader` — provably cannot address. It should either
drop the CTA split (allocate the wgmma operand with a 1-CTA CGA layout and let
the `local_alloc` do the cross-CTA movement) or refuse the pattern with a
diagnostic. Copying the split through is the one thing that cannot work.

### The `NDEBUG` half, which is worse than the crash

`assert` is compiled out of a release build. Then `smemLoad` keeps going and
builds the descriptor from `offsetElems` **alone**, dropping the `block`
component of the address. Every CTA in the cluster would read its own shared
memory at the same offset instead of the CTA the layout named — silently wrong
data from a build that produced no diagnostic at all. This is the same shape as
the `PlanCTA.cpp:242` note in `REVIEW.md`.

### The same condition at a second site — why `HIT-0062` folds in here

The `cp.async` lowering meets the same non-trivial `block` dimension and *does*
check for it:

```c++
// third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/LoadStoreOpToLLVM.cpp:1052-1057
auto smemLayout = ttg::toLinearLayout(dstTy);
auto cvt = srcLayout.invertAndCompose(smemLayout);
if (!cvt.isTrivialOver({str_attr("block")})) {
  return emitError(loc, "cp.async does not support non-trivial block dimension");
}
```

One condition, two sites, one pass (`ConvertTritonGPUToLLVM`), and which one you
hit depends only on which operand carries the split. Measured by flipping one
pointer dtype and nothing else, at `num_ctas = 2`:

| `arg_A` / `arg_B` | result |
|---|---|
| `*fp16` / `*fp16` | **compiles** |
| `*fp8e4nv` / `*fp8e5` | **compiles** |
| `*fp8e4nv` / `*fp8e4b15` | `assert(block == 0)`, `MMAHelpers.h:171` — this report |
| `*fp8e4b15` / `*fp8e4b15` | `cp.async does not support non-trivial block dimension` — `HIT-0062` |

And along `num_ctas`, holding the dtypes of this report's draw:

| `num_ctas` | result |
|---|---|
| 1 | compiles |
| 2 | `assert(block == 0)` — `MMAHelpers.h:171` |
| 4 | `assert(getReps(ll, shmemTileInv).has_value())` |
| 8 | `error: failed to find valid wgmma layout for operand B in shared memory` |

Four different messages, one condition. R4's signature grouping splits them into
four classes; they are one defect.

## 2. Reproduction

**(a) The 16-line hand-written TTGIR — no fp8, no kernel, no GPU, two
`triton-opt` passes.**

The file is a `ttng.warp_group_dot` whose `B` operand is a `ttg.memdesc` with
`#ttg.nvmma_shared<{..., CGALayout = [[1, 0]]}>` in a `"ttg.num-ctas" = 2`

```bash
            --convert-triton-gpu-to-llvm='compute-capability=90 ptx-version=88' \
            /tmp/good.ttgir -o /dev/null    # rc 0
```

That one-attribute control is the strongest single piece of evidence for §1: the
CTA split in the wgmma operand's shared layout is the whole trigger.

`triton_mm-nc2.ttgir` is the module the crashing pass was handed, lifted out of

## 3. Where it reproduces

**Hopper (sm_90 / sm_90a) only, and only at `num_ctas >= 2`.** The failing IR is
Hopper-specific by construction:

* the crashing code is in `third_party/nvidia/.../DotOpToLLVM/MMAHelpers.h`, the
  builder for the **wgmma** shared-memory descriptor — a Hopper instruction;
* the operand type is `#ttg.nvmma_shared`, the Hopper wgmma shared layout;
* `num_ctas > 1` (a CGA / thread-block cluster) is itself gated to sm_90+;
* the minimal file names `cuda:90` and `ttng.warp_group_dot`.

Nothing about it is generic. Blackwell's `tcgen05` MMA takes a different path
and is not covered by this evidence. AMD has no CGA and no wgmma.

Both recorded occurrences are sm_90.

## 4. Plain-language explanation

On Hopper you can ask for a *cluster*: several thread blocks that run together
and can see each other's fast on-chip memory. Triton calls that `num_ctas`.

When a cluster is used, Triton records for every tile "which block holds which
part of it". For the matrix `B` in this kernel it decided to cut the tile in half
and give one half to each block.

Then it feeds `B` to the tensor core. The Hopper tensor-core instruction is told
where its data is with a small 64-bit ticket. That ticket has room for an
address inside *the block's own* memory — and no room at all to say "the other
block's memory". Triton hands it a tile that lives half in one block and half in
the other, then checks and finds the ticket cannot say that, and stops with an
internal assertion.

Two things are wrong. The small one: the error a user sees is an internal
assertion, not a message. The bigger one: in a release build that check is
removed, and Triton writes a ticket that quietly points at the wrong half of the
data.

The reason a deprecated 8-bit float type is needed to reach it is indirect: that
type has no hardware conversion, so its values take a detour through registers,
and the detour is what carries the cluster split into the tensor-core operand. A
normal `f16` or `fp8e4nv` matrix goes straight to shared memory and gets no
split.

## 5. Can an SMT solver model this?

**No — and the interesting part is *why* it is out of reach, because it is not
the usual "it crashed" answer.**

Take the five options in turn.

* *A deterministic single-instance value-semantics difference?* No. Nothing runs.
  The compiler aborts, so there is no output buffer to compare against anything.
* *Needs whole-grid modelling?* Partly, and this is the real point. The fact that
  goes wrong is **which CTA of a cluster holds a tile element**. That is not a
  property of one program instance's values; it is a property of the map
  `(block, warp, lane, register) -> tensor index`. A checker that models a single
  program instance cannot even see the `block` coordinate, so it cannot notice
  that the wgmma operand's `block` component is non-zero.
* *Needs a concurrency / memory-ordering model?* Not for the crash, but the
  `NDEBUG` half does: dropping the `block` component means each CTA reads its own
  shared memory instead of a peer's, and "a peer CTA's shared memory" is a
  cluster memory-model notion.
* *Below the IR level?* No — and this is the encouraging part. Everything needed
  is *in* the IR: `#ttg.nvmma_shared`'s `CGALayout` and the `ttg.num-ctas`
  attribute are both written down. A checker that carried layouts as linear maps
  including the `block` input dimension could state the invariant directly:
  *for every `ttng.warp_group_dot`, the shared operand's layout must be trivial
  over `block`*. That is a decidable, cheap, purely structural check — the same
  one `LoadStoreOpToLLVM.cpp:1054` already performs for `cp.async` with
  `isTrivialOver({"block"})`.

So the honest answer is: **not as an equivalence check, but yes as a layout
well-formedness check** — and the check already exists in the codebase, one
directory away, just not on this op. The gap this bug exposes is not a missing
solver, it is a missing verifier on `ttng.warp_group_dot`.

## 6. Confidence

**High that it is a genuine compiler defect.**

* It reproduces from a 16-line hand-written file, with a one-attribute control
  that flips it between rc 134 and rc 0.
* The assert text names the exact line, and the source at that line shows why a
  non-zero `block` cannot be encoded — the descriptor has no field for it.
* The producer is pinned to a single line, `AccelerateMatmul.cpp:192`, by
  `MLIR_ENABLE_DUMP`: the first module containing `#ttg.nvmma_shared<...
  CGALayout = [[1, 0]]>` is the one dumped just after
  `TritonGPUAccelerateMatmul` ran.
* The sibling site in the same pass (`LoadStoreOpToLLVM.cpp:1054`) checks for
  exactly this condition and emits a diagnostic, which is the codebase agreeing
  that a non-trivial `block` dimension is a thing that must be handled, not
  asserted on.

**Where I am less sure**, and what would settle it:

1. **Whose fix is it.** I have called `AccelerateMatmul.cpp:192` the wrong step.
   An owner might instead say the wrong step is upstream — the default CGA layout
   assignment splitting `K` for a `tl.dot` operand at all — which would make this
   a cousin of `HIT-0038`. The `NDEBUG` behaviour is wrong either way, so the
   report stands, but the fix location is a judgement I cannot settle from
   outside. Running the same draw with a hand-edited CGA layout on the `i8` load
   would tell you.
2. **How narrow the trigger is.** I swept four dtype pairs and four `num_ctas`
   values on one kernel; that is enough to show `fp8e4b15` + `num_ctas >= 2`
   reaches it and that plain `f16` and `fp8e4nv` do not, on **this kernel**. It
   is *not* enough to claim `fp8e4b15` is the only way in. Any other operand that
   reaches wgmma through registers instead of straight from `cp.async` is a
   candidate; I did not enumerate them.
3. **Blackwell.** Untested. The `tcgen05` path does not use
   `DotOpMmaSmemLoader`, so this exact assert should not fire there, but whether
   the analogous descriptor has the same hole is unknown.
