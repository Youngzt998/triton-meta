# HIT-0016: the `tt.scan` lowering sizes its block counts from the whole-tensor shape but gets per-CTA values, so any `num_ctas > 1` scan aborts the compiler

Verdict: **CONFIRMED — kept**
Arch:    sm_90 and newer (`num_ctas > 1` needs Hopper thread-block clusters)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    assertion failure inside `ConvertTritonGPUToLLVM` (compiler abort, not a diagnostic)
Culprit: **`lib/Analysis/Utility.cpp:469-492`** (`ScanLoweringHelper::getAxisNumBlocks`
/ `getNonAxisNumBlocks`), tripped at
**`lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp:157-159`** and
**`ScanOpToLLVM.cpp:263-265`**

Input realism: **the kernel keeps its own pointer dtypes.** Nothing about the
program is synthetic — it is torch inductor's own `logcumsumexp` kernel. The only
unusual thing the user has to do is pass `num_ctas=4`, an ordinary
`@triton.jit` / `triton.Config` knob.

Occurrences: **56** as of 2026-08-19 19:00 = 15 under the `ScanOpToLLVM.cpp:265`
signature (this report) + 41 under the `ScanOpToLLVM.cpp:159` signature
(HIT-0017, rejected as a B4 duplicate). sm_90 only, across at least 5 distinct
kernels (`ind:triton_per_fused_logcumsumexp_0`, `ind:triton_per_fused_cumsum_0`,
`ind:triton_per_fused_cummax_0`, `ind:triton_red_fused_cumprod_0`,
`ind:triton_per_fused_cumsum_1`).

**Cross-reference, not a duplicate.** `tv/bug-report/triton/r2-oracle/HIT-0001`
records the *silent* face of the same hole in the compiler: with `num_ctas > 1`
a `tl.cumsum` whose axis is split across CTAs returns wrong data with no error.
That report and this one are different shapes of finding (REVIEW-CRITERIA §2
keeps a crash and a wrong-bits difference separately), so neither folds into the
other. Read them together: r2-oracle/HIT-0001 explains why nothing rejects a
cross-CTA scan in the first place; this report explains why, past a certain tile
size, the same hole aborts the compiler instead.

## 1. Root cause in the source

Checkout: `/home/youngzt/fuzz/triton-public`, commit `3277063a6` (public
triton-lang, version `3.8.0+git3277063a`).

When `num_ctas > 1` a layout carries a **CGA layout** — the part that says which
CTA of the cluster holds which elements. `ScanLoweringHelper` computes how many
"blocks" (repeats of the per-CTA tile) the scan has to walk, and it computes them
from the **whole tensor shape** divided by the **per-CTA** tile:

`lib/Analysis/Utility.cpp:469-477`

```cpp
unsigned ScanLoweringHelper::getAxisNumBlocks() {
  auto contigPerThread = getEncoding().getContigPerThread();
  auto threadsPerWarp  = getEncoding().getThreadsPerWarp();
  auto warpsPerCTA     = getEncoding().getWarpsPerCTA();
  unsigned axis = getAxis();
  return ceil<unsigned>(
      getShape()[axis],
      (contigPerThread[axis] * threadsPerWarp[axis] * warpsPerCTA[axis]));
}
```

`getNonAxisNumBlocks()` (lines 479-492) is the same expression over the other
dimensions.

The numerator and the denominator come from different worlds:

* `getShape()` is `op.getOperands()[0].getType().getShape()`
  (`Utility.cpp:405`) — the **whole logical tensor**, every CTA together.
* `getContigPerThread()` / `getThreadsPerWarp()` / `getWarpsPerCTA()` are
  `LinearEncodingAttr::basesPerDim` over the `register` / `lane` / `warp` input
  dimensions only (`lib/Dialect/TritonGPU/IR/Dialect.cpp:1167-1170` and
  `1236-1245`). The CTA dimension of the layout is a **fourth** input dimension
  named `block`, and it appears in neither.

So the quotient counts the blocks of the *whole* tensor while the divisor is a
*per-CTA* tile, and it over-counts by exactly the CTA split factor of that
dimension.

The consumer of those two numbers is the number of per-thread registers, which
*is* per-CTA. `ScanOpToLLVM.cpp:155-159`:

```cpp
unsigned numScanBlocks     = helper.getAxisNumBlocks();
unsigned numParallelBlocks = helper.getNonAxisNumBlocks();
assert(numScanBlocks * numParallelBlocks * parallelElementsPerThread *
           scanElementsPerThreads ==
       srcValues.size());
```

`srcValues` is the unpacked LLVM struct for this CTA's slice, so its size is
`getTotalElemsPerThread` of the layout — which *does* account for the `block`
dimension. The two sides therefore disagree by `product(CTASplitNum)` and the
assertion fires.

The identical assertion appears twice, once in each of the two partial-reduce
helpers, and which one runs is decided only by whether the scan axis spans more
than one warp (`emitFastScan` picks `AddPartialReduceOneWarp` when
`helper.getAxisNumWarpsWithUniqueData() == 1`):

* `ScanOpToLLVM.cpp:157-159` — `AddPartialReduce` (axis spans several warps)
* `ScanOpToLLVM.cpp:263-265` — `AddPartialReduceOneWarp` (axis inside one warp)

That is why R4 filed the same defect twice.

**Worked example** — this report's own draw. The failing layout is

```mlir
#blocked1 = #ttg.blocked<{sizePerThread = [1, 4], threadsPerWarp = [1, 32],
                          warpsPerCTA = [4, 1], order = [1, 0],
                          CGALayout = [[1, 0], [2, 0]]}>   // 4 CTAs, split on dim 0
```

on `tensor<256x128xf32>`, scan `axis = 1`:

| quantity | value | why |
|---|---|---|
| `getAxisNumBlocks()` | `ceil(128 / (4*32*1))` = 1 | dim 1, not split |
| `getNonAxisNumBlocks()` | `ceil(256 / (1*1*4))` = **64** | dim 0, whole shape 256 |
| `parallelElementsPerThread` | 1 | |
| `scanElementsPerThreads` | 4 | |
| product | **256** | what the lowering expects |
| `srcValues.size()` | **64** | `(256/4 CTAs × 128) / 128 threads` |

`256 / 64 = 4 = num_ctas`. Exactly the missing CTA term.

**Note the split is on the *non-scan* axis here.** This is wider than "the scan
axis crosses CTAs": *any* CTA split of *any* dimension breaks the count, because
both helpers make the same mistake. `HIT-0016/scan-cta-min-onewarp.mlir` pins
that case; `HIT-0016/scan-cta-min.mlir` pins the axis-split case.

**Why nothing catches it earlier.** `ScanLoweringHelper::isSupported()`
(`Utility.cpp:496-502`) is the only gate on the scan lowering and its whole body
rejects non-blocked encodings; it never looks at `getCTASplitNum(...)`. There is
no `isScanWithinCTA()` in the tree, although `ReduceOpHelper::isReduceWithinCTA()`
sits right next to it at `Utility.cpp:82-87`. `ScanOp` is likewise absent from
`hasCrossCTAScratch()` (`lib/Analysis/Allocation.cpp:149-172`) and
`needsClusterBarrier()` (`Utility.cpp:1319-1326`), both of which list `ReduceOp`,
and `PlanCTA` has a `processReduce` (`PlanCTA.cpp:278-282`) but no
`processScan`. So the scan is never told about clusters, never given cross-CTA
scratch, and never rejected.

## 3. Where it reproduces

**sm_90 (Hopper) and newer, only — and that is a property of the trigger, not of
the code.** `num_ctas > 1` is the sole trigger and Triton refuses it below sm_90
(`ValueError: num_ctas > 1 requires NVIDIA SM90+`). All 56 recorded occurrences
are sm_90.

What that judgement rests on: the failing IR contains **no** Hopper-only
construct — no `wgmma`, no TMA descriptor, no `mbarrier`, no warp specialization,
no `tcgen05`. It is a plain `tt.scan` on a `#ttg.blocked` layout. The wrong code
is in `lib/Analysis/Utility.cpp` and `lib/Conversion/TritonGPUToLLVM/`, both
shared by every NVIDIA target. The arch limit comes only from the fact that a CGA
layout that splits a tensor across CTAs cannot exist without hardware
thread-block clusters. So: any NVIDIA target with clusters — sm_90 today,
sm_100+ tomorrow.

Independent of `num_warps` (both warp paths crash), of `num_stages`, `maxnreg`,
`enable_fp_fusion` and `sanitize_overflow` — the 56 occurrences differ in those
and agree only in `num_ctas > 1`.

Whether you get **this crash** or **r2-oracle/HIT-0001's silent wrong answer**
depends on the tile: when the layout happens to make the two counts agree
(everything fits in one block per CTA) the lowering proceeds and silently drops
the cross-CTA carry; when they disagree the compiler aborts. r2-oracle/HIT-0001
measured the boundary on a 1-D `tl.cumsum` at `num_ctas=4`: N=8 and N=64 give
wrong data, N=256 and N=1024 abort.

## 4. In plain words

On an H100 you can ask Triton to run one program as a *cluster* of several thread
blocks (`num_ctas=4`). Triton then cuts the tile into pieces, one per block.

The code that turns `tl.cumsum` (and `cummax`, `cumprod`, `associative_scan`)
into machine code needs to know how many chunks of data each thread is holding.
It works that out by dividing the size of the **whole tile** by the size of the
piece **one block** can hold. But each thread only ever holds part of its own
block's piece, so the answer is too big — by exactly the number of blocks.

The compiler then checks its own arithmetic, sees the two numbers do not match,
and stops with an internal assertion. The user gets a crash and a C++ file name,
not a message about clusters and scans.

## 5. Can an SMT solver model this?

**Verdict: not expressible as an equivalence query, because one side does not
exist — but the class is squarely inside the reach of a layout well-formedness
obligation on the same IR, and that is the stronger result.**

1. **There is no second program to compare against.** An SMT translation
   validator proves `f_before ≡ f_after` for two IR modules. Here the compiler
   never produces the "after" module: it aborts inside
   `ConvertTritonGPUToLLVM`. One side of the equivalence does not exist, so the
   query cannot be written down at all. This is the same reasoning as
   `tv/bug-report/tilelang/CODEGEN-0001`.

2. **What *would* catch it, in the same solver and on the same IR.** The defect
   is a **counting** disagreement between two derived quantities of one layout,
   and both are closed-form functions of the layout attribute. A checker that
   models a TTGIR layout as a linear map from `(block, warp, lane, register)` to
   a tensor index — the vocabulary `tv/doc/tile-smt-design.md` already wants for
   the GPU layer — can state the lowering's precondition as a proof obligation
   and discharge it *symbolically over all shapes and layouts*, not per instance:

   ```
   for every blocked layout L and shape S:
       getAxisNumBlocks(L,S) * getNonAxisNumBlocks(L,S)
         * nonAxisElemsPerThread(L) * axisElemsPerThread(L)
       == totalElemsPerThread(L,S)
   ```

   Under the current definitions the left side omits the `block` dimension and
   the right side includes it, so the obligation is false as soon as
   `product(CTASplitNum) > 1`. That is a linear-integer-arithmetic query over
   powers of two — no bit-blasting, no floating point, decidable and cheap.
   Crucially it is a **whole-class** result: one answer covers every kernel, not
   just this draw.

3. **Nothing about the semantics is out of reach.** No concurrency model is
   needed (nothing runs), no bit-exact FP is needed (the combine region is
   irrelevant — the same assert fires with `arith.addi`), and no whole-grid
   modelling is needed (one cluster is one program instance; the grid stays
   symbolic). The only vocabulary item that is not optional is **the CTA
   dimension of a layout as a first-class dimension**. A model that folds the
   block dimension away — that assumes one CTA per program instance, which is
   the natural simplification — is blind to this bug *by construction*, and
   would reproduce the compiler's own mistake.

4. **Would the value abstraction hide it?** No. The bug is index arithmetic over
   layout parameters; the element values never enter. Both FP axiom profiles
   (exact bit-to-bit and reassoc-allowed) are irrelevant here.

5. **Cost.** Trivial. The smallest failing instance is a 256-element `i32` scan
   on 2 CTAs (`scan-cta-min.mlir`, 20 lines). The obligation in point 2 is a
   handful of integer divisions and one equality.

## 6. Confidence

**Very high that this is a genuine compiler bug.** The chain is closed:

* (a) It reproduces from a 20-line MLIR file through two `triton-opt` passes, so
  no Python, no corpus and no fuzzer machinery is involved.
* (b) The predicted mechanism and the observed numbers agree exactly: the
  measured ratio `expected / actual` is `4` at `num_ctas=4` and `2` at
  `num_ctas=2`, i.e. `product(CTASplitNum)`.
* (c) `num_ctas=1` compiles the identical kernel with no complaint, on both
  draws.
* (d) The source shows the missing term directly — `getShape()` is whole-tensor,
  `basesPerDim` skips the `block` dimension — and shows `ScanOp` absent from the
  three cross-CTA lists that `ReduceOp` is in.
* (e) An independent line found the silent-data face of the same hole
  (r2-oracle/HIT-0001) and its wrong answers restart with period
  `N / num_ctas`, which is what the missing CTA term predicts.

**The remaining doubt is scope, not correctness.** Nobody has written down that
`tl.cumsum` supports `num_ctas > 1`. `TritonGPUPlanCTAPass` — the pass that makes
these layouts — is skipped entirely at `num_ctas == 1` (`PlanCTA.cpp:986`) and
has **no lit tests at all**; its own file ends with a TODO asking for some. So it
is possible the maintainers regard clusters plus scan as an untested corner
rather than a promise.

That does not change the report: Triton **accepts** the configuration and then
aborts on an internal assertion. Even if cross-CTA scan is out of scope, the
correct behaviour is `ScanLoweringHelper::isSupported()` returning false when
`getCTASplitNum(encoding)[axis] != 1` — a two-line change that turns this crash
into a clear message and, per r2-oracle/HIT-0001, would also stop the silent
wrong answers. Note that check must cover the **non-axis** dimensions too: this
report's own draw splits only a non-scan axis and still crashes.

What would settle it: an upstream issue asking whether cross-CTA `tt.scan` is
meant to work. Either answer produces a fix.
