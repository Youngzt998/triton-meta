# HIT-0048: the frontend builds `tt.int_to_ptr` on an integer narrower than 64 bits, so casting a loaded handle to a pointer produces invalid IR

Verdict: **CONFIRMED — invalid IR built by the frontend** (`RuntimeError: error
         encountered during parsing`, no source location).
Arch:    **generic.** The failure is in the Python frontend, before any target
         is consulted. R4 saw it under sm_80, sm_89 and sm_90a; my minimal
         repro fails identically for every arch I passed.
Line:    r2-compile (R4, compile-only, no GPU)
Culprit: `Semantic.cast`, `python/triton/language/semantic.py:897-899`
Class:   R4 `invalid-ir-frontend`, rule `F10`, signature
         `verify:'tt.int_to_ptr' op operand #N must be N-bit signless integer or
         tensor of N-bit signless integer values, but got 'iN'`
Occurrences: 3 at the time of review (archs sm_80 / sm_89 / sm_90a, 1 each).
Review:  **KEPT** under REVIEW-CRITERIA §2, last bullet ("compile failure,
         crash, or invalid generated code — keep it"). Not a duplicate of any
         kept class in this line: the fourteen kept reports are six
         `TritonGPUPlanCTAPass` defects, five fp8 defects, one `tt.scan`
         lowering defect, one default-CGA-layout defect and one ptxas crash.
         This is none of them.
Reviewed: 2026-08-19
SMT verdict: **not applicable** — a compile-time failure, not a value
         difference. See §5.

## What goes wrong, in one sentence

`x.to(tl.pointer_type(T))` builds a `tt.int_to_ptr` op whatever the integer
width of `x` is, but the op only accepts `i64`, so any narrower integer gives
malformed IR and a `RuntimeError` with no source line — while the *opposite*
cast, pointer to integer, checks the width three lines above and raises a clean
Python error.

---

## 1. Root cause in the source

Two neighbouring branches of the same function, `Semantic.cast` in
`python/triton/language/semantic.py`:

```python
889        # Casting pointer types to integer types
890        if src_sca_ty.is_ptr() and dst_sca_ty.is_int():
891            bitwidth = dst_sca_ty.int_bitwidth
892            if bitwidth == 64:
893                return self.tensor(self.builder.create_ptr_to_int(...), dst_ty)
894            if bitwidth == 1:
895                return self.not_equal(self.cast(input, tl.int64), ...)
896
897        # Casting integer types to pointer types
898        if src_sca_ty.is_int() and dst_sca_ty.is_ptr():
899            return self.tensor(self.builder.create_int_to_ptr(input.handle,
900                                   dst_ty.to_ir(self.builder)), dst_ty)
```

The pointer → integer branch (890) **tests the width**: only 64 and 1 are
handled, and anything else falls through to the `assert False, f'cannot cast
{input} to {dst_ty}'` at the end of the function — a Python error naming both
types.

The integer → pointer branch (898) has **no width test at all**. It calls
`create_int_to_ptr` for an `i8`, `i16` or `i32` source just as happily as for an
`i64` one. But the op it builds is declared as taking `i64` only:

```tablegen
include/triton/Dialect/Triton/IR/TritonOps.td
40  def TT_IntToPtrOp : TT_Op<"int_to_ptr", [Elementwise, ...
44      let summary = "Cast int64 to pointer";
46      let arguments = (ins TT_I64Like:$src);        // TT_I64Like = AnyTypeOf<[I64, I64Tensor]>
                                                     // TritonTypes.td:42
```

So the module the frontend hands to the verifier is invalid. The verifier
reports it at `<unknown>:0` (the builder attaches no location to the op), and
`ast_to_ttir` turns that into

```
RuntimeError: error encountered during parsing
```

with no file, no line and no mention of the cast the user wrote. Either fix
removes it: widen the source with `extsi`/`extui` to `i64` before building the
op (what a user writing `ptr = handle.to(tl.pointer_type(T))` expects), or
mirror line 892 and fall through to the existing `assert False` so the user gets
`cannot cast tensor(i8) to pointer<f32>`.

The corpus kernel reaches it the natural way. `grouped_matmul_kernel` stores a
table of device pointers as integers and reads them back:

```python
a_ptr = tl.load(group_a_ptrs + g).to(tl.pointer_type(DTYPE))
```

R4 drew `group_a_ptrs` as `*u8` instead of `*i64` (the pointer-dtype axis,
PLAN-R2 §2a), so `tl.load` yields an 8-bit integer and the cast builds
`tt.int_to_ptr` on `i8`.

## 3. Where it reproduces

**Any machine, any NVIDIA target, and almost certainly any backend.** The
failure happens inside `ast_to_ttir`, before the TTIR is handed to a backend:
no `num_ctas`, no `num_warps`, no layout and no arch-specific construct is
involved, and the IR in the stderr dump contains no wgmma, TMA, mbarrier,
cluster or warp-specialization op. R4's own occurrence table already shows one
hit each under sm_80, sm_89 and sm_90a, and my repro (b) reproduces it for
sm_80. The AMD backend shares the same frontend, so it should fail there too,
though I did not test that.

## 4. Plain-language explanation

Triton lets a kernel keep pointers in a normal array and turn one back into a
pointer with `.to(tl.pointer_type(...))`. A pointer is 64 bits wide, so that
conversion only makes sense from a 64-bit integer. If you hand it a smaller
integer, Triton should either widen it for you or tell you it cannot do it.
Instead it builds the conversion anyway, the internal checker rejects the
program it just built, and the user sees "error encountered during parsing"
with no line number. The reverse conversion — pointer to integer — already
checks the width and gives a clear message, so the two halves of the same
function disagree.

## 5. Can an SMT solver model this?

**Not applicable, and out of reach for the right reason.** This is not a
difference between two runs; there is only one compilation and it never
produces a program. An SMT equivalence checker compares the meaning of two IR
modules, and here the second module does not exist — the frontend fails to
build a *well-formed* module at all.

What *would* catch it is a different kind of tool, and it is worth naming
because the campaign keeps meeting this class: an ordinary type check on the
builder. Every `create_*` call has a declared operand type in the ODS
definition (`TT_I64Like` here), and the frontend calls those builders from
Python where nothing enforces it. A checker that reads the `.td` files and
verifies that each `Semantic` branch can only build ops whose operand types it
has already constrained would find this statically, with no solver and no
inputs. Five of this line's fourteen kept reports (the fp8 family) have exactly
the same shape: a Python-level type predicate that does not match the MLIR type
the builder will demand.

## 6. Confidence

**High that it is a genuine defect; the only open question is severity.**

What is settled: the op accepts `i64` only (`TritonOps.td:46`), the frontend
does not check (`semantic.py:898`), the sibling branch does check
(`semantic.py:890-895`), and a hand-written five-case sweep shows the boundary
exactly at 64 bits. Nothing about the fuzzer's draw is needed to see it.

What is arguable: the *program* R4 fed in is one the corpus author never wrote —
R4 swapped `group_a_ptrs` from `*i64` to `*u8`, and the report's own banner says
so. A user could still write it by mistake, and this campaign's rule (and
REVIEW-CRITERIA §2) is that the compiler owes a diagnostic rather than malformed
IR. So the defect is real but **low severity: a diagnostic-quality defect, not a
miscompile.** The same judgement was already applied to the kept HIT-0002, whose
failing draw is also a swapped pointer dtype.

What would settle the remaining doubt: a maintainer's decision on whether
`int.to(pointer_type)` from a narrow integer should widen (accept) or be
rejected. Either answer makes the current behaviour wrong; only the fix differs.

an offset whose byte size is not a multiple of 16 removes the divisibility
hint), and `ptr_ty` is the pointer element type.

### kernel source

```python
@triton.jit
def grouped_matmul_kernel_87cbfee0(group_a_ptrs, group_b_ptrs, group_c_ptrs, group_gemm_sizes, g_lds, group_size, DTYPE: tl.constexpr, NUM_SMS: tl.constexpr, BLOCK_SIZE_M: tl.constexpr, BLOCK_SIZE_N: tl.constexpr, BLOCK_SIZE_K: tl.constexpr):
    tile_idx = tl.program_id(0)
    last_problem_end = 0
    for g in range(group_size):
        gm = tl.load(group_gemm_sizes + g * 3)
        gn = tl.load(group_gemm_sizes + g * 3 + 1)
        gk = tl.load(group_gemm_sizes + g * 3 + 2)
        num_m_tiles = tl.cdiv(gm, BLOCK_SIZE_M)
        num_n_tiles = tl.cdiv(gn, BLOCK_SIZE_N)
        num_tiles = num_m_tiles * num_n_tiles
        while tile_idx >= last_problem_end and tile_idx < last_problem_end + num_tiles:
            k = gk
            lda = tl.load(g_lds + g * 3)
            ldb = tl.load(g_lds + g * 3 + 1)
            ldc = tl.load(g_lds + g * 3 + 2)
            a_ptr = tl.load(group_a_ptrs + g).to(tl.pointer_type(DTYPE))
            b_ptr = tl.load(group_b_ptrs + g).to(tl.pointer_type(DTYPE))
            c_ptr = tl.load(group_c_ptrs + g).to(tl.pointer_type(DTYPE))
            tile_idx_in_gemm = tile_idx - last_problem_end
            tile_m_idx = tile_idx_in_gemm // num_n_tiles
            tile_n_idx = tile_idx_in_gemm % num_n_tiles
            offs_am = tile_m_idx * BLOCK_SIZE_M + tl.arange(0, BLOCK_SIZE_M)
            offs_bn = tile_n_idx * BLOCK_SIZE_N + tl.arange(0, BLOCK_SIZE_N)
            offs_k = tl.arange(0, BLOCK_SIZE_K)
            a_ptrs = a_ptr + offs_am[:, None] * lda + offs_k[None, :]
            b_ptrs = b_ptr + offs_k[:, None] * ldb + offs_bn[None, :]
            accumulator = tl.zeros((BLOCK_SIZE_M, BLOCK_SIZE_N), dtype=tl.float32)
            for kk in range(0, tl.cdiv(k, BLOCK_SIZE_K)):
                tl.multiple_of(a_ptrs, [16, 16])
                tl.multiple_of(b_ptrs, [16, 16])
                a = tl.load(a_ptrs)
                b = tl.load(b_ptrs)
                accumulator += tl.dot(a, b)
                a_ptrs += BLOCK_SIZE_K
                b_ptrs += BLOCK_SIZE_K * ldb
            c = accumulator.to(DTYPE)
            offs_cm = tile_m_idx * BLOCK_SIZE_M + tl.arange(0, BLOCK_SIZE_M)
            offs_cn = tile_n_idx * BLOCK_SIZE_N + tl.arange(0, BLOCK_SIZE_N)
            c_ptrs = c_ptr + ldc * offs_cm[:, None] + offs_cn[None, :]
            tl.store(c_ptrs, c)
            tile_idx += NUM_SMS
        last_problem_end = last_problem_end + num_tiles
```

Not yet pinned to a single pass. The failing *stage* is `frontend`. A `triage` task (the production pipeline replayed one pass at a time through `triton-opt`) is queued for this class; if it succeeded, the result is in `run/results.jsonl` under the same class signature.

## Why this is NOT a legitimate "unsupported configuration"

The frontend built IR that fails verification. The program itself may well be invalid — but then the frontend owes a `CompilationError` pointing at the source line, not malformed IR handed to the verifier at `<unknown>:0`. LOW SEVERITY: this is a diagnostic-quality defect, not a miscompile.

The rule this campaign applies, in full, is at the top of
`/home/youngzt/fuzz/r2-compile/fz/classify.py`. In one line: *a failure is a
finding only when the compiler lost control of itself; it is noise when the
compiler made a decision and reported it.* Illegal (kernel, config, arch)
points are drawn on purpose — `num_ctas > 1` below sm_90, `fp8e4nv` below
sm_89, a non-power-of-two `tl.arange`, a tile too big for shared memory — and
every one of those is expected to come back as a clean diagnostic. Those are
counted as `frontend-reject` / `config-reject` / `arch-unsupported` /
`resource-limit` in `STATUS.md` and are never written up.

## Determinism evidence

Every point is a pure function of `(seed, round, kernel index, arch)` and the
compile is deterministic by construction: no GPU is involved, no random input
data is generated, and `TRITON_ALWAYS_COMPILE=1` plus a private
`TRITON_CACHE_DIR` mean no cached artifact can leak in from another run or
another session. The class has been seen 6 times. Re-running
`repro.py` is the check a reviewer should run first.
