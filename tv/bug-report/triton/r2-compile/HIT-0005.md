# HIT-0005: PlanCTA asserts on any kernel that has no store, so `tl.device_assert`-only kernels cannot be compiled with `num_ctas > 1`

Verdict: **CONFIRMED — kept**
Arch:    hopper-only (sm_90; `num_ctas > 1` needs Hopper clusters)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    `assert` failure — the process aborts (SIGABRT). In a release build
         (`NDEBUG`) the assert is compiled out and the code walks off the end of
         an empty list instead; see §6.
Culprit: **`TritonGPUPlanCTAPass`** — `lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp:359`,
`CTAPlanner::processStoreLikeOps`

Input realism: **the kernel keeps its own pointer dtypes.** Nothing is
synthetic. The only unusual thing a user has to do is pass `num_ctas=2`.

Occurrences: **6**, sm_90 only, across at least 2 distinct kernels
(`bch:_assert_async_kernel_ffc659d7`,
`ind:triton_per_fused__assert_async_all_ge_lt_0_69d7fda8`) — both of them
assert-only kernels, which is the pattern.

---

## 1. Root cause in the source

`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp:355-359`:

```cpp
void CTAPlanner::processStoreLikeOps(triton::FuncOp &funcOp) {
  assert(!tiled && "CTA tiling is already determined");

  llvm::SmallVector<Operation *> stores;
  funcOp.walk([&](Operation *op) {
    if (llvm::isa<triton::StoreOp, triton::AtomicRMWOp, triton::AtomicCASOp,
                  triton::DescriptorStoreLikeOpInterface>(op))
      stores.push_back(op);
  });
  assert(stores.size() > 0 && "Cannot find store-like ops");          // line 359
```

The pass has to pick *some* tensor to decide the CTA split from. It tries three
sources in order (`CTAPlanner::run`, lines 159-176):

```cpp
processDot(funcOp);          // if there is a tt.dot, tile from it
nextStep();
processReduce(funcOp);       // else if there is a tt.reduce, tile from it
nextStep();
if (!tiled) {
  processStoreLikeOps(funcOp);   // else tile from the first store
  nextStep();
}
```

The third source is treated as a guaranteed fallback: `processStoreLikeOps`
asserts that at least one store-like op exists. **A Triton kernel is not required
to store anything.** The simplest counterexample is a kernel that only checks
something:

```python
@triton.jit
def _assert_async_kernel(x_ptr):
    ...
    tl.device_assert(cond)      # lowers to tt.assert — not a store
```

`tt.assert` is not in the `isa<>` list (nor should it be — it has no tensor
result to tile from), so `stores` is empty and line 359 fires. The same happens
for a kernel whose whole body is dead after constant folding, which is exactly
what the minimal artifact in this directory shows: by the time PlanCTA runs, the
function body has been reduced to a single `tt.return`.

The right behaviour is the one the function already implements two lines from
the end — `if (!tiled) markTiled();` (line 383) — i.e. no store, nothing to
split, leave the default CGA layout alone and return. The empty case needs an
early `return`, not an assert.

## 3. Where it reproduces

**Any NVIDIA target that accepts `num_ctas > 1`, i.e. sm_90 and later.**

- `PlanCTAPass::runOnOperation` returns immediately when `getNumCTAs(mod) == 1`
  (PlanCTA.cpp:986), so the default configuration never reaches this code.
- The failing module contains **no** Hopper-only construct at all — it contains
  nothing whatsoever except `tt.return`. There is no clearer demonstration that
  the arch label is about the `num_ctas` gate and not about the IR.
- The assert makes no target query.

R4 saw it on sm_90 only, having swept sm_80/sm_89 as well, where `num_ctas > 1`
is rejected before this pass.

**On user reachability:** assert-only kernels are a real pattern — torch
inductor generates them (`ind:triton_per_fused__assert_async_all_ge_lt_0` is one
of the two kernels in this class) for `torch._assert_async`. A user who turns on
clusters for a model that contains one of those kernels gets a compiler abort.

## 4. Plain-language explanation

When you ask for a cluster of thread blocks, the compiler must decide how to
split the work between them. It looks for something that tells it the shape of
the work: a matrix multiply, or a reduction, or — as a last resort — a store.

If the kernel has none of those, the compiler has nothing to split. That is fine:
the answer is "do not split anything". But the code treats the last resort as
something that must always exist and calls `assert` when it does not. A kernel
whose only job is to check a condition, with no store at all, makes the compiler
abort.

## 5. SMT reachability analysis

**Outside the equivalence question, and the smallest possible illustration of
why.**

1. **Root cause in semantic terms.** There is essentially no IR involved. The
   module contains one op, `tt.return`. The pass looked for `triton::StoreOp`,
   `triton::AtomicRMWOp`, `triton::AtomicCASOp` or a
   `DescriptorStoreLikeOpInterface` op, found none, and asserted. The semantic
   error is a broken **precondition inside the compiler**, not a wrong meaning
   given to any construct.
2. **Is the difference a pure input→output function difference?** No difference
   exists. The process dies. And here the point is especially sharp: the kernel
   has **no output at all**, so even if compilation succeeded there would be
   nothing for an equivalence checker to compare. Two runs of an empty kernel
   agree trivially.
3. **Fundamental verdict.** **Outside the equivalence question.** Every one of
   the six labels presumes there is a value-level or scheduling-level
   disagreement to find. There is not. An SMT model of this module is the formula
   `true`.
4. **Minimum semantic vocabulary required.** None. What is needed is a
   *reachability* argument over the compiler's own control flow: "can
   `processStoreLikeOps` be entered with an empty `stores` list?" That is a
   question about the pass, not about the program it compiles, and the tools for
   it are a fuzzer (which is how it was found), a coverage-guided unit test, or
   simply reading the code. Note the general shape: every assert in a compiler is
   a claim of the form "this IR shape cannot occur", and validating those claims
   is a different activity from validating that transformations preserve meaning.
   An SMT translation validator is built for the second and is blind to the
   first.
5. **Would the abstraction hide it?** The FP axiom profile is irrelevant — there
   is not a single arithmetic op in the module.
6. **Inherent cost.** Zero.

**What would catch this class instead:** compile-only sweeping with an adversarial
config, which is what R4 does. A cheaper targeted version: Triton's lit suite
should include, for `num_ctas = 2`, a kernel with no store, a kernel with only an
assert, and a kernel with only an atomic. `PlanCTA.cpp`'s own closing TODO list
ends with "Add some lit tests for this pass" — the file currently has none.

## 6. Confidence

**High.** The assert text names the file, the line and the condition; the source
at that line is a two-line walk collecting four op types followed by
`assert(stores.size() > 0)`; the minimal module has no op that can be collected;
and the module aborts the pass on its own in one `triton-opt` invocation.
The `num_ctas = 1` control passes.

One point worth flagging rather than a doubt: **the release build is worse, not
better.** With `NDEBUG` the assert vanishes and control falls into the loop
below it, which iterates over an empty `stores` vector, leaves `CGALayout` as a
default-constructed null attribute, and reaches `if (!tiled) markTiled();`. That
path does not crash here because the loop body never runs — so a release build
probably compiles this kernel *successfully*. I could not check that: the build
available to this line is an assert-enabled one. If a release build does succeed,
the assert is doing no protective work and deleting it is very nearly the whole
fix. That is the experiment that would settle the exact patch: build
`triton-opt` with `NDEBUG` and run the same 5-line module.
