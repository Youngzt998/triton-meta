# HIT-0003: PlanCTA's layout propagation knows only `scf.for` and `scf.if`; an `scf.while` carrying a tensor kills the compiler process

Verdict: **CONFIRMED — kept**
Arch:    hopper-only (sm_90; `num_ctas > 1` needs Hopper clusters)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    `llvm::report_fatal_error` — the process aborts (SIGABRT), no diagnostic
Culprit: **`TritonGPUPlanCTAPass`** — `lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp`,
`CTAPlanner::processBlockArgBackward` (line 849) and
`CTAPlanner::processYieldOpForward` (line 869)

Input realism: **the kernel keeps its own pointer dtypes.** Nothing synthetic.
The only unusual thing a user has to do is pass `num_ctas=2` (or 4, or 8).

Occurrences: **14** = 12 under the "block argument" signature (this report) + 2
under the "YieldOp" signature (HIT-0014, rejected as a B4 duplicate — same pass,
same missing feature, two different places it is noticed; see §1). sm_90 only,
across at least 5 distinct kernels (`bch:upsample_trilinear3d_kernel`,
`bch:upsample_nearest3d_kernel`, `bch:gcd_kernel_i16`,
`ind:triton_poi_fused_add_bucketize_0`, …).

---

## 1. Root cause in the source

`TritonGPUPlanCTAPass` decides how to split a tile across the CTAs of a cluster.
It does that by inserting `UnrealizedConversionCastOp`s with the layout it wants
and then **propagating** those casts through the function until they cancel out.
The propagation walks through region-carrying ops by hand, and the hand-written
list contains exactly two ops: `scf.for` and `scf.if`. Anything else aborts the
process.

**Site 1 — a region block argument (this report).**
`PlanCTA.cpp:842-851`:

```cpp
bool CTAPlanner::processBlockArgBackward(BlockArgument arg, CastOp cast) {
  if (auto forOp = llvm::dyn_cast<scf::ForOp>(arg.getOwner()->getParentOp())) {
    int index = int(arg.getArgNumber()) - forOp.getNumInductionVars();
    auto newType = cast.getResult(0).getType();
    return processForOp(forOp, index, newType);
  } else {
    llvm::report_fatal_error("Unexpected parent op of block argument");   // 849
    return true;
  }
}
```

An `scf.while` has **two** regions (`before` and `after`), and both take block
arguments. When the backward walk reaches one of those arguments, `dyn_cast` to
`scf::ForOp` fails and line 849 kills the process.

**Site 2 — a yield (HIT-0014, merged here).**
`PlanCTA.cpp:860-870`:

```cpp
bool CTAPlanner::processYieldOpForward(scf::YieldOp yieldOp, CastOp cast) {
  int index = cast.getResult(0).use_begin()->getOperandNumber();
  auto newType = cast.getOperand(0).getType();
  if (auto ifOp = llvm::dyn_cast<scf::IfOp>(yieldOp->getParentOp()))
    return processIfOp(ifOp, index, newType);
  else if (auto forOp = llvm::dyn_cast<scf::ForOp>(yieldOp->getParentOp()))
    return processForOp(forOp, index, newType);
  else
    llvm::report_fatal_error("Unexpected parent op of YieldOp");          // 869
  return true;
}
```

The `after` region of an `scf.while` is terminated by `scf.yield`. Its parent is
`scf::WhileOp`, so both `dyn_cast`s fail and line 869 kills the process.

**Both are the same missing feature**, reached from the two directions the
propagation walks (backward into a loop's carried value, forward out of a
yield). The evidence that it is one class, not two:

- The IR of both failing kernels contains **an `scf.while` carrying tensor
  values, and no `scf.for` and no `scf.if` at all** (checked: `pre-plan-cta-*.ttgir`
  in this directory — HIT-0003's has `scf.while` at line 110 carrying
  `tensor<256xi32>`, HIT-0014's at line 25 carrying two `tensor<16xi64>`).
  There is no other candidate parent op.
- Both abort inside the same propagation loop of the same pass, on the same
  `dyn_cast`-or-die pattern, written three lines apart in the same file.
- One fix removes both: teach the propagation about `scf.while` (or fall back to
  `processOpFallback`, which already exists at line 872 and does the generic
  "cast every tensor operand and result" thing).

Note the failure mode itself is also wrong independently of the missing feature:
`llvm::report_fatal_error` aborts the whole process with no source location and
no diagnostic. A pass that meets IR it cannot handle should `emitError` and let
the pass manager fail cleanly. `PlanCTA.cpp` has four of these
(`"Unreachable branch"`, `"Layout conflict for block arg"`,
`"replaceCGALayout not implemented"`, and the two above).

## 3. Where it reproduces

**Any NVIDIA target that accepts `num_ctas > 1`, i.e. sm_90 and later.**
Same reasoning as HIT-0001:

- `PlanCTAPass::runOnOperation` returns immediately when
  `getNumCTAs(mod) == 1` (PlanCTA.cpp:986), so the default `num_ctas=1` never
  reaches this code.
- The failing IR has **no** Hopper-only construct — no wgmma, no TMA, no
  mbarrier, no warp specialization. It is `scf.while` plus blocked layouts. The
  arch dependence is only that clusters are a Hopper feature.
- The two `dyn_cast`s make no target query.

R4 saw the class on sm_90 only; it swept sm_80/sm_89 too, but `num_ctas > 1` is
rejected before this pass there.

**On user reachability:** `scf.while` is not exotic. It is what Triton emits for
a Python `while` loop, and torch inductor emits it for `torch.bucketize`
(binary search) — `ind:triton_poi_fused_add_bucketize_0` is a real inductor
kernel. So a user with an inductor-generated bucketize kernel and `num_ctas=2`
gets a compiler crash with no message.

## 4. Plain-language explanation

To split a tile across a cluster of thread blocks, the compiler first marks the
places where the data layout must change, then pushes those marks through the
program until they meet and cancel.

Pushing a mark through a loop needs code that knows how that loop passes values
from one round to the next. The pass has that code for `for` loops and for `if`
statements. It has none for `while` loops. When a mark reaches a `while` loop,
the pass does not report an error — it calls `report_fatal_error`, which kills
the whole compiler process on the spot, with no line number and no message a user
could act on.

## 5. SMT reachability analysis

**Outside the equivalence question, and a good illustration of why "an SMT
checker could model this" and "an SMT checker could catch this" are different
claims.**

1. **Root cause in semantic terms.** The constructs are `scf.while` (its two
   regions, their block arguments, and the `after` region's `scf.yield`), an
   `#ttg.blocked` layout attribute, and the `UnrealizedConversionCastOp` the pass
   uses as a layout-change marker. The semantic error is *not* in any of them:
   the pass simply does not implement the case and aborts. Nothing wrong is
   computed; nothing is computed at all.
2. **Is the difference a pure input→output function difference?** No difference
   exists. The process dies, so there is no output program to compare against
   the input program. Runtime inputs, scheduling and hardware play no part.
3. **Fundamental verdict.** **Outside the equivalence question.** The honest
   answer is that an equivalence checker needs two programs and there is only
   one. It is worth being precise about why the tempting label
   `expressible but impractical` is wrong: the *semantics* here would be easy —
   an `scf.while` is a loop with a symbolic trip count and a carried tuple, and
   the layout attributes are index permutations over the tile, both of which a
   good model handles. The obstacle is not expressiveness or cost. There is
   simply no "after" program.
4. **Minimum semantic vocabulary required.** For the *hypothetical* case where
   the pass did not abort but silently produced a wrong layout, a checker would
   need: (a) `scf.while` as a loop over a symbolic trip count with a carried
   tuple and a data-dependent exit condition — note this is `scf.while`, so the
   trip count is genuinely data-dependent and cannot be turned into an affine
   recurrence; (b) layouts as index maps from (CTA, warp, lane, register) to
   tensor coordinates, so that "the same tensor under two layouts" is a
   statement about a permutation; (c) the CGA dimension, i.e. more than one CTA
   per program instance, which is a *whole-cluster* notion rather than a
   single-instance one. That combination — data-dependent loop plus multi-CTA
   layouts — is the expensive corner of the space, so the hypothetical version
   would plausibly be `needs whole-grid modeling` and close to impractical. The
   actual bug needs none of it.
5. **Would the abstraction hide it?** FP axiom profile is irrelevant: the
   carried values in both failing kernels are `i32` and `i64` tensors, and the
   fault is about layout metadata, not arithmetic.
6. **Inherent cost.** Zero solver cost.

**What would catch this class instead:** a rule that a compiler pass must never
call `llvm::report_fatal_error` for IR shapes it can meet — replace the four
occurrences in `PlanCTA.cpp` with `emitError`, and the crash becomes a clean
"unsupported" that a user can route around. Plus a lit test with `scf.while` and
`num_ctas=2`; the file's own closing TODO list asks for lit tests.
Structurally, an op-coverage lint — "for every region-carrying op in the
dialects this pass can see, is there a branch?" — finds it statically.

## 6. Confidence

**High.**

- Both abort sites were read in the source; both are a `dyn_cast`-or-die on the
  parent op, with only `scf::ForOp` (site 1) and `scf::IfOp` / `scf::ForOp`
  (site 2) accepted.
- Both failing modules were inspected: each contains an `scf.while` carrying
  tensors and **no** `scf.for` and **no** `scf.if`, so `scf.while` is the only
  possible parent op in both cases.
- Both reproduce with a single `triton-opt` pass on the saved module, which pins
  the pass.

Remaining doubt, and it is small: I did not step through the propagation in a
debugger to see the exact cast that reaches the while, so "the block argument is
the while's `before`-region argument rather than its `after`-region argument" is
inferred, not observed. That distinction does not change the diagnosis or the
fix. The way to settle it is `-debug-only` on the pass, or a breakpoint on line
849.
