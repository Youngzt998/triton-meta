# HIT-0008: the `fp8e4b15` conversion hard-codes `pack=4`, so converting a tensor whose element count is not a multiple of 4 builds invalid IR

Verdict: **CONFIRMED — kept**
Arch:    generic (sm_80, sm_89, sm_90 — the failure is in the frontend)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    invalid IR built by the Python frontend (MLIR verifier error at TTIR parse time)
Culprit: **`third_party/nvidia/language/cuda/utils.py:34-46` and `:51-83`** —
`convert_fp8e4b15_to_float16` and `convert_float16_to_fp8e4b15`, both of which
pass `pack=4` to `core.inline_asm_elementwise` with no check on the element count.
The verifier that rejects the result is
`lib/Dialect/Triton/IR/Ops.cpp:1500-1508`, `ElementwiseInlineAsmOp::verify`.

Input realism: **the fuzzer swapped a pointer dtype** — it drew `U: *fp8e4b15`
for a kernel whose corpus author used another type. Weigh it lower. But the
*other* half of the trigger is a shape, not a dtype: the draw also picked
`BLOCK_R = 1`. Any user who writes a small tile — 1 or 2 elements per program —
and an `fp8e4b15` buffer hits this, and small tiles are ordinary.

Occurrences: **18** — the largest class in this batch. All three archs (sm_80,
sm_89, sm_90), across at least 18 points and 4+ distinct kernels
(`bch:_rank2_svd_kernel_813eb03e`, `bch:_as_strided_copy_1d_kernel_d11a073d`,
`ind:triton_poi_fused_add_mul_relu_sigmoid_sub_tanh_0_e1f7d5c0`, …).

---

## 1. Root cause in the source

`fp8e4b15` has no hardware conversion instruction, so Triton converts it with a
hand-written PTX sequence that processes **four values at a time** — it packs
four 8-bit values into a 32-bit register and uses `prmt.b32` / `lop3.b32` on the
whole register. That "four at a time" is declared to the compiler through the
`pack` argument.

`third_party/nvidia/language/cuda/utils.py:34-46` (upcast):

```python
@core.builtin
def convert_fp8e4b15_to_float16(arg, _semantic=None):
    return core.inline_asm_elementwise(
        "{ ... prmt.b32 a0, 0, $2, 0x5746; ... }",
        "=r,=r,r", [arg], dtype=core.float16, is_pure=True, pack=4,     # line 46
        _semantic=_semantic)
```

`utils.py:51-83` (downcast) ends the same way:

```python
    return core.inline_asm_elementwise(asm, "=r,r,r", [arg],
                                       dtype=core.float8e4b15, is_pure=True, pack=4,   # line 82
                                       _semantic=_semantic)
```

`pack=4` becomes the `packed_element` attribute on the `tt.elementwise_inline_asm`
op, and the op's verifier requires the input element count to be divisible by it
— `lib/Dialect/Triton/IR/Ops.cpp:1500-1508`:

```cpp
LogicalResult ElementwiseInlineAsmOp::verify() {
  if (getNumOperands() >= 1) {
    auto tensorType = dyn_cast<RankedTensorType>(getOperand(0).getType());
    size_t numInputElems = tensorType ? tensorType.getNumElements() : 0;
    if (numInputElems % this->getPackedElement() != 0) {
      return emitError("number of input elements ")
             << numInputElems
             << " must be a multiple of the op's packed_element attribute, "
             << getPackedElement();
    }
  }
  return success();
}
```

**Neither helper checks the element count before choosing `pack=4`.** With a
1-element tensor the verifier fires:

```
error: number of input elements 1 must be a multiple of the op's packed_element attribute, 4
```

Note the verifier also treats a **scalar** operand as `numInputElems = 0` (the
`dyn_cast<RankedTensorType>` fails, so the ternary yields 0), and `0 % 4 == 0`,
so scalars slip through — but they produce a `tt.elementwise_inline_asm` with
`packed_element = 4` on one scalar value, which the failing module also contains
(`(i8) -> f16` with `packed_element = 4`). Whether the later lowering copes with
that is a separate question I did not chase; the tensor case is the one that is
caught and reported.

The trigger path in the failing kernel: `BLOCK_R = 1`, so
`offs = tl.arange(0, 1)` gives a 1-element tensor, and
`tl.store(ubase + offs * 2, u0, mask=mask)` with `ubase` derived from
`U: *fp8e4b15` makes `Semantic.store` cast a `tensor<1xf32>` down to
`fp8e4b15`. `Semantic.cast` routes it to `convert_custom_float8`
(`utils.py:87`), which converts f32 → f16 and then calls
`convert_float16_to_fp8e4b15` with `pack=4` on one element.

The fix is local: choose `pack` from the element count
(`pack = 4 if n % 4 == 0 else 2 if n % 2 == 0 else 1`) with a matching PTX
variant, or pad, or refuse with a clear message. What must not happen is
emitting an op the compiler's own verifier rejects.

## 3. Where it reproduces

**Every backend and every arch.** The judgement rests on:

- The failing stage is `frontend`: the module is rejected as soon as Triton
  parses what it just built. R4 observed it on sm_80, sm_89 and sm_90.
- `ElementwiseInlineAsmOp::verify` is in core, target-independent code
  (`lib/Dialect/Triton/IR/Ops.cpp`).
- The two helpers live under `third_party/nvidia/`, but both compute-capability
  variants (`convert_custom_float8_sm80` and `..._sm70`) funnel into the same
  `convert_custom_float8`, so both behave identically. Only the `has_minx2`
  choice differs, and it does not touch `pack`.
- AMD registers its own `convert_custom_types`; not tested. The verifier is
  shared, so any backend that uses `pack > 1` in an inline-asm conversion has
  the same exposure.

## 4. Plain-language explanation

Converting Triton's `fp8e4b15` format needs hand-written GPU assembly, and that
assembly works on four values at a time — it stuffs four 8-bit values into one
32-bit register and shuffles the bytes.

Triton tells the compiler "this op handles four elements per step". The compiler
then checks that the number of elements really is a multiple of four. Nobody
checks it *before* claiming four, so a tile of one element produces an op that
says "four at a time" over a single value, and the compiler's own check rejects
it.

So a small tile plus this one dtype is a compile error with a message about an
internal attribute the user never wrote.

## 5. SMT reachability analysis

**Outside the equivalence question. This one is a divisibility precondition on a
lowering rule, and the interesting part is that even the deep version of the
question sits below the IR.**

1. **Root cause in semantic terms.** The construct is
   `tt.elementwise_inline_asm` with `packed_element = 4`, produced by the
   frontend's fp8e4b15 cast. The semantic error is that the op's own
   well-formedness condition — element count divisible by `packed_element` — is
   not established by the code that builds it.
2. **Is the difference a pure input→output function difference?** No difference
   exists; compilation stops at the frontend. Nothing depends on runtime inputs,
   scheduling, or hardware. The whole trigger is
   `(BLOCK_R, dtype)` — two compile-time constants.
3. **Fundamental verdict.** **Outside the equivalence question** for the crash.
   And for the deeper question that lurks here — "does this PTX sequence actually
   compute an `fp8e4b15 → fp16` conversion?" — the right label is
   **`below the IR level`**. The payload is an opaque assembly string; the IR
   node carries only its text, its constraint string, and `packed_element`. No
   IR-level model can see inside it. A checker would have to model PTX bit
   operations (`prmt.b32`, `lop3.b32`, `shr.b32`, `mad.lo.u32`), which is a
   different tool.
4. **Minimum semantic vocabulary required.** For the actual bug: none in the
   solver sense. What is needed is the op's own precondition, checked at build
   time rather than at verify time — `assert numel % pack == 0` inside
   `inline_asm_elementwise`. Notice the general shape: the verifier already
   *states* the invariant; the bug is that a builder can violate it. A checker
   that mechanically pushed every op verifier's condition back to every builder
   of that op would find this class, and it needs no solver — just the constraint
   text that already exists.
   For the PTX question: bit-vector semantics for the PTX byte-permute and
   ternary-logic instructions, plus the `fp8e4b15` format definition
   (4-bit exponent, bias 15, `0xff`/`0x7f` mapped to ±1.75 rather than NaN — the
   comment at `utils.py:26-31` spells this out).
5. **Would the abstraction hide it?** FP axiom profile is irrelevant for the
   crash. For the PTX question it is decisive: under an uninterpreted-function FP
   encoding the inline-asm op is an opaque function and the checker would prove
   any implementation "equivalent" to any other. Only an **exact bit-to-bit**
   encoding could say anything, and even then only if it modelled PTX.
6. **Inherent cost.** Zero for the divisibility check. The PTX question is
   finite and tiny — `fp8e4b15` has 256 values, so exhaustive enumeration settles
   it with no solver at all.

**What would catch this class instead:** a shape sweep. Compile every corpus
kernel at tile sizes 1, 2, 3, 4, 5 — R4's §2a shape axis is exactly this, and it
is what found the bug. A targeted version for Triton's own suite: for every
`inline_asm_elementwise` in the tree that uses `pack > 1`, a test at each element
count from 1 to `pack`. There are only a handful of such call sites.

## 6. Confidence

**High.** Every link was read and matches what was observed:

- both fp8e4b15 helpers pass `pack=4` unconditionally (`utils.py:46`, `:82`);
- `ElementwiseInlineAsmOp::verify` requires `numInputElems % packed_element == 0`
  and produces exactly the observed message;
- the draw has `BLOCK_R = 1`, so `tl.arange(0, BLOCK_R)` is a 1-element tensor;
- the failing module contains `tt.elementwise_inline_asm` ops with
  `packed_element = 4 : i32` on the fp8e4b15 PTX strings.

Two smaller things I did not pin, neither of which changes the diagnosis:

- I did not confirm *which* of the several `tl.store`s into `U` is the one the
  verifier rejects; the kernel has four scalar stores and two 1-element tensor
  stores into `U`, and any of the tensor ones fits. A `-mlir-print-op-on-diagnostic`
  run would name it.
- I did not check whether the scalar case (`numInputElems` counted as 0, so the
  verifier passes) causes trouble further down. It might be silently fine, or it
  might be a second latent bug. Compiling a kernel that only does a *scalar*
  fp8e4b15 store, and reading the PTX, would settle it.

```python
def _rank2_svd_kernel_813eb03e(A, U, S, V, M: tl.constexpr, N: tl.constexpr,
                               TALL: tl.constexpr, BLOCK_R: tl.constexpr):
    pid = tl.program_id(0)
    offs = tl.arange(0, BLOCK_R)          # BLOCK_R = 1  ->  one element
    ...
    if TALL:
        ubase = U + pid * M * 2           # U : *fp8e4b15
        u0 = (x * vx0 + y * vy0) * inv_s0
        ...

        tl.store(ubase + offs * 2 + 1, u1, mask=mask)
```
