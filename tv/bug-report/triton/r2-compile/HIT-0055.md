# HIT-0055: `tl.dot` builds its implicit zero accumulator with an f32 constant but types it `out_dtype`, so any `out_dtype` other than f16/f32 makes invalid IR

Verdict: **CONFIRMED — kept**
Arch:    generic (verified sm_80, sm_89, sm_90; the code is in the target-independent Python frontend)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    invalid IR built by the Python frontend (MLIR verifier error at TTIR build time)
Culprit: **`python/triton/language/semantic.py:1510-1520`**, `Semantic.dot`
Oracle:  R4 compile-only (`invalid-ir-frontend`, classifier rule `F10`)
SMT verdict: no — a build-time type error, there is no pair of programs to compare (§5)

Input realism: the fuzzer swapped a pointer dtype (`*i8` → `*fp8e5`). Weigh the
*draw* lower — but **not the defect**: the minimal repro below needs no fp8 and
no dtype swap. Plain `fp16 × fp16` with `out_dtype=tl.int32`, which any user can
type, produces the same invalid IR on every arch.

Occurrences: **3**, on all three archs (sm_80, sm_89, sm_90). De-duplication
signature: `verify:'tt.splat' op requires the same element type for all operands
and results`.

---

## 1. Root cause in the source

`tl.dot(a, b, out_dtype=D)` with no explicit accumulator makes Triton create the
zero accumulator itself. `Semantic.dot` picks the zero constant and the result
element type in two separate places, and they can disagree.

`python/triton/language/semantic.py:1495-1520`:

```python
if lhs.type.scalar.is_int():                    # 1495
    assert lhs.type.scalar == tl.int8, "only int8 supported!"
    _0 = self.builder.get_int32(0)              # 1498  int zero
    ret_scalar_ty = tl.int32                    # 1499  int type      -> agree
elif out_dtype.is_bf16():                       # 1500
    raise ValueError(                           # 1501  clean rejection
        "out_dtype=bfloat16 is unsupported. ...")
elif lhs.type.scalar.is_fp32() or lhs.type.scalar.is_bf16():
    _0 = self.builder.get_fp32(0)               # f32 zero
    ret_scalar_ty = tl.float32                  #       -> agree
elif lhs.type.scalar.is_fp64():
    _0 = self.builder.get_fp64(0)
    ret_scalar_ty = tl.float64                  #       -> agree
else:                                           # 1510  fp16 / fp8 lhs
    _0 = self.builder.get_fp16(0) if out_dtype.is_fp16() \
         else self.builder.get_fp32(0)          # 1511  f16 or f32 zero, nothing else
    ret_scalar_ty = out_dtype                   # 1512  ANY dtype the caller asked for
...
ret_ty = tl.block_type(ret_scalar_ty, [B, M, N] if B else [M, N])   # 1518
if acc is None:
    acc_handle = self.builder.create_splat(ret_ty.to_ir(self.builder), _0)   # 1520
```

The first three branches keep the constant and the type in step. **The last
branch does not.** Line 1511 can only ever produce an `f16` or an `f32` zero,
while line 1512 copies whatever `out_dtype` the caller passed. Line 1520 then
splats that f32 zero into a tensor whose element type is `out_dtype`:

```mlir
%433 = "arith.constant"() <{value = 0.000000e+00 : f32}> : () -> f32
%434 = "tt.splat"(%433) : (f32) -> tensor<64x64xi32>
%435 = "tt.dot"(%401, %432, %434) : (tensor<64x32xf8E5M2>, tensor<32x64xf8E5M2>,
                                     tensor<64x64xi32>) -> tensor<64x64xi32>
```

`tt.splat` carries `SameOperandsAndResultElementType`, so the verifier rejects
the module the frontend just built:

```
error: 'tt.splat' op requires the same element type for all operands and results
RuntimeError: error encountered during parsing
```

Two separate things are wrong, and both matter:

1. **Nothing checks that `out_dtype` is reachable.** An integer `out_dtype` is
   only meaningful with `int8` operands, which branch 1 already handles.
   Reaching line 1512 with `out_dtype = tl.int32` means the caller asked for
   something the op cannot do, and the right answer is the kind of message the
   `bf16` branch three lines above already gives. `tl.float64` is the same case:
   line 1511 makes an f32 zero and line 1512 says `f64`.
2. **The zero and the type are chosen independently.** Even with a check added,
   deriving `_0` from `ret_scalar_ty` in one place would make this whole class of
   bug impossible instead of fixing one dtype at a time.

The sibling function has the same shape and no guard either:
`Semantic.dot_scaled`, `semantic.py:1625-1627`, does
`ret_ty = tl.block_type(out_dtype, ...)`, then `_0 = self.builder.get_fp32(0)`,
then the same `create_splat`. `out_dtype` defaults to `float32` there
(`core.py:2293`) but the caller can set it. Anyone fixing `dot` should fix
`dot_scaled` in the same change. (Read, not run — see §6.)

**Where the fuzzer found it.** Corpus kernel `ind:triton_mm_4942c5ab` is
torch-inductor's `mm` template specialised for **int8 × int8 → int32**:
`ACC_TYPE : tl.constexpr = tl.int32`, and the loop body is
`acc += tl.dot(a, b, allow_tf32=ALLOW_TF32, out_dtype=ACC_TYPE)` — no `acc=`
argument inside the `tl.dot`, so the implicit accumulator is built. R4 drew
`*fp8e5` for the two input pointers and left `out_dtype = tl.int32`, which moves
the call from branch 1 to branch 4.

## 3. Where it reproduces

**Any target, any backend.** The failing code is
`python/triton/language/semantic.py`, shared by every backend, and the failure
happens inside `ast_to_ttir`, before a single target-specific pass runs. The IR
that fails to verify contains no Hopper or Blackwell construct — no `wgmma`, no
TMA, no `mbarrier`, no cluster, no warp specialization. It is a bare `tt.splat`
in a plain TTIR module.

Measured directly on sm_80, sm_89 and sm_90 by the repro above (18 compiles; the
three failing rows are identical on all three archs), which matches the
campaign's own occurrence table `{"80": 1, "89": 1, "90": 1}`.

AMD was **not** run here. The only target-dependent thing on the path is
`codegen_fns["min_dot_size"]`, which is checked *before* line 1495 and never
looks at `out_dtype`, so there is no reason for AMD to differ — but that is a
code-reading argument, not a measurement, and should be read as such.

## 4. Plain-language explanation

`tl.dot(a, b)` can be told what type to give its answer, with `out_dtype`. When
you do not hand it a running total to add into, Triton makes one for you: a
block of zeros. It picks the zero and it picks the type of that block in two
different lines of code, and those two lines do not agree. The zero is always a
32-bit float (or a 16-bit float); the type of the block is whatever you asked
for. Ask for a 32-bit *integer* answer, or a 64-bit float one, and Triton tries
to put a 32-bit float zero into a block of integers. That is not a legal
program, so the compiler stops — but it stops with `RuntimeError: error
encountered during parsing` and no line number, which tells you nothing about
which `tl.dot` was wrong or why. The message you should get is the one the code
already prints one branch earlier for `bfloat16`: "out_dtype=X is unsupported",
naming the dtype.

## 5. Can an SMT solver model this?

**No — and not because of any limit of the tool. There is nothing to compare.**

Every other question in `REVIEW-CRITERIA.md` §4.5 is about a *value* difference
between two programs. This defect never gets that far: the compiler fails while
it is still building the first program, and what it built is not a program at
all — it is a module the type system rejects. An SMT equivalence check takes two
well-typed functions and asks whether they agree on every input. Here there is
one candidate and it does not type-check, so the question cannot even be stated.

The property that *is* violated is a **well-formedness invariant of the IR
builder**: every value the frontend creates has the type the frontend claims it
has. That is exactly what MLIR's own verifier checks, and it is what caught this.
The right tool is not a solver; it is either the existing verifier run earlier
and with a source location attached, or a two-line change that derives the zero
constant from `ret_scalar_ty` so the two cannot drift apart.

Worth stating plainly for the campaign's purposes: this report is evidence that
**a class of Triton defects sits outside what any IR-level equivalence checker
can reach** — the frontend can emit something that is not an IR at all. Those
need type discipline, not a solver.

## 6. Confidence

**High that it is a genuine defect. Medium on how much it matters.**

Genuine: the mechanism is read straight out of five lines of Python; the
predicted invalid op appears verbatim in the dumped module
(`"tt.splat"(%433) : (f32) -> tensor<64x64xi32>`); a hand-written file
reproduces it on three archs; and that same file's `float32`, `float16` and
`int8` controls all pass, which rules out "the harness broke the compile". There
is no measurement and no sampling here, so nothing can be a statistical
accident.

What would settle the remaining doubt, in order of value:

1. **Is `out_dtype=tl.int32` with float operands meant to be legal at all?** If
   the answer is "no, it should be rejected", the fix is one `raise ValueError`
   next to the `bf16` one and the severity is "bad diagnostic" — the same bucket
   as HIT-0002 and HIT-0048. If someone intends float × float → int32 to work,
   the fix is larger and the severity higher. `core.dot`'s docstring lists the
   accumulator types as `float16, float32, int32` without saying which operand
   types each goes with, so the intent is not written down anywhere.
2. **AMD.** One run of the same script against an AMD target would turn the
   "generic" claim in §3 from a code-reading argument into a measurement.
3. **`dot_scaled`.** The same pattern at `semantic.py:1625-1627` was read, not
   run. It should be exercised before the fix is called complete.

Severity: low to medium. Nothing miscompiles and nothing silently computes a
wrong answer — the compiler stops. What the user loses is the diagnostic: a bare
`RuntimeError` with no source location instead of a sentence naming the dtype.
