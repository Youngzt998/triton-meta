# HIT-0047: ptxas 12.9 segfaults at `--opt-level 2` on an sm_89 group-norm kernel

Verdict: **CONFIRMED — compiler crash** (`ptxas` dies with SIGSEGV, exit -11)
Arch:    **sm_89 only.** The very same PTX file compiles cleanly for sm_90 and
         sm_90a. Below sm_89 it cannot be tried: the file carries
         `.target sm_89`, so ptxas refuses a lower `--gpu-name`.
Line:    r2-compile (R4, compile-only, no GPU)
Culprit: **not Triton.** `ptxas` V12.9.86 (the binary Triton ships through
         `TRITON_PTXAS_PATH`, `deps/` in this environment). Triton's part is
         only that it generates the PTX and reports the failure as
         `triton.runtime.errors.PTXASError`
         (`third_party/nvidia/backend/compiler.py:630`).
Class:   R4 `crash-python`, rule `F14`, 1 occurrence.
Review:  **KEPT** under REVIEW-CRITERIA §2, last bullet ("compile failure,
         crash, or invalid generated code — keep it").
SMT verdict: **below the IR level** — no IR-level checker can ever see this.

## What goes wrong, in one sentence

`ptxas` crashes with a segmentation fault while optimizing a single 2868-line
PTX file for sm_89; the same file at `--opt-level 0` or `1`, or for sm_90 /
sm_90a at any level, compiles fine.

---

## 1. Root cause in the source

**I cannot give one, and I will not invent one.** `ptxas` is a closed-source
binary; there is no source to read and no symbols in the crash. What I can give
is a precise boundary around it.

The failure is entirely inside `ptxas`. Triton's contribution ends at handing it
a PTX file:

```
/home/youngzt/fuzz/triton-public/third_party/nvidia/backend/bin/ptxas \
    -lineinfo -suppress-debug-info --fmad=false -v --regAllocOptLevel=2 \
    --gpu-name=sm_89 <file>.ptx -o <file>.ptx.o
→ Segmentation fault (core dumped), exit -11
```

`third_party/nvidia/backend/compiler.py:630` turns the non-zero exit into
`PTXASError`, which is the right thing to do; the report reaches the user as
`PTXAS error: 'ptxas' failed with error code -11`.

**The PTX itself is valid.** The same file is accepted, and a `.cubin` produced,
by the same ptxas binary at `--opt-level 0` and `--opt-level 1`, and at every
opt level for `--gpu-name=sm_90` and `sm_90a`. A parser/verifier error would not
depend on the optimization level.

What I measured about the trigger (all with the same file,
`HIT-0047/ptxas-segv.ptx`):

| knob | values tried | result |
|---|---|---|
| `--opt-level` | 0, 1 | compiles, exit 0 |
| `--opt-level` | 2, 3 (3 is the default) | **SIGSEGV** |
| `--gpu-name` | sm_89 | **SIGSEGV** at `-O2`/`-O3` |
| `--gpu-name` | sm_90, sm_90a | compiles at every level |
| `--gpu-name` | sm_70…sm_87 | `ptxas fatal: SM version specified by .target is higher than default` — cannot be tested |
| `--regAllocOptLevel` | 0, 1, 2, 3 | SIGSEGV in all four |
| `--maxrregcount` | 32, 64, 128, 255 | SIGSEGV in all four |
| `--fmad` | true, false | SIGSEGV in both |
| `-lineinfo` | present, absent | SIGSEGV in both |

So it is **not** the register allocator (insensitive to both register knobs) and
not the fp8 conversion: replacing the file's single
`cvt.rn.satfinite.e4m3x2.f16x2` with a `mov.u16` still segfaults. It is an
sm_89-specific optimization stage that runs at `-O2` and above.

I did **not** shrink the PTX below its 2868 lines. Cutting a PTX body by hand
means repairing SSA and control flow, and a wrong cut proves nothing; the whole
file is committed instead, which is 105 KB of text.

This is a **new class** for the campaign, distinct from every kept report:

* it is not the ptxas *wrong-code* class (`ttgir-broad/HIT-0008` misplaces a
  store block, `r2-corpus/HIT-0024` computes wrong values) — here nothing is
  produced at all;
* it is not the `ptxas fatal : Insufficient registers` resource-limit class that
  pass 2 rejected six times (HIT-0020, 0026, 0036, 0040, 0042, 0044). Those are
  ptxas making a decision and reporting it with a number. A SIGSEGV is not a
  decision.

## 2. Reproduction

**(a) ptxas alone — no Triton, no GPU, no Python.** This is the whole bug:

```bash
cd /home/youngzt/tv/triton/tv/bug-report/triton/r2-compile/HIT-0047
/home/youngzt/fuzz/triton-public/third_party/nvidia/backend/bin/ptxas \
    --opt-level 2 --gpu-name=sm_89 ptxas-segv.ptx -o /dev/null
echo $?          # 139 = 128 + SIGSEGV
```

Controls that must pass:

```bash
... --opt-level 0 --gpu-name=sm_89  ptxas-segv.ptx -o /dev/null   # exit 0
... --opt-level 2 --gpu-name=sm_90a ptxas-segv.ptx -o /dev/null   # exit 0
```

ptxas version: `Cuda compilation tools, release 12.9, V12.9.86`,
`Build cuda_12.9.r12.9/compiler.36037853_0`.

**(b) End to end from the corpus, at the exact draw that found it.**

```bash
source /home/youngzt/fuzz/r2-compile/env.sh
python /home/youngzt/tv/triton/tv/bug-report/triton/r2-compile/HIT-0047/repro.py
```

Kernel `ind:triton_per_fused_native_group_norm_0_9294c0a8`, `arch = sm_89`,
config `num_warps=1 num_stages=7 num_ctas=1 maxnreg=None tf32 launch_pdl=True
enable_fp_fusion=False`, shape draw `xnumel=1 r0_numel=8192 XBLOCK=8`, pointer
element types **swapped by the fuzzer** to
`in_ptr0=*bf16 out_ptr0=*i16 out_ptr1=*fp8e4nv out_ptr2=*i16`. It ends in
`fz.compile1.StageFailure: cubin: PTXASError: ... error code -11`.
Verified 2026-08-19: (a) and (b) both reproduce.

To capture the PTX yourself, point Triton at a wrapper:

```bash
TRITON_PTXAS_PATH=/path/to/wrapper.sh python .../HIT-0047/repro.py
# wrapper.sh copies the .ptx argument aside, then execs the real ptxas
```

**On the swapped dtypes.** The draw needed `out_ptr1 = *fp8e4nv`, a program the
corpus author did not write, and REVIEW-CRITERIA would weigh a *Triton*
diagnostic bug lower for that reason. It does not apply here: the swap only
selects *which* PTX gets generated. Once the PTX exists it is a valid PTX file
that ptxas accepts at `-O1`, and a compiler must not segfault on valid input,
whatever produced it.

## 3. Where it reproduces

* **sm_89 (Ada) only**, with this ptxas (12.9.86), at `--opt-level ≥ 2`. sm_90
  and sm_90a are clean on the identical file, so this is an Ada-specific code
  path inside ptxas.
* **Independent of the GPU present in the machine** — ptxas is an offline
  assembler; the box here has H100s and never runs the result. Anyone with CUDA
  12.9's ptxas and this file reproduces it.
* **Not reproducible from Triton on an sm_90-only setup**: you have to ask
  Triton for sm_89, which is what R4's arch axis does and what no round-1 line
  did.
* Untested on other CUDA versions. Whether 12.8 or 13.x also crash is unknown —
  the environment pins one ptxas (PLAN §11), and I did not install another.

## 4. Plain-language explanation

Triton compiles a kernel down to PTX, which is NVIDIA's assembly-like text, and
then calls NVIDIA's `ptxas` to turn that text into machine code. For this one
kernel, when the target is an Ada card and optimization is on, `ptxas` itself
crashes — it does not print an error, it dies. So the user gets no kernel and no
useful message. The same text works if you turn optimization off, or if you aim
at a Hopper card, so nothing is wrong with the text; something inside NVIDIA's
assembler goes wrong.

## 5. Can an SMT solver model this?

**`below the IR level` — no IR-level equivalence checker can ever catch this.**

The question an SMT translation validator asks is "do these two IR modules
compute the same thing". Here there is no second module: the toolchain stops
before producing one. And the fault is not in any IR the checker could see —
TTIR, TTGIR and LLVM IR are all produced without complaint, and the PTX is
accepted by the same assembler one optimization level down. The defect lives in
a closed-source binary that runs *after* the last IR the checker models.

This is worth recording as a ground-truth data point for the tv project,
because it marks the ceiling precisely. Even a perfect model of Triton's IR
semantics — exact bit-level floating point, layouts as index permutations,
shared memory as a second address space, a full concurrency model — would report
"equivalent" here and be right. Everything Triton did was correct. The only
tools that reach this fault are differential testing against `-O0` (which is
exactly how it was found and confirmed) and fuzzing ptxas directly.

One narrower question *is* in reach and is worth separating out: a checker could
verify that the PTX Triton emits is well-formed. But well-formedness is not the
issue — ptxas at `-O1` proves the file is well-formed.

## 6. Confidence

**High that the observation is right; the root cause is explicitly unknown.**

Certain: the file segfaults ptxas 12.9.86 at sm_89 `-O2`/`-O3`, and does not at
`-O0`/`-O1` or at sm_90/sm_90a. That is a self-contained, one-command
reproduction with no Triton, no Python and no GPU in it, and it was run for
every cell of the table above.

Not established: which stage inside ptxas crashes, and whether the PTX has some
unusual property (very long straight-line body from `num_warps=1` with an 8192
element reduction, 80 `shfl.sync`, an fp8 store) that a shrunk file would expose.
A minimized `.ptx` would settle that; I judged hand-shrinking a 2868-line SSA
body a poor use of the review's time, and a wrong cut would be worse than no cut.

Not established either: whether other CUDA versions are affected. That is the
first thing to check before filing this with NVIDIA — if 13.x is clean, the fix
already exists upstream and the practical action for Triton is a version note,
not a workaround.
