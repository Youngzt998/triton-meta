# HIT-0050: ptxas 12.9 segfaults in its register allocator on a heavily spilling sm_90a cumulative-sum kernel

Verdict: **CONFIRMED — the assembler crashes** (`ptxas` dies with SIGSEGV;
         Triton reports `PTXASError: 'ptxas' failed with error code -11`)
Arch:    **sm_90a only** — the PTX carries `.target sm_90a`, so it cannot even
         be handed to sm_80 or sm_89. Not a Triton-side arch dependence.
Line:    r2-compile (R4, compile-only, no GPU)
Culprit: **not Triton.** `ptxas` V12.9.86 (`cuda_12.9.r12.9/compiler.36037853_0`),
         shipped in `third_party/nvidia/backend/bin/ptxas`. The PTX is valid:
         the same file assembles cleanly at `--opt-level 0` and `1`, and at any
         optimisation level once `--regAllocOptLevel=0` is given.
Class:   R4 `crash-python`, rule `F14`, signature
         `PTXASError@compiler.py:630:Repro command: ptxas ... --regAllocOptLevel=N --gpu-name=sm_Na ...`
Occurrences: 1, kernel `ind:triton_per_fused_logcumsumexp_0_1f363aee`.
Review:  **KEPT** under REVIEW-CRITERIA §2, last bullet. Checked against the
         other kept `ptxas` reports and it is **not** a duplicate of any of
         them — see §1.
SMT verdict: **below the IR level** — no IR-level checker can reach it.

## What goes wrong, in one sentence

`ptxas` takes a segmentation fault while allocating registers for one
23983-line PTX file, and turning the register allocator's optimisation off
(`--regAllocOptLevel=0`) is enough to make the same file assemble.

---

## 1. Root cause in the source

**There is no Triton source line to point at.** Everything Triton produces here
is valid: the frontend, TTIR, TTGIR, LLVM IR and PTX stages all complete, and
the PTX they produce is accepted by the very same `ptxas` binary at a lower
optimisation level. The fault is inside NVIDIA's closed-source assembler.

What I *can* pin down is which part of `ptxas` and under which switches, all
measured on the committed `HIT-0050/ptxas-segv-sm90a.ptx`:

| switches | result |
|---|---|
| `--gpu-name=sm_90a` (default `-O3`) | **SIGSEGV** |
| `--opt-level 0`, `--opt-level 1` | ok |
| `--opt-level 2`, `--opt-level 3` | **SIGSEGV** |
| `-O3 --regAllocOptLevel=0` | **ok** — 128 registers, 1640-byte stack frame, 7504 B spill stores, 12136 B spill loads |
| `-O3 --regAllocOptLevel=1 / 2 / 3` | **SIGSEGV** |
| `--maxrregcount=32 / 64 / 128 / 255` | **SIGSEGV** at all four |
| `--gpu-name=sm_80`, `sm_89`, `sm_90` | refused before compiling — the PTX says `.target sm_90a` |

`--regAllocOptLevel=0` rescuing it, while `--maxrregcount` changes nothing,
places the crash in the **optimising register allocator**, not in the
instruction selector and not in a register-budget check.

The input that provokes it is a fully unrolled scan. The kernel is
`tl.associative_scan` over 128 lanes at `num_warps = 1`, which after unrolling
is 22556 instructions in one function — 5280 `fma.rn.ftz.f32`, 3824 `mov.b32`,
2240 `selp.f32`, 192 `shfl.sync` — with heavy spilling (7.5 KB of spill stores
even in the run that succeeds). Big, spill-heavy, single-function input is the
kind of thing that finds allocator bugs.

**Distinct from the already-kept `ptxas` reports.**

* `r2-compile/HIT-0047` is also a `ptxas` SIGSEGV at `-O2`/`-O3`, so this
  needed a real check rather than an error-string comparison. It is a different
  crash: under `gdb` the two die at **different addresses with different call
  chains** — HIT-0050 at `0x961948` (callers `0x97cfe8, 0x986540, 0x98c12e,
  0x991be2, ...`), HIT-0047 at `0xa910d0` (callers `0x943bfd, 0xb6622f,
  0xa41ee7, 0xd802a3, ...`); they share only the outermost driver frame
  `0x6bdf1f`. And they answer the register-allocator switch in opposite ways:
  HIT-0047 is *insensitive* to `--regAllocOptLevel` (crashes at 0–3), this one
  is cured by `--regAllocOptLevel=0`. Different arch too: HIT-0047 is sm_89 and
  is clean at sm_90/sm_90a; this file is sm_90a.
* `ttgir-broad/HIT-0008` and `r2-corpus/HIT-0024` are `ptxas` **wrong-code**
  reports — it finishes and emits bad SASS. Here nothing is emitted at all.
* The six `Insufficient registers` reports that pass 2 rejected as
  `resource-limit` are `ptxas` **reporting** a limit and Triton raising a typed
  error. This is a segmentation fault: the assembler lost control of itself.

## 3. Where it reproduces

Wherever this `ptxas` build runs. It is a host-side program, needs no GPU, and
the crash is deterministic: 8 of 8 invocations in the table above behaved the
same. The relevant version axis is the CUDA toolkit, not the machine —
**V12.9.86**. It must be re-checked against a newer toolkit before anything is
reported to NVIDIA; if a later `ptxas` assembles the file, this report is
closed.

The target is `sm_90a`, so a Hopper feature level is required, but nothing in
the PTX is Hopper-specific in an interesting way — no wgmma, no TMA, no
mbarrier, no cluster instruction. It is an ordinary spill-heavy scalar
float kernel that happens to have been compiled for `sm_90a`.

## 4. Plain-language explanation

Triton turned the kernel into PTX, which is NVIDIA's portable assembly. The
tool that turns PTX into real machine code, `ptxas`, then crashed with a
segmentation fault instead of either producing code or printing an error.

The kernel is a running-total ("scan") over 128 values, and with only one warp
the compiler unrolls the whole thing, so a single function ends up with about
22 thousand instructions and far more live values than the chip has registers.
`ptxas` therefore has to park many of them in memory. When told to do that job
carefully it crashes; when told to do it in the simplest possible way
(`--regAllocOptLevel=0`) it finishes and the code is fine. So the fault is in
the part of NVIDIA's assembler that assigns registers, and Triton is not at
fault.

## 5. Can an SMT solver model this?

**No — below the IR level, and doubly out of reach because there is no output
to compare.**

Two independent reasons:

1. *Nothing is produced.* An equivalence check needs two programs and compares
   their results. Here one side never gets built, so there is no pair. This is
   the same shape as the crash reports in this line: a validator placed after
   any Triton pass would prove the IR fine and be right, because the IR *is*
   fine.
2. *The fault is under the IR.* Even if the question were rephrased as "is the
   generated machine code equivalent to the PTX", the failing step is inside a
   closed-source assembler. Modelling it needs a SASS-level semantics and the
   assembler's own internals, which no Triton-IR checker has.

The useful thing this records for the translation-validation project is the
same ceiling `r2-corpus/HIT-0024` records: proving the IR transformation
correct is necessary but not sufficient. What an IR checker *can* do here is
narrow the blame — showing the IR path is clean is exactly what turns "the
compiler broke" into "the assembler broke".

## 6. Confidence

**Very high that the crash is real and that Triton is not at fault.** It
reproduces from a committed file with a single command and no Triton in the
loop, it is deterministic, and the same file assembles under two different
switch settings, which is proof that the PTX itself is well formed.

**High that it is distinct from `HIT-0047`,** on two independent grounds: the
`gdb` crash addresses and call chains differ completely, and the two answer
`--regAllocOptLevel` in opposite ways. What would settle the last doubt: a
`ptxas` build with symbols, or NVIDIA confirming the two crash sites are
different defects.

**The open question is whether it is already fixed upstream.** I tested exactly
one toolkit, the one in this checkout. A run against CUDA 12.10+ is the next
step and costs one command.
