# HIT-0002: `tl.float8e4b15` says "I am floating point" but its MLIR type is `i8`, so the frontend builds `arith.cmpf` / `arith.addf` on integers

Verdict: **CONFIRMED — kept**
Arch:    generic (sm_80, sm_89, sm_90 — the failure is in the frontend, before any target pass)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    invalid IR built by the Python frontend (MLIR verifier error at TTIR parse time)
Culprit: **the Triton Python frontend** —
`python/src/ir.cc:1055` (the type mapping) together with
`python/triton/language/core.py:403` (the `is_floating()` classification)

Input realism: **the fuzzer swapped a pointer dtype** — it drew `inp: *fp8e4b15`
for a kernel whose corpus author used a different element type. Weigh that
lower: nobody wrote this exact program. But see §3 and §6 — `tl.float8e4b15` is a
documented, exported Triton dtype, `tl.min` on a tensor of it is an ordinary
thing to write, and Triton owes a diagnostic rather than invalid IR.

Occurrences: **6** = 3 under the `arith.cmpf` signature (this report) + 3 under
the `arith.addf` signature (HIT-0015, rejected as a B4 duplicate — same root
cause; see §1). All three archs (sm_80, sm_89, sm_90).

---

## 1. Root cause in the source

Two facts that contradict each other:

**Fact A — `fp8e4b15` has no MLIR floating-point type; it is lowered to `i8`.**
`python/src/ir.cc:1055`:

```cpp
.def("get_fp8e4b15_ty",
     [](TritonOpBuilder &self) -> Type {
       return self.getBuilder().getI8Type();     // <-- an INTEGER type
     })
```

This is deliberate and is stated in the tree:
`python/triton/language/semantic.py:1461` carries the comment
`# We upcast because there's no fp8e4b15 type in MLIR`. Every other fp8 name maps
to a real MLIR float type (`fp8e4nv` → `Float8E4M3FNType`, `fp8e5` →
`Float8E5M2Type`, …); `fp8e4b15` is the one exception, because it is a software
format with no hardware type behind it.

**Fact B — at the Python level, `fp8e4b15` is classified as floating point.**
`python/triton/language/core.py:403`:

```python
FP_TYPES = ['fp8e4b15', 'fp8e4nv', 'fp8e4b8', 'fp8e5', 'fp8e5b16', 'fp16', 'bf16', 'fp32', 'fp64']
```

so `dtype.is_floating()` returns `True` for it.

Every arithmetic and comparison builder in `python/triton/language/semantic.py`
dispatches on Fact B and then emits an op typed by Fact A:

| builder | line | emits |
|---|---|---|
| `Semantic.add` | 247–248 | `create_fadd` → `arith.addf` |
| `Semantic.mul` | 278–279 | `create_fmul` → `arith.mulf` |
| `Semantic.less_than` | 528–529 | `create_fcmpOLT` → `arith.cmpf olt` |
| `Semantic.equal` | 556–557 | `create_fcmpOEQ` → `arith.cmpf oeq` |

e.g.

```python
elif input_scalar_ty.is_floating():
    return self.tensor(self.builder.create_fadd(input.handle, other.handle), input.type)
```

`is_floating()` is `True`, so `arith.addf` is built — on two values whose MLIR
type is `i8`. MLIR's own verifier rejects that immediately:

```
error: 'arith.cmpf' op operand #0 must be floating-point-like, but got 'i8'
error: 'arith.addf' op operand #0 must be floating-point-like, but got 'i8'
```

**Why a reduction is the usual trigger.** For a plain binary expression the
operands normally get promoted to a wider type first, which hides the problem.
A reduce or scan *combine region* does not promote: it is built directly over the
element type. Both observed symptoms come from there:

- **`arith.cmpf` (this report).** `tl.min(x, return_indices=True)` →
  `python/triton/language/standard.py:206` `_argmin_combine`, whose body is
  `value1 == value2` and `value1 < value2` → `create_fcmpOEQ` / `create_fcmpOLT`
  on `i8`. The failing IR shows exactly predicates 1 (`oeq`) and 4 (`olt`) inside
  the reduce region.
- **`arith.addf` (HIT-0015, merged here).** `tl.cumsum(x)` →
  `standard.py:262` `_sum_combine`, whose body is `a + b` → `create_fadd` on
  `i8`.

One fix removes both: either give `fp8e4b15` a real MLIR float type, or stop
classifying it as floating point at the Python level and force an explicit
conversion (there already is one — see HIT-0007 and HIT-0008 for the two other
bugs in that conversion path).

## 3. Where it reproduces

**Every backend and every arch.** The judgement rests on:

- The failing stage is `frontend`: the IR is rejected the moment Triton parses
  the module it just built, before `convert-triton-to-tritongpu` and before any
  NVIDIA pass.
- The two facts that collide (`get_fp8e4b15_ty` returning `i8`;
  `fp8e4b15 ∈ FP_TYPES`) are in target-independent code — `python/src/ir.cc` and
  `python/triton/language/core.py`.
- R4 observed it on all three archs it swept (sm_80, sm_89, sm_90). AMD was not
  swept, but nothing in the mechanism is NVIDIA-specific; the AMD backend would
  hit the same frontend error.

**On user reachability.** The fuzzer chose the dtype, but the resulting program
is one a user can write:

```python
x = tl.load(p)              # p : *fp8e4b15
m = tl.min(x, axis=0)       # <-- invalid IR
```

`float8e4b15` is exported from `triton.language` (`__init__.py:200`) and
accepted in a kernel signature as `*fp8e4b15`. It is marked deprecated for `tt.dot`
operands on Hopper (`semantic.py:1457`) but not deprecated as a storage type.
So the class is not an artifact of dtype swapping; the swap only made it show up.

## 4. Plain-language explanation

Triton has a small 8-bit float format called `fp8e4b15`. MLIR, the compiler
framework underneath, has no type for that format, so Triton stores it as a plain
8-bit integer and converts it by hand with inline PTX when needed.

But the Python layer still lists `fp8e4b15` among the "floating point" types. So
when you write `a + b` or `a < b` on values of that type, Triton picks the
*float* add and the *float* compare — and hands them integers. MLIR checks the
types and refuses.

The two halves of Triton disagree about what this type is. The user's program is
fine; the compiler builds something it cannot accept.

## 5. SMT reachability analysis

**Not an equivalence question at all, and not even a semantics question — it is
a type-system question.**

1. **Root cause in semantic terms.** The constructs are `arith.addf`,
   `arith.cmpf` and the reduce/scan combine region of `tt.reduce` / `tt.scan`.
   The semantic error is that the operand *type* is an 8-bit integer while the
   operation is defined only on floating-point operands. There is no computation
   here that is "wrong"; there is a term that is not well-typed.
2. **Is the difference a pure input→output function difference?** No difference
   exists. Compilation stops at the frontend, so there is no second program and
   no output bits. Nothing depends on the kernel's runtime inputs, on scheduling,
   or on hardware.
3. **Fundamental verdict.** **Outside the equivalence question.** An SMT
   equivalence checker is handed two programs and asked whether they agree; here
   only one program was ever built, and it is rejected before it can be run or
   compared. Forcing one of the six labels would misrepresent it. Note also that
   an SMT model of the IR would *not even be able to build a formula* for
   `arith.addf : (i8, i8) -> i8` — the encoder would hit the same type error the
   verifier hit, which is the point: this is caught by typing, not by solving.
4. **Minimum semantic vocabulary required.** None, in the solver sense. What is
   needed is a *consistency check between two tables*: for every `tl.dtype`, the
   Python-level kind (`INTEGRAL` / `FLOATING` / `BOOLEAN`) must agree with the
   kind of the MLIR type that `dtype.to_ir()` returns. That is about ten lines of
   Python and it is checkable exhaustively — there are nine floating names and
   ten integer names.
5. **Would the abstraction hide it?** The FP axiom profile is irrelevant: no
   floating-point *value* is involved, only a floating-point *op name* applied to
   an integer. Neither the exact bit-to-bit profile nor the reassoc-allowed
   profile changes anything.
6. **Inherent cost.** Zero. A table comparison, not a query.

**What would catch this class instead:** a table-consistency assertion as above,
plus a frontend sweep that builds every `tl.` reduction and binary op once per
dtype — 19 dtypes × ~20 builders is a few hundred compiles and finds the whole
class in seconds. R4 found it by accident, through a random dtype draw; a
systematic dtype × operation matrix would find it on purpose.

## 6. Confidence

**High that the IR is invalid and that Triton produces it.** Read in the source
and confirmed by running: `get_fp8e4b15_ty` returns `getI8Type()`;
`FP_TYPES` contains `'fp8e4b15'`; the four `is_floating()` dispatch sites emit
`arith.addf` / `arith.cmpf`; the observed IR is
`"arith.cmpf"(%value1, %value2) : (i8, i8) -> i1` inside a reduce region, and
`"arith.addf"(%a, %b) : (i8, i8) -> i8` inside a scan region. The in-tree comment
`# We upcast because there's no fp8e4b15 type in MLIR` confirms the `i8`
representation is intentional, so the mismatch is not my misreading.

**Medium on the severity a Triton maintainer would assign.** The open question is
whether Triton considers arithmetic on `fp8e4b15` supported at all. My reading is
that it is not — the type exists to be *stored* and converted — but I found no
statement saying so, and the language exposes no way to find out other than
hitting this crash. Either way the outcome R4 measured is wrong: an unsupported
operation must produce a Python-level error naming the dtype, never invalid MLIR.

What would settle it: ask upstream whether `is_floating()` for `fp8e4b15` is
intended, or check whether `tl.min` on `*fp8e4nv` (a type with a real MLIR float
type) is considered supported — it builds valid TTIR and then fails later, in the
LLVM lowering, which is HIT-0004.

### Kernel source

```python
@triton.jit
def argmin_kernel_1_60cfa9bd(inp, mid_value, mid_index, M, BLOCK_SIZE: tl.constexpr):
    pid = ext_60cfa9bd.program_id(0)
    offset = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    inp_ptrs = inp + offset
    mask = offset < M
    max_value = get_dtype_max_60cfa9bd(inp.type.element_ty)
    inp_val = tl.load(inp_ptrs, mask=mask, other=max_value)
    min_val, min_index = tl.min(inp_val, axis=0, return_indices=True)

    mid_value_ptr = mid_value + pid
    min_index_ptr = mid_index + pid
    tl.store(mid_value_ptr, min_val)
    tl.store(min_index_ptr, min_index)
```

Drawn pointer types: `inp: *fp8e4b15`, `mid_value: *fp16`, `mid_index: *i64`.
