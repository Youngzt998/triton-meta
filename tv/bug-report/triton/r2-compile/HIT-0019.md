# HIT-0019: `PlanCTA`'s cast-propagation loop has a fixed 10000-step budget, so any large enough kernel with `num_ctas > 1` aborts the compiler

Verdict: **CONFIRMED — kept**
Arch:    sm_90 and newer (`num_ctas > 1` needs Hopper thread-block clusters)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    assertion failure inside `TritonGPUPlanCTAPass` (compiler abort, not a diagnostic)
Culprit: **`lib/Dialect/TritonNvidiaGPU/Transforms/PlanCTA.cpp:158-188`**,
`CTAPlanner::run` — budget at line 160, assert at line 164

Input realism: **the kernel keeps its own pointer dtypes.** Nothing about the
program is synthetic — it is a hand-written Jacobi SVD kernel from the bench
corpus, all `*fp32`. The only unusual thing the user has to do is pass
`num_ctas=2`.

Occurrences: **69** as of 2026-08-19 19:00, sm_90 only, across at least 4 distinct
kernels (`bch:_small_jacobi_svd_kernel`, `bch:_fused_backward_kernel`,
`bch:max_pool3d_forward_kernel`, `bch:_small_jacobi_svals_kernel`). This is the
**fifth** independent defect this line has found in `TritonGPUPlanCTAPass`, after
HIT-0001, HIT-0003, HIT-0005 and HIT-0006.

---

## 1. Root cause in the source

Checkout: `/home/youngzt/fuzz/triton-public`, commit `3277063a6` (public
triton-lang, version `3.8.0+git3277063a`).

`PlanCTA` decides how the CTAs of one cluster are spread over the axes of each
tensor. It does that by inserting `CastOp` markers and pushing them onto a
worklist, then draining the worklist until every cast has been resolved. The
whole driver is `PlanCTA.cpp:158-188`:

```cpp
void CTAPlanner::run(triton::FuncOp &funcOp) {
  static const unsigned maxSteps = 10000;                 // line 160

  auto nextStep = [&]() {
    ++step;
    assert(step < maxSteps && "Maximum number of steps exceeded");   // line 164
  };

  processDot(funcOp);            nextStep();
  processReduce(funcOp);         nextStep();
  if (!tiled) { processStoreLikeOps(funcOp); nextStep(); }

  while (!queue.empty()) {                                // line 178
    CastOp cast = queue.front();
    queue.pop();
    bool changed = propagate(cast);
    if (changed) {
      stepUnchanged = 0;
    } else {
      queue.push(cast);                                   // re-queued, retry later
      ++stepUnchanged;
    }
    nextStep();
  }
}
```

Two things about that loop are wrong together:

**(1) The budget is a constant, the work is not.** `maxSteps` is a hard-coded
`10000` with no relation to the size of the function. The number of casts pushed
onto the queue grows with the number of tensor-valued ops: `processOpFallback`
(lines 872-899) alone pushes one cast per tensor operand **and** one per tensor
result of every op it cannot handle specially. So the step count grows with the
function while the budget stays put.

**(2) Each stalled cast costs a lap of the whole queue, so the growth is
super-linear.** The only place `stepUnchanged` is read is
`processMultiUsersBackward`, line 911:

```cpp
      if (stepUnchanged <= queue.size())
        return false;          // give up for now, try again after a full lap
```

That is a deliberate "let everything else settle first" rule: a value with
several users is not split until the worklist has gone `queue.size()` steps
without any progress. Every such value therefore costs `O(|queue|)` steps of
pure re-queueing, and `|queue|` is itself proportional to the function size. So
the total step count grows roughly as the square of the number of tensor ops.

**(3) The reaction to running out is an assert, not a diagnostic.** Tripping
line 164 is an `abort()`. The user gets a C++ file and line number. There is no
message naming the kernel, `num_ctas`, or the fact that a budget was exhausted,
and there is no way to raise the budget.

**Measured: the trigger is function size, not any one construct.** The corpus
kernel is a Jacobi SVD whose rotation loop is `tl.static_range`, so it unrolls to
`K*(K-1)/2 * SWEEPS` copies of one identical block. Compiling the *same* kernel
at different `K` / `SWEEPS`, everything else fixed at `num_ctas=2`, and counting
the tensor-valued ops in the module `PlanCTA` receives:

| `K` | `SWEEPS` | rotation blocks | tensor-valued ops into `PlanCTA` | result |
|---|---|---|---|---|
| 3 | 2 | 6 | 367 | compiles |
| 4 | 1 | 6 | 391 | compiles |
| 3 | 3 | 9 | 499 | **assert at line 164** |
| 4 | 2 | 12 | 655 | **assert at line 164** |

The failing modules are *more copies of the block the passing modules already
handle*, so the pass is not stuck on a structure it cannot process — it runs out
of a fixed budget. The boundary sits between ~391 and ~499 tensor-valued ops,
i.e. about 20-25 steps per tensor op against a budget of 10000.

**What I could not determine.** Whether the loop would terminate given an
unlimited budget. Settling that needs a build with the assert removed (or with
`maxSteps` raised), and rebuilding the compiler was out of scope for this review.
Both readings are real defects and both have the same fix shape — a diagnostic
instead of an `abort()` — but the honest statement is: *measured*, the step count
scales with function size and a fixed 10000 is not enough for a 500-op function;
*not measured*, whether some function would spin forever.

## 3. Where it reproduces

**sm_90 (Hopper) and newer, only — and that is a property of the trigger, not of
the code.** `num_ctas > 1` is the gate; Triton refuses it below sm_90. All 69
recorded occurrences are sm_90.

What that judgement rests on: the failing IR contains **no** Hopper-only
construct — no `wgmma`, no TMA, no `mbarrier`, no cluster intrinsic, no warp
specialization. It is plain `tt.load` / `arith` / `tt.reduce` / `tt.store` on
`#ttg.blocked` layouts, and it fails *before* any Hopper-specific lowering runs.
The pass itself lives in the NVIDIA-specific `TritonNvidiaGPU` dialect, so this
is NVIDIA-only in the trivial sense that the pass does not exist elsewhere, but
nothing in the failing path is Hopper hardware. Blackwell (sm_100) also accepts
`num_ctas > 1` and runs the same pass; I could not test it (this box is 8× H100
and PLAN.md §11 warns the local ptxas is version-skewed for sm_100), so sm_100 is
a prediction from the source, not a measurement.

Independent of `num_warps`, `num_stages`, `maxnreg`, `enable_fp_fusion` and
pointer dtypes — the 69 occurrences differ in those and agree on `num_ctas > 1`
plus a large function.

## 4. In plain words

On an H100 you can run one program as a *cluster* of several thread blocks
(`num_ctas=4`). A compiler pass then has to decide, for every tensor in the
kernel, which block holds which part. It does this by putting a marker on each
tensor and working through a to-do list until all markers are resolved.

The to-do list has a hard stop after 10000 items. That number is fixed; the
length of the list is not — it grows with the size of the kernel, and worse than
in a straight line, because one rule in the pass makes a marker wait for a full
pass over the whole list before it will act.

So a kernel that is merely *big* runs past the stop. When it does, the compiler
does not say "this kernel is too large for the cluster planner"; it aborts on an
internal check and prints a C++ file name. In this case the kernel is a Jacobi
SVD with its rotation loop unrolled nine times — 500 tensor operations, which is
not a large kernel by any normal measure.

## 5. Can an SMT solver model this?

**Verdict: out of reach for an SMT equivalence checker, and unlike HIT-0016 it is
also out of reach for a well-formedness obligation on the IR. This is a
termination / cost property of a compiler algorithm, not a property of the
program being compiled.**

1. **No second program to compare.** The pass aborts, so there is no "after"
   module. An equivalence query `f_before ≡ f_after` cannot be written down.
   Same reasoning as `tv/bug-report/tilelang/CODEGEN-0001`.

2. **And there is no semantic obligation to state either.** This is the
   important difference from HIT-0016. There, the compiler had a *false belief
   about the IR* (a count that omits the CTA dimension), and that belief is a
   sentence about layouts which a solver can refute once and for all. Here the
   compiler's belief is about **itself**: "my worklist finishes in under 10000
   iterations". Nothing about the input kernel's semantics is wrong, and no
   property of `tensor<...>` values, layouts, or memory is being violated. The
   input is a perfectly ordinary module.

3. **What class of tool would catch it.** Termination and iteration-bound
   analysis of the *pass source*, not of the IR — a completely different
   activity from translation validation. In practice the things that would have
   caught it are much more ordinary:
   - a lit test for `PlanCTA` on a few hundred ops (the pass has **none**; the
     file's closing TODO asks for some);
   - replacing the `assert` with a real diagnostic, which turns a crash into a
     supported error and makes the limit visible;
   - making the budget a function of the worklist length instead of a constant.

4. **A checker that ran the pass would notice — but only as a hang or a
   crash, not as a proof.** A validator that compiles both arms would inherit the
   abort. That is a testing signal, which is exactly what this fuzzing line is,
   and it is how the defect was found. It is not an SMT result.

5. **Cost.** Not applicable — there is nothing to encode.

So: `below the level an IR equivalence checker can see`, and unlike most entries
in this campaign, also outside what a stronger IR-level checker could reach. The
right tool is a test and a diagnostic.

## 6. Confidence

**High that this is a genuine compiler defect; medium on the precise mechanism.**

Genuine, because: it reproduces in a single `triton-opt` pass on one committed
`.mlir` file; the same kernel compiles at `num_ctas=1`; the failure is an
`assert`, which by construction is the compiler's own invariant about itself, not
a judgement about the input; and the input is an unremarkable `*fp32` kernel with
no exotic construct.

The part I am less sure of is whether the underlying flaw is "budget too small"
or "worklist can stall forever". The measured size sweep (367 and 391 ops pass;
499 and 655 fail, on modules that are literally more copies of the same block)
points hard at the budget, and 23 ms for 10000 steps says the pass is spinning
rather than working. But I did not rebuild the compiler with the assert removed,
so I cannot state that the loop terminates.

What would settle it: build with `maxSteps` raised to, say, `10^7` and re-run
`plan-cta-maxsteps.mlir`. If it completes, the defect is a fixed budget plus a
super-linear worklist and the fix is a diagnostic plus a size-aware bound. If it
does not, the defect is a genuine stall in `propagate` and the fix is in the
propagation rules. Either way the assert must become a diagnostic: aborting the
process is never the right answer to "this kernel is bigger than I planned for".
