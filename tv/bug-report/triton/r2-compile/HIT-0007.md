# HIT-0007: the `fp8e4b15` conversion helper ignores its destination type unless it is fp32, so a cast silently returns fp16 and `tt.store` gets the wrong value type

Verdict: **CONFIRMED — kept**
Arch:    generic (sm_80, sm_89, sm_90 — the failure is in the frontend)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    invalid IR built by the Python frontend (MLIR verifier error at TTIR parse time)
Culprit: **`third_party/nvidia/language/cuda/utils.py:87-93`**, `convert_custom_float8`,
reached from `python/triton/language/semantic.py:823-826` (`Semantic.cast`) and
`semantic.py:1221` (`Semantic.store`)

Input realism: **the fuzzer swapped a pointer dtype** — it drew `key: *fp8e4b15`
for a kernel whose corpus author used another type. Weigh it lower. But the
defect it exposes is not about the dtype draw: **`Semantic.cast` can return a
value whose type is not the type it was asked for, and nothing checks.** That is
a hole in the frontend's type discipline, and any cast out of `fp8e4b15` to
anything other than fp32 walks into it.

Occurrences: **6**, on all three archs (sm_80, sm_89, sm_90), across at least 2
distinct kernels (`bch:reshape_and_cache_flash_kernel_476250f6`,
`bch:pixel_unshuffle_kernel_4e20b588`).

---

## 1. Root cause in the source

`fp8e4b15` has no MLIR type (it is stored as `i8` — see HIT-0002), so Triton
converts it with hand-written inline PTX supplied by the backend. The NVIDIA
backend registers that helper at
`third_party/nvidia/backend/compiler.py:253-260`:

```python
codegen_fns = {
    "convert_custom_types":
    cuda.convert_custom_float8_sm80 if capability >= 80 else cuda.convert_custom_float8_sm70,
    ...
}
```

and `Semantic.cast` routes **every** cast that touches `fp8e4b15` through it,
`python/triton/language/semantic.py:823-826`:

```python
if (src_sca_ty.is_fp8e4b15() or dst_sca_ty.is_fp8e4b15()):
    assert self.builder.codegen_fns.get("convert_custom_types") is not None, \
        "target doesn't provide conversion for this type."
    return self.builder.codegen_fns["convert_custom_types"](input, dst_ty, fp_downcast_rounding, _semantic=self)
```

Note that `cast` **returns whatever the helper returns**, with no check that the
result actually has type `dst_ty`.

The helper, `third_party/nvidia/language/cuda/utils.py:87-93`:

```python
@core.builtin
def convert_custom_float8(arg, dst_ty, fp_downcast_rounding, has_minx2, _semantic=None):
    if arg.type.scalar.is_fp8e4b15():
        upcast_val = convert_fp8e4b15_to_float16(arg, _semantic=_semantic)   # -> f16
        if dst_ty.scalar.is_fp32():
            upcast_val = upcast_val.to(core.float32, _semantic=_semantic)
        return upcast_val            # <-- for EVERY other dst_ty: returns f16
    ...
```

**The upcast branch handles exactly two destinations, fp16 and fp32, and
silently returns fp16 for all the rest.** Ask it for `fp8e4b15 → int32` and you
get an fp16 value labelled as the result of a cast to int32. Ask for
`fp8e4b15 → fp64`, or `→ bf16`, or `→ int8`: same.

The failure then surfaces at the first op that checks the type. Here it is the
store, `python/triton/language/semantic.py:1211-1221`:

```python
ptr_ty = ptr.type.scalar
elt_ty = ptr_ty.element_ty      # int32, because key_cache is *i32
...
val = self.cast(val, elt_ty)    # returns an f16 tensor
...
create_masked_store(ptr.handle, val.handle, mask.handle, cache, eviction)
```

producing

```mlir
"tt.store"(%46, %47, %13) : (tensor<512x!tt.ptr<i32>>, tensor<512xf16>, tensor<512xi1>) -> ()
```

```
error: 'tt.store' op failed to verify that value type matches ptr type
```

In the failing kernel the chain is: `key: *fp8e4b15` is loaded, giving a
`tensor<512xi8>` that Triton labels `fp8e4b15`; `tl.store(key_cache + idx,
tgt_key)` asks for a cast to `int32`; the helper returns fp16; the store is
built with mismatched types.

Two things are wrong and both are worth fixing:

1. `convert_custom_float8` should handle, or explicitly reject, every
   destination type. Today it does neither.
2. `Semantic.cast` should not return a value whose type differs from `dst_ty`.
   One assertion at line 826 turns a silent type-system hole into a clear error
   naming the dtype pair.

Note the downcast direction of the same helper does at least fail loudly —
`utils.py:94` is `assert arg.type.scalar.is_fp16() or arg.type.scalar.is_fp32()`.
It is only the upcast branch that returns the wrong type quietly.

## 3. Where it reproduces

**Every backend and every arch that registers a `convert_custom_types` helper —
in practice all of them.** The judgement rests on:

- The failing stage is `frontend`: the module is rejected as soon as Triton
  parses what it just built, before `convert-triton-to-tritongpu`.
- `Semantic.cast`'s unchecked return (`semantic.py:826`) is target-independent
  code.
- The two NVIDIA helpers (`convert_custom_float8_sm80` and `..._sm70`) both
  delegate to the same `convert_custom_float8`, so both compute capabilities
  behave identically. R4 confirmed the class on sm_80, sm_89 and sm_90.
- The interpreter has its own copy at
  `python/triton/runtime/interpreter.py:353`; I did not check whether it has the
  same hole, so `TRITON_INTERPRET=1` behaviour is unknown.
- AMD registers its own `convert_custom_types`; not tested here. The unchecked
  `cast` return is shared, so the *shape* of the bug is shared even if AMD's
  helper covers more destinations.

## 4. Plain-language explanation

`fp8e4b15` is an 8-bit float that only Triton knows about, so converting it to
anything needs a special hand-written routine.

That routine knows how to turn it into a 16-bit float, and how to go one step
further to a 32-bit float. For every other target type — a 32-bit integer, a
64-bit float, whatever — it just hands back the 16-bit float and says nothing.

So `cast(x, int32)` returns a 16-bit float. The caller believes it got an
integer. The store then writes a 16-bit float through an integer pointer, and
MLIR notices the types do not line up and stops.

The deeper problem is that a cast is allowed to return the wrong type at all.
One check inside `cast` would turn this into a clear message instead of confusing
IR.

## 5. SMT reachability analysis

**Outside the equivalence question — this is a type-soundness bug in the
frontend, and it is the kind an SMT equivalence check is least suited to.**

1. **Root cause in semantic terms.** The constructs are `tt.store`,
   `tt.elementwise_inline_asm` (the fp8e4b15 → fp16 PTX helper), and the
   frontend's `cast`. The semantic error: a cast operation whose stated result
   type is `int32` produces a value of type `f16`. The *stated* meaning and the
   *actual* meaning of one term disagree.
2. **Is the difference a pure input→output function difference?** No difference
   exists — compilation stops at the frontend. Nothing depends on runtime inputs,
   scheduling, or hardware.
3. **Fundamental verdict.** **Outside the equivalence question.** There is only
   one program, and it is rejected before it exists in compiled form. It is worth
   spelling out the deeper reason, because it applies to a whole family of
   frontend bugs: an SMT translation validator takes the IR as given and asks
   whether a *transformation* preserved meaning. This bug happens *before* there
   is an IR to validate — it is a mistake in the map from Python source to IR.
   Validating that map would require a formal semantics for the Triton *language*
   to compare the IR against, which is a different and much larger project than
   IR-to-IR equivalence. Nothing in `tile-smt`'s scope, which starts at TTIR,
   reaches it.
4. **Minimum semantic vocabulary required.** None, for the actual bug. The
   property is `typeof(cast(x, T)) == T`, which is a one-line assertion in the
   frontend. It is worth noticing that this is checkable *dynamically* at
   negligible cost, and that Triton simply does not do it.
   If one wanted the deeper property — "the inline PTX sequence really does
   compute the `fp8e4b15 → fp16` conversion" — that is below the IR level: the
   payload is a PTX string (`prmt.b32`, `lop3.b32`, `shr.b32`), and validating it
   means modelling PTX bit manipulation, not tensor semantics. **`below the IR
   level`** would be the right label for that question.
5. **Would the abstraction hide it?** FP axiom profile is irrelevant for the type
   error. For the PTX-payload question above it would be decisive: only an exact
   bit-to-bit encoding could check that the shift-and-mask sequence reproduces
   `fp8e4b15` semantics, and an uninterpreted-function encoding would treat the
   whole inline-asm op as an opaque function and prove anything about it.
6. **Inherent cost.** Zero for the type check. Exhaustive for the PTX question —
   `fp8e4b15` has 256 values, so the conversion can be verified by enumeration
   with no solver at all.

**What would catch this class instead:** an assertion at `semantic.py:826` that
the returned tensor has type `dst_ty`, plus a frontend matrix test — for each of
the 19 `tl` dtypes, cast to each of the other 18 and check that the result type
matches or that a clean error is raised. That is 342 tiny compiles and it pins
this bug, HIT-0008 and part of HIT-0009 in one run.

## 6. Confidence

**High.** The whole chain was read in the source, and the observed IR matches it
exactly at every step:

- `semantic.store:1221` calls `cast(val, elt_ty)` with `elt_ty = int32`;
- `semantic.cast:823-826` dispatches any `fp8e4b15` cast to `convert_custom_types`
  and returns its result unchecked;
- `compiler.py:257` binds that to `convert_custom_float8_sm80`;
- `utils.py:88-93` returns the fp16 value for every destination except fp32;
- the emitted IR is
  `"tt.store"(..., tensor<512x!tt.ptr<i32>>, tensor<512xf16>, tensor<512xi1>)`,
  and the preceding `tt.elementwise_inline_asm` is exactly
  `(tensor<512xi8>) -> tensor<512xf16>`, i.e. the fp8e4b15→fp16 helper.

Remaining doubt is only about how a maintainer would classify it: whether the
intended contract is "casting fp8e4b15 to a non-float type is unsupported" (then
the fix is an error message) or "it should work via fp16" (then the fix is the
missing `.to(dst_ty)`). Either way the current behaviour — returning a value of
the wrong type and letting the verifier find out — is wrong. Reading upstream's
intent, or asking, settles which patch.

### Kernel source

```python
@triton.jit
def reshape_and_cache_flash_kernel_476250f6(key, value, key_cache, value_cache,
                                            slot_mapping, block_stride, key_stride,
                                            value_stride, num_heads, head_size,
                                            block_size, k_scale, v_scale, n: tl.constexpr):
    token_idx = tl.program_id(0)
    slot_idx = tl.load(slot_mapping + token_idx)
    if slot_idx < 0:
        return
    block_idx = slot_idx // block_size
    block_offset = slot_idx % block_size
    i = tl.arange(0, triton.next_power_of_2(n))
    mask = i < n
    src_key_idx = token_idx * key_stride + i
    src_value_idx = token_idx * value_stride + i
    head_idx = i // head_size
    head_offset = i % head_size
    tgt_key_value_idx = block_idx * block_stride + block_offset * num_heads * head_size + head_idx * head_size + head_offset
    tgt_key = tl.load(key + src_key_idx, mask=mask)
    tgt_value = tl.load(value + src_value_idx, mask=mask)
    tl.store(key_cache + tgt_key_value_idx, tgt_key, mask=mask)      # <-- here
    tl.store(value_cache + tgt_key_value_idx, tgt_value, mask=mask)
```

Drawn pointer types: `key: *fp8e4b15`, `key_cache: *i32` (and `value: *fp32`,
`value_cache: *fp16`, `slot_mapping: *i64`, `k_scale: *fp32`, `v_scale: *fp8e5`).

### Occurrence count update (appended by the second review pass, 2026-08-19 19:08)

Two more ids for this same root cause, both rejected as B4 duplicates:
**HIT-0024** (`'arith.mulf' op requires the same type for all operands and
results`, 2) and **HIT-0039** (the same for `arith.addf`, 3). The verifier
message is different from this report's `tt.store` one, but the defect is
identical and I traced it in the IR rather than assuming it. In HIT-0024 the
failing op is

```mlir
%124 = "tt.elementwise_inline_asm"(%117) <{... packed_element = 4 ...}>
         : (tensor<4x1024xi8>) -> tensor<4x1024xf16>
%125 = "arith.mulf"(%123, %124)
         : (tensor<4x1024xf64>, tensor<4x1024xf16>) -> tensor<4x1024xf64>
```

`%124` is `convert_fp8e4b15_to_float16`'s inline PTX. `computation_type_impl`
(`python/triton/language/semantic.py:80-82`) correctly picked `float64` as the
common type and called `cast(x, float64)`; `convert_custom_float8` returned
`f16` because `dst_ty` is not fp32, and `binary_op_type_checking_impl` built the
`arith.mulf` on the two different types without checking. So this is the same
line of the same helper, reached through a binary operator instead of through a
store — a third symptom of "`Semantic.cast` can return a value whose type is not
the type it was asked for".

HIT-0039 3.
