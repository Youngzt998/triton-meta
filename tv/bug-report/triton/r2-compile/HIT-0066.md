# HIT-0066: the AxisInfo constant folder runs `%` and `/` on host integers with no zero check, so `arith.remsi x, 0` in the IR makes the compiler die with SIGFPE

Verdict: **CONFIRMED — kept**
Arch:    generic (seen on sm_80 x2, sm_89, sm_90; the code is target-independent
         host C++ in `lib/Analysis/`, and no GPU is involved)
Line:    r2-compile (R4, compile-only, no GPU)
Kind:    hard crash — SIGFPE (integer divide by zero) inside a compiler analysis
Culprit: **`lib/Analysis/AxisInfo.cpp:574`** (`RemOpAxisInfoVisitor::getConstantValue`)
         and the same hole at **`:506`** (`DivOpAxisInfoVisitor::getConstantValue`)
Oracle:  R4 compile-only (`crash-python`, classifier rule `F13`)
SMT verdict: no — a host-side crash in an analysis, there is no pair of
         programs to compare (§5)

Input realism: **the kernel keeps its own pointer dtypes.** No fuzzer dtype
swap is involved. The failing draw is `W_in = 1` on a reflection-pad kernel — a
one-pixel-wide image — which any user can pass. The minimal reproducer below is
9 lines of plain TTIR and needs no kernel at all.

Occurrences: **4**, on three archs (sm_80 x2, sm_89, sm_90), all at `num_ctas = 1`.
De-duplication signature: `RuntimeError@compiler.py:371:PassManager::run failed`.

**This is a new family.** It is not `PlanCTA` / `num_ctas > 1` (it reproduces at
`num_ctas = 1` and on sm_80), not the fp8-is-storage-only family (no fp8
anywhere), not `ptxas` (it dies before PTX exists), and not a frontend type hole
(the frontend builds valid IR; a *middle-end analysis* crashes on it).

---

## 1. Root cause in the source

`TritonGPUCoalesce` starts by building `ModuleAxisInfoAnalysis`
(`lib/Dialect/TritonGPU/Transforms/Coalesce.cpp:84`). That analysis walks every
op and, for a binary integer op whose two operands are both known constants,
computes the result constant **in host C++**:

```c++
// lib/Analysis/AxisInfo.cpp:570-578  RemOpAxisInfoVisitor::getConstantValue
std::optional<int64_t> getConstantValue(OpTy op, const AxisInfo &lhs,
                                        const AxisInfo &rhs) override {
  if (lhs.getConstantValue().has_value() &&
      rhs.getConstantValue().has_value())
    return {lhs.getConstantValue().value() % rhs.getConstantValue().value()};
  //                                       ^^^ no check that rhs != 0
  else if (rhs.getConstantValue().has_value() &&
           rhs.getConstantValue().value() == 1)
    return {0};
  return {};
}
```

The sibling visitor a few lines above has exactly the same hole for division:

```c++
// lib/Analysis/AxisInfo.cpp:502-508  DivOpAxisInfoVisitor::getConstantValue
    return {lhs.getConstantValue().value() / rhs.getConstantValue().value()};
//                                         ^^^ no check that rhs != 0
```

On x86-64 an `idiv` by zero raises `SIGFPE`. Nothing in Triton catches it, so
the compiler process dies. The symbolised stack, from the crash the pass prints:

```
#4  RemOpAxisInfoVisitor<arith::RemSIOp>::getConstantValue(...)  AxisInfo.cpp:574:46
#5  BinaryOpVisitorImpl<arith::RemSIOp>::getAxisInfo(...)        AxisInfo.cpp:95:26
#7  AxisInfoAnalysis::visitOperation(...)                        AxisInfo.cpp:1269:22
#11 mlir::DataFlowSolver::initializeAndRun(...)
#12 ModuleAxisInfoAnalysis::initialize(...)                      AxisInfo.cpp:1499:7
#20 mlir::triton::gpu::CoalescePass::runOnOperation()            Coalesce.cpp:84:45
```

### Why the divisor is a literal zero

The kernel is `reflection_pad2d`. Reflection padding of a `W_in`-wide row uses
the period `pW = 2 * (W_in - 1)`:

```python
Wm1 = W_in - 1
pW  = 2 * Wm1
t_w = tl.abs(x)
m_w = t_w % pW        # <-- x % 0 when W_in == 1
```

The draw sets `W_in = 1` (a constexpr after Triton's specialisation), so
`pW` folds to `0` and the frontend emits, verbatim:

```mlir
%16 = arith.remsi %c1_i32, %c0_i32 : i32
```

That op is legal MLIR. `arith.remsi` by zero is *undefined behaviour at run
time* — MLIR's own `arith.remsi` folder is careful about it and returns no
result rather than dividing — but it is a perfectly well-formed op that a
compiler must be able to walk over. Triton's analysis executes it on the host
instead.

### Three distinct triggers, one pair of functions

| trigger | site | result |
|---|---|---|
| `arith.remsi x, 0` | `AxisInfo.cpp:574` | SIGFPE (rc 136) |
| `arith.divsi x, 0` | `AxisInfo.cpp:506` | SIGFPE (rc 136) |
| `arith.divsi INT64_MIN, -1` | `AxisInfo.cpp:506` | SIGFPE (rc 136) — signed overflow, not division by zero |

`arith.remui` / `arith.divui` go through the same two templates
(`AxisInfo.cpp:1224-1225` registers `RemOpAxisInfoVisitor` for both `RemSIOp`
and `RemUIOp`), so the unsigned forms have the same hole.

### Why the Python side reports it as a bland `RuntimeError`

Under `triton-opt` the process simply dies with `Floating point exception
(core dumped)`. Under `triton.compile` the pipeline runs inside MLIR's crash
reproducer, which uses an `llvm::CrashRecoveryContext`; that catches the signal,
prints the reproducer and turns the crash into a returned failure. The user
therefore sees

```
RuntimeError: PassManager::run failed
```

with no message naming a cause. The compiler *did* lose control — the bland
exception hides it.

## 3. Where it reproduces

**Everywhere.** The judgement rests on three things:

1. The failing code is `lib/Analysis/AxisInfo.cpp` — core Triton, no target in
   it. `AxisInfoAnalysis` is a host-side dataflow analysis over TTGIR; it never
   looks at the compute capability.
2. The pass that triggers it, `tritongpu-coalesce`, is in
   `lib/Dialect/TritonGPU/Transforms/` and runs in every backend's `make_ttgir`,
   including AMD's.
3. The campaign already saw it on **sm_80, sm_89 and sm_90** (4 occurrences),
   at `num_ctas = 1`, with no Hopper-only construct anywhere in the IR — no
   wgmma, no TMA, no mbarrier, no cluster, no warp specialisation. The minimal
   file is plain TTIR with one `arith` op and one store.

It also needs no GPU: `triton-opt` crashes on a CPU-only box.

The blast radius is not limited to `tritongpu-coalesce`. Any pass that builds
`ModuleAxisInfoAnalysis` on the same module will die the same way — the pass
that happens to run first is the one that reports it.

---

## 4. Plain-language explanation

Triton tries to learn facts about each value while it compiles: is it a
constant, is it a multiple of 16, are neighbouring lanes contiguous. When it
sees `a % b` and already knows both `a` and `b`, it just computes `a % b` on the
compiler's own CPU and remembers the answer.

The kernel here has `x % 0` in it, because reflection padding of a 1-pixel-wide
row computes a period of `2 * (1 - 1) = 0`. Dividing by zero on a CPU is fatal:
the compiler is killed on the spot. It never even gets to say what went wrong —
the user just sees "PassManager::run failed".

`x % 0` at run time is a broken thing to ask the GPU to do, and the kernel is
arguably wrong to ask for it. But it is a legal instruction to *write down*, and
a compiler must survive reading it. The fix is one line in each of two places:
give up (return no constant) when the divisor is zero, the way MLIR's own folder
already does.

## 5. Can an SMT solver model this?

**No — and not because of a modelling limit, but because there is nothing to
compare.**

The five options in the criteria are all about a *value* difference between two
programs. Here there is one program and no output at all: the compiler process
receives `SIGFPE` and dies. An equivalence checker takes two programs and asks
whether they agree; it cannot be handed a compiler that crashed.

The semantics *at the root* is trivially expressible — "the divisor of an
`arith.remsi` may be zero" is a one-line SMT constraint, and a solver would find
the witness instantly. But the property to check is not about the program's
semantics, it is about the **compiler's own C++**: a host-side `idiv` executed
on a value the analysis never constrained. Catching that class needs a tool
pointed at the compiler (a sanitizer, a fuzzer, or an assertion in
`getConstantValue`), not at the IR.

There is one thing an IR-level checker *could* usefully say, and it is worth
recording: the value the analysis wanted to compute is **poison**, not a number.
A translation validator that modelled `arith.remsi x, 0` as poison would
immediately show that any constant the analysis records for it is unsound —
even in a build where the SIGFPE did not happen. So the *soundness* half of this
bug is in scope for an IR-level checker; the *crash* half is not.

---

## 6. Confidence

**Very high that it is a genuine compiler defect.** The evidence is direct, not
inferred:

* a symbolised backtrace naming the exact source line, `AxisInfo.cpp:574:46`;
* a 9-line hand-written TTIR that reproduces it with two `triton-opt` commands
  and no kernel, no Python, no GPU;
* two further hand-written files hitting the sibling `/` at `:506`, one by zero
  and one by `INT64_MIN / -1`;
* the fix is visibly missing — MLIR's own `arith` folder guards the same
  operation, and Triton's own `getDivisibility` a few lines up already tests
  `rhs.getConstantValue()` before using it, so the guard exists in the file,
  just not here.

**The remaining doubt is only about how much it matters, not about whether it is
real.** `x % 0` is undefined behaviour at run time, so one could argue the user
program was already broken. Two answers: (i) the compiler must still not die —
the criteria's §2 counts "compile failure, crash, or invalid generated code" as
a keep, and a `SIGFPE` with no diagnostic is the worst shape of it; (ii) the same
crash fires for `INT64_MIN / -1`, which is much easier to reach by accident.

What would settle the last doubt: check whether the analysis's recorded constant
is *used* on any path where the divide does not trap — for example an unsigned
`remui` by zero on a target whose host does not raise `SIGFPE`. If it is, the bug
is not only a crash but a silent wrong fact in the analysis, which would make it
strictly worse. I did not chase that.

### The failing kernel

```python
@triton.jit
def reflection_pad2d_kernel_00c19208(in_ptr, out_ptr, B, H_in, W_in, pad_left,
                                     pad_top, H_out, W_out,
                                     BLOCK_HW: tl.constexpr):
    pid_b = tl.program_id(axis=0)
    pid_n = tl.program_id(axis=1)
    offs_n = pid_n * BLOCK_HW + tl.arange(0, BLOCK_HW)
    h_idx = offs_n // W_out
    w_idx = offs_n % W_out
    mask = (offs_n < H_out * W_out) & (pid_b < B)
    base_in = pid_b * (H_in * W_in)
    base_out = pid_b * (H_out * W_out)
    y = h_idx.to(tl.int32) - pad_top
    Hm1 = H_in - 1
    pH = 2 * Hm1
    t_h = tl.abs(y)
    m_h = t_h % pH
    ih = tl.where(m_h < H_in, m_h, pH - m_h)
    x = w_idx.to(tl.int32) - pad_left
    Wm1 = W_in - 1
    pW = 2 * Wm1                     # 0 when W_in == 1
    t_w = tl.abs(x)
    m_w = t_w % pW                   # arith.remsi %c1_i32, %c0_i32
    iw = tl.where(m_w < W_in, m_w, pW - m_w)
    in_offs = ih * W_in + iw
    vals = tl.load(in_ptr + base_in + in_offs, mask=mask, other=0)
    tl.store(out_ptr + base_out + offs_n, vals, mask=mask)
```

Drawn shape: `{"scalars": {"B": 127, "H_in": 7, "W_in": 1, "pad_left": 1,
"pad_top": 1024, "H_out": 35, "W_out": 1}, "consts": {"BLOCK_HW": 1},
"dtype_swapped": false}`. Only `W_in = 1` matters; `H_in = 7` keeps `pH = 12`
non-zero, which is why the crash comes from the `w` half and not the `h` half.

Line numbers are those of the build under test,
`/home/youngzt/fuzz/triton-public`.
