# HIT-0043: dropping `StorageRewrite` leaves one buffer split into four, and the whole output becomes NaN

Verdict: **CONFIRMED — genuine compiler bug** (reviewed 2026-08-17)
Arch:    Hopper here (the kernel is warp-specialized by default and the trigger
         needs WS turned off), but nothing in the broken step is arch-specific
Line:    tilelang (TileLang 0.1.12, pypi wheel, H100 sm_90a, nvcc 12.8.93)
Culprit: `tl.LowerOpaqueBlock` splits one fragment buffer into four allocations
         and the pipeline relies on `tir.StorageRewrite` to merge them back.
         Trigger: drop `StorageRewrite` **and** turn warp specialization off —
         either with `{"tl.disable_warp_specialized": true}` or by dropping the
         `ProducerConsumerWarpSpecialized` pass; both routes give the same
         all-NaN output.

Summary: an attention-with-sinks kernel compiles to CUDA that reads local arrays
it never writes. **All 32768 output elements come out NaN.** The reference is
correct. Neither knob alone changes anything; together they expose a buffer that
`LowerOpaqueBlock` had split into four separate allocations and that only works
because `StorageRewrite` normally merges them back into one.

Labels: pass-class:numerics-changing, kernel-has-gemm, kernel-has-reduce,
input-mode:captured, nan-pattern-changed

**Occurrences: 2.** `HIT-0075` is the same bug on the same kernel, reached the
other way round: `skip StorageRewrite` + `skip ProducerConsumerWarpSpecialized`
instead of `skip StorageRewrite` + `tl.disable_warp_specialized`. Same all-NaN
output with the same first element, same two-knob requirement (neither alone
does anything), and the same signature in the generated CUDA — 14 local arrays
declared, read and never written (`scores_max_prev_2`, `scores_max_prev_3`,
`acc_s_2`, `acc_s_4`, `acc_s_8`, `acc_s_10`, `scores_scale_2/3/6/7`,
`scores_sum_2/5`), against none in the reference. It was rejected as a B4
duplicate and moved to `bug-report-rejected/tilelang/HIT-0075`.

## 1. Root cause in the source

**Symptom in the emitted CUDA.** `ir/candidate.cu` declares four `float[2]`
arrays for the one source-level `scores_max_prev`, and two of them are read
without ever being written:

```c
   85:  float scores_max_prev[2];      // 1 mention,  0 writes
   89:  float scores_max_prev_1[2];    // written at line 128
   91:  float scores_max_prev_2[2];    // read at line 144, NEVER written
   93:  float scores_max_prev_3[2];    // read at line 148, NEVER written
  128:    *(float2*)(scores_max_prev_1 + 0) = *(float2*)(scores_max_7 + 0);
  144:      scores_max_7[i_8]  = max(scores_max_7[i_8], scores_max_prev_2[i_8]);
  148:      scores_scale_1[i_9] = exp2f((scores_max_prev_3[i_9] * 0x1.0527dbd5cafffp-3f)
                                       - (scores_max_7[i_9]     * 0x1.0527dbd5cafffp-3f));
```

`acc_s` is split the same way (`acc_s_2` read, never written). The softmax then
runs on uninitialised registers, `exp2f(garbage - garbage)` produces NaN, and
the NaN spreads through the accumulator, so every element of `Output` is NaN.
`ir/reference.cu` has exactly one `scores_max_prev` and one `acc_s`.

**Where the split is made, measured pass by pass.** Dumping the IR after every
pass (`pass_configs={"tl.enable_dump_ir": True, "tl.dump_ir_path": ...}`) and
counting `alloc_buffer` nodes for `scores_max_prev`:

| dump file | candidate (no StorageRewrite) | reference |
|---|---|---|
| `020_tl.LowerTileOp.py` | 1 allocation + alias views `T.Buffer((2,), data=scores_max_prev.data)` | same |
| `033_tl.LowerOpaqueBlock.py` | **4 allocations** | **4 allocations** |
| `036_tl.FlattenBuffer.py` | 4 | 4 |
| `039_tl.VectorizeLoop.py` | 4 | 4 |
| next pass | `040_tl.LoopUnswitching.py`: still **4** | `040_tir.StorageRewrite.py`: **1** |
| `UnrollLoop` | **8** | 1 |

So:

1. `tl.LowerTileOp` (dump 020) is fine. It creates several `T.Buffer` *views*
   that all carry `data=scores_max_prev.data` — i.e. they explicitly share one
   backing storage `Var`.
2. `tl.LowerOpaqueBlock` (dump 033) turns those views into **four independent
   `alloc_buffer` nodes**. The `data=` link that said "this is the same storage"
   is gone. From here the program is only correct if something merges them
   again, because the write and the matching read now sit in different
   allocations.
3. `tir.StorageRewrite` (`tilelang/cuda/pipeline.py:186`) is that something: in
   the reference it collapses 4 into 1 and the kernel is correct.
4. With `StorageRewrite` dropped, the four survive into the C codegen, which
   emits one array per allocation. `UnrollLoop` then doubles them to eight.

The bug is step 2 relying on step 3. `StorageRewrite` is a storage-reuse
**optimization** — TileLang lists it next to `LoopUnswitching` and `UnrollLoop`,
and on other kernels dropping it only changes the generated text, not the
result (measured: on this same kernel, dropping `StorageRewrite` *alone* gives
bit-identical output). Making a correctness property depend on it is the defect,
and the failure mode is silent wrong data rather than an error.

**Why `tl.disable_warp_specialized` is also needed.** Measured on this kernel
and this input:

```
StorageRewrite drop only        -> differs = False
disable_warp_specialized only   -> differs = False
both                            -> differs = True, 32768/32768 NaN
```

With warp specialization on, the producer/consumer split routes the fragment
buffers through a different lowering and the aliases end up merged anyway. Not
investigated further; the two-knob requirement is a measurement, not a theory.

**Two possible fixes**, both worth considering:

* `LowerOpaqueBlock` should keep one allocation when the input buffers share a
  `data` var, instead of emitting one per view. Then nothing downstream has to
  repair it.
* Failing that, `StorageRewrite` must not be droppable on this path — and the
  pipeline should say so, the way `VectorizeLoop` and
  `MergeSharedMemoryAllocations` already fail loudly when removed.

## 3. Where it reproduces

* **The splitting step is target-independent.** `LowerOpaqueBlock` and
  `StorageRewrite` are both in the shared `tilelang.transform` set, called from
  every backend pipeline. Nothing in the four-way split depends on sm_90.
* **The trigger, as found, is Hopper-flavoured.** The kernel is warp-specialized
  by default on sm_90, and the failure needs WS switched off, so the exact knob
  pair here is specific to a target where WS is on in the first place. On a
  target with no warp specialization the `StorageRewrite` drop alone might be
  enough — not tested.
* **No GPU needed to see it.** The read-before-write is visible in the generated
  CUDA text, which `lower()` produces without nvcc.

## 4. Plain-language explanation

The kernel keeps a small scratch value per row — the previous maximum score of
the softmax. In the source that is one variable.

Partway through compilation the compiler rewrites the program in a way that
turns that one variable into four separate variables that are *supposed* to be
the same piece of memory. A later step, whose real job is just to save memory by
letting unrelated buffers share space, happens to glue the four back into one.
So the normal build works.

Turn that memory-saving step off — which should only ever cost memory, never
change results — and the four stay apart. The kernel now writes the previous
maximum into one of them and reads it back out of another one, which was never
written. It reads leftover register contents, the softmax computes `exp` of
nonsense, and every single output value becomes NaN.

## 5. Can an SMT solver model this?

**Yes — this is the good case for an IR-level checker, with one condition.**

* It is a deterministic, single-instance, value-semantics difference. One thread
  block's worth of straight-line code plus a small loop; both sides are
  bit-stable across repeats; no atomics, no cross-instance behaviour, no
  concurrency needed to expose it (the corruption is present with warp
  specialization *off*, i.e. in the simplest execution model).
* No floating-point reasoning is required either. The two sides differ because
  one of them reads a location that was never written. A checker with an
  abstract FP model — opaque values and uninterpreted operations — is enough:
  it only has to notice that one program's output depends on an unconstrained
  symbol.
* **The condition**: the memory model must distinguish "this buffer holds a
  written value" from "this buffer holds anything". A checker that initialises
  every local buffer to a fixed value (zero, say) would make both programs
  well-defined and might prove them *inequivalent* for the wrong reason, or
  *equivalent* for the wrong reason, depending on the constant. The honest model
  is an unconstrained fresh symbol per uninitialised location, with the property
  "the output must not depend on it". That is a standard uninitialised-read
  check, cheap, and it does not even need the second program.
* Scale is small: two 128x128 tiles and a 2-iteration loop. Well inside what a
  solver handles, and the bug shows up on element 0, so no deep unrolling is
  needed to reach it.

In short: a single-program uninitialised-read check would have caught this
without any equivalence machinery at all, and a value-equivalence check catches
it too. This is the class of bug an IR-level tool is actually good at.

## 6. Confidence

**High.**

* The generated CUDA objectively contains arrays that are read and never
  written; that is a property of the text, not an interpretation.
* The whole output is NaN, not a few ulp — no numeric licence explains it.
* `-fmad=false` does not remove it, and no fast-math knob is involved, so the
  two standard licences (contraction, fast math) are both excluded by
  measurement.
* Both binaries are self-consistent across repeats, so it is not a race.
* The pass-by-pass allocation counts show exactly where the one buffer becomes
  four and exactly which pass puts it back.

Remaining doubt, and how to settle it:

* *Is dropping `StorageRewrite` a supported configuration?* TileLang has no
  public switch for it — the campaign drops it by re-registering the pipeline.
  If TileLang's position is "the pass list is not a menu", then the finding
  should be re-filed as "`LowerOpaqueBlock` produces IR that is only correct
  after `StorageRewrite`", which is still a real defect, just a design one.
  A maintainer's answer settles this; nothing measurable here does.
* *Does the same split break a non-warp-specialized target?* Not tested. Compile
  the same kernel for a target without WS and drop `StorageRewrite` alone.
* *Which allocation should have been merged with which?* I confirmed the counts
  (4 -> 1) but did not trace each individual write to its intended read, because
  the C codegen renumbers names independently of the IR, so the names cannot be
  matched across the two. The counts and the never-written arrays are enough to
  establish the defect; a fix would need that mapping.
