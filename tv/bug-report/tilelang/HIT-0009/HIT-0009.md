# HIT-0009: `tl.enable_fast_math` turns `inf * denormal` into NaN

Verdict: **CONFIRMED as a bit difference; NOT a compiler bug.** Kept only
because a one-sided NaN is a never-reject case in
`tv/bug-report/REVIEW-CRITERIA.md` §2. (reviewed 2026-08-17)
Arch:    generic (plain elementwise kernel, no Hopper construct)
Line:    tilelang (TileLang 0.1.12, pypi wheel, H100 sm_90a, nvcc 12.8.93)
Culprit: **no TileLang pass.** `tl.enable_fast_math` only appends
         `--use_fast_math` to the nvcc command line. The generated CUDA is
         byte-identical on both sides.

Summary: with `tl.enable_fast_math`, 809 of 16384 outputs of a plain
`B = A * C` kernel differ, and 29 of them are NaN on the fast-math side only.
Every one of the 809 is explained by `-ftz=true` (denormals flushed to zero),
which `--use_fast_math` implies: 765 are a denormal result becoming `+-0`, 15
are a denormal *input* flushed before the multiply, and the 29 NaNs are
`inf * denormal` becoming `inf * 0`.

Labels: pass-class:numerics-changing, input-mode:extremes, nan-pattern-changed

---

## 1. Root cause in the source

Not in TileLang's IR. `tilelang/engine/lower.py:114` reads the pass config and
`:144-145` appends the flag:

```python
    enable_fast_math = bool(cfg.get(PassConfigKey.TL_ENABLE_FAST_MATH, False))
    ...
    if enable_fast_math:
        options.append("--use_fast_math")
```

Measured directly: with `{"tl.enable_fast_math": true}` the generated CUDA is
**1148 chars on both sides and `identical=True`**. Nothing in the IR changed;
only nvcc's flag list did. `nvcc --use_fast_math` implies `-ftz=true`
(denormals flushed to zero on input and output), `-prec-div=false`,
`-prec-sqrt=false` and `-fmad=true`.

The kernel is one multiply per element:

```python
for col in T.vectorized(128):
    B[row, col] = A[row, col] * C[row, col // 2]
```

With `-ftz=true` every denormal operand is read as `+-0` and every denormal
result is written as `+-0`. Three consequences, and all 809 differing elements
fall into them. Classification script
(`/home/youngzt/fuzz-tilelang/reviewer/chk_h9.py`), run on the failing draw:

```
differing elements                 809
  NaN only on the fast-math side   29
  NaN only on the stock side       0
  ... of which inf * denormal      29 / 29
  other differences                780
  ... of which denormal -> +-0     765 / 780
  the remaining 15: ref = +-6.55e-36, cand = +-0.0,
                    from A = +-65504.0 and C = +-9.99994610111476e-41
```

* 765: the product itself is denormal, e.g. `1e-40 * 1.0`, and gets flushed.
* 15: the product is **normal** (`65504 * 1e-40 = 6.55e-36`), but the *input*
  `1e-40` is denormal and is flushed to `0` before the multiply, so the answer
  is `0`.
* 29: `inf * 1e-40` is `inf` in IEEE, but `inf * 0` is NaN. This is the only
  reason the NaN counts differ (437 vs 466).

`1e-40` and `-1e-40` are two of the twelve special values the sweep's
`extremes` input mode injects (`tlfz/core.py:88-99`), which is why this only
shows up on `extremes` draws.

Note the sweep's minimal variant lists `tirx.disable_vectorize` as well. Checked
directly: it is not needed. `{"tl.enable_fast_math": true}` alone reproduces the
difference exactly; `{"tirx.disable_vectorize": true}` alone gives
`NO DIFFERENCE`.

## 3. Where it reproduces

**Any NVIDIA GPU, any CUDA version.** `-ftz=true` is documented nvcc behaviour
for `--use_fast_math`, not a TileLang or a Hopper property. The generated code
is a plain elementwise loop: no wgmma, no TMA, no mbarrier, no cluster, no warp
specialization, no `__syncthreads`, no atomics. Nothing in it is target-specific
beyond being CUDA.

It also is not TileLang-specific in any deep sense: the same source compiled by
hand with `nvcc --use_fast_math` would behave the same way.

## 4. Plain-language explanation

Very small numbers close to zero ("denormals") are slow on some hardware, so
`--use_fast_math` tells the compiler to treat them as zero. TileLang passes that
flag to nvcc when you set `tl.enable_fast_math`.

The test feeds the kernel some of these very small numbers together with
infinity. Multiplying infinity by a very small number gives infinity. But if the
very small number is first turned into zero, then it is infinity times zero,
which is "not a number". So the fast-math build produces 29 NaNs the normal
build does not, and 780 other places where a tiny answer became zero.

Nothing was compiled wrongly. This is what the flag is for.

## 5. Can an SMT solver model this?

**Yes in principle, but only with a bit-exact FP theory *and* an explicit model
of the flush-to-zero mode — and it is the wrong question to ask a checker.**

* The kernel is a single-instance, deterministic, elementwise map. No grid
  modelling, no concurrency, no memory ordering. Structurally this is the
  easiest shape there is.
* But the whole difference lives in FP corner cases: denormal ranges, signed
  zero, `inf * 0 = NaN`. An abstract FP model (opaque values, uninterpreted
  `mul`, a few axioms) cannot see it at all. You need `FPA` bitvector floats
  with explicit denormal handling, plus a second semantics for the same `mul`
  op parameterised by "ftz on/off". That means the checker must carry **two**
  interpretations of every arithmetic op and be told which side uses which.
* Even then the interesting answer is not "these two programs differ" — they
  obviously do, that is the flag's purpose — but "is the difference inside the
  licence the user asked for". Equivalence checking does not answer that
  question; it is a policy question.

So: expressible with a bit-exact FP theory and an ftz-aware op model, cheap to
solve, and not worth building for this purpose. The practical rule for the
campaign is the one already in the criteria: put `tl.enable_fast_math` in the
numerics-changing set and require a difference to survive without it.

## 6. Confidence

**High confidence that this is *not* a compiler bug.**

* The generated CUDA is byte-identical on both sides, so no TileLang pass is
  involved at all.
* All 809 differing elements — 100%, not a sample — are accounted for by three
  documented `-ftz=true` effects. Nothing is left unexplained.
* Removing `tl.enable_fast_math` removes the difference.

**Why the report is kept anyway.** `REVIEW-CRITERIA.md` §2 lists "NaN or Inf
appears on one side only" as a never-reject case, with no exception for
fast math. This report matches that bullet, so the reviewer keeps it rather than
apply criterion B1 on its own judgement. The criteria owner may want to add an
exception: `--use_fast_math` *can* manufacture a NaN out of finite inputs
(`inf * denormal -> inf * 0`), so a one-sided NaN is not by itself proof that
something outside a numeric licence happened.

What would change the reading: if a differing NaN could be produced with
`tl.enable_fast_math` **off**, this would become a real finding. It cannot be —
measured above.

## RETRACTED (2026-08-17 22:49:45)

The kernel `cap_6c3c978802144450` was later retired as `suspect-unstable`: 3 *distinct* culprit pass sets each produced a bit difference on it.  That pattern means the kernel itself is unstable under any code motion -- most likely an aliasing or ordering effect a static scan cannot follow -- not that 3 separate compiler bugs exist.  Treat this report as withdrawn.

### Reviewer note on the retraction (2026-08-17)

The retraction above is appended automatically by the sweep's
`suspect-unstable` net. **Its premise does not hold for this kernel, and the
report's conclusion is unchanged.** This report is pinned by the project owner
as the documented representative of the fast-math NaN class, and it still does
that job.

The net counts *distinct minimal culprit sets* and treats three as evidence of
an unstable kernel. Read off the campaign's own `run/results.jsonl`, the three
sets for `cap_6c3c978802144450` are:

```
{"skip": [],                          "cfg": {"tirx.disable_vectorize": true, "tl.enable_fast_math": true}}
{"skip": ["AnnotateReadOnlyParams"],  "cfg": {"tl.enable_fast_math": true}}
{"skip": [],                          "cfg": {"tl.enable_lower_ldgstg": true, "tl.enable_fast_math": true}}
```

All three contain `tl.enable_fast_math`. They are **one** cause with three
different, irrelevant companions — not three independent findings, and not
evidence of instability. The measurements in this report already pin that down:

* with fast math alone the generated CUDA is **byte-identical** on both sides
  (1148 chars each), so no TileLang pass is involved at all;
* all **809 of 809** differing elements are accounted for by `-ftz=true`
  (29 `inf × denormal → inf × 0 = NaN`, 765 denormal results flushed, 15
  denormal inputs flushed before the multiply);
* removing `tl.enable_fast_math` removes the difference, and each companion
  knob alone produces none.

So the kernel is not unstable — it is a two-line elementwise multiply that is
perfectly deterministic on both sides (verified across repeated runs and under a
17 MB heap shift). What is "unstable" is the *label*: any kernel whose corpus
sweep pairs fast math with several different companion knobs will trip a
count-distinct-sets heuristic. That is worth fixing in the net (collapse sets
that share a numerics-changing knob before counting), and it is the same class
of false signal this report was kept to document.

**Resolved.** The campaign line audited the net after this note. It had retired
**42 kernels, 41 of them wrongly** — the fast-math miscount described above,
plus the same error one level up: dropping the
`ProducerConsumerWarpSpecialized` pass and setting `tl.disable_warp_specialized`
(the config that makes the pipeline skip that same pass) were being counted as
two separate causes. All 41 kernels are back in the corpus and the bogus
retractions have been withdrawn. The net now ignores variants carrying a
numerics-changing knob and reads the pin list from `REVIEW-CRITERIA.md`.
**The `## RETRACTED` banner above is void**; it is left in place only as a
record of what happened.
