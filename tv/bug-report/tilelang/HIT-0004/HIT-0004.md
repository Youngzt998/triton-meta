# HIT-0004: vectorizing a `T.rng_rand_float` loop swaps in a curand API that returns different numbers

Verdict: **CONFIRMED — real value difference; genuine bug is likely but not
certain** (reviewed 2026-08-17)
Arch:    generic (plain serial loops, no Hopper construct)
Line:    tilelang (TileLang 0.1.12, pypi wheel, H100 sm_90a, nvcc 12.8.93)
Culprit: the CUDA codegen's vector printing of the `tl.rng_rand_float`
         intrinsic, enabled/disabled by `{"tirx.disable_vectorize": true}`

Summary: the same random-number kernel gives different numbers depending on
whether the loop vectorizer ran. With the vectorizer on (the default) TileLang
prints one `curand_normal4()` per 4 lanes; with `tirx.disable_vectorize` it
prints 4 separate `curand_normal()` calls. Those two curand entry points do
**not** produce the same values, so every element of three of the five output
tensors differs. The uniform-float and raw-uint32 outputs are bit-identical, so
the substitution is value-preserving for some distributions and not for others.

Labels: pass-class:bit-preserving, input-mode:captured, gross

---

## 1. Root cause in the source

**The substitution.** `src/cuda/codegen/codegen_cuda.cc`, lines 5404-5450
(`CodeGenTileLangCUDA`'s broadcast/vector-value printer). When the value being
broadcast to `lanes` lanes is the intrinsic `tl::rng_rand_float()` or
`tl::rng_rand()`, the printer emits curand's N-wide entry point instead of N
scalar calls:

```cpp
      if (call->op.same_as(tl::rng_rand()) && lanes == 4) {
        os << "curand4(&" << this->curand_random_generator_state << ")";
        return;
      }
      if (call->op.same_as(tl::rng_rand_float())) {
        int bits = call->dtype.bits();
        std::string dist = call->args[0].as<StringImmNode>()->value;
        if (bits == 32) {
          if (lanes == 4) {
            os << "curand_" << dist << "4(&" ... );   // curand_uniform4 / curand_normal4
            return;
          } else if (lanes == 2 && dist == "normal") {
            os << "curand_normal2(&" ... );
            return;
          }
        } else {
          if (lanes == 2) {
            os << "curand_" << dist << "2_double(&" ... );
            return;
          }
        }
      }
```

**Why that is not value-preserving.** From the CUDA 12.8 headers on this box:

| what the source asks for | scalar form | N-wide form the codegen picks | same numbers? |
|---|---|---|---|
| `rng_rand()` (uint32) | `curand()` | `curand4()` | **yes** (measured, arg 0 bit-identical) |
| `rng_rand_float("uniform")` f32 | `curand_uniform()` | `curand_uniform4()` | **yes** (measured, arg 1 bit-identical) |
| `rng_rand_float("uniform")` f64 | `curand_uniform_double()` | `curand_uniform2_double()` | **no** |
| `rng_rand_float("normal")` f32 | `curand_normal()` | `curand_normal4()` | **no** |
| `rng_rand_float("normal")` f64 | `curand_normal_double()` | `curand_normal2_double()` | **no** |

The two "no" mechanisms, read out of the headers:

* `curand_uniform.h:333` — `curand_uniform_double(state)` is
  `_curand_uniform_double(curand(state))`: **one** 32-bit draw, low-quality
  double. `curand_uniform.h:217` — `curand_uniform2_double(state)` calls
  `curand4(state)` and builds two doubles with `_curand_uniform_double_hq(x,y)`
  and `(z,w)`: **four** draws, a different conversion function, different
  values.
* `curand_normal.h:345` — `curand_normal(state)` runs Box-Muller on two draws,
  returns `v.x` and **caches `v.y` in `state->boxmuller_extra`**; the next call
  returns the cached value and consumes nothing. `curand_normal.h:444` —
  `curand_normal4(state)` is `curand_box_muller4(state)`: four fresh values, the
  cache is neither read nor written.

So four sequential `curand_normal()` calls and one `curand_normal4()` are
different functions of the same state, not two spellings of one function.

**Why the vectorizer is allowed to get here at all.** The intrinsics are
declared side-effecting — `src/op/builtin.cc:164-171` gives `rng_rand`,
`rng_rand_float` and `rng_init` `CallEffectKind::kOpaque`. An opaque call is
exactly the kind of expression whose *number of evaluations* and *order* are
part of the meaning. `VectorizeLoop` still folds 4 evaluations into one 4-lane
value, and the codegen then has to invent a 4-lane meaning for it. The mistake
is one of these two, depending on which behaviour TileLang wants:

* `VectorizeLoop` should refuse to widen a loop body containing a `kOpaque`
  call, or
* the codegen should only use an N-wide curand entry point where it is known to
  reproduce the scalar sequence (true for `curand4` and `curand_uniform4`, false
  for the three above), and print N scalar calls otherwise.

**The generated code**, `ir/reference.cu` vs `ir/candidate.cu`:

```c
/* reference: vectorizer on (stock) */
*(float4*)(D + (...)) = curand_normal4(&__random_generator_state);
*(double2*)(E + (...)) = curand_normal2_double(&__random_generator_state);

/* candidate: tirx.disable_vectorize */
for (int vec_3 = 0; vec_3 < 4; ++vec_3) { D[...+vec_3] = curand_normal(&__random_generator_state); }
for (int vec_4 = 0; vec_4 < 2; ++vec_4) { E[...+vec_4] = curand_normal_double(&__random_generator_state); }
```

## 3. Where it reproduces

**Any NVIDIA GPU, and you do not need a GPU to see it** — the difference is
already in the generated CUDA text, which the `lower()`-only path produces
without nvcc.

* The failing code is a plain serial `for` loop with a `curand*` call and a
  store. No wgmma, no TMA, no mbarrier, no cluster, no warp specialization.
* The substitution table above is in `src/cuda/codegen/codegen_cuda.cc`, guarded
  only by the generator state type (`curandStatePhilox4_32_10_t`, plus a smaller
  table for MRG32k3a and XORWOW) — not by target arch.
* The value difference comes from the CUDA curand headers, which are the same on
  every NVIDIA target. Whether the *exact* numbers here reproduce on another
  CUDA version depends on curand's implementation; whether the *difference*
  reproduces does not.
* CUDA-only in the sense that only the CUDA backend has this rng codegen; the
  ROCm/CPU/Metal backends do not implement `rng_rand_float` this way.

## 4. Plain-language explanation

The kernel asks for 128 random numbers, one after another, from one generator.

Reading four numbers one at a time and reading four numbers in one go are not
the same operation in NVIDIA's random-number library. The "normal distribution"
call makes two numbers at a time and keeps the spare one for the next call; the
"four at once" call does not use that spare. The double-precision "uniform" call
uses one raw draw per number; the "two at once" version uses four raw draws and
a better conversion.

TileLang's compiler swaps the one-at-a-time calls for the all-at-once call when
the loop is vectorized. For plain integers and single-precision uniform numbers
the swap happens to give the same numbers, so nobody noticed. For normal numbers
and for double-precision uniform numbers it gives different numbers. So turning
the vectorizer off changes every value the kernel produces.

## 5. Can an SMT solver model this?

**Split answer: the unsoundness yes, the wrong values no.**

*What an IR-level checker can see.* Model the generator as an opaque state and
each `rng_rand_float` as `(state, value) = f(state)`. Then the reference does
**one** state step per 4 outputs (a 4-lane broadcast of one call) and the
candidate does **four**. Those two programs are not equivalent under any
interpretation of `f`, so a checker that treats `CallEffectKind::kOpaque` as a
real state effect — instead of a pure function it may duplicate or merge —
reports NOT EQUIVALENT. That is a deterministic single-instance value-semantics
difference: single thread, no memory ordering, no floating-point reasoning
needed. Cheap and decidable.

*What no IR-level checker can see.* Which numbers actually come out. The
reference's 4-lane call becomes `curand_normal4`, whose behaviour lives in
`curand_normal.h`, i.e. in a CUDA header below TileLang's IR. To predict
`0.201201` vs `0.410568` a checker would have to model Philox-4x32-10 rounds,
the Box-Muller transform, and the `boxmuller_flag` cache — bit-exact FP plus a
library implementation the IR never mentions. That is out of reach of an
IR-level equivalence check, and it is also the wrong place to put it.

*Practical consequence.* The useful check is the cheap one: forbid merging or
duplicating opaque effects. It catches this whole class without modelling curand
at all. A checker that models `rng_rand_float` as a **pure** function would call
these two programs equivalent and miss the bug entirely.

## 6. Confidence

**The value difference: certain.** Re-run and confirmed; deterministic on both
sides across 3 runs each; visible in the generated CUDA before nvcc even runs.

**That it is a *bug*: likely, not certain.** The honest uncertainty is what
TileLang promises. Two readings:

* *Bug.* `tirx.disable_vectorize` is a supported public knob and an optimisation
  switch. An optimisation switch must not change results. And the codegen is
  substituting a different library function for a side-effecting call, which is
  not a rounding or ordering licence — it is a different computation.
* *Not a bug.* One could argue the only contract for a random-number kernel is
  the distribution, not the exact stream, in which case the substitution is
  intentional and merely undocumented.

The evidence leans to "bug" for one concrete reason: the codegen already gets
this right for two of the five cases. `curand4` and `curand_uniform4` reproduce
the scalar sequence bit for bit, which suggests the table was written expecting
all the N-wide forms to be equivalent, and three entries of it are wrong.

What would settle it: a statement from TileLang about whether a fixed seed is
meant to give a fixed stream, or an upstream test in
`testing/python/language/test_tilelang_language_rand.py` (the kernel's own
source file) that pins values with and without the vectorizer.
