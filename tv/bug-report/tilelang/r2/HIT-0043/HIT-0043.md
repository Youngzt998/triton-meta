# HIT-0043: the stock pipeline randomly drops two shared-memory barriers — `tl.ThreadSync` is not a function of its input

Verdict: **CONFIRMED — genuine compiler bug, but NOT the one the sweep wrote
down** (reviewed 2026-08-19)
Arch:    hopper-only (the affected epilogue is `stmatrix` into shared memory
         followed by a TMA store)
Line:    tilelang r2 (TileLang 0.1.12, pypi wheel, H100 sm_90a, nvcc 12.8.93)
Culprit: pass `tl.ThreadSync("shared.dyn")`.
         **Not** `FuseMBarrierArriveExpectTx`, which is what the sweep named.

Summary: compiling this kernel with the **stock, unmodified** TileLang pipeline
gives one of two different kernels, chosen at random, and the two compute
different results. The difference is exactly two dropped barriers:

```c
    tl::__sync_thread_partial(3, 128);      /* before the stmatrix into Os  */
    ...  ptx_stmatrix_m8n8_x4(... Os ...)
    tl::__sync_thread_partial(3, 128);      /* before the TMA store of Os   */
    if (tl::tl_shuffle_elect<128>()) { ... tl::tma_store(O_desc, &Os[0], ...) }
```

Without the second one, all 128 threads write the shared staging buffer `Os`
with `stmatrix` and then **one** elected thread issues a TMA store that reads
the whole of `Os`, with nothing ordering the two. That is a shared-memory race
that the compiler introduced.

Measured rate: over 24 compiles of the stock pipeline in 4 fresh processes,
**20 kept the barriers and 4 dropped them**. Over 50 applications of the same
pass object to the *same in-memory* `IRModule` in one process, **38 kept and
12 dropped**.

The report's original claim — "dropping `FuseMBarrierArriveExpectTx` changes
the bits" — is false. That toggle is not the cause; see §7, where the sibling
reports `HIT-0044` and `HIT-0045` show their pass toggles produce
**byte-identical CUDA** to the reference and still "differ" 4-5 times in 12.

Labels: pass-class:bit-preserving, kernel-has-gemm, kernel-has-reduce,
input-mode:boundary, shared-config:ptxas-reg-level=10, nan-pattern-changed,
gross

**Occurrences: 4** — `HIT-0044`, `HIT-0045` (same instance, rejected as B4
duplicates) and the two `boundary` draws of `HIT-0042` (whose *reported*
difference is a separate fast-math one and is rejected under B1).

## 1. Root cause in the source

### 1.1 The pass is pinned by measurement, not by guessing

`tlfz/steps.py` runs the stock pass list one pass at a time, so the module can
be hashed before and after any single pass. Compiling the reference 14 times
and hashing around three neighbouring passes:

| pass | input hash | output hashes |
|---|---|---|
| `MergeSharedMemoryAllocations` | `5347bc0c` x14 | `36d4bda2` x14 |
| `InjectFenceProxy` | `36d4bda2` x14 | `6549ecf3` x14 |
| **`ThreadSync.shared.dyn`** | **`6549ecf3` x14** | **`adbdd531` x12, `d960d9ae` x2** |

Everything before it is stable. The pass itself takes one input and returns
two different outputs. Stronger version of the same test, which removes any
possibility that the input differs by node address: capture the `IRModule`
once, then apply **the same pass object** to **that same object** 50 times in
one process — `adbdd531` x38, `d960d9ae` x12.

The diff between the two outputs is two statements and nothing else
(`ir/threadsync_out_with_barriers.tir.py` vs
`ir/threadsync_out_missing_barriers.tir.py`):

```
133d132
<             T.tvm_storage_sync("shared.dyn", 3, 128)
136d134
<             T.tvm_storage_sync("shared.dyn", 3, 128)
```

surrounding

```python
for i in T.unroll(2):
    T.ptx_stmatrix(0, 4, T.tvm_access_ptr(..., Os, tx % 128 // 32 * 512 + ...), ...)
if T.tl_shuffle_elect(128):
    T.fence_proxy_async()
    T.tma_store(O_desc, T.tvm_access_ptr(..., Os, 0, 2048, 1), 0, bx * 64, by, bz, 0, 0)
```

Note there is a **third** `shared.dyn` barrier in the same function, at line 51
of both outputs, and it survives in both. It is emitted as a *full* extent sync
(`T.tvm_storage_sync("shared.dyn")`, one argument). Only the two **partial**
syncs — the ones that carry a barrier id and a thread count — are affected.
That is the shape of the defect.

### 1.2 The line that deletes a barrier

`src/transform/thread_storage_sync.cc`, `ThreadPartialSyncRewriter`
(class at line 240) turns each planner-inserted `tvm_storage_sync("shared.dyn")`
into a partial barrier. `ProcessSharedSync` (line 273):

```cpp
    auto [barrier_id, thread_count] =
        GetOrCreateBarrier(key, extent_tx, extent_ty, extent_tz);   // line 296-297
    if (thread_count % 32 != 0) {                                   // line 298
      // TODO(lei): This is a workaround for the case where the thread count is
      // not a multiple of 32. we should enhance the pass to analysis index
      // instead of buffer expression etc.
      return Stmt();                                                // line 302
    }
```

`return Stmt()` is an **empty statement**: the barrier is removed from the
program. That is never a safe answer to "I am not sure how many threads reach
this barrier". The safe answer is a full `__syncthreads()`.

`thread_count` comes from `CalculateThreadExtent` (line 343), which is built on
a Z3 model enumeration:

```cpp
    int64_t z3_count =
        analyzer_->z3_prover.CountSatisfyingValues(iv->var, extent);   // line 353
    if (z3_count > 0) {
      return static_cast<size_t>(z3_count);
    }
    // Fallback to range-based calculation if Z3 enumeration failed
    return static_cast<size_t>(bound->max_value - bound->min_value + 1);
```

and a second enumeration at line 468 (`ConditionThreadPropertyChecker::
AnalyzeCondition`) decides whether a sync has to be hoisted out of an
`if`. `GetOrCreateBarrier` (line 312) **caches** the count per
`ThreadBoundKey`, which explains why the two barriers — same thread bounds,
same key — always vanish together and never one at a time.

### 1.3 What I proved and what I inferred

Proved: the pass returns two different results for one input; the difference is
those two barriers; the resulting kernels compute different values.

Inferred: that the varying quantity is the Z3 count. The argument is by
elimination — every other step in this pass is a deterministic walk over an
`IRModule` that does not change between the 50 in-process applications, and a
model enumeration with an internal resource budget is the one component whose
answer may vary. I could **not** read `CountSatisfyingValues`: it lives in the
`3rdparty/tvm` submodule, which is not checked out in the source copy here
(`tilelang-src/3rdparty/tvm` is empty). I also did not instrument the pass to
print `thread_count`, which is the one experiment that would turn this
inference into a fact. **Treat §1.2 as the strongest available explanation, not
as a proven line.**

## 3. Where it reproduces

**Hopper (sm_90) and later.** The judgement rests on the code the barriers
guard: `ptx_stmatrix` into a `shared.dyn` staging buffer, followed by
`tl::tma_store` under `tl_shuffle_elect`. `stmatrix` is sm_90+, TMA is sm_90+.
On a target without them the epilogue writes `O` directly and there is no
`Os` staging buffer to protect.

The *pass* is target-neutral, so the nondeterminism itself is presumably not
Hopper-specific — any kernel whose barriers go through the partial-sync path
(a sync inside a thread-range-restricted region) can hit it. I did not test
that: everything here is one FA instance on one H100.

Whether a dropped barrier actually changes the answer depends on the input.
Over 20 draws of this instance only the two `boundary` draws (values near the
fp16 limit and the 2^24 integer boundary) showed it; the other 18, including
`zeros`, `intvalued` and `extremes`, were bit-identical. A race is often
benign.

## 4. Plain-language explanation

At the end of this attention kernel, all 128 threads write their piece of the
answer into a small shared buffer, and then a single thread asks the copy
engine to move the whole buffer out to global memory. Between those two steps
the threads must wait for each other, otherwise the copy can start before some
threads have written.

The compiler knows this and normally puts a wait there. But the pass that
places waits asks a solver "how many threads reach this point?", and if the
answer is not a whole number of warps it **deletes the wait** instead of
falling back to a plain full wait. The solver does not always give the same
answer, so compiling the very same program twice gives the wait about three
times out of four and no wait the fourth time. The version without the wait
reads the shared buffer too early and produces different numbers.

So the bug is two bugs stacked: an answer that is allowed to vary, and a
"don't know" path that removes a safety barrier rather than adding one.

## 5. SMT reachability analysis

1. **Root cause in semantic terms.** The constructs are `T.ptx_stmatrix`
   (128 threads each writing 8 `bfloat16` into `Os`, a `shared.dyn` buffer),
   `T.tvm_storage_sync("shared.dyn", 3, 128)` (a named-barrier wait over the
   128-thread group), and `T.tma_store` issued by one elected thread reading
   `Os[0:2048]`. The semantic error: **the write-to-`Os` by 128 threads and the
   read-of-`Os` by one thread are not separated by any happens-before edge**,
   so the value the TMA store copies out is not determined by the program.

2. **Is the difference a pure input -> output function difference?** No. For a
   *fixed* schedule the barrier-less kernel is still a function of its inputs,
   but nothing in the IR fixes the schedule; the whole difference between the
   two compilations is a synchronisation edge, not a value computation. Two
   further points make it worse for a functional checker: the difference is
   between two *outputs of the same compiler run on the same input*, so there
   is no stable "candidate IR" to hand a checker; and on this GPU the racy
   kernel happens to be self-consistent across repeats, so a run-it-twice
   oracle does not see it either.

3. **Fundamental verdict:** `needs a concurrency / memory-ordering model`.
   An equivalence check over values alone sees two programs that compute the
   same expression from the same inputs — the barrier is not an operation that
   produces a value. To notice that one of them is wrong, the model must carry
   (a) shared memory as state visible to many threads, (b) a happens-before
   relation that barriers create and that ordinary statements do not, and
   (c) a rule that reading a location written by another thread without an
   intervening edge is undefined. With those, the checker does not even need
   two programs: the barrier-less kernel alone fails a race-freedom check.
   Without them, no amount of FP fidelity or grid modelling helps.

   Second, orthogonal point: even a perfect checker is only run on the IR it is
   given. This bug is a compiler that emits two different IRs for one input,
   so it is caught only if the checker is wired into every compile (then the
   racy 1-in-4 output is rejected on the spot). Translation validation as a
   one-off offline check would pass the good compile and never see the bad one.

4. **Minimum semantic vocabulary required.**
   * shared memory as a second address space with per-thread visibility, not a
     single flat array;
   * a thread group and a barrier as a synchronisation edge over that group,
     including *partial* barriers over a sub-range of threads (that is exactly
     what `tvm_storage_sync(scope, id, count)` is);
   * `stmatrix` as 128 separate writes at thread-dependent offsets, and
     `tma_store` as a single bulk read of the whole buffer issued by one
     thread — i.e. the asymmetry that makes the barrier necessary;
   * `tl_shuffle_elect` as "exactly one thread of the group", so the model
     knows the reader is not the writer.

5. **Would the abstraction hide it?** The FP axiom profile is irrelevant here —
   under any profile, exact or reassoc-allowed, the two programs compute the
   same expression. What hides the bug is not the FP abstraction but a
   sequential-execution abstraction: a model that runs one program instance as
   straight-line code sees the writes and the read in program order and
   concludes they are ordered. So the bug is invisible to precisely the class
   of checker that is good at everything else in this campaign.

6. **Inherent cost.** If a concurrency model existed, the query is cheap: it is
   a race-freedom question about one buffer, one write set and one read set,
   with no arithmetic at all. The expensive part is building the model, not
   solving it.

## 6. Confidence

**High** that the compiler has a real defect; **medium** on the exact line.

High, because these are direct measurements, not inferences: byte-identical
input to the pass, two outputs, 38/12 over 50 applications; the diff is two
barriers; the barrier-less kernel disagrees with the barrier-full one on real
data; and the missing barrier sits between a many-writer `stmatrix` and a
one-reader TMA store, which is textbook.

Medium on the line, for the reasons in §1.3 — the Z3 step is inference by
elimination and the prover source is not in this checkout. Two experiments
would settle it: print `thread_count` at
`thread_storage_sync.cc:298` across repeated runs, and replace `return Stmt();`
with a full `__syncthreads()` and check the nondeterminism disappears from the
*output* (it should become "always safe", even if the count still varies).

One thing I want to flag rather than hide: I have **not** established which of
the two kernels is the correct one. The barrier-full one is correct by
construction; I did not compare either against a torch reference, so
"different" is proven and "the barrier-less one is wrong" is an argument from
the missing happens-before edge, not a measurement against ground truth.

## 7. Duplicates, and why the sweep mis-attributed this

All three reports are the same instance `gen_fa_ca4121f27fc1c5` on the
`boundary` draws. I re-ran each report's own minimal variant 12 times, freshly
compiling **both** arms each time, and recorded the source hash of each arm:

| report | its pass toggle | outcome over 12 pairs | (reference source, candidate source) |
|---|---|---|---|
| **HIT-0043** (this one) | drop `FuseMBarrierArriveExpectTx`, `tl.if_stmt_binding_inline_replayable_binds=true` | 11 same, 1 diff | `ef86f1 \| ddfc37` x11, `ef86f1 \| 35817b` x1 |
| HIT-0044 | drop `Simplify#1`, `tl.loop_unswitching_allow_non_trivial_else=true` | 7 same, 5 diff | `ef86f1 \| ef86f1` x7, `75321f \| ef86f1` x3, `ef86f1 \| 75321f` x2 |
| HIT-0045 | drop `Simplify#5`, `InjectSoftwarePipeline`, `tirx.debug_keep_trivial_loop=true` | 8 same, 4 diff | `ef86f1 \| ef86f1` x8, `ef86f1 \| 75321f` x2, `75321f \| ef86f1` x2 |

Read the last column. For HIT-0044 and HIT-0045 the candidate's source hash is
drawn from **the same two values as the reference's** — their pass toggles
change the generated CUDA not at all — and the output differs in exactly the
pairs where the two arms drew different lottery outcomes. For this report the
toggle does change the source (`ddfc37`), but 11 of 12 pairs still agree; the
one differing pair is the one where the candidate drew `35817b`.

So: `HIT-0044` and `HIT-0045` are rejected as B4 duplicates of this report.
`HIT-0042`'s two `boundary` draws are the same lottery; its *reported*
difference is on a `uniform` draw and is a plain fast-math one, so it is
rejected under B1 separately.

`ef86f1` (9043 chars) is the barrier-full kernel; `75321f` (8965 chars) is the
barrier-less one; they differ only by the two `tl::__sync_thread_partial(3,
128);` lines.
