# HIT-0008: warp specialization gives a fragment a wrong per-thread index, so the kernel reads uninitialised registers

Verdict: **CONFIRMED — genuine compiler bug** (reviewed 2026-08-19)
Arch:    hopper-only in practice (warp specialization is only turned on for
         sm_90+), but the faulty index arithmetic itself is target-neutral
Line:    tilelang r2 (TileLang 0.1.12, pypi wheel, H100 sm_90a, nvcc 12.8.93)
Culprit: pass `ProducerConsumerWarpSpecialized` + the thread-offset fix-up in
         `PartitionLoop`

Summary: this is a bug in the **stock** TileLang pipeline, not in an optional
pass. When `ProducerConsumerWarpSpecialized` splits the block into a producer
warp (threads 0-31) and a consumer warp (threads 32-63), every index in the
consumer must be rewritten from `threadIdx.x` to `threadIdx.x - 32`. Shared
memory indices get that fix-up. The **register fragment** index does not: it is
folded to a constant *before* the fix-up runs, and the constant keeps the +32
offset baked in. The result is a fragment that is written at local slots
`4 .. 515` and read at local slots `0 .. 511`, in an array declared
`float p[512]`. So the kernel

* **reads 4 never-written registers per thread**, and
* **writes 4 floats past the end of the local array.**

The clean demonstration: with **all-zero input** the correct answer is all
zeros, and the stock pipeline returns `NaN` at 8 of the 511 outputs — one per
thread block. Dropping `ProducerConsumerWarpSpecialized` returns all zeros.

Labels: pass-class:numerics-changing, layout-reorders-reduction,
kernel-has-reduce, input-mode:large, shared-config:ptxas-reg-level=8,
shared-config:index-bits=64, nan-pattern-changed, gross

**Occurrences: 3.** `HIT-0007` and `HIT-0009` are the same defect on the same
instance and are rejected as B4 duplicates (see §7).

⚠️ The `exact-int-accum:reassociation-excluded` label the sweep put on this
report is **sound** for this kernel (a plain sum of products, no
transcendental — see `EXACT-INT-LABEL-NOTE.md`), but the review does not lean
on it. The all-zero test below is stronger and needs no argument about
accumulator width.

## 1. Root cause in the source

### 1.1 What the two arms emit

`ir/reference.cu` (stock pipeline, warp specialization on) and
`ir/candidate.cu` (same pipeline minus `ProducerConsumerWarpSpecialized`)
declare the same register fragment:

```c
  float p[512];
```

Reference, consumer branch (`threadIdx.x` in `[32, 64)`):

```c
    float4 v_   = *(float4*)(((float*)As) + ((((ko_1 % 3) * 16384) + (i_1 * 128)) + (((int64_t)threadIdx.x) * 4)) - 128);
    ...
    *(float4*)(p + ((i_1 * 4) + 4)) = __1;          /* i_1 = 0 .. 127  ->  p[4 .. 515] */
    ...
      acc_clear[i_2] = (acc_clear[i_2] + p[(((i_2 * 8) + ((rv & 1) * 4)) + (rv >> 1))]);   /* p[0 .. 511] */
```

Candidate (no warp specialization, `threadIdx.x` in `[0, 32)`):

```c
    *(float4*)(p + (i_10 * 4)) = __2;               /* p[0 .. 511] — correct */
```

Note the shared-memory address in the reference: `threadIdx.x * 4 - 128`, i.e.
`(threadIdx.x - 32) * 4`. That one **was** corrected. The fragment index
`i_1 * 4 + 4` was not: the `+ 4` is `(32 / 32) * 4`, the producer's 32 threads
divided by the layout's 32-thread extent, times the 4-wide vector.

### 1.2 Where the two disagree in the compiler

The bad index already exists in the TIR immediately after `LowerTileOp`
(dumped with `python -m tlfz.trace ... '{"skip":["LowerTileOp"]}'`):

```python
p[i * 4 + vec + 4] = As[ko % 3, (i * 4 + vec) // 8,
                        (i * 4 + vec) % 8 // 4 * 128 + (tx - 32) * 4 + (i * 4 + vec) % 4]
                     * Xs[0, 0, ko % 3, ... + (tx - 32) * 4 + ...]
...
acc_clear[i] = acc_clear[i] + p[i * 8 + rv % 2 * 4 + rv // 2]
```

Same statement: `As` and `Xs` carry `(tx - 32)`, `p` carries a bare `+ 4`.

The fix-up lives in **`src/transform/loop_partition.cc`, `PartitionLoop`,
lines 160-168**:

```cpp
  body = BufferIndiceSimplify(analyzer)(body);      // line 164

  if (has_thread_offset) {
    body = Substitute(body, thread_offset_map);     // line 166-168
  }
  return Downcast<For>(body);
```

`thread_offset_map` is built at lines 91-97 and maps
`thread_var -> thread_var - loop_layout->ThreadRange()->min`, i.e.
`tx -> tx - 32`. It is a **syntactic substitution applied last**.

`BufferIndiceSimplify` (same file, lines 42-64) runs one line earlier and
simplifies every buffer index with an `arith::Analyzer` that has already been
told the *real* consumer bound `tx in [32, 64)`. The fragment's local index is

```
  local = floordiv(i * 32 + tx, 32) * 4 + vec
```

(the layout built in `LoopPartitioner::Partition`, same file, lines 208-212:
`idx = FloorDiv(access_idx, thread_extent_const) * vector_extent + ...`).
With `tx in [32, 64)` the analyzer legitimately folds
`floordiv(i * 32 + tx, 32)` to `i + 1`. The thread variable is now **gone from
the expression**, so the substitution on line 166 has nothing to rewrite and
the `+ 1` (i.e. `+ 4` after the `* 4`) stays. The shared-memory indices keep a
bare `tx` term, so they *are* rewritten.

So the defect is an ordering one: the pass simplifies with the un-normalised
thread bound and then normalises by substitution. Either the simplification
must be done under `tx in [0, 32)`, or the substitution must happen before the
simplification.

`ProducerConsumerWarpSpecialized` is named as the culprit because it is what
creates a non-zero `ThreadRange()->min`; the wrong arithmetic is in
`PartitionLoop`. The TIR right after `ProducerConsumerWarpSpecialized`
(`ir/ref_after_ProducerConsumerWarpSpecialized.tir.py`) is still correct — it
addresses `p[i, j]` symbolically.

### 1.3 Why this is incorrect, not merely different

`p[0..3]` are read before any write, so their value is whatever was left in
those registers. `p[512..515]` are written past the end of a `float[512]`
local array. Both are undefined behaviour in the generated CUDA, and the
uninitialised value reaches global memory through
`acc_clear[0] -> AllReduce -> acc[0] -> Y[bx * 64]`.

## 3. Where it reproduces

**Any NVIDIA target on which TileLang turns warp specialization on**, which
today means sm_90 and later (`allow_warp_specialized()` in
`tilelang/cuda/pipeline.py`). It was found and re-run on H100 / sm_90a.

The judgement rests on this: the failing arithmetic is in `PartitionLoop`,
which is target-neutral, and the broken statement is an ordinary
`T.Parallel` elementwise loop writing a register fragment — no wgmma, no MMA
layout, no TMA. Hopper only enters because warp specialization is the only
thing in the pipeline that sets a non-zero `ThreadRange()->min`; the reference
kernel does use TMA and mbarrier for the `X` copy, but those are not part of
the faulty index.

**How narrow is it?** Measured, with an oracle that needs no second
compilation: run the **stock pipeline only** on all-zero input, where a gemv
must return all zeros, and count non-zero or `NaN` outputs. Over a
`threads x bM x bK` grid at the same `M=511, K=1025, num_stages=3, float32`
(16 points, 4 rejected by the shared-memory limit, **12 ran**):

| threads | bM | bK | bad outputs |
|---|---|---|---|
| 32 | 64 | 64 | 0 |
| **32** | **64** | **256** | **16** (8 `NaN`, one per block) |
| 32 | 128 | 64 | 0 |
| 64 / 128 / 256 | 64, 128 | 64, 256 | 0 (8 points) |

So: 1 of 12. The wider thread counts are clean, which fits the mechanism — the
fold to a constant needs the analyzer to prove `floordiv(i * T + tx, T)`
constant over the consumer's range, and that needs the **consumer thread count
to equal the layout thread extent** (one producer warp, one consumer warp).
But `threads=32` alone is not enough: `bK=64` is clean at the same thread
count, so the tile shape matters too and I do not have an account of why. Treat
the affected set as "at least this point", not as "all `threads=32` kernels".

Two side facts from the same sweep: the failing point does **not** need the
report's `tl.ptxas_register_usage_level=8` or `tl.config_index_bitwidth=64` —
the sweep ran with empty `pass_configs` and still failed — and the sweep is a
cheap standing check anyone can re-run
(`python reviewer_zero_oracle.py gemv`, in `/home/youngzt/fuzz-tilelang-r2`).

## 4. Plain-language explanation

The compiler splits the threads of a block into two groups: one group loads
data, the other computes. The computing group now has thread numbers 32 to 63
instead of 0 to 31, so every place that uses the thread number has to subtract
32. The compiler does that as a find-and-replace at the very end.

Just before that, it simplifies the address arithmetic. For the per-thread
register array the simplification is good enough to make the thread number
disappear from the expression — it turns "which slot of my own registers" into
a plain number. But that plain number was computed with thread numbers 32-63,
so it is one slot too high. The find-and-replace then finds nothing to fix.

The consequence is that the computing threads write their products into slots
4..515 of a 512-slot register array and later add up slots 0..511. Slots 0..3
were never written, so the kernel adds whatever was left in those registers,
and 4 values fall off the end of the array. With an all-zero input, where the
answer must be zero, the compiler's own kernel returns `NaN`.

## 5. SMT reachability analysis

1. **Root cause in semantic terms.** In the tile IR the statement is
   `p[i, j] = As[ko, i, j] * Xs[ko, j]` inside a `T.parallel(64) x
   T.parallel(256)` loop, followed by `T.reduce(p, acc, "sum", dim=1)`.
   `PartitionLoop` replaces the two loop variables by an index map
   `(i, j) -> (local_slot, thread)` and must express both the store and the
   reduce in the *same* map. It does not: the store's `local_slot` is
   evaluated with `thread in [32, 64)` and the reduce's with `thread in
   [0, 32)`. Semantic error in one sentence: **the same fragment is written
   under one index map and read under a different one, so the read sees
   uninitialised storage.**

2. **Is the difference a pure input -> output function difference?** Almost.
   The *presence* of the bug is a pure single-instance property: for a fixed
   thread, the set of written slots and the set of read slots are disjoint at
   four positions, and that is decided by the index expressions alone — no
   scheduling, no other program instance, no other thread. What the four
   uninitialised registers happen to contain is *not* a function of the input;
   it is undefined. So the correct statement is: the two programs are provably
   **not equivalent** as functions, because one of them is not a function at
   all — its output depends on unconstrained state.

3. **Fundamental verdict:** `SMT-decidable in principle`.
   An SMT model of this IR that (a) gives each thread its own fragment array,
   (b) models the thread id as a symbolic integer with the declared range, and
   (c) initialises fragment slots to *unconstrained* symbols would refute
   equivalence immediately: the reference's `Y[bx*64]` contains an
   unconstrained symbol that the candidate's does not. The counterexample is
   tiny — one block, one thread, one reduce slot. No floating-point subtlety
   is needed; the query is over the index arithmetic, which is pure integer
   `floordiv`/`floormod`. This is a good case for a validator, and it is
   exactly the kind of bug a validator would find *faster* than a fuzzer: the
   fuzzer needed a specific shape draw plus an input class that makes the
   garbage register visible.

4. **Minimum semantic vocabulary required.**
   * a per-thread register file (`local.fragment`) as an array indexed by an
     integer slot, with an explicit *undefined / unconstrained* initial value
     (not zero — modelling it as zero would hide this bug completely);
   * the thread index as a symbolic integer with a range constraint, and
     layouts as index maps from tile coordinates to `(thread, slot)`;
   * integer `floordiv` / `floormod` under those range constraints, because
     the whole bug is one `floordiv` folded under the wrong bound;
   * array-bounds checking on the fragment (the `p[512..515]` store), which is
     a second, independent way to catch the same defect and does not even need
     the two programs to be compared — a single-program well-formedness check
     would flag it.

5. **Would the abstraction hide it?** No, and the FP axiom profile does not
   matter. The two sides differ by *which values* are summed, not by the order
   or rounding of the sum, so even the weakest uninterpreted-function FP
   encoding distinguishes them: one side's result mentions an extra
   uninterpreted symbol. Under a reassoc-allowed profile the difference still
   survives, because reassociation cannot introduce a fresh unconstrained
   term. This is the opposite of the benign reordering the sweep mostly finds.

6. **Inherent cost.** Small. Shrink to one block and one `ko` iteration and
   the query is a handful of integer index expressions plus 8 symbolic adds.
   Proving non-equivalence (SAT) is the expensive direction in general, but
   here the witness is structural — the solver only has to pick a value for
   one uninitialised slot — so it should be found immediately.

## 6. Confidence

**High** that this is a genuine compiler bug.

What is proven, not inferred: the two index ranges disagree in the generated
CUDA and in the TIR (read the files); the stock pipeline returns `NaN` where
the answer must be `0` (run the repro); dropping the one pass fixes it; the
kernel source itself contains no uninitialised read (`T.fill(acc, 0)` is
present and `p` is fully written by the `T.Parallel` loop, at the tile level).

What is inference, and where the remaining doubt is:

* The attribution to lines 164-168 of `loop_partition.cc` is read off the code
  plus the shape of the emitted expression (`+4 = (32/32) * 4`, and `As` keeps
  a `tx` term while `p` does not). I did not rebuild TileLang with the two
  lines swapped to confirm the fix. That is the one experiment that would
  settle it.
* The affected set is only partly mapped (§3): 1 of 12 points in a small
  `threads x bM x bK` grid on this one family. The mechanism explains why the
  wide-thread points are clean but not why `bK=64` is clean at `threads=32`,
  so I cannot yet state a rule for which kernels are hit.

Neither doubt touches the verdict: whatever the exact line, the stock pipeline
emits a kernel that reads registers it never wrote.

## 7. Duplicates

Same instance, same defect, rejected under B4:

* **`r2/HIT-0007`** — `{"skip": ["ConfigIndexBitwidth"]}`. Both arms are
  warp-specialised and **both** contain `*(float4*)(p + ((i_1 * 4) + 4))`; the
  two CUDA files differ only by `int` vs `int64_t`. The reported difference is
  the *same* uninitialised `p[0..3]` holding different garbage in two builds.
  The named culprit is not a cause, only a perturbation.
* **`r2/HIT-0009`** — `{"cfg": {"tl.disable_warp_specialized": true}}`. The
  same comparison as this report, reached by the knob instead of by dropping
  the pass; identical bits (511/511, `max_abs 85476848.0`).

## 8. Raw sweep data (kept from the original report)

Reference: `tilelang/cuda/pipeline.py::CUDAPassPipelineBody`, reproduced step
by step in `tlfz/steps.py`. Candidate: the same list minus
`ProducerConsumerWarpSpecialized`.

Instance: family `gemv`, shape `{"M": 511, "K": 1025}`, config
`{"bM": 64, "bK": 256, "th": 32, "st": 3, "dt": "float32"}`, shared
pass_configs on both arms
`{"tl.ptxas_register_usage_level": 8, "tl.config_index_bitwidth": 64}`.

Kernel source (`ir/kernel_source.py`):

```python
@T.prim_func
def main(A: T.Tensor((511, 1025), "float32"), X: T.Tensor((1025,), "float32"), Y: T.Tensor((511,), "float32")):
    with T.Kernel(T.ceildiv(511, 64), threads=32) as bx:
        As = T.alloc_shared((64, 256), "float32")
        Xs = T.alloc_shared((256,), "float32")
        p = T.alloc_fragment((64, 256), "float32")
        acc = T.alloc_fragment((64,), "float32")
        T.fill(acc, 0)
        for ko in T.Pipelined(T.ceildiv(1025, 256), num_stages=3):
            T.copy(A[bx * 64, ko * 256], As)
            T.copy(X[ko * 256], Xs)
            for i, j in T.Parallel(64, 256):
                p[i, j] = T.cast(As[i, j], "float32") * T.cast(Xs[j], "float32")
            T.reduce_sum(p, acc, dim=1, clear=False)
        T.copy(acc, Y[bx * 64])
```

Draws that show the difference: 18 of 20, modes `boundary, denormal,
intvalued, large, normal, pow2, uniform, zeros`.

First differing element on draw 0 (`large`, seed 166000):
`{"idx": 0, "ref": NaN, "cand": -7221871.0}`; per-parameter record

"nan_mask_differs": true, "n_diff": 511, "n_total": 511,
"max_abs": 85476848.0, "ulp_max": 1829257183}`.

Determinism: reference and candidate each self-consistent across repeats; the
