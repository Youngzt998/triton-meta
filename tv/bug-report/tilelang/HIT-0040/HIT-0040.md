# HIT-0040: `tl.enable_aggressive_shared_memory_merge` aliases a live buffer and makes the kernel racy

Verdict: **CONFIRMED — genuine compiler bug, and the most serious one in this
directory** (reviewed 2026-08-17)
Arch:    the allocator bug is target-independent; the visible corruption needs
         the Hopper producer/consumer warp split (sm_90a here)
Line:    tilelang (TileLang 0.1.12, pypi wheel, H100 sm_90a, nvcc 12.8.93)
Culprit: pass `tl.MergeSharedMemoryAllocations`, driven by pass_config
         `{"tl.enable_aggressive_shared_memory_merge": true}`

Summary: with the aggressive shared-memory merge on, TileLang places the
cross-thread reduction workspace **on top of** the pipelined `As` staging
buffer, which is still live. The producer warpgroup's next TMA load and the
consumer warpgroup's `AllReduce` then write the same shared memory at the same
time. The kernel stops being deterministic: 8 runs of the same binary on the
same input gave **8 different answers**, and the answers are wrong by up to 65
on a row sum whose correct magnitude is around 30.

Labels: pass-class:bit-preserving, kernel-has-reduce, input-mode:uniform, gross

**Occurrences: 3.** The sweep has hit this same bug twice more, both on the
`max` version of the same kernel (`hw_rrmax_256x4096`), both with the same
one-line workspace-offset change and a non-deterministic candidate:
`HIT-0062` (4 distinct results over 8 runs) and `HIT-0072` (8 distinct results
over 8 runs, wrong by up to 568 against a correct reference). Both were
rejected as B4 duplicates and moved to `bug-report-rejected/tilelang/`.

---

## 1. Root cause in the source

**The whole difference in the generated CUDA is one number.** `ir/reference.cu`
vs `ir/candidate.cu`, 88 lines each, one differing line:

```c
/* reference */  void* workspace = ((void*)((char*)buf_dyn_shmem + 65536));
/* candidate */  void* workspace = ((void*)((char*)buf_dyn_shmem + 0));
```

Offset 0 is `As`:

```c
  void* As        = ((void*)((char*)buf_dyn_shmem + 0));       // both sides
```

`As` is a 32x256 fp32 tile with `num_stages=2`, i.e. `2 * 8192` floats =
**65536 bytes**, so it occupies `[0, 65536)`. The reference puts the workspace
immediately after it; the candidate puts it **inside** it.

**Why that is a race and not just a different layout.** The kernel is
warp-specialized. Producer warpgroup (`threadIdx.x < 128`):

```c
      mbarrier[((ko & 1) + 2)].wait((((ko & 3) >> 1) ^ 1));
      ...
        tl::tma_load(A_desc, mbarrier[(ko & 1)], (&(((float*)As)[((ko & 1) * 8192)])), ...);
```

Consumer warpgroup, same loop iteration:

```c
      mbarrier[((ko_1 & 1) + 2)].arrive();          // <-- "As slot is free, load the next tile"
      tl::__sync_thread_partial(3, 128);
      for (int i_2 = 0; i_2 < 16; ++i_2) {
        ...
        tmp[i_2] = tl::AllReduce<tl::SumOp, 64, 1, 128, tl::NamedBarrier<128>>::run(
                       tmp[i_2], (&(((float*)workspace)[0])));   // <-- writes workspace
      }
```

The consumer releases the `As` slot **before** it runs the `AllReduce`. That is
correct as written, because `workspace` is supposed to be its own memory. With
the workspace moved to offset 0 it is not: the producer is filling `As` for the
next tile while the consumer is still writing reduction partials into the same
bytes.

**The pass step that gets it wrong.**
`src/transform/merge_shared_memory_allocations.cc`. In aggressive mode the
liveness collector attributes every touch of a shared buffer to the
**innermost** scope frame instead of the frame that owns the allocation. Three
identical places — `VisitStmt_(BufferStoreNode)` line 170,
`VisitExpr_(BufferLoadNode)` line 217, `VisitExpr_(VarNode)` line 241:

```cpp
        auto enable_aggressive_merge = enable_aggressive_merge_;
        if (enable_aggressive_merge) {
          scope_[scope_.size() - 1].touched.push_back(buf);   // innermost frame
        } else {
          scope_[it->second.level].touched.push_back(buf);    // allocation frame
        }
```

`scope_[it->second.level]` is the frame the buffer was allocated in, so in the
default mode a buffer touched anywhere inside the `ko` loop is live for the
whole loop. `scope_[scope_.size() - 1]` is the statement currently being
visited, so in aggressive mode the same buffer looks live only for that one
statement. The linear-scan allocator built on those intervals then sees `As`
(touched by the copy statement) and `workspace` (touched by the reduce
statement) as non-overlapping and gives them the same offset.

The shortening is unsound for two separate reasons, and either one alone breaks
this kernel:

* **Loop carry.** `As` is written in iteration `k` and read in iteration `k`;
  attributing each access to its own statement drops the fact that the buffer
  must survive from one statement to the next inside the loop body.
* **Concurrency.** The producer and consumer warpgroups run at the same time.
  Even a correct sequential live range would be wrong here: two buffers touched
  by statements in *different partitions* are live simultaneously no matter what
  the statement order says. The aggressive mode has no notion of the warp
  partition at all.

## 3. Where it reproduces

**The allocator mistake: any target.** `MergeSharedMemoryAllocations` is in
`src/transform/`, not under `src/cuda/`, and the three lines above do not look
at the target. Every backend pipeline calls it.

**The visible corruption: needs concurrent writers, so on this kernel it needs
sm_90.** The judgement rests on reading the generated code: the aliasing only
turns into wrong data because the producer warpgroup (`threadIdx.x < 128`,
`tl::tma_load`, `mbarrier`) runs at the same time as the consumer warpgroup.
Those are Hopper constructs — TMA, mbarrier, `warpgroup_reg_alloc`, the
`tl_shuffle_elect` producer/consumer split. On a target without the warp split
the two accesses would be ordered by `__syncthreads`, and the same aliasing
might silently produce the right answer.

Not tested: whether a non-warp-specialized kernel with a similar buffer pattern
also gets a bad offset. Worth doing — the allocator input does not depend on the
target, so a plain multi-stage pipeline is a candidate.

## 4. Plain-language explanation

Shared memory on a GPU is small, so the compiler packs several buffers into it
and lets two buffers share the same bytes when their lifetimes do not overlap.
Deciding "do not overlap" is the whole job.

The aggressive setting computes each buffer's lifetime as "just the one
statement that touches it". That is far too short. In this kernel one buffer
holds the tile being streamed in from memory and another holds the scratch space
for adding numbers across threads. Both are alive at the same moment, but each
is *touched* by a different statement, so the compiler thinks they can share the
same bytes and puts them at the same address.

Worse, the two are used by two different halves of the thread block at the same
time: one half is loading the next tile while the other half is still adding up
the current one. They now write on top of each other. Which write lands last is
a matter of timing, so the kernel gives a different answer every time it runs.

## 5. Can an SMT solver model this?

**No, not as a value-equivalence question. This one needs a concurrency and
memory model.**

* Under a *sequential* reading of the program the two compilations are
  equivalent. Same statements, same order, same arithmetic. The only difference
  is a base address, and if the two warpgroups were serialized the answer would
  be the same. A single-instance value-semantics checker — even a bit-exact FP
  one — would prove them EQUIVALENT and be wrong about the machine.
* What is needed is a model with: two concurrent thread groups, the mbarrier
  arrive/wait ordering between them, a shared-memory address space where two
  named buffers can overlap, and a definition of a data race. Then the property
  to check is not "same output" but "no two concurrent accesses to the same
  address where at least one is a write". That is race detection, not
  equivalence checking, and it is exactly the class of thing the criteria file
  means by "needs a concurrency/memory-ordering model".
* There is a much cheaper formulation that a solver *is* good at, and it is
  arguably the right one: check the allocator's own contract. Give each buffer
  an interval `[start, end)` in program order plus a warp-partition tag, and
  assert `forall i != j: overlap_in_time(i, j) => disjoint_in_space(i, j)`.
  That is a small linear-arithmetic problem, decided in milliseconds, and it
  would have caught this before any GPU ran. It does not need the kernel's
  values at all.
* An extra reason a value-equivalence tool cannot help: the buggy program has
  **no single output**. It produced 8 different results in 8 runs. "Compare the
  outputs" is not even well defined for it.

So: out of reach of an IR-level value-equivalence check, in reach of a static
allocator-invariant check, and detectable at runtime by `compute-sanitizer
racecheck` (not run here — the 8-different-results measurement is already
conclusive and much cheaper).

## 6. Confidence

**High that this is a genuine compiler bug.**

* The generated CUDA differs in exactly one number, and that number puts one
  buffer on top of another. There is no room for an alternative reading of what
  changed.
* The sizes line up exactly: `As` is `2 * 8192` floats = 65536 bytes, the
  reference workspace starts at 65536, the candidate workspace starts at 0.
* The consumer releases the `As` slot (`mbarrier[...].arrive()`) *before* it
  writes the workspace, so the overlap really is concurrent, not merely adjacent
  in time.
* The candidate binary gives 8 different answers in 8 runs while the reference
  gives 1. Non-determinism from a single binary on a kernel whose source has no
  atomics, no data-dependent store address and no uninitialised read can only
  come from the compilation.
* The pass source shows a liveness rule that is short by construction, with the
  default branch right next to it doing the correct thing.

Remaining doubt, and how to settle it:

* *Is `tl.enable_aggressive_shared_memory_merge` a supported setting or an
  "at your own risk" switch?* It is a registered pass config
  (`src/op/builtin.cc:28`) with no warning in the code and no documentation
  found either way. If TileLang intends it as unsafe-by-design it should say so
  and the knob should refuse to run on warp-specialized kernels. Either way the
  current behaviour — silently wrong, non-deterministic output — is not
  acceptable for a public knob.
* *Does it also break non-warp-specialized kernels?* Not tested. Compile a
  multi-stage pipeline without warp specialization and compare offsets.

## Kernel

corpus id `hw_rrsum_256x4096`, from `tlfz.mkcorpus:rrsum_256x4096` — a row-sum
reduction, 256 rows of 4096, staged through shared memory in 16 chunks of 256
with `num_stages=2`.

```python
# from tvm.script import tirx as T

@T.prim_func
def main(A_handle: T.handle, Out_handle: T.handle):
    A = T.match_buffer(A_handle, (256, 4096), strides=(4096, 1))
    Out = T.match_buffer(Out_handle, (256,), strides=(1,))
    for bx in T.thread_binding(8, thread="blockIdx.x"):
        for tx in T.thread_binding(128, thread="threadIdx.x"):
          ...
            As       = T.sblock_alloc_buffer((32, 256), scope="shared.dyn")
            acc      = T.sblock_alloc_buffer((32,),     scope="local.fragment")
            tmp      = T.sblock_alloc_buffer((32,),     scope="local.fragment")
            As_frag  = T.sblock_alloc_buffer((32, 256), scope="local.fragment")
            T.fill(T.region(acc[0], 2, 32), 0)
            for ko in T.serial(16, annotations={"num_stages": 2}):
                T.copy(T.region(A[bx * 32, ko * 256], 1, 32, 256), T.region(As[0, 0], 2, 32, 256))
                T.copy(T.region(As[0, 0], 1, 32, 256), T.region(As_frag[0, 0], 2, 32, 256))
                T.reduce(T.region(As_frag[0, 0], 1, 32, 256), T.region(tmp[0], 2, 32), "sum", 1, T.bool(True))
                for i in T.parallel(32):
                    acc[i] = acc[i] + tmp[i]
            T.copy(T.region(acc[0], 1, 32), T.region(Out[bx * 32], 2, 32))
```

The kernel itself is clean: no atomics, no store address computed from loaded
data, every buffer written before it is read.

## Noise gates

* reference self-consistent across repeats: **True** (1 distinct result in 8)
* candidate self-consistent across repeats: **False** (8 distinct results in 8)
  — this is the finding, not a disqualification. Criterion A3 rejects a kernel
  that is non-deterministic under a *single* binary because that means the
  kernel has undefined behaviour. Here the kernel is deterministic under the
  stock binary and the source has no UB; the non-determinism is created by the
  candidate compilation, so A3 does not apply.
* difference still present under a 17 MB heap shift: **True**
* the kernel passed the campaign's determinism pre-screen before any variant ran
* exact-integer control: the difference shows on `intvalued` draws too, so it is
  not reassociation
* fast math: not involved. The *effective* `pass_configs` for this kernel —
  after `core._merged_cfg` folds in the corpus entry's own config — is exactly
  `{"tl.enable_aggressive_shared_memory_merge": true}`, with no
  `tl.enable_fast_math` on either side. So the amended section-2 fast-math
  exception cannot apply.
