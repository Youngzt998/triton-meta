# HIT-0001: `tl.config_index_bitwidth` widens a value cast, breaking sign extension

Verdict: **CONFIRMED — genuine compiler bug** (reviewed 2026-08-17)
Arch:    generic (no Hopper construct anywhere in the failing code)
Line:    tilelang (TileLang 0.1.12, pypi wheel, H100 sm_90a, nvcc 12.8.93)
Culprit: pass `tl.ConfigIndexBitwidth`, driven by pass_config
         `{"tl.config_index_bitwidth": 64}`

Summary: setting the public knob `tl.config_index_bitwidth = 64` changes the
**computed values** of a kernel, not just its address arithmetic. The pass is
meant to widen buffer *index* expressions to 64 bit. It also widens integer
casts that sit in the *stored value*. In this kernel that turns the standard
sign-extension idiom `((int32)b << 24) >> 24` into 64-bit arithmetic, where the
same shift pair no longer sign-extends. 3 of 7 outputs flip: `-128.0` becomes
`+128.0`.

Labels: pass-class:bit-preserving, input-mode:captured, integer-valued
difference, survives the exact-integer control

---

## 1. Root cause in the source

Two files.

**`src/transform/config_index_bitwidth.cc`, lines 54-70** — TileLang's
`ConfigIndexBitwidthRewriter` overrides the buffer store and buffer load
visitors and force-enables the rewrite flag around the *whole* parent visit:

```cpp
  Stmt VisitStmt_(const BufferStoreNode *op) final {
    // Force indices to be int64
    bool is_enabled = is_enabled_;
    is_enabled_ = true;
    auto node = Downcast<BufferStore>(Parent::VisitStmt_(op));   // <-- visits the VALUE too
    is_enabled_ = is_enabled;
    return std::move(node);
  }
```

The comment says "indices", but `Parent::VisitStmt_(op)` walks the stored value
as well as the indices, and `is_enabled_` stays `true` for that whole walk.

**`src/transform/config_index_bitwidth.cc`, lines 46-52** — with the flag on,
*every* narrow signed-int cast in the subtree is rewritten:

```cpp
  PrimExpr VisitExpr_(const CastNode *op) final {
    if (is_enabled_ && op->dtype.is_int() && op->dtype.bits() < 64) {
      PrimExpr value = VisitExpr(op->value);
      return Cast(DataType::Int(_index_bitwidth_), value);
    }
    return Parent::VisitExpr_(op);
  }
```

That is the incorrect step: a cast in a stored value is a value cast, not an
index cast, and its width is part of the program's meaning.

**Why the flag is wrong there.** The base class states its own contract in
`3rdparty/tvm/src/tirx/ir/data_type_rewriter.h:94` — `is_enabled_` means "the
current expression **is a buffer index**". Upstream keeps that true: in
`3rdparty/tvm/src/tirx/ir/data_type_rewriter.cc:429-448`,
`IndexDataTypeRewriter::VisitStmt_(BufferStoreNode)` visits `op->value` with the
flag untouched and turns it on only inside `VisitIndices()`
(same file, lines 464-467). TileLang's override defeats that separation.

Secondary inconsistency in the same file: `VisitExpr_(VarNode)` (line 31)
hard-codes `DataType::Int(64)` while `IntImm` and `Cast` use
`_index_bitwidth_`. So with `tl.config_index_bitwidth = 32` the vars and the
constants disagree. Not the cause of this report; worth fixing with it.

**What the two compilations emit.** `ir/reference.cu` vs `ir/candidate.cu`,
same kernel, one line each:

```c
/* reference  (knob unset)  */
decoded_values[i] = ((float)((((int)((packed_values[(i >> 2)] >> ((uint)((i & 3) * 8))) & (uint)255)) << 24) >> 24));

/* candidate  (knob = 64)   */
decoded_values[i] = ((float)((((int64_t)((packed_values[(i >> (int64_t)2)] >> ((uint)((i & (int64_t)3) * (int64_t)8))) & (uint)255)) << (int64_t)24) >> (int64_t)24));
```

`(int)` became `(int64_t)`. For the byte `0x80`:

| | shift left 24 | arithmetic shift right 24 |
|---|---|---|
| int32  | `0x80000000` | `0xFFFFFF80` = **-128** |
| int64  | `0x0000000080000000` | `0x80` = **+128** |

The pass runs only when the knob is set (`config_index_bitwidth.cc:177`), which
is why the stock pipeline is correct.

## 3. Where it reproduces

**Anywhere.** The judgement rests on three things:

* The failing generated code is a plain serial `for` loop over 7 elements with
  one load, some integer shifts and a store. No wgmma, no TMA, no mbarrier, no
  cluster, no warp specialization, no `__syncthreads`, no atomics.
* The bug is in a target-independent TIR pass. `ConfigIndexBitwidth` is called
  from **all five** pipelines: `tilelang/{cuda,rocm,cpu,metal,webgpu}/pipeline.py`.
  Nothing in the pass looks at the target.
* The wrong value comes from C integer semantics (`<<`/`>>` on a wider type),
  not from any GPU instruction, so nvcc, the driver and the GPU model are not
  involved.

The one precondition is the knob: `tl.config_index_bitwidth` must be set.

## 4. Plain-language explanation

The kernel unpacks four signed bytes out of a 32-bit word. To turn a byte into
a signed number it uses the usual trick: put the byte in a 32-bit register,
shift it left 24 so its top bit lands on the sign bit, then shift right 24 so
the sign is copied back down. The width of the register is the whole point of
the trick.

The knob "use 64-bit indices" is supposed to touch only the arithmetic that
computes *where* to read and write. The pass applies it too widely and also
changes the register width in the *value* being computed. In a 64-bit register
the byte's top bit lands in the middle, not on the sign bit, so the number
stays positive. `-128` comes out as `+128`.

## 5. Can an SMT solver model this?

**Yes, and it is close to the easiest possible case.**

* Single program instance. The kernel is a serial loop with grid `1x1x1` and
  one thread. No cross-instance behaviour to model.
* Pure integer/bit semantics. Load a `uint32`, shift, mask, cast, shift, cast
  to `float32`, store. Everything up to the final cast is exact bitvector
  arithmetic — `BitVec32` / `BitVec64`, `bvshl`, `bvashr`, `bvand`,
  `sign_extend` / `zero_extend`. No rounding, so no FP axiom profile is needed;
  even the closing `int -> float32` can be left as an uninterpreted injective
  function, because the two sides already differ *before* it.
* Fully deterministic on both sides (3 runs each, bit-identical).
* No memory-ordering or race question: one thread, disjoint writes.
* The bug is visible **at the IR level** — it is a difference between two TIR
  programs, so an IR-level checker is at the right altitude. It is not a
  codegen or ptxas artifact.

A checker that models a store as `heap' = store(heap, addr, value)` and compares
the two heaps at a symbolic witness address would report NOT EQUIVALENT with a
counterexample such as `packed_values[0] = 0x80`, in milliseconds. The loop trip
count is a constant 7, so even full unrolling is cheap.

The only modelling requirement worth naming: the checker must keep the **width**
of every intermediate, not normalise integers to one machine word. A checker
that models all integers as unbounded mathematical integers would call these two
programs equal and miss the bug.

## 6. Confidence

**High.** The chain is short and every link was checked directly, not inferred:
the two generated CUDA lines differ only in `int` vs `int64_t`; C semantics for
that pair of shifts is unambiguous; the observed values `-128` and `+128` are
exactly what the two widths predict; and the source line that produces the
widening is visible, with the upstream base class documenting the opposite
contract.

What could still change the reading, and what would settle it:

* *Could `tl.config_index_bitwidth = 64` be documented as "may change integer
  value widths"?* `tilelang/transform/pass_config.py:85` says only "Bitwidth for
  configuration indices. Default: 32". Nothing about values. To settle it fully
  one would want a maintainer's statement, or a test in
  `testing/python/transform/test_tilelang_transform_config_index_bitwidth.py`
  that pins the intended scope.
* *Could the widening come from a different pass?* Not checked pass by pass. The
  cheap way to settle it is to run only `ConfigIndexBitwidth` on the pre-pass IR
  and diff — `ir/input.tir.py` and `ir/cand_after_whole_pipeline.tir.py` are in
  this directory for that. The source reading above already makes this near
  certain.

# from tvm.script import tirx as T

@T.prim_func
def main(packed_values_handle: T.handle, decoded_values_handle: T.handle):
    packed_values = T.match_buffer(packed_values_handle, (2,), "uint32", strides=(1,))
    decoded_values = T.match_buffer(decoded_values_handle, (7,), strides=(1,))
    for bx in T.thread_binding(1, thread="blockIdx.x"):
        for tx in T.thread_binding(1, thread="threadIdx.x"):
            for ty in T.thread_binding(1, thread="threadIdx.y"):
                for tz in T.thread_binding(1, thread="threadIdx.z"):

                        for i in range(7):
                            decoded_values[i] = T.Cast("float32", T.shift_right(T.shift_left(T.Cast("int32", T.bitwise_and(T.shift_right(packed_values[i // 4], T.Cast("uint32", i % 4 * 8)), T.uint32(255))), 24), 24))
