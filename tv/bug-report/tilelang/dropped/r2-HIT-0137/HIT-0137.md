# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the automatic text the fuzzing
line wrote; **none of it has been corrected**, including any statement this
banner contradicts.

**Criterion: B1** (the fast-math class), and also B4 -- a duplicate of the
pinned round-1 report `tilelang/HIT-0009`, which stays in the repo as the
documented representative of this pattern.

**The measurement that settled it:** dropped `tl.enable_fast_math` from the
minimal variant and re-ran -- **the one differing draw no longer differs**.

**This report is a keep signal that is still a rejection.** The single differing
element is `Infinity` on the reference against `NaN` on the candidate. Section 2
of `REVIEW-CRITERIA.md` says a NaN appearing on one side only is a **keep**, and
names exactly **one** exception: fast math. This is that exception. Fast math
implies `-ftz=true`, so a denormal operand becomes `0`, and `inf x 0 = NaN`
manufactures a NaN out of finite and infinite inputs. That is the flag working
as documented.

**Read this report's `## Fast-math control` section with care -- it is wrong.**
It says *"fast math was OFF on both arms"*. **That is false.** The minimal
variant recorded a few lines above it is
`{"tl.disable_warp_specialized": true, "tl.enable_fast_math": true}` -- fast
math is set on the **candidate arm only**. The line had a harness defect in
which `tl.enable_fast_math` leaked onto one arm while the report printed that
both were clean; **110 of 135 reports written before the fix (2026-08-19,
~22:10) carry this false line.** This copy is deliberately a pre-fix report, so
that the defect is visible in the repo and not only described in a note. See
`dropped/README.md` for what changed after the fix.

**One label that is *not* a reason.** The report carries
`reference-mostly-nan:1.00`: the reference output of the differing tensor is
almost entirely NaN, so the oracle is weak. That is information, not grounds for
rejection -- one of the campaign's two TileLang keeps, `r2/HIT-0043`, came from
a draw whose reference was 99.29% NaN.

**Re-verified by the reviewer, 2026-08-20.** The difference reproduces exactly
-- 1 of 2037, `inf` on the reference against `nan` on the candidate -- and with
`tl.enable_fast_math` removed from the variant the run prints `NO DIFFERENCE`.
The other knob, `tl.disable_warp_specialized`, is still applied in that ablation
and still rewrites the kernel completely (candidate CUDA 10591 chars against the
reference's 4620), yet not one bit of output changes. So the pass under test is
innocent and the flag did all of it.

## Minimal kernel source

id `gen_gemv_d4bc1ef49dd602`, provenance `tlfz.gen:gemv`

```python
import tilelang
import tilelang.language as T


@T.prim_func
def main(A: T.Tensor((2037, 224), "bfloat16"), X: T.Tensor((224,), "bfloat16"), Y: T.Tensor((2037,), "float32")):
    with T.Kernel(T.ceildiv(2037, 64), threads=32) as bx:
        As = T.alloc_shared((64, 64), "bfloat16")
        Xs = T.alloc_shared((64,), "bfloat16")
        p = T.alloc_fragment((64, 64), "float32")
        acc = T.alloc_fragment((64,), "float32")
        T.fill(acc, 0)
        for ko in T.Pipelined(T.ceildiv(224, 64), num_stages=5):
            T.copy(A[bx * 64, ko * 64], As)
            T.copy(X[ko * 64], Xs)
            for i, j in T.Parallel(64, 64):
                p[i, j] = T.cast(As[i, j], "float32") * T.cast(Xs[j], "float32")
            T.reduce_sum(p, acc, dim=1, clear=False)
        T.copy(acc, Y[bx * 64])

```
