# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the automatic text the fuzzing
line wrote; **none of it has been corrected**, including any statement this
banner contradicts.

**Criterion: B1** -- the fast-math class, the largest rejection class in this
campaign by far.

**The measurement that settled it:** re-ran the minimal variant with the single
key `tl.enable_fast_math` removed -- **no difference**. The other key in the
variant, `tl.config_index_bitwidth: 64`, on its own changes nothing on this
kernel.

**What fast math did here, in one number.** The two differing values are
`9.99994610111476e-41` on the reference and `0.0` on the candidate.
`tl.enable_fast_math` only adds `--use_fast_math` to the nvcc command line
(`tilelang/engine/lower.py`), and `--use_fast_math` implies `-ftz=true`, which
flushes denormal results to zero. `9.99e-41` is a denormal. That is the
documented behaviour of the flag, not a compiler defect.

**Note on size, which is *not* the reason.** Only **2 of 30720** elements
differ. Section 3 of `REVIEW-CRITERIA.md` says smallness is never on its own a
reason to reject; this report was rejected because the ablation above explains
the difference, and it would have been kept at 2 elements if it had not.

**Re-verified by the reviewer, 2026-08-20**, on the round-2 harness (which keeps
its own copy of the same corpus, so round 1 was not touched). The difference
reproduces exactly -- 2 of 30720, `9.99994610111476e-41` against `0.0` -- and
with `tl.enable_fast_math` removed the run prints `NO DIFFERENCE`. Worth noting:
the remaining knob still changes the code (candidate CUDA 1852 chars against the
reference's 1649, not identical), it just does not change any output bit. A pass
that visibly rewrites the program and changes nothing numerically is the normal
case, not a suspicious one.
