# EXAMPLE OF A REJECTED REPORT -- not an open finding

This is a frozen copy of a report the review **rejected**. It is kept here only
as a worked example of one rejection class, so a reader of `bug-report/` can
judge the filtering. Everything below the line is the automatic text the fuzzing
line wrote; **none of it has been corrected**, including any statement this
banner contradicts.

**Criterion: B3** -- floating-point contraction (`mul + add -> fma`). That is a
licence held by the whole compiler, not by any one pass, so *any* change that
merely reshapes the IR can trigger it.

**The measurement that settled it:** recompiled **both** arms with
`-fmad=false` and re-ran every draw that had ever differed -- **0 of 7 still
differ**. A changed summation *order* would survive `-fmad=false`; contraction
does not. The exact-integer control agrees independently: 4 `intvalued` draws,
no difference.

**Two checks run before believing the difference at all.** (1) The
compile-determinism gate: TileLang can compile the same kernel to different CUDA
on some points, so each arm was lowered **12 times** -- one source hash each,
`95484a11` for the reference, so this is not that lottery. (2) Fast math: this
is a **post-fix** report, its shared `pass_configs` are `{}` and its minimal
variant carries no fast-math key, so its "fast math was OFF on both arms" line
is true and needs no re-run.

**The mechanism, visible in `ir/reference.cu` vs `ir/candidate.cu`.** Both arms
compute `p[i] = As[..] * Xs[..]` and later `acc += p[i]`. The reference is warp
specialised (a producer warp and a consumer warp); the candidate is a prologue
plus an 8-iteration loop plus an epilogue. Same arithmetic, same order,
different code shape -- and nvcc fuses the multiply and the add into an `fma` in
different places. Ruled out: this is **not** the register-index defect of the
kept `r2/HIT-0008`, whose fingerprint is a fragment written at `p + i*4 + 4` and
read at `p[0..]`; here the write and the read cover the same range.

**Re-recording.** The same instance and the same output bits were filed **three
times** -- `r2/HIT-0148`, `r2/HIT-0149`, `r2/HIT-0150` -- under three unrelated
toggles (`tl.disable_warp_specialized`, `tl.config_index_bitwidth: 32`,
`tl.config_index_bitwidth: 64`). Three unrelated knobs producing bit-identical
output is itself the signature of B3: none of them has a numeric licence, they
only move the code around.

## Minimal kernel source

id `gen_gemv_4da8042d09cfec`, provenance `tlfz.gen:gemv`

```python
import tilelang
import tilelang.language as T


@T.prim_func
def main(A: T.Tensor((31, 1027), "float32"), X: T.Tensor((1027,), "float32"), Y: T.Tensor((31,), "float32")):
    with T.Kernel(T.ceildiv(31, 64), threads=32) as bx:
        As = T.alloc_shared((64, 128), "float32")
        Xs = T.alloc_shared((128,), "float32")
        p = T.alloc_fragment((64, 128), "float32")
        acc = T.alloc_fragment((64,), "float32")
        T.fill(acc, 0)
        for ko in T.Pipelined(T.ceildiv(1027, 128), num_stages=1):
            T.copy(A[bx * 64, ko * 128], As)
            T.copy(X[ko * 128], Xs)
            for i, j in T.Parallel(64, 128):
                p[i, j] = T.cast(As[i, j], "float32") * T.cast(Xs[j], "float32")
            T.reduce_sum(p, acc, dim=1, clear=False)
        T.copy(acc, Y[bx * 64])

```
